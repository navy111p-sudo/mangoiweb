## 1. 「B2B / 학원」 항목이 실제로 무엇에 연결돼 있었나

결제하기 → 상품 선택의 `B2B / 학원 (기업·학원 단체 도입, 맞춤 견적)` 카드입니다.

- 위치: `cloudflare-deploy/public/index.html` — `<button class="product-card" data-program="b2b" data-price="0">`
- 상품 정의: `cloudflare-deploy/public/js/idx-payment-modal.js` — `PROG_INFO['b2b']`

**동작(수정 전):**

1. 카드 클릭 → 금액 0원이라 로그인 검사도 통과 → **정보 입력 단계**로 진입
2. 결제자·학생·연락처를 다 입력 → **결제수단 선택 단계**로 진입
3. 카드/가상계좌 등 결제수단까지 고르고 「결제 완료 확인」
4. 서버 `POST /api/pay/manual-request` 가 **거부** —
   `cloudflare-deploy/src/api-pay.ts` 의 서버 가격표 `PRICES` 에 `b2b` 키가 **없다**
   → `400 not_payable` / *"이 상품은 상담으로 진행됩니다. 카카오 상담을 이용해 주세요."*

즉 **"맞춤 견적"이라고 안내해 놓고 결제 깔때기 끝까지 끌고 간 뒤 문전박대**하는 흐름이었습니다.
문의가 접수되는 것도 아니어서, **누가 단체 도입을 문의했는지 회사에 기록이 남지 않습니다.**

> 참고: 무료체험(`trial`)은 이미 같은 함정을 한 번 겪고 2026-07-29 에 고쳐졌습니다
> (「무료라더니 결제하라네」). `b2b` 만 그때 같이 고쳐지지 않고 남아 있었습니다.

## 2. 기존 LMS 의 B2B 방식과 하나씩 대조

| 기존 LMS 기능 | 현재 사이트 | 근거 |
|---|---|---|
| 기관 단위 **일괄 결제** | ❌ 없음 | `PRICES`(api-pay.ts)는 개인 수강권 8종 + 부가옵션 6종뿐. 인원×기간 견적 로직 없음 |
| 기관 담당자 **로그인** | ❌ 없음 | 로그인 역할은 학생·학부모·강사·본사/지사/대리점/캐피타운. **기관(고객사) 역할 자체가 없음** |
| 담당자가 **소속 학생 결제** | ❌ 없음 | 결제 API 는 전부 `authUidFromRequest` 로 **본인 uid** 만 허용(IDOR 차단). 남의 학생을 대신 결제할 통로가 없음 |
| **세금계산서** 발행 | ❌ 없음 | 코드 전체에서 세금계산서는 `accounting-reports.ts` 의 **회사 내부 회계 리포트 항목명**으로만 등장. 발행 기능 없음 |
| 단체 **계약/정산** | △ 다른 것 | `org-settlement.ts` 가 있으나 이건 **가맹점 정산**(본사→지사→대리점 수수료)이지, 고객사가 우리에게 내는 B2B 결제가 아님 |

**DB 확인 (운영 D1, SELECT only):**

| 확인 항목 | 결과 |
|---|---|
| 기관/법인/계약/세금계산서 테이블 | **없음** (`org%`,`corp%`,`invoice%`,`contract%`,`b2b%` 로 검색 → `org_nodes`·`org_settlement_ledger`·`student_org_override` 뿐 = 가맹점 정산용) |
| `students_erp.payment_type` (LMS의 'B2B 결제' 라벨) | **29,388명 전원 빈값**. 이 컬럼은 관리자 학생표·CSV에 *글자만* 찍는 표시용이고, 결제 동작에 아무 영향이 없음. 값이 들어간 건 개발용 가짜 학생 20명 시드(`api-mango.ts`)뿐 |
| `payment_orders` 에 b2b 주문 | **0건** (전체 29건 = `1on1-4` 23 / `enroll` 4 / `1on1-8` 2, 그중 결제완료 5·실패 12 — 전부 토스 테스트키 기간) |
| 조직 트리 규모(참고) | `org_nodes` 247개 · `students_erp.shop_name` 고유값 **729개** |

> 729개 학원/센터가 이미 학생 레코드에 붙어 있습니다. **"어느 기관 소속인가"는 이미 있고,
> 없는 것은 "그 기관이 돈을 내는 길"** 입니다. 새로 만들 때 소속 정보를 처음부터 만들 필요는 없습니다.

## 3. 관련 파일 지도 (후속 개발용)

| 파일 | 이번 건에서의 역할 |
|---|---|
| `cloudflare-deploy/src/api-pay.ts` | 서버 가격표 `PRICES`, 주문 생성/확정, 토스 연동. **B2B 가격 산정이 들어갈 자리** |

| `cloudflare-deploy/src/scope.ts` | 역할별 데이터 격리. **기관 담당자 역할을 넣는다면 여기** |

## 4. 이번에 함께 고친 것 (막다른 길 제거)

`b2b` 를 무료체험과 같은 방식으로 **상담 접수**로 돌렸습니다 — 결제 모듈을 아예 거치지 않습니다.

- 파일: `cloudflare-deploy/public/js/idx-payment-modal.js` → `submitB2BInquiry()`
- 접수처: `POST /api/student/inquiry` (무료체험과 **같은 창구**, 새 폼을 만들지 않음)
- 결과 화면: 「결제는 진행되지 않았어요 — 인원·기간에 따라 맞춤 견적으로 안내드립니다」

이제 **단체 도입 문의가 실제로 회사에 남습니다.** (이전에는 400 에러만 뜨고 아무 기록도 안 됨)

⚠️ 이건 **B2B 결제 기능이 아닙니다.** 문의를 잃지 않게 만든 것뿐입니다.

## 5. 기존 LMS 수준으로 만들려면 — 작업 범위(개략)

전제: 사장님이 **B2B 를 실제 상품으로 팔 것인지** 먼저 정해야 합니다. 아래는 "판다"고 했을 때의 범위입니다.

| 단계 | 내용 | 개략 공수 |
|---|---|---|
| ① 기관 마스터 | `orgs` 테이블(기관명·사업자번호·담당자·계약단가·결제주기) + 학생↔기관 연결(이미 있는 `shop_name` 재사용) | 1~2일 |
| ② 기관 담당자 역할 | 로그인 역할 `org_manager` 추가 + `scope.ts` 격리(자기 기관 학생만) + 관리자 화면에서 계정 발급 | 3~4일 |
| ③ 단체 견적·주문 | 인원×기간 견적기(`enrollQuoteCalc` 확장), 기관 단위 주문서 생성, 학생 일괄 배정 | 4~5일 |
| ④ 결제 수단 | 토스 **가상계좌**(법인 실무상 가장 현실적) + 카드. 빌링키 정기결제는 선택 | 2~3일 |
| ⑤ 세금계산서 | 국세청 직접연동은 과함 → **팝빌/바로빌 등 대행 API** 연동 권장. 사업자번호·공급가/부가세 분리 저장 | 3~4일 (+ 대행사 계약) |
| ⑥ 관리자 화면 | 기관 목록·계약·미수금·정산 내역 | 3~4일 |
| **합계** | | **약 16~22일(3~4주)** + 세금계산서 대행사 계약 기간 |

**권고 — 단계적으로:**

1. **1차(2~3일)**: 지금의 상담 접수 + **관리자 화면에서 "결제 링크 발급"**.
   이미 `admin/send-pay-link.html` 과 `pay-link.html` 이 있습니다. 기관 담당자에게 금액을 넣은
   링크를 보내면 **오늘이라도 단체 대금을 실제로 받을 수 있습니다.** 세금계산서는 수기 발행.
   → 기관이 몇 곳 안 될 때는 이게 ①~⑥ 전체보다 **압도적으로 싸고 빠릅니다.**
2. **2차**: 기관 수가 10곳을 넘거나 수기 세금계산서가 부담이 되면 그때 ①~⑥ 착수.

> 판단 근거: 운영 DB의 B2B 주문 실적이 **0건**입니다. 수요가 확인되기 전에 3~4주를 쓰는 것보다,
> 1차로 실제 청구를 받아 보고 건수가 쌓이는지부터 보는 편이 안전합니다.
