# 작업 5 수강 결제 스케줄 정합성 검증

개별 작업의 기준 소스는 navy111p-sudo/mangoiweb main 27ec8ce91c624a80559ee82311fc425664b07319이다. 이후 최신 main과의 통합 검증은 별도 통합 결과로 확인해야 한다. 결과는 로컬 수정안과 격리된 실제 서버 모듈 검증이다. 운영 DB, 실제 결제·환불·영수증·알림은 변경하지 않았다. 원격 push, PR, 병합, 배포도 하지 않았다. 전체 사용자 흐름의 운영 정상 판정은 보류한다.

## 1 현재 문제

결제 승인과 수강 등록·수업 생성이 별도 단계여서 중간 실패 시 수업이 누락되고 동시 요청 시 중복될 수 있었다. 부분환불은 미사용 수업과 연결되지 않았고, 외부 환불과 장부 기록의 금액이 어긋날 수 있었다. 정기청구는 결과를 모르는 요청 뒤에 새 주문으로 다시 결제할 수 있었다. 관리자 점검은 회차 불일치나 점검 자체의 실패를 충분히 보여 주지 않았다.

## 2 문제 재현 결과

운영 TypeScript 파일을 임시 경로에서 그대로 실행하고 SQLite와 모의 결제사를 사용했다. 초기43개 중 수정 전30개 통과·13개 실패였다. 24회 주문의 생성 실패 후 재시도해도0회, 동시 콜백의 수강 등록2개, 240회 생성 중81번째 실패 후80회 잔존, 늦은 중복 요청의48회 생성, 동시 부분환불의 PG2호출을 재현했다.

독립 검토에서 추가로 외부30,000원 환불을 장부에 기록하면60,000원으로 합산, 뒤늦은 승인으로 환불 상태 덮어쓰기, HTTP500 뒤 새 환불 키 발급, 반액 DONE 응답으로24회 부여, 선점 직전 출석 변경 무시, 수동 장부 동시 기록의 합계 누락을 재현했다. AI·화상 정기청구는 연결 끊김 뒤 새 주문으로 PG2호출을 만들었다. 구독 교체·지연 조회·늦은 카드 거절 조건도 별도로 재현했다.

## 3 확인된 원인

- paid 또는 기존 수강 행을 발견하면 후속 수업 생성을 건너뜀
- 존재 확인과 삽입·환불 선점이 별도 SQL이고, 대량 수업을 여러 batch로 나눔
- 오래된 PG 응답이 최신 상태를 고려하지 않고 갱신함
- 완료된 생성과 수동 전체 삭제를 구분하는 복구 근거가 없음
- 환불 대상 회차·외부 환불 누적액·완료 장부가 같은 기준으로 대사되지 않음
- HTTP 성공·DONE만으로 실제 금액이나 취소 결과를 단정함
- 정기청구의 짧은 리스만 있고 미확정 결과를 다음 요청에 전달할 영속 표식이 없음
- 서로 다른 구독ID의 동일 학생·상품 청구는 리스가 독립적임
- 실패 상태 전이가 거부돼도 청구 실패 횟수와 다음 청구일을 변경함
- API에 추가한 점검 결과를 관리자 화면이 렌더링하지 않음

## 4 수정한 내용

수업 전량을 JSON 기반 단일 INSERT로 생성한다. 기존 payment_orders.fail_reason에 schedule_generation_pending:v1을 먼저 남기고, 수업 INSERT와 그 표식의 제거를 같은 batch에 넣었다. 표식이 있는 미완료 생성만 복구하며, 정상 생성 후 전체 수동 삭제나 표식 없는 과거 누락은 자동 복원하지 않는다. 수강 행과 수업 생성 전체가 하나의 트랜잭션인 것은 아니다.

승인·대기·실패 응답의 상태 전이를 조건부로 바꿨고, 확인된 전액과 주문 정보를 검증한다. 부분환불은 해당 주문의 미래·미사용 수업ID를 명시적으로 선택한다. 선점 SQL에서 출석·시간·소유권·중복 배정을 다시 검사한다. 외부 환불 기록은 이미 확인된 미기록 금액의 배분으로 구분하고 이중 합산하지 않는다. 완료 장부 합계와 현재 외부 누적액을 원자적으로 반영한다. 불명확한 PG 결과는 기존 요청을 유지하며 새 금융 요청을 차단한다.

정기청구는 기존 주문 필드에 billing_pending:v1 표식을 PG 호출 전에 남긴다. 동일 학생·상품의 미확정 주문을 확인하고, 다른 구독ID의 활성 리스도 함께 검사한다. 미확정 시 다음 청구를 보류하며 검증된 웹훅으로 해결한다. 확정적 카드 거절은 실제 실패 상태 전이가 성공했을 때만 재시도 일정을 바꾼다. 새 DB 구조나 운영 데이터 이전은 없다.

## 10 테스트 중 추가 발견된 문제

외부 환불을 기록할 때 이중 합산, 미배분 외부 환불 누락, 과거 응답에 의한 환불·정상 결제 상태 변경, 원자적 선점 직전 사용 수업 환불, 정상 수업 전체 삭제의 잘못된 복구, 미확정 정기청구의 재청구, 구독 교체로 보류 우회, 늦은 실패로 다음 청구일이27일 앞당겨지는 문제, 늦은 조회 조건에서 서로 다른 구독ID가 동시에 청구하는 문제를 추가 발견했다.

환불 권한은 지사 계정의 두 번째 scope 조회에 장애가 나면 none fallback으로 환불을 허용하는 기존 결손도 재현했다. 이 권한 변경은 별도 승인 전이므로 수정하지 않았다.

## 11 추가 문제 수정 내용

각 재현을 고정 회귀로 추가한 뒤 금액·상태·선점 조건을 수정했다. 통합 재검토에서 eligibility 조회 직후 출석이나 시작일이 바뀌어도 최종 UPDATE가 취소하는 별도 경쟁을 발견했다. 최종 UPDATE 자체가 현재 DB 시각 기준 미래 수업 및 학생 출석 부재를 다시 검사하도록 보완했다. 원자적 회차 검증은 PG 요청 이전의 변경을 막는다. PG 요청이 진행되는 동안 출석이 바뀌는 경우는 종료 시 재검사·경고·수업 배분 보류로 남긴다. 외부 환불350,000원은 실제 추가 환불 잔액10,000원과 장부 미기록350,000원을 구분한다. 수동 기록 두 건의 누적액은 완료 원장의 SUM을 포함한다. 생성 복구 표식은 성공한 수업 batch에서만 지운다. 정기청구의 영속 보류와 일시적 리스를 분리하고, 일반 confirm이나 잘못된 웹훅이 보류 근거를 지우지 못하게 했다.

## 14 성능 개선 전 후 비교

240회 생성 쓰기는 기존3개 batch/240개 INSERT에서1개 batch 안의1개 수업 INSERT+1개 복구 표식 UPDATE로 바뀌었다. D1 바인드 제한을 넘지 않도록 JSON payload를 사용한다. 이는 코드·SQLite 실행 구조의 변화다. 운영 D1 지연, 결제사 응답시간, 한국–필리핀 네트워크, 브라우저 화면 지연의 전후 수치는 측정하지 않았다.

## 15 남아 있는 위험요소

- 환불 권한 fail-open은 재현됐으나 승인 대기로 남아 있다. 이 상태에서 운영 적용 준비 완료로 판정할 수 없다.
- 실제 학생·교사·관리자 브라우저 흐름, 수업방 영상·음성, 실제 PG 연동은 미검증이다.
- 수강 등록과 수업 생성 전체는 단일 트랜잭션이 아니다. 생성 표식과 재시도로 회복 가능성을 높인 구조다.
- 과거 표식 없는 누락·전체 삭제는 원인을 추측하지 않고 관리자 확인 대상으로 남긴다. 이전 미확정 정기청구도 새 표식으로 자동 이전하지 않는다.
- PG 진행 중 수업 상태 변경이나 환불 뒤 DB 실패는 금융 요청을 다시 보내지 않고 기록·경고·미배분 대사로 보존한다. 별도 관리자 조정이 필요하다.
- 외부 환불은 미사용 수업을 사람이 지정해야 한다. 선택 대상이나 새 수업당 환불 단가를 임의로 만들지 않았다.
- 회차 대사는 최근 신청 주문500개, 미확정 정기청구 표시는100개까지다. 제한·실패를 화면에 표시한다.
- Cafe24의 안정적 원주문 ID, 반복 수업·보강과 결제의 연결, AI 이용권 계약의 실제 라우트 통합은 별도 검증이 필요하다.
- 생산 데이터 정정·실금융 작업·원격 게시·병합·배포는 이번 로컬 수정과 별도의 승인 대상이다.

## 16 최종 검증 상태

확인된 결제·환불·생성·정기청구 오류의 로컬 수정 및 실제 모듈/SQLite 검증을 수행했다. 기존186개 수정안의 독립 검토와 추가2개 데이터 쓰기 경쟁의 자체 반복 결과를 구분해 제공한다. 환불 권한 변경 승인 및 실제 브라우저·PG·수업의 종단 검증이 남아 있어 전체 완료나 운영 정상으로 선언하지 않는다.

## 종합표용 요약

작업 전: 누락·중복 생성, 선택 없는 부분환불, 금액 대사 오류, 미확정 정기청구 재청구. 수정: 생성 근거와 원자적 batch, 선택 회차 환불, 누적액 대사, 미확정 금융 요청 보류, 상태 경쟁 차단, 관리자 표시. Harness:188/188×3 및 변이13/13 탐지.
