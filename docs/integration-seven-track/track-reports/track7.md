## 1. 현재 문제

- AI 말하기 실제 소스 경로에서 미결제·만료·취소 학생의 AI 모델 사용이 차단되지 않는다.
- 화상수업의 무료 AI와 별도 유료 AI 구독이 함께 있을 때 유료 AI 자동 청구를 막을 공통 권한 상태가 없다.
- 단순 시작일·종료일 및 enrollment 메모로는 결제 출처, 잔여 유료 기간, 중단/재개, 보강, 선택 환불을 안전하게 연결하기 어렵다.
- 기존 진단·명부의 유형 분류는 현재 유료 접근권과 의미가 다르다. 이 분류는 고치지 않았다.

## 3. 확인된 원인

- 로그인 소유자 확인과 상품 이용권 확인은 별개인데 현재 경로에는 후자가 연결되지 않았다.
- `chargeAiPassOnce`는 기존 AI 구독을 별도로 청구하며 화상 무료 AI 상태를 공통으로 읽지 않는다.
- `activateEnrollment`의 과거 출처 연결은 `notes LIKE '%orderId%'` 중심이다. 출처 고유키와 학생 단위 동시성 보호가 별도로 필요하다.
- `student-track.ts`는 과거 수업도 교사 평가 대상으로 보존한다. 현재 접근권 판정에 재사용할 수 없다.
- `cafe24-sync.ts`는 `student_payments`를 삭제 후 재삽입하며 원본 `p.pay_id`를 저장하지 않는다. 이 테이블의 로컬 자동번호를 지속 가능한 이용권 출처로 삼으면 안 된다.

## 10. 테스트 중 추가 발견된 문제

- 첫 신규 SQLite 구현에서 이벤트 INSERT 자리표시자 수가 컬럼 수보다 1개 많아 실행 실패했다.

- SQLite의 INSERT OR REPLACE는 재귀 트리거 설정에 따라 DELETE 방지만으로 불변 기록 보호를 우회할 수 있다.
- 초기 sparse checkout에는 기존 회귀 검사에 필요한 HTML/JS가 없어 파일 부족 오류가 났다. 기준 커밋의 필요한 텍스트 파일만 추가했다.

## 16. 추가 검토에서 발견·수정한 저장 계층 문제

추가 검토는 읽기 전용으로 시작했다. 아래 재현 뒤 담당 조정에 따라 승인된 로컬 제안·샌드박스 범위 안에서 같은 검토자가 좁은 수정을 수행했다. 따라서 수정 뒤 결과를 별도 제3자의 최종 승인으로 표현하지 않는다.

- 수정 전: SQLite CHECK가 NULL을 통과시켜 유료 AI의 `purchased_ms` 또는 `remaining_ms`를 NULL로 바꿀 수 있었다. 순수 계약의 정상 명령을 통한 접근 우회는 아니며, 직접 SQL로 확인한 저장 방어 결함이다. 두 값의 명시적 IS NOT NULL 조건을 추가했다.
- 수정 전: 파생 `student_entitlements` 행을 훼손하거나 삭제해도 `verifyReplay`는 학생 JSON만 대조했다. 이제 읽기와 원장 재생에서 모든 유료/화상 파생 행의 개수·출처·유형·상태·잔여기간·JSON을 정본 상태와 대조하고 불일치 시 실패한다.
- 추가 보호: 정본과 파생 행을 서로 다른 커밋 시점에서 읽는 오탐을 피하도록 읽기/원장 재생 전체를 하나의 SQLite 읽기 트랜잭션에 둔다. 별도 연결이 중간에 커밋하는 WAL 검사를 통과했다. D1 동작을 증명하는 검사는 아니다.
- 수정 전: 유효한 선택 속성 `makeupApprovalRef: undefined`가 있는 타입 입력은 순수 계약을 통과하지만 명령 JSON에 `undefined`가 기록되어 저장에 실패했다. JSON 직렬화 규칙으로 정규화한 뒤 키를 정렬하여 해시·저장 모두 같은 값을 사용한다. 선택 속성이 생략된 전송 재시도도 동일 명령으로 처리된다.
- 세 회귀 그룹은 원본에서 모두 실패했다(`review-before-fix.log`: 기존 30 통과/신규 3 실패). 수정 뒤 같은 세 그룹과 동시 읽기 한 그룹을 포함한 34그룹이 3회 모두 통과했다. `review-after-fix.log`, 최종 `contract-round-1..3.log`와 별도 `review-independent-oracle.log`를 보존했다.
- 60개 기존 생성 이력의 이름을 실제 내용인 중단/만료/재조정으로 바로잡았다. 환불 명령은 별도 시나리오 그룹에서 검증하며 이 60개 이력에는 포함되지 않는다.
- 스키마 변경은 새 합성 DB 생성용 제안만 고쳤다. 이전에 만든 로컬 DB에 CREATE TABLE IF NOT EXISTS를 다시 실행해도 CHECK가 갱신되지는 않으므로 새 샌드박스를 생성해야 한다. 운영/기존 DB 마이그레이션은 실행하지 않았다.

## 17. 최종 검증 상태

**승인된 범위인 추가 테이블 설계와 로컬 생명주기 샌드박스 검증은 완료했다. 7번 전체 업무는 “추가 검증 필요”다.**

다음 단계는 검증된 기존 결제/학생 매핑의 read-only 대조, 미확인 집단의 처리 결정, D1 저장·기존 결제/스케줄 연동 테스트, 보안 승인 범위의 접근권 적용 및 실제 브라우저 E2E다. 최종 승인 없이 운영 DB 변경·병합·배포하지 않았다.
