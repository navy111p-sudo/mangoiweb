신고 1 · 손가락으로 크게 해도 안 커진다

CASE 1

«휴대폰에서 교재를 손가락으로 크게 해도 커지지 않아»

원인 ①핀치가 끝나는 순간 코드가 스스로 100%로 되돌립니다

교재 영역에는 손가락 처리가 두 벌 붙어 있습니다. 핀치 확대와 더블탭 → 100% 되돌리기입니다. 그런데 더블탭 판정이 「손가락 하나가 떨어진 일이 300밀리초 안에 두 번 있었나」만 봅니다.

핀치를 놓으면 손가락이 두 개 떨어집니다. 대개 몇 밀리초 간격으로 각각 신호를 내므로, 더블탭 판정이 그 둘을 「더블탭」으로 셉니다. 손가락을 벌리는 동안에는 실제로 커지다가, 떼는 순간 원래 크기로 튕겨 돌아갑니다.

// cloudflare-deploy/public/js/idx-main.js:3195~3210
// 더블탭 → 100% reset (pinch zoom 후 빠르게 원상복구)
var lastTap = 0;
wrap.addEventListener('touchend', function(e){
  if (e.changedTouches.length !== 1) return;
  var now = Date.now();
  if (now - lastTap < 300) {
    if (typeof window.pdfSetZoom === 'function') window.pdfSetZoom(1);  ← 핀치 직후 여기로 들어옴
    lastTap = 0;
  } else { lastTap = now; }
});

바로 위 핀치 종료 처리(3188~3193행)는 pinching = false만 하고 더블탭 쪽에는 아무 표시도 남기지 않습니다. 두 처리가 같은 요소에 각각 붙어 있어서 서로를 모릅니다.

왜 「가끔은 되는 것 같기도」 한가

두 손가락이 완전히 같은 순간 떨어지면 신호가 한 번에 묶여 나오고(changedTouches.length === 2), 그러면 더블탭 판정이 첫 줄에서 그냥 빠져나가 확대가 남습니다. 그래서 재현이 들쭉날쭉하고 「내 손가락이 이상한가」 싶어집니다.

원인 ⑥브라우저가 원래 해 주던 확대를 그 자리에서만 꺼 놨습니다

교재 상자에 touch-action: pan-x pan-y가 걸려 있습니다. 이 값은 「끌어서 넘기기는 허용, 핀치 확대는 브라우저가 하지 마라」는 뜻입니다. 즉 확대는 전적으로 위 자체 코드에 맡겨져 있고, 그것이 실패하면 대체 수단이 하나도 없습니다.

// cloudflare-deploy/public/index.html:2234~2239
@media (max-width: 1024px) {
  #pdf-scroll-wrap, .pdf-scroll-wrap {
    touch-action: pan-x pan-y !important;
    -webkit-overflow-scrolling: touch !important;
  }
}
원인 ⑦휴대폰에는 확대 버튼도 화면에 없습니다

확대·축소 버튼(.pdf-pan-btn 등)은 1024px 이하에서 display:none으로 전부 숨겨져 있습니다 (index.html:2216~2232). 나머지 확대 버튼은 「교재도구」 칩을 펼쳐야 나오는데, 그 칩 줄은 좁은 폰에서 화면 밖으로 밀립니다. 그래서 손가락이 유일한 길인데 그 길이 막혀 있었습니다.

고침핀치가 끝난 뒤 400밀리초는 더블탭을 무시

핀치 종료 시각을 남겨 두고, 더블탭 판정 첫 줄에서 그 시각을 확인해 빠져나가면 됩니다. 되돌리기 기능 자체는 그대로 살아 있습니다.

  • 핀치 종료 처리에 window.__pdfPinchEndAt = Date.now() 한 줄, 더블탭 판정 맨 앞에 if (Date.now() - (window.__pdfPinchEndAt||0) < 400) { lastTap = 0; return; } 두 줄.
  • 덤으로 확대 버튼 두 개(+/−)를 폰 화면 아래 고정 노출하는 편이 안전합니다. 손가락 처리가 또 어긋나도 사장님과 학생이 쓸 수 있는 길이 남습니다.

다만 확대가 살아나도 「선명해지지는」 않습니다. 확대하면 더 큰 캔버스에 다시 그리긴 하지만, 그 캔버스가 애초에 화면 해상도의 3분의 1입니다 → 원인 ②(신고 4)을 같이 고쳐야 글자가 읽힙니다.

신고 2 · 교사 화면이 작고 학생 화면이 크다

CASE 2

«교사화면이 작고 학생 화면이 커. 반대로 교사화면이 크던가 최소한 같은 크기로»

타일(칸) 크기는 이미 같습니다. 작아 보이는 것은 칸 안에서 교사 얼굴만 검은 띠에 둘러싸여 있기 때문입니다. 보내 주신 화면에서 강선생님 칸의 위아래에 검은 여백이 넓게 있는 것이 그것입니다.

원인 ③「꽉 채우기」 예외가 세로폰에만 있습니다

영상을 칸에 맞추는 규칙(vcSmartFitVideo)은, 영상과 칸의 방향이 다르거나 비율 차가 1.35배를 넘으면 잘리지 않게 contain(전체 보이기 = 검은 띠 생김)으로 바꿉니다.

2026-07-14에 「교사 화면도 학생처럼 꽉 차게」 지시가 있어 예외를 넣었는데, 그 예외에 「세로폰일 때만」이라는 조건이 붙어 있습니다. 그래서 가로폰·태블릿·PC에서는 예외가 안 걸리고, 교사의 가로(16:9) 웹캠이 세로로 긴 칸에 들어가면 위아래가 검게 남습니다.

// cloudflare-deploy/public/js/idx-main.js:6346~6352
if (box.id !== 'vc-local-box'
    && matchMedia('(max-width:920px) and (orientation:portrait)').matches) {
  v.style.setProperty('object-fit', 'cover', 'important');   ← 꽉 채움
  return;
}
// ↓ 위 조건에 안 걸리면 여기로 내려와 검은 띠가 생긴다
var mismatch = vbgOn || ((vr < 1) !== (br < 1)) || (Math.max(vr,br)/Math.min(vr,br) > 1.35);
v.style.setProperty('object-fit', mismatch ? 'contain' : 'cover', 'important');

계산 예 · 교사 16:9 = 1.78 / 칸 685×770 = 0.89 → 방향이 서로 달라 mismatch → contain

왜 학생만 커 보이나사장님 폰 카메라는 세로 영상입니다

휴대폰 세로 카메라는 9:16 영상을 보냅니다. 세로로 긴 칸과 방향이 같아서 거의 여백 없이 칸을 채웁니다. 같은 크기의 칸인데 한쪽만 여백이 크니 「교사가 작다」로 보입니다.

고침「가로 영상이면 꽉 채우고, 세로 영상일 때만 전체 보이기」

예외의 조건을 화면 폭이 아니라 「보내온 영상이 세로인가」로 바꿉니다. 그러면 교사가 PC 웹캠(가로)이면 어느 기기에서도 꽉 차고, 교사가 휴대폰 세로로 들어와도 얼굴이 잘리지 않습니다.

「교사를 더 크게」까지 원하시면 칸 비중을 grid-template-rows: 1.6fr 1fr로 주면 됩니다.

고칠 때 반드시 함께 볼 곳 · 「정확히 반반」 규칙이 다섯 벌입니다

원인 ②교재를 화면 해상도의 3분의 1로 그립니다 · 가장 큰 원인

교재는 <canvas>에 그립니다. 캔버스는 「몇 개의 점으로 그릴지」를 따로 정해 줘야 합니다. 안 정하면 브라우저가 쓰는 논리 단위(CSS 픽셀)를 그대로 씁니다.

그런데 요즘 휴대폰은 논리 1칸을 실제 점 3개로 표시합니다(devicePixelRatio 3). 즉 화면은 1170개의 점을 쓸 수 있는데 390개만 그려 놓고 3배로 늘려서 보여주는 셈입니다. 획이 가는 한글은 이 단계에서 뭉개져 사라집니다.

// cloudflare-deploy/public/js/idx-main.js:11843~11847
function _pdfFitCanvas(canvas, w, h) {
  const W = Math.max(1, Math.floor(w)), H = Math.max(1, Math.floor(h));
  canvas.width = W; canvas.height = H;   ← 화면 배율(devicePixelRatio)이 없다
}

확인 · devicePixelRatio라는 낱말이 index.html과 idx-main.js 전체에 0건입니다. 교재 그리는 길 어디에도 화면 배율을 반영하는 곳이 없습니다.

원인 ⑦펼침면 한 장 · 폭이 반으로 나뉩니다

보내 주신 화면의 교재는 책을 펼쳐 두 쪽을 한 장에 찍은 사진입니다. 화면은 그 한 장을 폭에 맞추므로, 한 쪽이 실제로 받는 폭은 절반입니다. 신고 3의 좁은 자리와 겹치면 한 쪽당 190픽셀이 됩니다.

업로드 쪽은 죄가 없습니다 — 올릴 때 줄이거나 다시 압축하는 코드가 없어(js/idx-main.js:11550 pdfUploadOne) 원본이 그대로 서버에 있습니다. 즉 범인은 「화면에서 줄이는 단계」일 가능성이 큽니다.

고침화면 배율을 반영하고, 축소 품질을 올립니다
  • 캔버스의 점 개수를 × devicePixelRatio로 잡고, 보이는 크기는 style.width/height로 원래대로 둡니다. 필기 겹칩 캔버스(pdf-anno)도 같이 맞춰야 합니다 — 안 하면 펜 자국이 어긋납니다.
  • 배율은 2로 상한을 두시길 권합니다. 3배로 하면 점 개수가 9배가 되어 구형 폰에서 발열·버벅임이 납니다.
  • 사진은 imageSmoothingQuality = 'high'로 그립니다(한 줄).
  • 강사에게는 「한 장에 한 쪽씩」 안내하는 것이 화면 어떤 개선보다 효과가 큽니다.

이 건에서 확인하지 못한 것

작업 환경(원격 컨테이너)의 프록시가 mangoi.ai를 막고 있어, 그 방에 실제로 올라와 있던 교재 파일을 열어 보지 못했습니다. 원본 자체가 흐린 사진이었을 가능성은 아직 남아 있습니다.

강선생님 제보 3건 · 뿌리가 하나입니다

교재와 칠판은 이미 예외로 빼 뒀습니다(2026-07-15 칠판, 2026-08-20 교재 — 같은 신고가 두 번 있었다는 뜻입니다). 배경화면·동영상·학생게임·AI웜업만 아직 접힙니다.

교재 올리기 버튼(📁 교재 업로드)과 라이브러리 버튼은 교재 탭 안의 도구줄에 있습니다. 본문이 접히면 그 줄도 함께 사라집니다. 게다가 접힌 상태를 다시 펴는 버튼이 화면에 따로 없습니다 — 📖 교재 탭을 다시 눌러야 돌아옵니다. 그 방법을 모르면 수업 도중에 교재를 올릴 길이 사라집니다.

고침접기를 없애거나, 되돌아오는 길을 보이게
  • 권장 — 교재·칠판과 똑같이 배경화면도 예외로 추가합니다(조건에 && tabName !== 'bg' 한 줄). 다시 누르면 그냥 그대로 있습니다. 같은 신고가 세 번째이므로, 접기 자체를 없애는 것도 생각해 볼 만합니다.
  • 접기를 남긴다면, 접힌 동안 「📖 교재로 돌아가기」 띠를 화면에 한 줄 띄워야 합니다. 지금은 아무 표시가 없어 「고장」으로 읽힙니다.

세 건을 관통하는 것 · 화면이 중국어로 말하지 않습니다

강선생님이 받은 안내는 전부 이런 것들입니다 — 「교재는 선생님만 바꿀 수 있어요」 · 「교재 화면에 바로 못 여는 파일이 있어요」 · 「⚠ 로드 실패 (네트워크 확인)」. 한국어와 영어뿐이고, 언어 전환도 KO / EN 두 가지만 돕니다.

그래서 「막혔다」와 「고장났다」를 구분할 방법이 강선생님께 없습니다. 세 건을 다 고쳐도, 다음에 다른 것이 막히면 같은 모양의 제보가 또 옵니다.

최소 조치 — 수업 화면에서 실제로 사람을 막아 세우는 문구만(권한 거절·형식 거절·모델 로드 실패·업로드 실패, 대략 10줄 안팎) 중국어를 함께 넣습니다. 화면 전체를 중국어로 만드는 일이 아니라, 「왜 안 되는지」 말해 주는 줄에만 붙이는 것입니다. 언어 전환 목록에 중국어를 넣는 것은 별건이고 훨씬 큰 일입니다.

고칠 때 걸리는 제약 세 가지

1 · 첫 화면 무게에 여유가 0KB입니다

방금 실제로 재 봤습니다. index.html이 첫 화면에서 받는 무게가 1562KB인데 상한이 1562KB(기준선 1550 + 여유 12)입니다. 주석 한 문단만 더해도 게이트가 빨간불입니다.

$ node test-harness/first_paint_budget_harness.mjs
index.html    blocking 1562KB (인라인 273KB + 외부 1289KB) · defer 1039KB
✅ 첫 화면 무게 예산 유지        ← 상한 1550+12 = 1562KB, 여유 0

그러므로 새 코드는 idx-main.js나 index.html 안에 넣으면 안 됩니다. 별도 파일 + defer로 빼고, 원래 함수를 감싸는 방식으로 붙여야 합니다. 그 예산은 필리핀 회선을 지키려고 둔 것이라 기준선을 올리는 것은 마지막 수단입니다.

2 · 여기는 공동 금지구역입니다

public/index.html은 CLAUDE.md 4-2장에서 배포 권한자(A) 전용으로 지정된 파일입니다. js/idx-main.js는 그 인라인 스크립트를 그대로 옮겨 둔 것이라 실질적으로 같은 영역입니다. 이번 수정은 배포 권한자가 직접 하거나, 최소한 사전에 알리고 진행해야 합니다.

3 · 이런 버그는 지금의 검사가 못 잡습니다

네 건 모두 「함수도 값도 다 있고, 몇 픽셀인가 / 어느 순서인가만 틀린」 종류입니다. 글자를 찾는 회귀 검사 211개와 타입체크는 전부 초록불인 상태에서 이 문제들이 살아 있었습니다.

고치면서 진짜 브라우저로 재는 검사를 함께 만들어야 재발을 막습니다 — 390픽셀 폭에서 ① 두 손가락 확대 후 배율이 유지되는가 ② 교사·학생 칸의 실제 영상 표시 면적 ③ 교재 영역 높이 ④ 캔버스 점 개수가 화면 배율만큼인가. 기존 test-harness/manual/ 검사들이 본보기입니다.

사장님께 여쭙는 것 · 두 가지

  1. 세로로 든 폰에서 얼굴을 오른쪽으로 옮길까요? 2026-07-14에 「세로폰은 항상 1/2 반반, PIP 절대 금지」라고 지시하셔서 지금 코드가 그렇게 못 박혀 있습니다. 옮기면 그 지시를 거두는 것이 됩니다. (옮기지 않고 얼굴 높이만 줄이는 3번만으로도 교재는 1.5배 커집니다.)
  2. 그 수업의 교재 원본이 원래 흐렸는지 확인이 필요합니다. 위 «확인 방법»의 주소를 한 번 열어 보시거나, 강선생님께 그날 올린 사진 파일을 받아 주시면 화면 문제인지 원본 문제인지 갈립니다.
  3. 강선생님께 두 가지만 물어봐 주십시오 — ① 올리려던 파일 확장자(.webp·.heic·.jpg 중 무엇인지) ② 브라우저에서 storage.googleapis.com이 열리는지. 이 둘이면 신고 5·6의 원인이 확정됩니다.
  4. 중국어 안내를 어디까지 넣을까요? 지금 권하는 것은 「막혔을 때 이유를 말해 주는 문구 10줄 안팎」뿐입니다. 수업 화면 전체를 중국어로 만드는 것은 훨씬 큰 일이고, 중국인 강사가 몇 분인지에 따라 판단이 갈립니다.
