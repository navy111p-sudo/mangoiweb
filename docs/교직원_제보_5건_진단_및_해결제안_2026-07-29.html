가장 중요한 한 가지

결제 시스템은 아직 "테스트 모드"입니다. 운영 DB payment_orders의 결제완료 5건이 전부 토스 테스트 가맹점(tvivarepublica) 기록입니다. 즉 카드로 실제 돈이 빠져나간 적은 아직 0건입니다.

이 사실이 우선순위를 뒤집습니다.

  • 제보 #4(무료체험 결제)는 아직 실제 청구로 이어지지 않았습니다. 다만 실키(live) 전환하는 순간 즉시 사고가 됩니다.
  • 반대로 계좌이체 · 카카오페이 · 토스송금 · 가상계좌는 PG를 거치지 않습니다. 화면에 적힌 계좌로 학부모가 직접 송금하는 방식이라 테스트/실전 구분이 없습니다. 지금 이 순간에도 실제 돈이 움직일 수 있는데, 그 계좌번호가 자리표시자이거나 난수입니다.

따라서 오늘 당장 막아야 할 것은 제보 #4가 아니라 신규 발견 A·C 입니다.

1. 신규 발견 (제보에 없지만 더 급한 것)

즉시 조치(오늘, 30분): 가상계좌 결제수단 카드를 화면에서 숨김. 정식 PG 가상계좌를 붙이기 전까지는 노출하지 않습니다.

B. 🔴 「결제 완료 확인」 버튼이 부르는 API가 서버에 없습니다

증거

  • 호출부: idx-payment-modal.js:1058 → fetch('/api/student/payment', {method:'POST'})
  • 서버: src/ 전체에 /api/student/payment 핸들러 없음
  • 라우팅 종단: src/index.ts:1780 — 매칭 안 된 /api/* 는 404 JSON 반환
  • 라이브 확인: GET https://test.mangoi.co.kr/api/student/payment → 404

실제로 벌어지는 일: 학부모가 송금한 뒤 「✅ 결제 완료 확인」을 누르면 alert('결제 처리 중 오류: Not Found') 만 뜨고 접수가 전혀 되지 않습니다.

즉 카드를 제외한 5개 결제수단(카카오페이·토스·계좌이체·네이버페이·가상계좌)은 접수 경로 자체가 끊겨 있습니다. 위 DB 표에 카드 외 기록이 0건인 이유가 이것입니다.

조치(1일): POST /api/student/payment 신설 — 주문을 payment_orders에 status='pending_manual'로 기록하고, 관리자 결제센터에 "입금 확인 대기" 목록으로 띄웁니다. ⚠️ src/index.ts 라우팅 + 인증 게이트에 반드시 등록해야 동작합니다(CLAUDE.md 함정 항목).

슬라이드 3 — 계좌이체 → 실시간 계좌이체 전환 🟡

제보: 가상계좌는 자동 식별되는데, 계좌이체는 입금자-회원 매칭이 안 돼 관리자가 수동으로 기간을 연장해야 함.

확인: 문제 인식은 정확합니다. 다만 전제 한 가지를 바로잡아야 합니다.

제보 전제: "가상계좌는 입금 시 회원 식별이 자동으로 되어 별도 작업이 필요 없음" 현재 시스템에서는 사실이 아닙니다. 지금의 가상계좌는 정식 PG 발급이 아니라 브라우저가 지어낸 난수입니다(신규발견 A). 식별은커녕 돈이 어디로 가는지도 모릅니다.

현행 「계좌이체」 화면이 하는 일은 은행/계좌/예금주/금액/입금자명(랜덤 4자리 부여)을 보여주고 "송금 후 확인 버튼을 눌러달라"고 안내하는 것이 전부입니다(idx-payment-modal.js:466-505). PG를 전혀 거치지 않으므로 자동 매칭이 원리적으로 불가능합니다. 그 "확인 버튼"마저 404입니다.

해결 — 2단계로 나눌 것을 제안합니다

3-1단계 (권장, 먼저) — 정식 PG 가상계좌 켜기 - 토스페이먼츠 결제창의 가상계좌를 호출: tp.requestPayment('가상계좌', {...}) - 입금 통보 웹훅은 이미 만들어져 있습니다: src/api-pay.ts:267 (/api/pay/webhook) - 웹훅 본문을 신뢰하지 않고 토스 API로 재조회해 검증, 금액 대조, 멱등 처리, 입금 확인 시 activateEnrollment()로 수강 자동 활성화까지 이미 구현돼 있습니다. - 즉 서버 작업이 사실상 끝나 있고, 프론트에서 난수 발급을 진짜 PG 호출로 바꾸기만 하면 됩니다. - 공수: 2~3일 · 추가 계약 불필요(토스 계약 범위 내)

3-2단계 — 실시간 계좌이체 추가 - 토스페이먼츠 결제창의 계좌이체를 호출: tp.requestPayment('계좌이체', {...}) - 학부모가 결제창에서 본인 은행 인증 후 즉시 출금 → 주문번호에 묶여 들어오므로 입금자명 매칭 자체가 불필요 - 공수: 개발 1~2일 + PG 계약 항목 추가 리드타임(실시간 계좌이체는 별도 심사·수수료율)

Appendix B. Executive Summary (English)

Scope: 5 issues reported by staff on https://test.mangoi.co.kr, verified against source code, the live site, and the production D1 database (read-only).

All 5 reports are confirmed. Three additional, more urgent problems were found.

# Finding Severity
A Virtual account numbers are fabricated in the browser via Math.random(), yet shown as "issued successfully". A parent transferring money sends it nowhere — or to a stranger. 🔴 P0
B The "confirm payment" button calls an API that does not exist (/api/student/payment → 404). Every non-card method (KakaoPay, Toss, bank transfer, NaverPay, virtual account) fails to register. Confirmed by DB: zero non-card orders ever recorded. 🔴 P0
C Bank account shown to parents is a development placeholder (Shinhan 110-555-123456). KakaoPay code and Toss ID are placeholders too. 🔴 P0
1 KakaoTalk consult button 404 — channel ID is the example value _mangoi from a code comment; the real one is _xlqnSxd. Affects 7+ entry points, not just the reported one. One-line fix. 🟠 P1
4 Free trial still enters the payment flow. No real charge occurs today — the server price table has no trial entry and rejects it — but the flow must be branched before going live. 🟠 P1
2 Required fields (sessions/months/start date/teacher/days/time) — there are two payment entry points. enroll.html already validates all six correctly but is nearly unreachable; the home modal collects only "sessions". Recommend routing regular courses to enroll.html. 🟠 P1

Key context: The payment system is still in test mode — all 5 completed orders in production used the Toss test merchant. No real card money has moved. However, bank transfer / KakaoPay / Toss transfer / virtual account bypass the PG entirely, so real money can move today into placeholder or fabricated account numbers. That, not the free-trial bug, is the true P0.

Total engineering effort: ~7–10 days, excluding PG contract lead time. Most fixes touch public/index.html and src/index.ts, which are owner-restricted files — they must be done sequentially by the deploy owner.

Decisions needed from management: (1) apply for real-time bank transfer with the PG, (2) confirm the real corporate bank account / KakaoPay code / Toss ID to display, (3) decide whether to implement or disable the 7 dormant point rules, (4) confirm free-trial policy.
