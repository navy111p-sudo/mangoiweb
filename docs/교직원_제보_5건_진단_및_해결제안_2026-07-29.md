### 가장 중요한 한 가지

> **결제 시스템은 아직 "테스트 모드"입니다.**
> 운영 DB `payment_orders`의 결제완료 5건이 **전부 토스 테스트 가맹점(`tvivarepublica`)** 기록입니다.
> 즉 **카드로 실제 돈이 빠져나간 적은 아직 0건**입니다.

이 사실이 우선순위를 뒤집습니다.

- 제보 #4(무료체험 결제)는 **아직 실제 청구로 이어지지 않았습니다.** 다만 실키(live) 전환하는 순간 즉시 사고가 됩니다.
- 반대로 **계좌이체 · 카카오페이 · 토스송금 · 가상계좌는 PG를 거치지 않습니다.** 화면에 적힌 계좌로 학부모가 직접 송금하는 방식이라 **테스트/실전 구분이 없습니다.** 지금 이 순간에도 실제 돈이 움직일 수 있는데, 그 계좌번호가 **자리표시자이거나 난수**입니다.

**따라서 오늘 당장 막아야 할 것은 제보 #4가 아니라 신규 발견 A·C 입니다.**

### A. 🔴 가상계좌가 실제로는 존재하지 않는 번호입니다

**증거** — `cloudflare-deploy/public/js/idx-payment-modal.js:530-566`

```js
} else if (method === 'virtual') {
  // 가상계좌 — 즉시 발급 시뮬레이션 (실제 PG 연동 시 서버에서 발급)
  const va = '79' + (Math.floor(Math.random()*1e10).toString().padStart(10,'0'));

이렇게 만든 난수를 화면에는 이렇게 표시합니다.

- 「**가상계좌 즉시 발급 완료**」
- 「발급 은행: 우리은행 (가상계좌)」
- 「✅ 위 가상계좌로 입금하시면 자동으로 결제 처리됩니다 (24시간 유효)」

**실제로 벌어지는 일**: 학부모가 이 번호로 입금하면 **존재하지 않는 계좌이면 반송**, **우연히 타인 계좌와 일치하면 남에게 송금**됩니다. 어느 쪽이든 우리 장부에는 아무 기록도 남지 않습니다(`payment_orders`에 행 자체가 생기지 않음 — 아래 표 참고).

**운영 DB 실측** (`payment_orders` 전체)

| method | status | 건수 |
|---|---|---|
| card | failed | 12 |
| card | pending | 7 |
| card | paid | 5 |

→ **카드 외 결제수단은 주문 기록이 단 1건도 없습니다.** 가상계좌·계좌이체로 접수된 건은 시스템상 아예 존재하지 않습니다.

**즉시 조치(오늘, 30분)**: 가상계좌 결제수단 카드를 **화면에서 숨김**. 정식 PG 가상계좌를 붙이기 전까지는 노출하지 않습니다.

### B. 🔴 「결제 완료 확인」 버튼이 부르는 API가 서버에 없습니다

**증거**

`alert('결제 처리 중 오류: Not Found')` 만 뜨고 **접수가 전혀 되지 않습니다.**

⚠️ `src/index.ts` 라우팅 + 인증 게이트에 **반드시 등록**해야 동작합니다(CLAUDE.md 함정 항목).

window.openKakao = function(){
  var url = 'https://pf.kakao.com/' + KAKAO_CHANNEL_ID + '/chat';
```

**라이브 실측**

| URL | 페이지 제목 |
|---|---|
| `https://pf.kakao.com/_mangoi` | **채널 - 페이지를 찾을 수 없습니다.** |
| `https://pf.kakao.com/_xlqnSxd` | 카카오톡채널 - **망고아이** |

- 카테고리 그리드의 「카톡으로 신청」, 「카톡 채널 추가」

### 슬라이드 2 — 결제창 필수 선택 항목 누락 🟠

**제보**: 횟수·개월·시작날짜·강사·요일·시간 6개를 다 골라야 하는데, "횟수"만 고르면 바로 결제로 넘어감.

**확인**: 사실입니다. 다만 원인은 "검증 로직이 빠진 것"이 아니라 **결제 진입점이 두 개로 갈라져 있는 것**입니다.

| 진입점 | 파일 | 받는 항목 | 결제 버튼 잠금 | 접근 경로 |
|---|---|---|---|---|
| **홈 결제 모달** | `index.html:21000~21352` | **횟수(상품)만** | 없음 | 홈 상단 「💳 결제하기」, 사이드바, AI검색 — **주 동선** |

`enroll.html`은 이미 제보 내용대로 정확히 동작합니다.

- 강사 카드 선택 → 주 횟수 / 기간(개월) / 수업 길이 → 요일 / 시작 시각 / 시작일

  (`enroll.html:219` — `btnPay.disabled = !(CHECK_OK && QUOTE && st.teacher)`)
- 요일 개수가 모자라면 안내: 「요일을 N개 선택해 주세요 (지금 M개)」

반면 홈 결제 모달에는 **`요일`·`개월`·`시작일` 이라는 글자 자체가 한 번도 등장하지 않습니다**(모달 영역 전수 검색 결과 0건). 강사 선택 UI도 없습니다. 즉 "검증을 추가"할 대상이 없습니다.

**해결 — 두 가지 안**

| 안 | 내용 | 공수 | 장단점 |
|---|---|---|---|
| **A (권장)** | 홈 「결제하기」에서 **정규 수강권**을 고르면 `enroll.html`로 넘김. 모달은 무료체험·상담·연장 전용으로 축소 | **1~2일** | 이미 검증된 흐름 재사용. 중복 코드 제거. 사고 반경 작음 |

**권장: A안.** 이유는 세 가지입니다.
1. 슬롯 충돌 확인·가격 계산·자동 스케줄 생성이 이미 `enroll` API에 다 있습니다.
2. 홈 모달의 결제 접수 경로는 어차피 끊겨 있습니다(신규발견 B). 살릴 이유보다 정리할 이유가 큽니다.
3. `index.html`은 공동 금지구역이라 수정 반경을 최소화하는 편이 안전합니다.

**검증**: 6개 중 하나라도 비우면 결제 버튼이 잠기는지 / 요일 수가 주 횟수와 다르면 안내가 뜨는지 / 결제 후 스케줄이 실제로 생성되는지.

### 슬라이드 3 — 계좌이체 → 실시간 계좌이체 전환 🟡

**제보**: 가상계좌는 자동 식별되는데, 계좌이체는 입금자-회원 매칭이 안 돼 관리자가 수동으로 기간을 연장해야 함.

**확인**: 문제 인식은 정확합니다. 다만 전제 한 가지를 바로잡아야 합니다.

> 제보 전제: "가상계좌는 입금 시 회원 식별이 자동으로 되어 별도 작업이 필요 없음"
> **현재 시스템에서는 사실이 아닙니다.** 지금의 가상계좌는 정식 PG 발급이 아니라 브라우저가 지어낸 난수입니다(신규발견 A). 식별은커녕 돈이 어디로 가는지도 모릅니다.

현행 「계좌이체」 화면이 하는 일은 **은행/계좌/예금주/금액/입금자명(랜덤 4자리 부여)을 보여주고 "송금 후 확인 버튼을 눌러달라"고 안내**하는 것이 전부입니다(`idx-payment-modal.js:466-505`). PG를 전혀 거치지 않으므로 자동 매칭이 원리적으로 불가능합니다. 그 "확인 버튼"마저 404입니다.

**해결 — 2단계로 나눌 것을 제안합니다**

**3-1단계 (권장, 먼저)** — 정식 **PG 가상계좌** 켜기
- 토스페이먼츠 결제창의 가상계좌를 호출: `tp.requestPayment('가상계좌', {...})`
- 입금 통보 웹훅은 **이미 만들어져 있습니다**: `src/api-pay.ts:267` (`/api/pay/webhook`)
  - 웹훅 본문을 신뢰하지 않고 토스 API로 재조회해 검증, 금액 대조, 멱등 처리, 입금 확인 시 `activateEnrollment()`로 **수강 자동 활성화**까지 이미 구현돼 있습니다.
- 즉 **서버 작업이 사실상 끝나 있고, 프론트에서 난수 발급을 진짜 PG 호출로 바꾸기만 하면 됩니다.**
- 공수: **2~3일** · 추가 계약 불필요(토스 계약 범위 내)

**3-2단계** — **실시간 계좌이체** 추가
- 토스페이먼츠 결제창의 계좌이체를 호출: `tp.requestPayment('계좌이체', {...})`
- 학부모가 결제창에서 본인 은행 인증 후 즉시 출금 → 주문번호에 묶여 들어오므로 **입금자명 매칭 자체가 불필요**
- 공수: 개발 1~2일 + **PG 계약 항목 추가 리드타임**(실시간 계좌이체는 별도 심사·수수료율)

> ⚠️ **통장 정보를 우리 화면에서 직접 입력받는 방식은 제안하지 않습니다.**
> 제보 원문의 "결제 팝업창에서 회원이 본인 통장 정보(은행/계좌번호)를 입력" 은
> 우리 페이지가 금융정보를 직접 다루게 되어 **PG사 정책·전자금융거래법상 불가**합니다.
> 실제 구현은 **PG가 띄우는 결제창 안에서 은행 인증**으로 이뤄지며, 사용자 경험은 제보 취지와 동일합니다.

**병행 조치**: 3-1단계 완료 전까지 「계좌이체」는 실제 법인계좌로 바로잡고(신규발견 C), 「가상계좌」는 숨깁니다.

**Scope**: 5 issues reported by staff on https://test.mangoi.co.kr, verified against source code, the live site, and the production D1 database (read-only).
