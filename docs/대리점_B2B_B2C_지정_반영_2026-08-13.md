## 3. 테스트·관리용 계정 5행 제외 (2026-08-14 지시 반영)

이름상 실제 학원이 아닌 3개 계정을 미지정으로 되돌렸습니다.

| id | 학원명 | 결제건수 |
|---:|---|---:|
| 1 | 테스트 B2C | 20 |
| 28 · 91 · 845 | 미사용 (중복 등록 3줄) | 9 |
| 273 | N TEST대리점 | 1 |

- «미사용»은 **3줄이 전부** 미지정이어야 합니다. 결제내역 분리는 ID 가 아니라 **이름**으로
  매칭해서 `ORDER BY c.id LIMIT 1` 로 대표 한 줄을 뽑기 때문에, 한 줄만 남겨두면
  그 줄이 대표가 되어 그대로 B2B 로 잡힙니다. 그래서 «3곳»이 실제로는 **5행**입니다.
- 이 조치로 B2B 매출 집계에서 **30건이 빠졌습니다**
  (첫 보고에서 29건이라고 적었으나 20+9+1 = **30건**이 맞습니다).

## 4. 반영 전 검증

1. **검토표 자체 검사** — 574행 ID 중복 없음, 확정값이 `B2B`/`B2C` 아닌 칸 0개, 빈칸 0개.
2. **ID ↔ 학원명 대조** — 검토표를 만든 8/12 이후 `centers` 가 바뀌었을 수 있어,
   574개 ID 의 `centers.name` 이 검토표 학원명과 **글자 그대로** 같은지
   `id%8` 버킷 체크섬 8개로 대조 → **8/8 전부 일치, 건수도 574 일치**.
3. **이름 충돌 검사** — 같은 학원명이 여러 줄인 9개 그룹이 전부 같은 값인지 확인 → 충돌 0건.

## 5. 🔴 첫 반영분이 지워진 사고와 그 원인

### 무슨 일이 있었나

| 시각 (KST) | 일 |
|---|---|
| 08-14 03:29~03:33 | 1차 반영 (B2B 451 / B2C 123). 집계·결제내역 분리까지 정상 확인 |
| 08-14 03:45:51 | **야간 동기화가 `centers` 921행을 통째로 다시 써서 payment_type 전멸** |
| 08-14 04:0x | 되돌리기 작업 중 발견 — 전 행이 NULL 로 돌아가 있었음 |

`centers.updated_at` 이 921행 전부 `2026-08-14 03:45:51` 한 값으로 덮여 있는 것으로 확인했습니다.

### 원인 — `INSERT OR REPLACE`

`src/cafe24-sync.ts` `importCafe24Org()` 가 이렇게 돼 있었습니다.

```sql
INSERT OR REPLACE INTO centers (id, franchise_id, name, address, manager, active, created_at, updated_at)
```

SQLite 의 `REPLACE` 는 UPDATE 가 아니라 **«기존 행을 지우고 새 행을 넣는»** 동작입니다.
그래서 위 목록에 없는 `payment_type` 은 매일 새벽 **NULL 로 초기화**됐습니다.
동기화는 워커 cron `"0 18 * * *"`(UTC) = **매일 03:00 KST** 로 돌아갑니다.

### 이게 왜 중요한가

이건 제 작업만의 문제가 아닙니다. **기능 자체가 처음부터 동작할 수 없는 상태였습니다.**
관리자가 `PATCH /api/admin/centers` 로 결제유형을 지정해도 **그날 밤이면 사라집니다.**
8/12 에 만든 «대리점 결제유형 지정»(수정요청 #05)은 지금껏 한 번도 유지된 적이 없습니다.

### 고친 내용

`INSERT OR REPLACE` → **UPSERT**(`ON CONFLICT(id) DO UPDATE`)로 바꿔,
카페24가 주는 컬럼(`name`·`address`·`manager`·`active`·`franchise_id`)만 덮어쓰고
**D1 에서만 관리하는 값(`payment_type`, `country`)은 건드리지 않게** 했습니다.

`franchises` 도 같은 결함이 있어 함께 고쳤습니다(`opened_at` 이 매일 밤 지워지고 있었습니다).

### ⏰ 남은 조건 — 배포

**코드 수정은 배포돼야 효력이 생깁니다.** 지금 데이터는 다시 넣어 뒀지만,
수정이 배포되지 않은 채 **다음 03:00 KST** 가 지나면 또 지워집니다.

- 배포 전이라면: 위 마이그레이션 SQL 을 다시 돌리면 복구됩니다(몇 초).
- 저는 배포 권한이 없어 **배포하지 않았습니다.** `main` 병합 시 GitHub Actions 가 자동 배포합니다.

## 6. 실제로 무엇이 달라졌나 — 결제내역 B2B/B2C 분리

이 컬럼이 비어 있는 동안에는 분리 기능이 **사실상 동작하지 않았습니다.**

| 결제 11,640건 | 반영 전 | 현재 |
|---|---:|---:|
| B2B | **0건** | 11건 (196.8만원) |
| B2C | 11,640건 (100%) | 11,629건 |

반영 전에는 `centers.payment_type` 이 전부 비어 있어 학생 쪽 대체값(`students_erp.payment_type`)으로
넘어갔는데, 그 값이 `B2B%` 인 학생이 **한 명도 없어** 전건이 B2C 로 떨어졌습니다.

현재 B2B 로 잡히는 11건의 내역입니다. 테스트 계정은 §3 조치로 모두 빠졌습니다.

| 학원명 | 건수 | 금액 |
|---|---:|---:|
| N 안산 SLP 가정망고 | 5 | 1,518,000 |
| N 리시움학원수업 | 5 | 420,200 |
| N 안산 LAB | 1 | 30,000 |

## 7. 되돌리는 방법

최초 적용 전에는 921곳이 **전부** 미지정이었으므로 한 줄이면 됩니다.

```sql
UPDATE centers SET payment_type = NULL WHERE payment_type IS NOT NULL;
```

## 8. 앞으로 — 화면에서 고칠 수 있게 하려면

지금은 대리점의 결제유형을 **관리자 화면에서 보거나 고칠 수 없습니다.**
서버 API 는 있는데(`PATCH /api/admin/centers` — `{id, payment_type}`),
`public/admin.html` 에 그걸 쓰는 UI 가 아직 없습니다.

- 새 대리점이 생기면 결제유형이 **미지정으로 시작**하고, 지정하려면 사람이 API 를 직접 불러야 합니다.
- 대리점 목록 화면에 «결제유형» 열 + 드롭다운을 붙이는 작업이 필요합니다.
  `public/admin.html` 은 **A(배포 권한자) 담당 영역**이라 이번 작업에는 넣지 않았습니다.
  진행 여부를 정해 주시면 그때 반영하겠습니다.
