1. 먼저 이 한 장 — 전체 그림

1-1. 한 문장 요약

인터넷에 "진짜 원본" 폴더를 하나 두고, 세 사람이 각자 복사본을 받아 고친 뒤, 원본에 다시 합칩니다. 합쳐진 원본이 실제 홈페이지로 나갑니다.

4. 누가 어떤 파일을 맡는가

충돌을 없애는 방법은 기술이 아니라 약속입니다. 이유는 파일 크기 때문입니다.

왜 파일을 나눠야 하나요 index.html 은 1.6MB, admin.html 은 1.3MB 짜리 거대한 한 덩어리 파일입니다. 이 파일을 두 사람이 동시에 고치면, 깃이 "어느 쪽이 맞는지" 판단하지 못해 충돌 해결이 사실상 불가능합니다. 잘못 풀면 남의 작업이 통째로 사라집니다.

4-2. 직원 A 와 B 는 어떻게 나누나

게임은 파일이 하나씩 따로 있어서 서로 안 겹칩니다. 그래서 "파일 단위"로 나누면 충돌이 0에 가깝습니다.

  • 예) A = 단어장·복습퀴즈·웜업   /   B = 게임들·발음코치·AI 영작
  • 단, api-games.ts, api-points.ts 는 둘 다 쓰는 공용 파일입니다. 여기를 고칠 땐 먼저 상대에게 한마디 하세요.
  • 내 영역 밖 파일을 꼭 고쳐야 하면 혼자 고치지 말고 사장님께 먼저 말씀하세요.

5. 매일 하는 4단계

1
아침에 최신본 받기 — 커피보다 먼저 
git checkout main
git pull
어제 남이 고쳐놓은 것을 내 컴퓨터로 가져옵니다. 이것만 지켜도 문제의 절반은 안 생깁니다.
2
내 작업방(브랜치) 만들기 
git checkout -b 단어장-정렬수정
원본을 직접 건드리지 않고 나만의 복사본에서 작업합니다. 여기서 뭘 망가뜨려도 남에게 영향이 없습니다.
이름 예시: 로그인-오류수정, 게임-속도개선. 한글도 됩니다.
3
다 고쳤으면 도장 찍고 올리기 
git add -A
git commit -m "단어장 목록을 가나다순으로 정렬"
git push -u origin 단어장-정렬수정
-m 뒤 따옴표 안에는 무엇을 했는지 한글로 적습니다. 나중에 "이거 누가 왜 고쳤지?" 할 때 이 문장을 봅니다.
한 번 -u 로 올리고 나면, 그 다음부터는 git push 만 치면 됩니다.
4
사장님께 결재 올리기 (Pull Request) GitHub 사이트에 들어가면 "Compare & pull request" 초록 버튼이 보입니다. 눌러서 제출하세요. 제목에 무엇을 고쳤는지, 본문에 왜 고쳤는지와 어떻게 확인했는지를 적습니다.
"내가 고친 게 홈페이지에 안 보여요" — 정상입니다 4단계까지는 제안일 뿐입니다. 사장님이 검사하고 합쳐야(6장), 그리고 배포돼야(8장) 화면에 나옵니다.

5-1. 커밋은 자주, 작게

하루 종일 고치고 저녁에 한 번 커밋하면, 문제가 생겼을 때 어디서부터 잘못됐는지 찾을 수 없습니다. "한 가지 일이 끝날 때마다" 커밋하세요. 커밋은 공짜입니다.

6. 합치기(merge) — 사장님이 검사하는 법

6-1. PR 화면에서 무엇을 보나

  1. Files changed 탭 — 바뀐 줄이 초록(추가) / 빨강(삭제)으로 보입니다.
  2. 바뀐 파일이 담당 영역 안인지 먼저 봅니다. 직원 PR 에 index.html 이나 wrangler.toml 이 들어 있으면 그 자리에서 되돌려 보내세요.
  3. 비밀 열쇠(.env, 토큰 문자열)가 섞여 있지 않은지 확인합니다.
"파일 53개가 바뀌었다"고 나와도 놀라지 마세요 배포할 때마다 모든 HTML 맨 아래에 배포 시각 도장이 새로 찍힙니다. 
<!-- BUILD:20260811145740 -->
그래서 배포 직후 git pull 하면 53개가 바뀐 것처럼 보이지만, 대부분 이 1줄짜리 도장뿐입니다. 진짜 변경만 보려면 도장을 빼고 봅니다: 
git diff -I'BUILD:' main..작업브랜치

6-2. 충돌(conflict)이 났을 때

충돌 지점어떻게 하나
<!-- BUILD:숫자 --> 줄아무 쪽이나 골라도 됩니다. 어차피 다음 배포 때 새로 찍힙니다.
그 외 모든 곳직원은 혼자 풀지 마세요. 사장님께 알리고 같이 봅니다. 잘못 풀면 남의 작업이 사라집니다.

6-3. 깃이 못 잡는 충돌 — "보이지 않는 충돌"

이게 제일 무섭습니다 두 사람이 같은 버그를 각자 다르게 고치면, 두 수정이 서로 다른 줄에 있기 때문에 깃은 충돌이라고 알려주지 않고 조용히 둘 다 넣어버립니다. 결과는 "고침이 두 번 적용된" 이상한 화면입니다. (실제로 겪었습니다.)

예방책은 하나뿐입니다 — 시작하기 전에 "나 이거 고칠게요" 라고 말하는 것. 원격이라 서로 뭘 하는지 안 보입니다. 아침에 한 줄씩 공유하세요.

6-4. 합치는 방법

검사가 끝나면 PR 화면에서 Merge pull request 버튼을 누릅니다. 그 순간 main 이 바뀌고, 자동 배포가 시작됩니다 (8장).

이 저장소는 무료 플랜이라 main 을 기술적으로 잠글 수 없습니다 즉 마음만 먹으면 누구나 main 에 바로 push 할 수 있습니다. 규칙으로만 막힙니다. 직원은 절대 main 에 직접 push 하지 마세요. (그 push 하나가 즉시 배포로 이어집니다.)

7. 검사 3종 — "고쳤습니다"만 말하면 안 됩니다

코드를 고쳤으면 PR 을 올리기 전에 내 컴퓨터에서 아래 3가지를 돌립니다. 그리고 PR 본문에 결과를 붙여 넣으세요.

검사 1. 문법 검사 (약 20초)

cd cloudflare-deploy
node node_modules/typescript/bin/tsc --noEmit
함정 — npx tsc 를 쓰면 안 됩니다 npx 는 조용히 실패해도 아무것도 안 찍습니다. 통과했을 때와 화면이 똑같습니다. "출력이 없으니 통과했다"고 착각하고 배포해서 사고가 난 적이 있습니다. 반드시 위 node ... 형태로 쓰세요.

검사 2. 회귀 하니스 (약 90초) — 가장 중요

# 반드시 «저장소 맨 위 폴더»에서 실행
node test-harness/run.mjs --fast

기준선: PASS 114~115 / SKIP 20 / FAIL 0. FAIL 이 하나라도 있으면 PR 을 올리지 마세요.

SKIP 20개는 실제 화상수업 화면이 필요한 검사라 자동으로 빠집니다 — 정상입니다.

함정 — 실행 위치 검사 1 에서 cd cloudflare-deploy 를 했으므로, 이어서 그대로 치면 실패합니다 (MODULE_NOT_FOUND). cloudflare-deploy/test-harness/ 에도 같은 이름 폴더가 있지만 그 안엔 run.mjs 가 없습니다. 꼭 저장소 맨 위로 돌아가서 실행하세요 (cd ..).

이 하니스 138개 하나하나가 "예전에 이렇게 고장 났었다"는 사고 기록입니다. 그래서 이걸 통과하면 같은 사고가 다시 나지 않습니다.

검사 3. 실제 브라우저 확인

화면을 고쳤으면 반드시 눈으로 봅니다. 캡처를 PR 에 첨부하면 사장님이 훨씬 빨리 승인합니다.

보고 방식 (약속) "고쳤습니다"라고만 하지 말고 무엇으로 확인했는지 같이 씁니다.
○ 좋은 예 : "단어장 정렬 수정. tsc 통과 / 하니스 PASS 114 FAIL 0 / 크롬에서 가나다순 확인(캡처 첨부)"
✕ 나쁜 예 : "수정 완료했습니다"
실패했으면 실패했다고, 건너뛴 게 있으면 건너뛰었다고 그대로 쓰세요. 확인 안 된 걸 "됐습니다"라고 하는 게 가장 큰 사고의 원인입니다.

8. 배포 — 길이 두 개 있고, 서로를 모릅니다

길 A. main 에 합치면 자동 배포 (권장)

PR 을 main 에 머지하는 순간, GitHub Actions 가 알아서 아래를 순서대로 합니다.

순서하는 일실패하면
1필요한 프로그램 설치 (npm ci)전부 "차단" 게이트입니다.
하나라도 실패하면 배포하지 않고 멈춥니다.
2문법 검사 (tsc)
3회귀 하니스 138종
4HTML 안 JS 문법 전수 검사
5정적파일 캐시버전(?v=) 누락 검사
6Cloudflare 에 Worker 2개 배포
(기본 + production — 실서비스는 production 쪽입니다)		경고 표시
7배포 후 접속 확인(헬스체크)경고 표시

진행 상황은 GitHub 저장소 → Actions 탭에서 실시간으로 볼 수 있습니다. 초록 체크가 뜨면 성공입니다.

길 B. 사장님 PC 에서 직접 배포 (deploy.ps1)

powershell -File deploy.ps1

이 스크립트는 검사 → 도장찍기 → 커밋 → 배포 → 재확인까지 한 번에 합니다.

직원은 이 파일을 절대 실행하지 않습니다 이 스크립트는 내 컴퓨터의 cloudflare-deploy/public/ 폴더를 통째로 업로드합니다. 즉 커밋하지 않은 미완성 파일까지 그대로 실서비스에 올라갑니다. 학생 29,000명이 즉시 그 화면을 보게 됩니다.

사장님도 실행 전 git status 확인은 필수입니다. 스크립트가 "이번에 올라갈 파일 목록"을 화면에 뿌려 주니, 모르는 파일이 보이면 Ctrl+C 로 즉시 중단하세요.

8-1. 두 길이 충돌하면 생기는 사고 (실제 사례)

"합쳤을 뿐인데 라이브가 3일 전으로 되돌아갔다" 사장님이 deploy.ps1 로 5번 배포했는데 그 내용이 main 에는 없었습니다. 그 상태에서 다른 PR 을 main 에 머지하자, 자동배포가 옛날 main 내용으로 라이브를 덮어썼습니다. 그 5번의 작업이 라이브에서 사라졌습니다.

예방책 : 로컬 배포를 했으면 그 브랜치를 반드시 곧 main 에 합치세요. 로컬 배포는 "임시", 진짜 정본은 언제나 main 이어야 합니다.

8-2. 배포 전 마지막 확인 한 가지

"지금 내 커밋이 이 브랜치의 맨 앞(tip)인가?" — 배포 직전에 확인합니다.

git log --oneline -3

과거에 "남의 미완성 파일을 피하려고" 내 커밋 시점에 고정해 배포했다가, 그 사이 남이 정상적으로 커밋한 11개 작업이 라이브에서 통째로 사라진 적이 있습니다.

9. test.mangoi.co.kr 에서 실제로 확인하기

주소를 헷갈리지 마세요 실서비스 주소는 https://test.mangoi.co.kr 입니다. 일부 옛 문서와 스크립트에 mango-i.com 이 적혀 있는데, 그 도메인은 등록조차 되어 있지 않습니다(접속 불가). 고객에게 나가는 링크에 그걸 쓰면 죽은 링크가 발송됩니다.

9-1. 1단계 — 캐시부터 지우세요 (99%가 여기서 착각합니다)

배포는 잘 됐는데 내 화면만 옛날 그대로인 경우가 대부분입니다. 브라우저가 옛 파일을 저장해 두기 때문입니다.

기기확인 방법
PC시크릿 창(Ctrl+Shift+N)으로 여는 게 가장 확실합니다. 또는 Ctrl+Shift+R (강력 새로고침)
휴대폰브라우저 설정 → 사이트 데이터 → test.mangoi.co.kr 데이터 완전 삭제
또는 시크릿/InPrivate 모드로 접속 (가장 확실)
앱으로 설치한 경우홈 화면 아이콘을 길게 눌러 앱 삭제 후 재설치

9-2. 2단계 — "언제 배포된 버전인지" 확인

화면 소스 맨 아래에 있는 배포 도장을 봅니다.

# 배포 도장 확인 (캐시 우회를 위해 뒤에 아무 숫자나 붙임)
curl --compressed -s "https://test.mangoi.co.kr/?nocache=1" | findstr "BUILD:"
함정 — BUILD 도장만 믿으면 안 됩니다 이 도장은 deploy.ps1(길 B)로 배포할 때만 새로 찍힙니다. GitHub Actions 자동배포(길 A)는 도장을 새로 찍지 않습니다.

그래서 "도장이 그대로다 = 배포가 안 됐다" 는 틀린 판단입니다. 내가 고친 그 글자·그 기능이 실제로 보이는지로 판단하세요. 그게 유일하게 확실한 방법입니다.

9-3. 3단계 — 실제 눈으로 확인 (필수)

  1. 시크릿 창으로 https://test.mangoi.co.kr 접속
  2. 내가 고친 그 화면으로 직접 이동해서 고친 부분이 보이는지 확인
  3. 휴대폰에서도 한 번 더 확인 (화면 크기 때문에 PC 에선 멀쩡한데 폰에서 깨지는 일이 흔합니다)
  4. 고친 기능을 실제로 눌러서 동작하는지 확인 (보이는 것 ≠ 작동하는 것)
확인 순서 요약 ① Actions 탭 초록 체크 → ② 시크릿 창으로 접속 → ③ 내가 고친 부분이 보이는지 → ④ 눌러서 동작하는지 → ⑤ 휴대폰에서 한 번 더

10. 사고가 났을 때 (되돌리기)

10-1. 아직 커밋 안 했는데 파일을 망쳤다

git checkout .

마지막 커밋 상태로 되돌아갑니다. 단, 그 이후 작업한 건 전부 사라집니다. 아까우면 실행 전에 물어보세요.

10-2. 이미 합쳤는데 잘못됐다

git revert <커밋번호>

"그 변경을 취소하는 새 커밋"을 만듭니다. 기록은 남기면서 되돌리는, 가장 안전한 방법입니다.

10-3. 라이브가 깨졌다 — 가장 급한 상황 (사장님만)

cd cloudflare-deploy
npx wrangler rollback
npx wrangler rollback --env production   # 실서비스는 이쪽이 진짜

직전 배포 버전으로 즉시 되돌립니다. 먼저 되돌리고, 원인은 그 다음에 찾으세요.

연락 순서 라이브가 이상하면 혼자 해결하려 하지 말고 즉시 사장님께 연락하세요. 학생 29,000명이 쓰는 서비스입니다. 억지로 고치려다 더 크게 만드는 경우가 가장 많습니다.

12. 절대 하지 말 것

금지이유
DB 에 DELETE / UPDATE / DROP 개발용 DB 와 운영 DB 가 같습니다. 테스트용이 따로 없습니다. 실제 학생 29,000명의 데이터입니다. 확인은 SELECT 만. 변경이 필요하면 반드시 사람에게 먼저 말하세요.

.env / .dev.vars 커밋 결제·DB·AI 열쇠가 통째로 노출됩니다. 전부 재발급해야 합니다.

"없길래 다시 넣었어요" 일부러 없앤 기능들이 있습니다 (관리자 hover 카드, 화상수업 웜업 버튼, 관리자 서비스워커 등). 없는 데는 이유가 있습니다. CLAUDE.md 를 먼저 읽으세요.
JS/CSS 고치고 ?v= 안 올리기 "배포는 됐는데 기존 사용자에겐 옛 파일" 상태가 됩니다. 화면은 새것, 스크립트는 옛것이라 원인 찾기가 특히 어렵습니다. (다행히 검사 게이트가 잡아 줍니다 — 그래서 검사를 건너뛰면 안 됩니다.)

13. 용어사전 — 서류함으로 비유하면

깃 용어실제로 무슨 뜻이냐면
git pull서류함에서 최신 서류 꺼내오기
브랜치 (작업방)원본 말고 복사본에 연필로 수정하기
git add제출할 서류를 봉투에 담기
git commit"여기까지 고쳤음" 하고 도장 찍기 (아직 내 책상 위)
git push도장 찍은 봉투를 서류함에 제출하기
Pull Request (PR)사장님께 "원본에 반영해 주세요" 결재 올리기
머지 (merge)결재가 나서 원본에 실제로 합쳐지는 것
충돌 (conflict)두 사람이 같은 줄을 고쳐서 깃이 판단을 못 하는 상태
배포 (deploy)합쳐진 내용을 진짜 홈페이지에 올리는 것 (사장님만)
롤백 (rollback)배포를 직전 버전으로 되돌리는 것
워크트리 (worktree)같은 저장소를 쓰는 별도 작업 폴더 (사장님 전용 고급 기능)
