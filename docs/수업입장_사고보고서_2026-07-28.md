## 3. 확인된 문제 6가지

강사 계정 `hq_t_kang` 이 예약 848의 `teacher_id` / `teacher_name` 어느 쪽과도 매칭되지 않아 차단됐습니다.

### 문제 2 — 【P0】 강사 이름이 두 곳에 다르게 저장돼 있었음 (근본 원인)

> ⚠️ **2026-07-29 정정.** 최초 보고서에는 "강사가 시연용 계정을 쓰고 있었다"고 적었으나 **사실이 아닙니다.**
> DB 조회 결과 계정(`hq_t_kang`)·예약(848~851)·담당 강사 지정 모두 **처음부터 정상**이었습니다.
> `hq_t_` 는 시연용 접두사가 아니라 **역할을 교사로 판정시키려고 일부러 붙인 접두사**입니다
> (`cloudflare-deploy/migration-teacher-kang.sql` 에 그렇게 기록돼 있음).

실제 원인은 **같은 사람의 이름이 두 곳에 다르게 저장**돼 있었던 것입니다.

| 저장 위치 | 값 |
|---|---|
| 로그인 계정 (`admin_account.name`) | `강선생님` |
| 강사 명부 (`teachers.name`, id=29) | `중국어 강선생님` |
| 입장할 때 실제로 전달되는 값 | `교사 강선생님` ← 앞에 `교사 ` 가 붙음 |

입장 검사는 두 이름의 **부분일치(양방향)** 로 대조하는데,
`교사 강선생님` 과 `중국어 강선생님` 은 서로를 포함하지 않아 대조가 깨졌습니다.
접두사가 양쪽에 각각 붙어 있었던 것이 핵심입니다.

### 문제 3 — 【P1】 강사의 공식 입장 버튼을 눌렀어도 똑같이 막혔다

강사 마이페이지에는 「🎥 수업 입장」 카드가 있고, 이 버튼이 만드는 주소는
관리자가 손으로 보낸 링크와 **완전히 동일한 형식**입니다.

```
/?vc_autojoin=1&vc_role=teacher&vc_room={오늘 내 예약 방}&vc_name=교사 {이름}
```
— [admin/mypage.html:1038](../cloudflare-deploy/public/admin/mypage.html#L1038)

따라서 이번 사고는 "강사가 버튼을 못 찾아서"가 아니라 **정상 동선 자체가 막혀 있던 것**입니다.
링크를 아무리 잘 보내도 결과는 같았습니다.

### 문제 4 — 【P1】 차단 안내 문구가 강사에게는 쓸모없고, 한국어 전용

경고문은 학생을 전제로 쓰였습니다.

- `"회원님 수업은 '🎓 오늘 내 수업 바로 입장' 버튼으로 들어가 주세요"`
  → 그 버튼은 **학생 홈에만 있고 강사 화면에는 없습니다.** 존재하지 않는 버튼을 안내한 셈입니다.
- 문구가 **한국어 전용**입니다. 상대는 중국어권 강사로, 브라우저 번역(`翻译`)을 켜고 읽어야 했습니다.
- 회사 원칙(한/영 병기)에도 어긋납니다.

### 문제 5 — 【P1】 수업 전 체크리스트가 조용히 입장을 막는다

강사 마이페이지의 「수업 입장」 버튼은 **체크리스트 4개 + 전체동의**를 모두 체크하지 않으면
입장하지 않고 **토스트 메시지만** 띄우고 끝납니다.

- [mypage.html:1014](../cloudflare-deploy/public/admin/mypage.html#L1014) → `blockClassEntry()`
- [mypage.html:894](../cloudflare-deploy/public/admin/mypage.html#L894) 토스트 2.6초 후 사라짐

강사 입장에서는 **"버튼을 눌렀는데 아무 일도 안 일어난다"** 로 보입니다.
오늘 강사가 마이페이지에 머물러 있던 것도 이 단계에서 멈췄을 가능성이 있습니다. (강사 확인 필요)

### 문제 6 — 【P2】 설계는 "막지 않는다"인데 이 경우만 막힌다

검증 로직은 원래 **정상 수업을 방해하지 않는 것**을 우선해, 애매하면 통과시키도록 설계돼 있습니다.

| 상황 | 결과 |
|---|---|
| 예약을 못 찾음 | 통과 (fail-open) |
| 신원 정보가 아예 없음 | 통과 (fail-open) |
| 역할이 admin / observer | 통과 (privileged) |
| **이름·ID는 있는데 예약과 불일치** | **차단** ← 오늘 여기 걸림 |

강사 계정이 예약과 어긋나는 건 운영에서 흔한 상황인데, 하필 유일한 차단 조건에 정확히 들어맞았습니다.

### 문제 7 — 【P2】 긴급 우회 수단이 "강사에게 관리자 권한 주기" 뿐

오늘 쓴 우회책은 `vc_role=admin` 입니다. 이건 검증을 건너뛰는 대신
**강사에게 수업 통제 권한(전체 음소거·집중 모드 등)까지 부여**합니다.
급할 때 쓸 수는 있지만, 상시 수단으로 두면 안 되는 방식입니다.

## Summary (EN — for the teacher / staff)

**What happened:** The teacher could not enter today's class room `class-848-20260728`.

**Direct cause:** The server checks whether the person entering is the booked student or the assigned
teacher for that reservation. The teacher's account (`hq_t_kang`) is not registered as the assigned
teacher of booking 848, so entry was blocked.

**Root cause:** `hq_t_*` is the *demo* teacher account convention. Real teacher accounts use
`mangoi_NNN`. This teacher has no real account yet, so the mismatch will happen every time.

**What we did today:** Entered with `vc_role=admin`, which skips the check. This is a temporary
workaround, not a fix.

1. Issue a real teacher account and assign it to the booking. *(operations — do this first)*
2. Warn instead of block when the person is a teacher. *(code)*
