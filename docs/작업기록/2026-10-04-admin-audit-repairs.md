# 관리자 감사 수정 (순차 진행)

## 1. 담당 강사 변경의 충돌·근무불가 검사

- 증상: 변경 후보가 전원 선택 가능하고 PATCH는 수업 겹침, 휴가, 반복 휴식시간을 확인하지 않았다.
- 변경: 기존 등록용 `findScheduleConflicts`는 동작을 유지하고, 이동 전용의 실패 시 차단 검증을 추가했다. 날짜 수업과 반복 수업을 함께 비교하고 시작일, NULL 활성 상태, 종일/부분 휴가, 자정 경계, 한국어/영문 요일을 검사한다. 같은 학생은 겹칠 수 없고, 기존의 같은 시각·같은 길이 합반 규칙은 유지한다.
- 후보 화면: 모든 예약 ID를 읽기 전용 preview API로 확인한다. 확인 중·실패·불가능 후보는 비활성화한다. 오류 후 재시도, 숫자 강사 ID, 닫힌 창/오래된 응답을 검사했다. PATCH는 preview를 신뢰하지 않고 저장 시 다시 확인한다.
- 제외한 방식: 현재 주의 SLOTS만으로 가능 여부를 확정하지 않는다. 다른 주의 반복 수업/휴가와 API 조회 실패를 알 수 없기 때문이다. `force`로 충돌을 우회하지 않는다. 기존 등록 API의 실패 처리 규칙을 전역 변경하지 않았다.
- 검증: TypeScript noEmit 통과. 실제 handler + SQLite 및 Worker 라우팅 격리 검사 151/151, picker 실행 15/15, 기존 드래그/저장 187/187, 학생/강사 방 동기화 123/123. 운영 데이터에 쓰지 않았다.
- 한계: 이 단계의 단일 행 검사는 조회-저장 사이의 경쟁 상태를 원자적으로 잠그지 않는다. 다음 순서의 그룹 원자 이동에서 함께 보완한다. 브라우저 시각 검사는 실행 환경의 Chromium socket 제한 및 cloud browser의 localhost 차단으로 수행하지 못했다. 배포/병합하지 않았다.

## 2. 묶음 이동·되돌리기의 원자성

- 하나의 PATCH 요청과 D1.batch 트랜잭션으로 묶음 전체를 처리한다. 검증 전에 읽은 관련 수업·강사·권한·휴가·스키마 스냅샷을 같은 트랜잭션의 CHECK guard로 비교한다. 하나라도 바뀌거나 어떤 UPDATE/이력 저장이 실패하면 전체를 롤백한다.
- 각 행의 상태 버전을 화면에 내려주며 저장 후의 버전은 쓴 값에서 결정한다. 밀리초 시계가 같은 동안에도 updated_at을 단조 증가시켜 ABA를 막는다. 되돌리기는 ID/이전 값/커밋된 버전을 복사해서 보관하고, 중간 변경이 있으면 전체 거절한다.
- 반복·날짜 수업이 같은 칸에 섞여도 서버가 각 행의 올바른 필드를 정한다. 합반의 기존 같은 시각·길이 겹침은 유지하며, 기존 목적지 그룹에 합류한 뒤에도 옮긴 사람만 되돌린다.
- 수업 ID, 학생별 기존 방 번호, 방 override는 변경하지 않는다. 이동/되돌리기 후 각 학생과 담당 강사가 같은 방·시각을 받는 것을 실제 API로 확인했다. 같은 시각이라는 이유로 별개 학생의 방을 합치지 않았다.
- 외부 Worker 라우터의 정확일치 목록에 teacher-options/move 두 경로만 등록했다. 인증과 조직 차단 규칙은 그대로다.
- 검증: 원자성/경쟁/실패 주입 215/215, handler+실제 Worker 라우터 153/153, 학생/강사/관리자 흐름 174/174, 드래그/잠금/되돌리기 189/189, picker 15/15. 격리 SQLite의 batch는 실제 BEGIN/COMMIT/ROLLBACK을 사용한다. 전체 게이트는 npm 도구 경로/캐시를 고친 환경으로 재실행 중이다.

## 5. 후속 경고·최종 에스컬레이션의 내구성

- 알림 큐 삽입, 이벤트 기록, 경고 단계 확정을 D1.batch 안에서 처리한다. 큐 또는 이벤트 쓰기 실패 시 경고 단계를 소비하지 않아 최종 에스컬레이션을 재시도할 수 있다. 외부 푸시 깨우기 실패는 이미 저장한 큐를 제거하거나 저장 성공을 실패로 바꾸지 않는다.
- 기존 notices 테이블에 단계별·수신자별 전달 상태를 기록한다. 구독이 있는 수신자는 즉시 큐에 들어가고, 구독이 없는 수신자만 대기한다. 서비스 워커가 큐를 소비한 뒤에도 같은 수신자에게 재전송하지 않는다. 대기 수신자는 보고 화면에 표시하며, 최근 시도 순서로 순회해 처음 100건이 다음 보고를 막지 않는다.
- 같은 보고의 수정·확인·기한·상위 수신자·보류·읽기 시간 변경은 트랜잭션 안에서 다시 검사한다. 운영 알림을 보내지 않았으며 별도 outbox 시스템을 만들지 않았다.
- 검증: 실제 SQLite 롤백, 실패 주입, 동시 실행, 구독 복구, 큐 소비 후 중복 방지, 101건 공정성, 인앱 대기 표시를 포함한 daily_handover_harness 통과. TypeScript, D1 bind 26/26, asset 266/266, cache policy 5/5 통과. 전체 회귀 검사는 9단계 완료 후 최종 커밋에서 다시 수행한다.

## 6. 확인·보완요청 응답의 원자성·안전한 재시도

- 증상: 확인·보완요청은 보고 상태와 버전을 먼저 저장한 뒤 이벤트를 따로 기록했다. 이벤트 INSERT가 실패하면 이미 바뀐 보고를 되돌리지 못한 채 503을 반환했다.
- 변경: `daily-handover.ts`에서 버전·허용 상태 조건 UPDATE와 응답 이벤트 INSERT를 한 D1.batch로 묶었다. 이벤트 실패 시 보고 전체 필드, 버전, BEFORE UPDATE 트리거가 남긴 이전 이력까지 모두 롤백한다. 이벤트는 바로 앞 UPDATE의 `changes()=1`일 때만 삽입하므로 경쟁에서 진 요청은 이벤트를 남기지 않는다.
- 동일 요청의 재전송: 현재 보고가 요청의 바로 다음 버전이고, 같은 응답자·동작·정규화된 피드백 및 같은 응답 시각의 이벤트가 모두 일치할 때만 `ok:true, duplicate:true`를 반환한다. 다른 사람·다른 동작·다른 피드백, 재제출 뒤 오래된 버전, 이벤트 없는 과거의 부분 성공은 409다. 기존 본인 확인 금지, 관련 없는 직원의 조회 차단, 교사·Origin 검사를 유지했다.
- 알림 정리는 커밋 뒤 세 태그별로 독립 시도한다. 하나가 실패해도 다른 태그 정리는 계속하고 저장 성공을 실패로 바꾸지 않는다. 정확한 재시도에서도 요청의 기준 버전 태그만 다시 정리하며 새 버전의 큐는 보존한다.
- 제외한 방식: UPDATE 뒤의 이벤트 오류를 단순히 무시하지 않았다(성공이라고 해도 감사 이력이 사라짐). 현재 상태만 보고 재시도를 성공 처리하지 않았다(타인의 응답·다른 피드백·오래된 보고가 섞임). 푸시 정리를 트랜잭션에 넣지 않았다(부수 작업 실패로 응답 저장을 막지 않음). 5단계 전달 상태와 7단계 화면은 변경하지 않았다.
- 검증: `node test-harness/daily_handover_harness.mjs` 통과. 실제 SQLite 실패 트리거로 상태/버전/이력 롤백, 확인·보완요청의 반복 및 동시 요청, 상이한 사용자/동작/피드백, 재제출 뒤 충돌, 읽기 이후 경쟁 변경, 각 알림 정리 및 전체 정리 실패·재시도 복구를 검사했다. 기존 5단계 전달 테스트도 함께 통과했다. 하니스 batch는 BEGIN/COMMIT/ROLLBACK 내부에 JavaScript await를 두지 않아 다른 요청의 단일 SQL이 중간에 끼어드는 잘못된 모사를 막았다.
- TypeScript: `cd cloudflare-deploy && node node_modules/typescript/bin/tsc --noEmit` 통과. 전체 회귀는 최종 통합 단계에서 수행한다. 운영 호출·DB 쓰기·배포·push·merge는 하지 않았다.
- 근거: [Cloudflare D1 batch 트랜잭션](https://developers.cloudflare.com/d1/worker-api/d1-database/#batch), [SQLite changes()의 트리거 제외 계약](https://www.sqlite.org/lang_corefunc.html#changes).

## 7. 독촉·응답 이력의 저장 버전 구분

- 증상: 과거 제출 때 남긴 경고와 응답에 버전 표시가 없어 수정·재전달한 현재 보고의 경고처럼 읽혔다.
- API: `/api/approval/handover/followup-history`는 보고의 권한 필드, 현재 저장 버전, 이벤트를 한 SQLite 조회로 읽고 `current_version`을 반환한다. 기존 `visible` 범위를 유지한다. 선택적인 `version`은 정확한 양의 안전 정수만 허용하며, 중복·빈 값·소수·음수·지수 표기 등은 400이다. 존재하지 않는 버전은 다른 버전으로 대체하지 않고 빈 목록으로 응답한다. 실패하거나 결과 배열이 없는 DB 조회는 빈 이력/404 대신 503이다.
- 저장 계약: `daily_handovers.version`은 제출뿐 아니라 확인·보완 요청에도 증가한다. 응답 이벤트는 처리 전 저장 버전을 보존한다. 따라서 화면은 현재/이전 저장 버전을 명시하고 확인·보완 요청에 «처리 전 저장 버전»을 덧붙인다. 제출 차수라는 이름이나 `version-1` 추정은 쓰지 않는다.
- 화면: 전체 저장 버전과 현재 저장 버전의 정확 필터를 선택할 수 있다. 서버의 현재 버전이 화면의 보고와 다르면 목록 새로고침을 안내한다. 조회 중 현재 버전이 바뀌면 이전 결과를 현재로 그리지 않고 이력 새로고침을 요구하며, 재시도는 새 버전을 사용한다. 필터 전환·보고 선택/재그리기 뒤에 도착한 낡은 응답과 오류는 버린다. 실패하면 기존 이력을 지우고 재시도할 수 있다.
- 한도: 각 선택 범위에서 최신순 최대 50건만 반환·표시한다. 한 건의 내부 sentinel로 추가 기록 존재 여부를 알려 주며, 화면에 «이전 기록 생략»을 표시한다. 페이지네이션이나 과거 버전 내용 복원 기능은 추가하지 않았다.
- 제외한 방식: 과거 이벤트를 현재 버전으로 옮기거나 내용을 다시 쓰지 않았다. 별도의 내용 수정 차수·제출 그룹화·스키마 마이그레이션을 도입하지 않았다. 5단계 알림 전달 및 6단계 응답 트랜잭션은 변경하지 않았다.
- 검증: `daily_handover_harness.mjs` 통과. 실제 격리 SQLite로 경고→보완요청→수정 재제출→확인, 정확/잘못된 버전, 권한·초안 비공개, 불변 과거 이력, 50건 제한, DB 조회 실패를 검사했다. 출하 JS의 렌더러/이벤트 핸들러를 DOM 트리 모사에서 실제 실행하여 현재/이전 문구, 응답 기준 버전, 필터, 뒤늦은 응답·오류·화면 제거, 다시 시도, 텍스트 안전성을 검사했다. 기존 5·6단계 실패 주입·동시성 회귀도 통과했다. 실제 브라우저 시각 검사는 이 단계에서 실행하지 않았다.
- TypeScript noEmit, JS 구문 검사, `git diff --check`, 자산 버전 266/266, 캐시 정책 5/5 통과. `daily-handover.js?v=10`과 하니스가 생성한 자산 원장을 함께 갱신했다. 전체 통합 회귀는 상위 최종 단계에서 수행한다. 운영 호출·운영 DB 쓰기·commit·push·merge·배포는 하지 않았다.

## 8. 조직 계정의 오래된 클라이언트 허용목록

- 서버가 이미 허용하는 조직/강사/AI 이용·청구/수업 요청/게시판·캘린더 경로가 브라우저에서 합성 403으로 막히던 목록을 서버 정본과 맞췄다. 서버 인증·스코프 SQL·쓰기 권한은 변경하지 않았다.
- 실행 하니스가 실제 서버 함수의 목록과 브라우저 목록의 동등성을 검증하고 agency/branch/franchise, 구형 uid 접두사, query/Request 입력, public 예외, 비관리자·외부 origin, 중복 설치를 검사한다. 서버가 내린 403은 그대로 유지한다. 향후 목록이 한쪽만 바뀌면 CI가 실패한다.
- 검증: 클라이언트/서버 목록 실행 217/217, 조직 목록 격리 27/27, 서버 조직 차단 34/34, 정적자산 266/266 및 인라인 JS 문법 통과. 세 HTML 진입점의 자산 버전을 모두 v2로 올렸다.


## 9. 진단 화면의 자동 변경 요청 제거

- 증상: `admin/health.html`은 페이지 열기와 10초 갱신마다 다수의 API를 호출했다. GET인 R2 테스트도 실제 put/get/delete를 수행하며, TURN 자격증명 발급·더미 방 강제 종료·heartbeat·POST/PATCH/PUT 등도 자동 실행 목록에 있었다. GET 또는 잘못된 입력의 4xx라는 이유로 안전한 진단으로 보지 않는다.
- 자동 조회: 기존 인증·스코프 게이트 뒤의 `/api/admin/health-check?mode=passive` 한 경로만 호출한다. 서버의 추가 변경은 passive 모드에서 진단용 SELECT 1을 생략하고 mode를 표시하는 것뿐이다. 매개변수가 없는 기존 API는 SELECT 1 동작을 유지한다. 기존 R2/TURN/업무 API 구현은 제거하거나 변경하지 않았다.
- 범위: 수동으로 체크한 `/api/health`(순수 Worker 응답)와 기존 health-check의 D1 SELECT 1만 설명·확인 후 한 번 실행한다. 처음에는 둘 다 미선택이다. 자동 갱신은 수동 결과를 지우거나 재실행하지 않는다. 실행 잠금, 중복 클릭, 10초 요청 제한, 취소, 취소 후 재시도, 오래된 응답 무시, pagehide/pageshow를 처리했다. 취소는 이미 도착한 읽기 요청을 서버에서 되돌린다고 약속하지 않는다.
- 표시 계약: 실제 `bindings.DB/RECORDINGS/PDF_STORE/...` Boolean만 읽어 «있음·동작 미검증 / 미설정 / 미확인»으로 구분한다. 과거의 중첩 객체 가정, 시크릿 길이, 전체 정상 녹색 판정, `buildInfo.stamp` 가정을 제거했다. 실제 `build_stamp`는 Worker 보고 값으로만 표시하고 배포 성공·배포 시각으로 주장하지 않는다. passive 표시가 없는 구버전 응답, 누락·잘못된 응답·인증 오류는 미확인이다. 실패 시 이전 빌드/구성을 지우고, 응답·오류의 임의 필드나 시크릿 원문은 화면에 내보내지 않는다.
- 중요한 한계: passive는 «진단 부작용 없음»의 의미다. 기존 관리자 인증은 D1 조회와 `admin_sessions.last_seen_at` 갱신을 수행하고, 초기 인증/스코프 경로에는 기존 스키마 생성·계정 초기화/보완 작업도 있다. 이 기존 경로를 바꾸지 않았으므로 «DB 접근/쓰기 전혀 없음»이라고 보고하면 안 된다. 인증이나 조직 접근 범위를 넓히지 않았다.
- 검증: `admin_health_passive_harness.mjs` 56개 검사 통과. 출하 인라인 스크립트를 가짜 DOM에서 실행하고 전체 Worker를 esbuild로 번들하여 실제 인증/라우팅 코드와 계측 D1/불활성 바인딩을 사용했다. 로드·타이머·새로고침의 passive 단일 경로, 선택/확인/취소/중복/실행 중 타이머/오류/timeout/뒤로가기, 실제 응답 schema, 시크릿 Boolean, passive 쿼리 생략과 기존 쿼리 유지, 두 모드의 같은 인증, 순수 health GET을 실행 검증했다. 모든 fetch와 저장소는 격리 모형이며 운영 호출·운영 쓰기는 하지 않았다.
- 추가 확인: TypeScript noEmit, 인라인 JS 전수 문법(580개), 정적자산 266/266, 캐시 정책 5/5, 시크릿 이름 22/22, `git diff --check` 통과. 외부 JS/CSS 내용 변경이 없어 버전 원장 갱신은 필요하지 않다. 전체 회귀는 상위 최종 단계에서 수행한다. Chromium socket 제한 및 cloud browser의 localhost 차단으로 실제 브라우저 시각 검사는 수행하지 못했다. commit/push/merge/배포하지 않았다.

## 부수 항목: 관리자 계정 확인 오류·재시도

- `adm-identity`는 실패를 조용히 무시하고 타임아웃 없이 한 번만 조회해, 미확인 문구가 계속 남을 수 있었다. 8초 상한과 중립적 오류 상태·수동 재시도를 추가했다. 실제 관측된 4분 지연의 원인까지 입증한 것은 아니다.
- 중복 클릭은 같은 요청을 공유하며, 타임아웃 뒤 늦은 응답이나 계정 저장값/로그아웃 변경 뒤 이전 요청이 현재 신원을 덮지 못한다. 자동 무한 재시도, 신원 추정, 인증 쿠키·서버 권한 변경은 없다.
- 검증: 출하 JS를 실행하는 16개 시나리오에서 HTTP 401/500·네트워크·JSON 오류, 타임아웃, 중복, 복구, 같은 탭/다른 탭의 계정 변경, 로그아웃 후 늦은 응답을 확인했다. 자산 버전 v2/원장 및 문법 검사 통과. 최종 코드 전체 게이트와 실패 주입 검사는 반복 수행한다.

## 추가 일정 QA: 관리자 입장·참관 방 일치

- 실제 override 저장 → 같은 날 시간·강사 이동 → 역할별 조회를 이어 실행하니 학생/강사는 지정 meet 방을 받지만 관리자 `classes-now`와 `classes/today`는 원래 class 방을 돌려주었다. 출하된 Observe 함수도 그 잘못된 방을 열었다.
- 두 관리자 응답에 기존 `applyRoomOverrides`를 적용했다. `classes-now`는 회차의 KST 날짜별로 처리하고, 지정된 방을 기준으로 connected/live_room도 다시 대조한다. `classes/today`는 방에 연결된 평가·출석 보강 전에 적용한다. 조회 스코프·학생별 방 ID·override 저장 내용은 바꾸지 않는다.
- 실제 Worker/SQLite의 PUT override → 원자 이동 → 학생/강사/관리자 today/관리자 now 검사가 세 번 반복되어 414/414 통과했다. 옛 방의 출석이 지정된 방을 접속 중으로 보이게 하지 않는 것도 확인했다. 기존 classes-now 81/81, override 62/62 및 TypeScript 통과. 전용 참관 UI 하니스 36/36도 UTC·Los Angeles·Seoul에서 통과했다. 수리 전 코드·resolver 제거·presence 재대조 제거·오늘 날짜만 사용·스코프 제거 변이는 각각 실제 실패했다. 최종 전체 검사는 계속 수행한다.
- 리마인더의 실제 메시지 링크는 `/?go=videocall`이므로 방별 URL 문제가 없었다. 전달 중복 방지 키나 알림 발송 동작은 바꾸지 않았다.

### 실제 브라우저 표시 검증 추가

실제 Chromium의 두 화면 폭에서 되돌리기 버튼은 눌렸지만, 저장 안내가 여러 줄이면 두 안내가 겹치는 것을 확인했다. 고정 간격 대신 안내의 실제 높이를 재어 되돌리기를 위에 배치하고 화면 폭 변경에도 다시 계산한다. 수업 저장·되돌리기 상태나 요청 계약은 바꾸지 않는다. 브라우저 검사는 안내 비겹침과 클릭 가능 여부를 함께 확인한다.
