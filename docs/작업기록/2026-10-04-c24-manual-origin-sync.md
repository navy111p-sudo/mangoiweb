# 트랙 6: 수동 이동한 Cafe24 수업의 원본 ID 보호

기준: main 27ec8ce (PR #1369). 상태: 로컬 수정·오프라인 검증, 미게시·미병합·미배포. 운영 동기화·데이터 수정 없음. 사용자 승인 범위는 수동 변경 우선과 앞으로의 이동/동기화 보호이며, 기존 데이터 일괄 정리/삭제는 포함하지 않는다.

## 1. 현재 문제

기존 학생/관리자 이동, 원자적 묶음 이동, 실패 롤백, 승인 충돌·중복·오래된 요청 보호, 세 역할 달력, 수업방 조회는 이미 구현되어 있다. 추가 점검에서 Cafe24 수업을 날짜 이동한 뒤 동기화하면 원래 날짜 수업이 다시 생기는 경계를 발견했다. 단순히 수동 표시를 생략하면 중복 대신 나중에 이동된 수업이 취소될 수 있다.

## 2. 문제 재현 결과

배포본의 실제 이동 모듈/관리자 핸들러와 실제 applyMirror를 합성 SQLite에서 연결했다. 순방향·역방향 날짜 이동, 직접/묶음/개별 PATCH, 기존 수동 행, 창 범위 변경, 반복 동기화, 되돌리기에서 중복 또는 잘못된 취소를 재현했다. 고정된 이전 재현 검사는 241개 관찰을 통과했으며 이는 결함 존재를 확인한 수치다.

## 3. 확인된 원인

수동 표시는 source를 c24-mirror:manual로 바꾼다. 기존 동기화는 같은 학생+같은 날짜만 보호하고 조회도 요청 날짜 창에 한정했다. 원본 notes의 부분 UNIQUE 인덱스는 c24-mirror에만 적용되어 수동 표시 후 중복을 막지 못했다. 읽기 실패를 빈 목록으로 취급하거나 계획 이후 상태 변경을 쓰기 시점에 재검사하지 않는 경계도 있었다.

## 4. 수정한 내용

- 기존 notes의 유효한 c24 원본 ID와 학생 소유권으로 수동 행을 날짜 밖에서도 보호한다.
- 이동과 승인 트랜잭션에서 수동 표시를 함께 저장한다. 되돌리기도 원본 ID를 보존한다.
- 전역 수동 ID 목록과 날짜 창 내 취소 후보는 분리한다. 조회 범위를 넓혀 취소 범위까지 넓히지 않는다.
- INSERT에서 원본 ID를 다시 검사하여 계획 뒤 이동·동시 생성 경합을 막는다. UPDATE/취소는 기존 source 조건을 유지한다.
- 실제 변경 행 수만 성공으로 센다. 실패/불확실한 읽기/모호한 소유권을 성공으로 숨기지 않는다.
- 원본 ID가 없는 기존 행의 같은 날짜 보호는 유지한다. 원본 ID를 확인할 수 없는 날짜 이동은 409로 보류한다.
- 서로 다른 유효한 원본 ID는 같은 학생의 같은 날이라는 이유만으로 합치거나 차단하지 않는다. 실제 시간 겹침은 기존 규칙으로 검사한다.

## 5. 변경 파일 및 주요 로직

- src/c24-identity.ts: 원본 토큰 검증, 주석 보존, JavaScript/SQLite 경계 일치
- src/c24-mirror.ts: 전역 수동 ID 읽기, 소유권 충돌 표시, 원자적 INSERT 재검사, 쓰기 결과 확인
- src/class-schedule-move.ts: 날짜 이동 전 확인 가능한 원본 ID 검사
- src/api-admin.ts: 승인 수동 표시와 기존 날짜+강사 동시 변경 제한 보존
- test-harness/c24_mirror_identity_harness.mjs, c24_mirror_move_sync_harness.mjs: 신규 영구 회귀
- student_schedule_lifecycle_sync_harness.mjs: 학생/관리자 이동→반복 동기화→역할별 조회 연결
- c24_mirror_harness.mjs, manager_today_reschedule_harness.mjs: 실제 D1 쓰기 결과 fixture와 새 보호 계약에 맞춘 오래된 검사 수정

새 테이블/컬럼/인덱스/마이그레이션 없음. 수강권·결제·공유방 설계·권한 확대 없음.

## 6. Harness 테스트

실제 모듈/인증된 Worker 라우터/학생 요청 UI와 교사 입장 함수/합성 SQLite를 사용한다. 원본 날짜 포함·원본만·이동 날짜만 있는 창, 양방향 이동, 반복, undo, 묶음, 모든 수동 상태, 서로 다른 ID, 메모 주석, 중복·잘못된 ID, UID 불일치, 조회 오류·실패 응답·불완전 결과, 동기화와 이동 경합, 계획 후 INSERT 경합, 날짜+강사 승인 제한을 검사한다.

## 7. Sandbox 테스트

Node 24의 메모리 SQLite와 D1 인터페이스 대역, 실제 TypeScript 번들. Cafe24 응답은 합성 READ 대역이며 전역 fetch는 외부 요청을 거부한다. 로컬 격리 실행이며 Cloudflare Sandbox/운영 D1/실제 Cafe24 호출이 아니다. 실제 고객 데이터·일정·알림을 사용하지 않았다.

## 8. 테스트 횟수

최종 코드 e19eae98178351fad97e5136654588b526e247ab에서 신규 이동/동기화 **569**, 토큰/SQL 일치 **3,276**, 확장 전체 역할 lifecycle **648**개를 각각 UTC·America/Los_Angeles·Asia/Seoul에서 반복했다. **3종×3시간대=9회, 모두 통과**. 토큰 조합 검사 수는 사용자 세션 수가 아니다. 기존 mirror 287, manager 84, 학생 요청 117개 검사도 통과했다.

같은 핀에서 전체 게이트 **2회** 실행: 매회 **474개 하니스 통과, 0 실패, 선언된 E2E 20개 제외**, TypeScript, JS 581조각, 캐시 참조 266개 통과. 1,445개 소스/테스트 파일 manifest가 두 실행 전후 동일했다. Manifest SHA-256: 206fef1135a5778cc142eb6ec9cf2f76e6330f5da516f51cda16769568a7e1b4. 보고서 갱신 외 코드 변경 없음.

## 9. 통과·실패

최종 핀의 실행한 검사에서 실패 0. 첫 aggregate의 누락 이미지·npx 의존성 문제는 main 파일을 blob hash로 검증해 복구하고 설치된 의존성으로 해결했다. 다음 aggregate의 기존 추출형 학생 요청 fixture는 새 실제 identity 모듈 주입/notes 컬럼을 갖추지 못해 2건 실패했으며, fixture를 실제 계약에 맞춘 뒤 117/0으로 재검증했다. 기능 assertion을 제거하지 않았다. 합격 수는 브라우저 클릭/미디어 연결 성공을 뜻하지 않는다.

## 10. 새로 발견한 문제

독립 검토에서 첫 날짜 이동 후 수동 표시가 붙으면 다음 날짜+교사 변경 승인이 기존 제한을 우회할 수 있었다. JavaScript는 NUL 뒤 토큰을 읽지만 SQLite GLOB은 NUL에서 멈춰 계획 후 잘못된 notes 삽입이 보호를 우회할 수 있었다.

## 11. 추가 수정

승인 제한에 이미 수동 표시된 Cafe24 행도 포함한다. 직접 시간표의 기존 허용 권한은 유지한다. NUL이 있는 mirror notes는 확인 실패로 보류하고, INSERT도 그런 mirror 행이 있으면 생성하지 않는다. 내용을 정리하거나 소유권을 추측하지 않는다.

## 12. 재검증

첫 날짜 이동→두 번째 날짜+교사 승인 거절, 같은 요청의 대기 유지, 직접 시간표 변경 허용 대조를 실제 핸들러에서 검사했다. NUL 두 형태×base/manual×읽기/계획 후 주입 모두 중복·거짓 성공 없이 보류되는 것을 검사했다. 추가 독립 변이 검사에서 전역 ID 조회를 제거하면 33건, 승인 제한을 되돌리면 2건, INSERT ID 보호를 제거하면 6건 실패했다. 초기 하니스가 마지막 변이를 놓치는 검사 공백을 찾아 실제 계획 후 유효 ID 경합 8개와 관련 없는 원본/출처 대조 3개를 영구 추가했다. 독립 실제 이동-after-plan probe는 정상 5/0, ID 가드 제거 시 3/2였다.

## 13. 회귀 범위

PR #1369의 승인 원자성·가용성·오래된 신청·ABA·중복 요청·묶음 일관성과 학생/교사/관리자 달력 및 수업방 투영을 재사용해 검사한다. 날짜별 room override는 날짜를 옮긴다고 자동 승계하지 않는 기존 계약을 유지한다. 새 날짜에서 세 역할은 동일한 기본 방으로 라우팅되며, 새 날짜에 명시적으로 지정된 override도 동일하다. meet-* 방 검증은 기존 unmanaged-room 계약이므로 관리된 class-*의 역할 인증과 구분한다.

## 14. 성능 전후

운영 지연/부하를 측정하지 않아 개선 수치를 제시하지 않는다. 전역 수동 ID 조회 1회와 INSERT의 재검사가 추가된다. 실제 데이터 규모에서 비용 확인이 필요하다. 스키마/인덱스를 임의로 추가하지 않는다. 기존 캘린더 첫 로딩 관찰만으로 이 수정의 성능 회귀라고 판단하지 않는다.

## 15. 남은 위험

- 이미 생긴 중복이나 이전 base 상태의 잘못된 이동 행은 소급 수정하지 않는다. 별도 읽기 전용 현황과 사람 검토가 필요하다.
- 확인할 수 없는 원본 ID/소유권 충돌은 자동 이동·생성이 보류될 수 있다. 잘못된 ID를 추측해 이어 붙이지 않는다.
- NUL이 있는 mirror notes는 안전을 위해 동기화를 중단하거나 새 생성을 막을 수 있다. 희소 손상 상황의 가용성 절충이며 운영 데이터 정리를 수행하지 않았다.
- 실제 D1 규모, Cafe24 연결, 브라우저 전체 흐름, 학생·교사 실제 미디어 회의는 미검증이다. 방 ID 일치는 실제 음성/영상 연결 증거가 아니다.
- 운영 통합과 배포는 사용자 최종 승인 전 보류한다.

## 16. 최종 검증 상태

**로컬 수정·격리 반복·전체 회귀 2회·독립 검토 통과. 실제 사용환경 추가 검증 필요.** 새로 확인된 로컬 기능 차단점은 없다. 실제 미디어 회의/운영 D1/실기기 검증을 완료했다고 표시하지 않으며, 원격 게시·병합·배포는 수행하지 않았다.
