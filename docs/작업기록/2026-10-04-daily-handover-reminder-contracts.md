# 매일 보고 미작성·미확인 알림 보강: 16항목 검증 보고

기준 main: `27ec8ce91c624a80559ee82311fc425664b07319`.
범위: 로컬 코드·격리 테스트. 운영 데이터/직원 알림/운영 배포/원격 게시 없음. 신규 테이블·컬럼·마이그레이션 없음.
상태: **로컬 수정·반복 검증 통과, 실제 브라우저·기기 수신 추가 검증 필요.** 병합·배포·중요한 데이터 구조 변경은 최종 승인 전 실행하지 않는다.

## 1. 현재 문제

기존 PR1369의 영속 경고 큐, 원자적 확인/보완 요청, 버전별 이력을 유지하면서 다음 잔여 결함을 확인했다.

- 미작성 알림 큐 등록 실패/기기 미등록 뒤 같은 단계에서 재시도하지 않음
- 일반 미확인 알림과 확인 완료 경합 시 구 버전 경고가 새로 등록됨
- 확인 후 제출 버전의 기한·단계를 찾지 못해 지연 응답을 표시하지 못함
- 관리자 화면에 미작성 알림 상태와 제출 시각이 없음
- KST 자정 직전/직후 마감의 점검 대상 날짜 누락
- 확인은 정상 완료됐지만 큐 정리가 실패하면 구 경고 본문이 기기에 제공될 수 있음

## 2. 문제 재현 결과

수정 전 6개 결함을 실제 API 코드와 메모리 SQLite에서 각각 3회 재현했다.

1. 큐 INSERT 오류 제거 후 같은 단계 sweep 2회에도 큐 0건
2. 기기 미등록 기록 후 구독 추가 시에도 큐 0건
3. 실제 /ack가 완료된 뒤 동시 미확인 경고 1건 등록·wakeup 호출
4. 기한 5분 뒤 관리자 확인 시 확인자·시각은 맞지만 followup=null, 지연 판정 없음
5. 저장된 no_subscription 상태가 관리자 /home에 없음
6. 23:55 KST 마감을 다음 날 00:05 KST에 점검하면 전날 알림 없음

추가로 확인 후 큐 삭제 실패 시 기존 /api/push/pending이 구 본문을 반환할 수 있음을 확인했다.

## 3. 확인된 원인

미작성은 단계 키를 미리 선점하고 실패 여부와 관계없이 건너뛰었다. 일반 미확인은 상태 확인/주기 선점과 큐 쓰기가 분리돼 있었다. 응답으로 저장 버전이 증가하지만 조회는 현재 버전의 메타데이터만 결합했다. 관리자 조회에 notices가 없고 UI는 submitted_at을 표시하지 않았다. 날짜 점검은 현재 KST 하루뿐이었다. 최종 push pending은 보고 상태/버전을 검사하지 않았다.

## 4. 수정한 내용

- 미작성의 활성 일정·미제출 조건, 모든 기기 큐 등록, 단계 상태 갱신을 원자적으로 처리; 실패/기기 미등록 재시도, 성공 단계 중복 억제
- 일반 미확인의 보고 ID/버전/상태/수신자/보류/근무시간·주기 선점과 큐 쓰기를 같은 트랜잭션으로 처리
- 완료 보고는 제출 이력에서 실제 제출 버전을 찾아 기한·단계·지연 여부 표시; 현재 버전-1로 추정하거나 과거 이력을 수정하지 않음
- 제출시각, 알림 등록/접수/실패/기기 미등록, 정확한 경고 단계 표시; 접수를 실기기 수신으로 표현하지 않음
- 기존 -30분~+120분 창에 걸치는 전날/다음날도 점검; 과거 전체 보고를 새로 독촉하지 않음
- 최종 wake 대상 조회에서도 현재 제출 상태/버전·관련 자격과 fetched_at을 재확인; 확인이 이미 완료됐거나 payload를 이미 가져간 기기를 새로 깨우지 않음. 기존 다중 수신자 follow-up도 동일하게 확인하고, 여러 수신자 조회 사이 응답이 완료되면 수집된 대상 전체를 다시 검사함
- 최종 payload claim에서 handover 상태/버전을 재검사; 확인/보완 요청/삭제/새 버전/제출 완료로 무효인 본문 차단
- DB 오류는 무효로 단정하지 않고 큐 항목을 보존; 최대 50개 후보에서 최대 5개 유효 메시지 반환

## 6. Harness 테스트 내용

정상 제출·확인·관리자 확인, 미작성·미확인, 중복/동시 요청, 직원별 수신자 분리, 모든 기기 큐 롤백·재시도·구독 복구, 확인/보완 요청/재제출/보류/근무시간 경합, 실제 /ack→큐 삭제 실패→실제 pending 차단, 정시/지연 응답·저장 버전 구분·재제출 초기화, 관리자 조회 범위, 문자 안전 표시, 자정 경계·휴가·기존 창 제한, DB 오류 시 큐 보존, unrelated 알림·endpoint 분리·50개 한도와 다음 호출 진행을 검증했다.

독립 리뷰에서 확인 직후 큐 정리 실패 시 wake SELECT 자체가 구 큐를 선택하는 추가 경합을 발견했다. 수정 후 실제 확인/관리자 확인/보완 요청이 조회 전에 완료되면 wake 호출 0회이며, 이미 fetched된 행·미작성 해소·다중 수신자 조회 중 확인도 차단된다. 조회 오류 시 payload를 보존하고 이후 pending fetch로 복구하는 사례와, 최종 조회가 끝난 뒤 확인이 경합하는 외부 전송 경계도 영구 테스트로 추가했다.

## 7. Sandbox 테스트 내용

Node24.19.0, TypeScript5.9.3, 실제 메모리 SQLite와 D1 모사 래퍼를 사용했다. INSERT 실패·두 번째 기기 실패·푸시 서비스 오류·구독 복구·확인/큐 경합·DB lookup 오류·자정 경계를 주입했다. Web Push는 메모리 대역이며 외부 발송은 없다. 실제 Cloudflare Sandbox/운영 D1/실제 직원 계정·기기/브라우저 전체 클릭 흐름은 사용하지 않았다.

## 9. 성공·실패 결과

수정 전 6개 계약은 각각 3회 실패 재현. 수정 후 결함·경합·오류 복구와 기존 테스트는 모두 반복 통과. 라이브 수신 검증은 미실행이며 로컬 성공을 운영 전달 성공으로 판단하지 않는다.

## 10. 테스트 중 추가 발견된 문제

최종 wake 자격 조회 전에 완료된 확인은 추가 발송을 막는다. 다만 조회가 반환된 직후 확인이 완료되는 경합에서 DB 조회와 외부 전송을 하나의 원자적 작업으로 묶을 수는 없다. 이 경계 또는 이미 나간 payload 없는 wakeup은 보고가 확인된 후에도 service worker의 빈 pending fallback으로 일반 알림을 표시할 수 있다. 이미 기기가 받아 표시한 알림은 회수할 수 없다. 실제 의무 제출 명단/휴일/수신자 정책이 현재 개인 설정과 같은지는 미확정이다.

## 11. 추가 문제 수정 내용

확인 후 큐 정리 실패에 대한 공용 pending guard와 wake 선택 단계의 현재 상태/fetched 검사를 추가했다. 알 수 없는 DB 상태를 성공/무효로 꾸미지 않는다. 지시된 범위에 따라 service worker의 일반 fallback은 변경하지 않았다.

## 12. 재테스트 결과

실패 주입 해제 후 큐가 복구되고, 확인 후 새로운 구 버전 큐 생성이 차단된다. 남은 구 본문도 최종 claim에서 제외된다. 같은 계약이 3회 반복에서 동일한 결과를 보였다.

## 13. 회귀테스트 결과

PR1369 수신자별 영속 단계 큐·원자적 응답·이력·정확한 재요청 의미는 기존 API 하니스에서 유지됐다. 로그인 소리/음성입력/알림 연락처·강사 푸시도 통과했다. 전체 서비스 브라우저 회귀는 미실행이다.

## 14. 성능 개선 전·후 비교

신뢰성/정합성 개선이며 실제 기기 지연 개선 수치는 측정하지 않았다. pending 반환 상한은 기존처럼 5개이며, 무효 handover가 앞에 쌓이면 후보 최대 50개를 확인한다. 실제 D1 부하/실기기 수신 지연은 별도 검증이 필요하다.

## 15. 남아 있는 위험요소

- 검사 이전에 이미 반환된 본문·이미 표시된 알림은 회수할 수 없다.
- 최종 자격 조회 이후의 경합·이미 나간 zero-byte wakeup은 구 보고 본문이 차단돼도 일반 알림을 띄울 수 있다. **확인 후 모든 알림이 절대로 울리지 않는다는 보장은 하지 않는다.**
- 실제 기기 수신, 실제 Cloudflare D1/브라우저 흐름은 미검증이다.
- 의무 작성 직원, 정확한 마감·시간대, 공휴일/휴가, 작성자→확인자, 경고 수신자·간격을 운영 기준과 대조해야 한다.
- 영속 큐 등록/외부 wakeup 접수는 사람이 읽었다는 증거가 아니다.
- 캐시 원장, 독립 리뷰, 전체 게이트 2회는 이 트랙의 최종 코드에서 통과했다. 다른 트랙과 합친 최종 코드의 통합 검증 및 병합·배포는 결과 보고 후 최종 승인이 필요하다.
