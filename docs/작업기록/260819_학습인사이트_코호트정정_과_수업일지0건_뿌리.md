안내 글을 쓰려고 화면을 열었더니 **「주의 28,309명 · 안정 0명」** 이었다.

그다음 안내 글**을 쓰기로 했다(사장님 승인).

## 2. 학습 인사이트 — 무엇이 틀렸나 (PR #219)

이 화면이 보는 신호(출석·집중도·조기이탈·끊김)는 전부 **화상수업 접속 기록**에서만
나오는데, 분석 대상은 `students_erp` 활성 학생 **28,672명 전부**였다.
화상수업을 쓰지 않는 28,000여 명이 「기간 내 출석 0회」로 자동 +3점을 받아
통째로 '주의'가 됐다. **학원에 안 나온 게 아니라 애초에 이 표에 잡히지 않는 학생**이었다.

| 항목 | 전 | 후 |
|---|---|---|
| 분석 대상 | 28,672명 | **802명** |
| 평균 출석일 | 0.1 | **4.5** |
| 평균 집중도 | `-` | **51.9%** |
| 평균 평가 | `-` | 「기록 없음 · 최근 30일 입력 0건」 |
| 안정 | **0명** | 정상 분류 |

곁가지로 나온 결함 3건:

1. 집계에 `role` 필터가 없어 **강사 접속까지 학생 출석**으로 셌다.
2. 출석 행의 `user_id` 가 두 종류(LMS 아이디 `gng01` / 계정 uid `u_…`)인데
   **집중도 기록은 대부분 `u_` 쪽**이라 ERP 조인만으로는 **결과가 0건**이었다.
   → `attendance.username` 을 이름 대체값으로 함께 받아 해결.
3. 미래 날짜 행(최대 2030-02-20)이 「마지막 출석」에 잡혀 음수가 될 수 있었다.

**중복 정리**: 「오늘의 케어 대상」이 `/admin/retention` 과 같은 일을 두 번 하고 있었다.
retention 쪽이 카페24 본 DB 의 실제 만료·휴면일수를 쓰고 학부모 연락까지 갖춘 정본이라
그쪽으로 일원화. 하니스는 「있는지」 대신 **「없는지」를 감시**하도록 뒤집었다.

## 3. 검토했다가 버린 방법 ← 가장 중요

### 버린 것 ①: 수업일지를 「화상수업 기록(attendance)」에 붙이기 (B안)

수업일지가 0건인 원인을 쫓다가 「실제 수업은 `attendance` 에 남으니 거기에 일지를 붙이자」로
방향을 잡고 사장님 승인까지 받았다. **그런데 코드를 쓰기 전에 데이터를 다시 재면서 철회했다.**

이유: 최근 30일 `attendance` 방 3,746개 중 **강사가 동석한 방은 20개뿐**이었다.
나머지 3,706개는 학생이 혼자 들어갔다 나온 것이다. B안대로 만들면 강사가 얻는
「일지 쓰기」 버튼이 한 달에 20개 남짓이고, 그중 다수는 공용방 `mangoi-class`
(30일간 학생 84명이 드나든 **한 개의 방**)라 「누구를 가르쳤는지」를 특정할 수 없다.

⚠️ **이때 내가 먼저 사장님께 「방 3,746개 = 수업 3,746번」이라고 잘못 보고했다.**
방 개수만 세고 강사 동석 여부를 안 봤다. 정정하고 방향을 A안(카페24 동기화)으로 바꿨다.

### 버린 것 ②: 강사 리마인더를 새로 만들기

「수업일지 안 쓰면 강사에게 알림」을 새로 만들려다가, **이미 있다**는 것을 발견했다
(`runFeedbackReminderSweep`, 매일 19:00 KST cron, SMS 발송·dedup·상한·on/off 완비,
강사 연락처도 33명 중 25명 보유).

그런데 **한 번도 보낸 적이 없었다.** 증거: `feedback_reminder_log` 테이블이 아예 존재하지 않는다.
그 테이블은 「오늘 끝난 수업」이 있어야 생성되는 자리에 있는데, 이 함수도
`class_schedules`(정규 수업 0건)만 보기 때문에 늘 즉시 return 했다.

→ 새로 만들지 않고, **조회 대상만 바꾸면 되는 일**로 정리. 다만 담당 판정이
바로잡힌 뒤에 하기로 하고 보류했다(아래 5장).

## 4. 수업일지 0건의 진짜 뿌리 (PR #226)

`student_evaluations` 104건을 전부 열어 보니 **진짜 강사가 쓴 일지는 0건**이었다.
100건은 2026-06-04 14:46:55 **한 초에** 들어간 시드, 1건은 학생 「홍길동」 데모,
2건은 `'   chloes123'`(앞 공백 3칸) 같은 쓰레기. **104건 전부 `teacher_uid` 가 NULL** —
강사 화면을 거쳐 들어온 행이 하나도 없다는 뜻이다.

사슬은 이렇다:

```
강사는 옛 LMS 에서 수업한다 (사장님 확인)
  → 그 수업은 이미 D1 에 있다 (attendance, room_id='c24-*', 179,998건)
  → 그런데 강사 화면은 예약표(class_schedules)만 본다   ← 끊긴 곳
  → 예약표엔 정규 수업이 0건 (673행 중 자리표시를 빼면 15행, 그나마 레벨테스트)
  → 「일지 쓰기」는 끝난 수업이 있어야 그려진다  if (done)
  → 버튼이 한 번도 뜬 적이 없다 → 수업일지 0건
```

**고친 것**: 카페24 동기화가 수업을 가져올 때 강사도 함께 가져오게 하고
(`attendance.teacher_uid`/`teacher_name`), 강사 포털에 최근 14일 끝난 LMS 수업을 실었다.
화면은 이미 완료된 수업에 버튼을 그리므로 `teacher.html` 수정 없이 살아난다.

**결과(2026-08-19 03:40 실측)**: 최근 14일 LMS 수업 1,685건 **전부(100%)** 에 강사번호가 채워졌다.
카페24 `:Class` 는 강사 속성을 정상적으로 주고 있었다 — 걱정했던 서버 작업은 필요 없었다.

## 5. 🔴 그런데 내가 사고를 냈다 (PR #299)

`attendance.teacher_uid` 는 **카페24 강사번호**(9~196)인데,
D1 `teachers.id`(지역 일련번호 1~29)와 같은 것으로 취급했다. **다른 체계다.**
번호가 겹치는 자리에서 정확히 「다른 사람」이 걸렸다:

| 계정(`teachers.id`) | 붙은 카페24 번호 | 실제 그 번호의 주인 | 영향 |
|---|---|---|---|
| HANNAH (24) | 24 | **Teacher Mariane** | 수업 **127건** |
| MELCA (26) | 26 | **Teacher Rica** | 11건 |
| ZEE (9) | 9 | 테스트 강사 | 2건 |

진짜 Hannah 의 카페24 번호는 **189** 다. 수업 카드에는 **학생 이름이 함께** 나오므로
「남의 수업이 보이는」 사고 그대로였다.

이 저장소에 이미 기록돼 있던 「`Anna` → `H-ANNA-H`(HANNAH)에 붙어 남의 수업이 보이던」
사고와 **같은 종류**인데, 이름이 아니라 **숫자**라서 눈에 더 안 띄었다.

**왜 하니스가 못 잡았나** — PR #226 에서 내가 넣은 감시가
`tch.includes('linkedTeacherIds.length')` 였는데, 그 문자열이 파일 다른 곳에도 있어
그냥 통과했다. **「배선이 있는가」만 보고 「배선이 맞는가」는 안 본 감시**였다.
→ 잘못된 패턴 자체(`tConds = linkedTeacherIds`)를 금지하는 쪽으로 교체.

**고친 방식**: 계정 → 카페24 번호를 따로 해석한다.
`teacher_profiles.korean_name/english_name` **완전일치** → `teacher_payroll_auto.teacher_name`
→ `teacher_id`. 이 표는 카페24가 **번호와 이름을 함께** 밀어넣은 것이라 그 안에서는 안 어긋난다.
33명 중 26명이 후보 1개로 해석되고, 나머지 7명은 **아무것도 안 보여준다**(안전한 실패).
완전일치만 쓰고 후보가 2개 이상이면 붙이지 않는다 — **모르는 것보다 틀린 게 나쁘다.**

**노출 범위**: 값이 채워진 것은 03:00, 수정 배포는 04:03 → 약 **1시간**.
필리핀 강사 근무 시간대는 아니지만 **접속 로그가 없어 실제로 본 사람이 있었는지는 알 수 없다.**
기록된 틀린 이름 140건은 **D1 을 손대지 않았고**(개발·운영 같은 DB),
야간 동기화가 [60일 전, 180일 후] 창을 다시 넣으며 스스로 교정된다.

## 6. 같은 함정이 하루에 세 번 밟혔다

1. **수업 목록** — 이 작업(PR #226 → #299 수리)
2. **급여 화면** — 다른 세션(PR #300 「번호로 이은 자리를 이름으로 바로잡음」,
   「강사 뷰에서 남의 급여 유출 차단」)
3. **`class_schedules` 씨앗 만들기** — `api-admin.ts` 의 `source='attendance_seed'` 경로가
   `attendance.teacher_uid`(카페24 번호)를 `class_schedules.teacher_id`(=`teachers.id` 로 읽는 칸)에
   그대로 넣는다. **2026-08-19 기준 `attendance_seed` 0건이라 피해는 없지만, 쓰는 순간 재현된다.**
   ⚠️ 이건 다른 세션의 새 기능이라 임의로 고치지 않고 알림만 남긴다.

두 세션이 각각 밟았다는 것은 **우연이 아니라 구조**다.
그래서 작업기록이 아니라 **`CLAUDE.md` 2장 함정 표에 등재**했다(클로드가 매번 자동으로 읽으므로).
