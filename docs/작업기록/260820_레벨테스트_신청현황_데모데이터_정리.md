# 레벨테스트 신청 현황(leveltest_applications)에 쌓인 데모 데이터 정리 — 실행은 대표님 PC에서 예정

- 날짜: 2026-08-20
- 작업자: Claude (원격 세션) + 대표님(사장님)
- 브랜치 / PR: 없음 — **코드 변경 없이 조사와 SQL 명령어 준비만 진행**. 실제 DELETE는 아직 실행 전.

## 1. 왜 했나

사장님이 관리자 대시보드 「레벨테스트 신청 현황」 화면 스크린샷을 보여주며
**"레벨테스트에 데모데이터가 너무 많아. 데모로 진행한 데이터는 삭제해줘."** 라고 요청.

화면에는 `paul7038`·`paul6019`·`pauljeong`·`paul710619`·`jeong7038`·`김수(kim4545)` 같은
이름·아이디가 대기 5건 포함 전체 17건 떠 있었다. 뒤이어 사장님이 범위를 명확히 함:
"실제 레벨테스트는 잡지 않았어. 헷갈리게 되어있으니까 모두 지워줘도 돼." →
**신청 현황 전체(17건)가 전부 테스트/데모용이고, 실제 학생 신청은 0건**이라는 뜻.
이후 "그 계정도 삭제해줘. 지금 중요한건 틀이야. 그 안에 데모데이터는 불필요해." 로
연결된 체험 계정까지 정리 범위에 포함.

## 2. 무엇을 확인했나

- 테이블: `leveltest_applications` (`cloudflare-deploy/src/api-admin.ts` 8336행 `ensureLtApps()`).
  **"이건 데모다" 라고 표시하는 칸(is_demo 같은 플래그)이 아예 없다** — `source` 칸에도
  `'level-test'`(기본값)·`'ai-diagnosis'` 정도만 들어가서, 코드만 보고는 데모/실제 신청을
  구분할 수 없었다. 그래서 처음엔 사장님께 판단 기준(이름 패턴·날짜·상태값)을 되물었다.
- `cloudflare-deploy/src/leveltest-schedule.ts` 를 읽고 확인한 연쇄 관계:
  1. 신청 시 날짜·시간·배정교사가 갖춰지면 `autoScheduleOnApply()` 가 **자동으로**
     `class_schedules` 에 `class_type='level_test', source='leveltest_app'` 행을 만들고
     `leveltest_applications.schedule_id` 로 연결한다 (43행 주석 — 손으로 「수업 만들기」
     누르던 것을 신청 즉시 자동화한 것).
  2. 신청서에 연결할 학생 계정이 없으면 `createTrialStudent()` 가 `students_erp` 에
     `user_id='lt{신청id}'`, `source='leveltest'` 로 **체험 계정을 자동 생성**한다 — 화면의
     「아이디」 칸에 뜬 `lt18`·`lt16`·`lt15` 가 바로 이것.
  → 즉 `leveltest_applications` 만 지우면 **연결된 "유령 수업"(class_schedules)과
    체험 계정(students_erp)이 그대로 남아** 캘린더·강사 화면 등에 계속 보일 수 있다.

## 3. 왜 그렇게 풀었나 — 검토했다가 버린 방법

### ❌ 이름/아이디 패턴(`paul`·`jeong`·`kim4545`)만 지우기
처음엔 사장님이 이 세 패턴만 지목했다(패턴에 맞춰 지운 SELECT/DELETE 문도 준비했었다).
그런데 뒤이어 "실제 레벨테스트는 잡지 않았어" 로 **17건 전체가 데모**라는 게 확인돼,
패턴 매칭보다 **`leveltest_applications` 전체 삭제**가 더 정확하고 안전한 범위가 됐다.
패턴(LIKE) 매칭은 이후에 들어온 진짜 신청까지 실수로 걸릴 위험도 있어 폐기.

### ❌ 이 세션에서 직접 `wrangler d1 execute` 실행
`npx wrangler whoami` → **"You are not authenticated"**. 이 원격 컨테이너에는
Cloudflare 인증도, `.dev.vars`/API 토큰도 없다(둘 다 깃에 없음 — CLAUDE.md 5장 원칙).
`mango-db` 는 개발·운영 공용 DB 라 CLAUDE.md 1-1 이 애초에 "DELETE 는 사람에게 먼저
알리고, SELECT 만"이라 명시하기도 해서, 인증이 있었어도 확인 없이 바로 지우진 않았을 것.
→ **정확한 SQL을 준비해 대표님 로컬(wrangler 로그인 된 PC)에서 실행하도록 넘기는 쪽**으로 결정.

### ❌ 체험 계정(`students_erp`)까지 무조건 같이 지우기
사장님이 지우라고는 했지만, `user_id`/`student_uid` 를 참조하는 테이블이
`class_schedules`·`point_transactions`·`student_evaluations` 등 최소 수십 개다.
이 계정들은 레벨테스트 신청에서만 자동 생성돼 실제 수업이 열린 적이 없을 가능성이 높지만
**단정하지 않고**, 삭제 전에 그 uid 로 다른 테이블(수업·포인트·평가)에 기록이 있는지
먼저 세어 보는 확인 쿼리를 앞에 넣었다 — 0건이면 안전, 아니면 실행 전 재확인하도록 안내.

## 4. 확인한 방법 / 어디까지 진행됐나

- 코드 읽기로 테이블·연쇄 관계 확인(위 2장) — **DB 자체는 조회하지 못했다**
  (이 세션에 D1 접근 권한이 없음).
- **DELETE는 아직 한 건도 실행되지 않았다.** 사용자가 "지금 대표님 PC로 사용하는게 아니라서,
  일단 작업은 여기까지 하고 실제 반영은 대표님께 부탁드릴게" 라고 해서, 이 세션의 역할은
  **조사 + 실행할 SQL 준비**까지로 마무리.

## 5. 대표님이 실행할 SQL (순서대로)

**① 확인 (SELECT만)**
```sql
-- 신청 건수
SELECT COUNT(*) AS apps FROM leveltest_applications;

-- 이 신청들에서 만들어진 체험 계정 목록
SELECT user_id, login_id, student_name FROM students_erp WHERE source='leveltest';

-- 그 계정들에 다른 활동 기록(수업/포인트/평가)이 있는지 — 전부 0이어야 안전
SELECT
  (SELECT COUNT(*) FROM class_schedules   WHERE user_id IN (SELECT user_id FROM students_erp WHERE source='leveltest')) AS classes,
  (SELECT COUNT(*) FROM point_transactions WHERE user_id IN (SELECT user_id FROM students_erp WHERE source='leveltest')) AS points,
  (SELECT COUNT(*) FROM student_evaluations WHERE user_id IN (SELECT user_id FROM students_erp WHERE source='leveltest')) AS evals;
```

**② 삭제 (①에서 classes/points/evals 가 전부 0일 때)**
```sql
DELETE FROM leveltest_applications;                    -- ① 신청 전체
DELETE FROM class_schedules WHERE source='leveltest_app'; -- ② 자동 생성된 유령 수업
DELETE FROM students_erp WHERE source='leveltest';        -- ③ 자동 생성된 체험 계정
```

각각 `npx wrangler d1 execute mango-db --remote --command "..."` 로 실행.

## 6. 남은 것 / 주의할 것

- **아직 실행 전이다.** 대표님이 위 SQL을 실행한 뒤, 관리자 화면 「레벨테스트 신청 현황」이
  0건으로 뜨는지 사람이 눈으로 확인해야 마무리된다.
- ①의 확인 쿼리에서 `classes`/`points`/`evals` 중 0이 아닌 게 나오면 — 그 체험 계정이
  실제로 뭔가에 쓰였다는 뜻이므로 ③번(계정 삭제)은 보류하고 먼저 재확인이 필요하다.
- 이번 정리로 `leveltest_applications` 에 "이게 데모인지" 표시하는 칸이 없다는 게
  드러났다. 같은 혼란이 반복되지 않으려면 신청 폼에 테스트 여부를 남기는 방법(예:
  관리자 전용 "테스트 신청" 버튼에서만 `source='admin_test'` 로 남기기 등)을 고려할 수
  있으나, **이번 지시 범위 밖이라 손대지 않았다.**
