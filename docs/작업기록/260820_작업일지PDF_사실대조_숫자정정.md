## 3. 왜 141 인가 — 세는 법이 세 가지였다

같은 이틀을 두고도 값이 갈렸다.

| 세는 법 | 값 |
|---|---:|
| 로컬 이력의 `Merge pull request` 커밋 | 84 |
| 위 + 스쿼시 병합의 `(#NNN)` 접미사까지 | 123 |
| **GitHub 병합 기록(`is:merged merged:…`)** | **141** |

**94 는 어느 것과도 안 맞는다.** 인접일(8/17·8/20)을 더해 봐도, 병합 커밋만 세도,
first-parent 로 세도(144) 나오지 않는다. 근거를 복원할 수 없는 숫자였다.

- **채택**: GitHub 병합 기록 141. 정본이고, 스쿼시·머지 방식에 좌우되지 않는다.
- **커밋 179**: 병합 커밋을 뺀 수. 전체 344, first-parent 144 와 구분해 적었다.
- ✅ **세는 기준을 문서 본문에 명시**했다. 숫자만 고치면 다음 사람이 또 다른 값을 낸다.

### 검토했다가 버린 것

- **«대략 100건» 처럼 뭉개기 — 버림.** 보고서 첫 화면의 큰 숫자다. 뭉개면 나머지도 어림값으로 읽힌다.

## 4. 조판 문제 — 원본 PDF 2쪽이 두 줄만 남고 비어 있었다

1쪽 「새로 만든 것」 목록이 쪽 경계에서 잘려 두 줄이 2쪽으로 넘어가고 그 아래가 백지였다.
`CLAUDE.md` 2장 「A4 인쇄용 HTML 을 화면·웹으로 내보냈더니 아래가 잘림」과 같은 뿌리다.

그래서 옮길 때 **A4 고정 높이를 버리고 흐르는 레이아웃**으로 만들었다.
인쇄는 `@media print` 에서 `break-inside` 로 카드·표만 보호한다.

### ⚠️ 같은 함정을 내가 다시 밟았다 (점검보고 PDF 를 만들면서)

새로 만든 점검보고 PDF 도 **처음 렌더에서 4쪽이 되고 4쪽에 꼬리말만** 남았다.
내용 높이는 **771mm** 로 3쪽(891mm)에 충분히 들어가는데도 그랬다.

원인은 여백이 아니라 **`table { break-inside: avoid }`** 였다.
10행짜리 표가 통째로 안 쪼개지니 다음 쪽으로 통째로 밀리고, 앞 쪽에 빈 공간이 남고,
그 뒤가 전부 밀려 한 쪽이 더 생겼다.

✅ **표는 쪼개지게 두고 `tr` 에만 `break-inside: avoid`** 를 걸어 3쪽(935·1152·900자)으로 균형이 맞았다.
`thead { display: table-header-group }` 도 함께 넣어 쪽이 넘어가도 머리행이 따라간다.

> 📌 **여백부터 줄이지 말 것.** 「쪽이 하나 더 생긴다」의 원인은 대개 여백이 아니라
> **안 쪼개지는 큰 덩어리**다. 먼저 내용 높이(mm)를 재서 «정말 넘치는지» 확인하고,
> 넘치지 않는데 쪽이 늘면 `break-inside:avoid` 가 걸린 덩어리를 찾아라.
