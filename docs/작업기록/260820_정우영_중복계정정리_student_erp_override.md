D1 을 뒤져 보니 실제로는 이랬습니다:

- 정우영 한 사람의 학생계정이 **카페24에 15개** 있었습니다

즉 「수업이 없다」가 아니라 **「수업을 들고 있는 계정이 안 보인다」** 였습니다.

수업이 **두 갈래**로 갈려 있던 것도 이때 드러났습니다:

| | 계정 | 수업 시각 | 출처 |

| 카페24(옛 LMS) | `정우영2` | 화·수·금 18:00 / 목 07:10 | `attendance` `room_id='c24-*'` 709건, **지금도 계속 생성 중** |
| mangoi.ai 화상수업 | `jeong` | **화·수·목·금 19:20** | `class_schedules` 848~851 |

사장님 확인 결과 **19:20 이 맞고 카페24 시각은 전부 틀린 것**이었습니다(처음엔 07:10 하나만 잘못된 줄 알았습니다).

## 3. 왜 그렇게 풀었나 — 검토했다가 버린 방법

**핵심 벽:** `students_erp` 는 **카페24가 정본**입니다. 매일 밤 03:00 KST 에 `importCafe24Students` 가

```sql
DELETE FROM students_erp WHERE created_at = CAFE24_STUDENT_SENTINEL   -- (=1751500000000) 전부 지우고
INSERT OR REPLACE INTO students_erp (...)                             -- 카페24 :Student 로 다시 채운다
```

로 통째로 갈아엎습니다. **15개 계정 전부** 그 센티넬을 달고 있었습니다.

| 버린 방법 | 왜 버렸나 |
|---|---|
| **D1 에서 14개 계정 `DELETE`** | 오늘 밤 03:00 에 전부 되살아납니다. 게다가 그 사이 붙어 있던 출석 947건만 주인을 잃습니다 |
| **`korean_name` 을 직접 `UPDATE` 만 하고 끝** | `INSERT OR REPLACE` 가 밤에 덮습니다. `cafe24-sync.ts` 주석에도 「여기 값을 손으로 고치면 안 된다」고 적혀 있습니다 |
| **`students_erp` 에 `hidden` 컬럼 추가** | 같은 이유로 날아갑니다. `INSERT OR REPLACE` 는 **컬럼 목록에 없는 칸을 NULL 로** 만듭니다(2026-08-18 전화번호 전멸 사고와 같은 뿌리) |
| **숨김 전용 `/api` 경로 신설** | `src/index.ts` 가 공동 금지구역입니다(라우팅+인증 게이트 둘 다 건드려야 함). 건수가 적어 D1 직접 지정으로 갈음했습니다 |
| **명부에서만 감추고 로그인은 그대로** | 「없앴다」가 아닙니다. 옛 계정으로 들어가 「내 수업이 안 보인다」가 그대로 재현됩니다 |
| **조건절을 항상 붙이기 (fail-closed)** | `erp-list` 는 **어떤 에러든 삼켜 빈 배열**을 돌려줍니다. 표가 없을 때 `no such table` 이 나면 **학생 29,000명 명부가 통째로 사라진 것처럼** 보입니다. 「14개가 다시 보이는 것」이 「전체가 사라지는 것」보다 압도적으로 낫습니다 |
| **카페24 원본을 손대는 것으로 한 번에 끝내기** | 워커에는 `:Student`·`:Class` 를 **읽는 코드만** 있고 Neo4j 시크릿도 개발 환경에 없습니다. 못 합니다 → 요청서 방식으로 전환 |

### 카페24 쪽 처리 — (A)안을 고른 이유

조사 중 **`정우영2` 는 지금도 새 중국어 수업이 생기는 것**을 발견했습니다(`class_id 511068`, 8/21 18:00).
그래서 그냥 지우면 **진행 중인 수강이 끊깁니다.** 세 가지를 놓고 사장님이 (A)를 고르셨습니다.

- **(A) 수강을 `jeong` 으로 옮긴 뒤 정우영2 삭제** ← 채택
- (B) 카페24 수강은 접고 통째로 삭제 → 8/21 수업도 함께 없어짐
- (C) 정우영2 는 살려두고 13개만 삭제 → 이력은 안전하지만 계정이 둘로 남음

⚠️ `jeong` 은 원래 **사장님이 테스트용으로 만든 본인 계정**입니다. 그 사실을 확인하고도
「앞으로 이 하나로 통합한다」로 (A)를 재확인하셨습니다(같은 날 두 차례).

## 5. 남은 것 / 주의할 것

### 5-1. 카페24 담당자 작업 대기 (요청서 전달됨)

1. `정우영2` 의 `:Class` **709건 → `jeong`** 이관 + **앞으로 새 수업도 `jeong`**
2. `class_id 510899`(8/20 07:10) — 옮기지 말고 **삭제**
3. `class_id 511068`(8/21 18:00) — 시각을 **19:20** 으로 정정
4. 앞으로 만드는 중국어 수업: **화·수·목·금 19:20 · 20분**
5. 계정 **14개 삭제**(`:Class` 도 함께). ⛔ **`jeong` 은 삭제 금지**

### 5-2. 카페24 작업이 끝나면 개발 쪽이 할 일

- `student_erp_override` 의 14행 정리 (`center_franchise_override` 와 같은 원칙 — 정본이 고쳐지면 임시 지정은 없앤다)
- **D1 `attendance` 673건 이관** — 야간 동기화는 `[60일 전, 180일 후]` 창만 다시 씁니다.
  정우영2 의 709건 중 창 안은 **36건**뿐이라, 카페24에서 옮겨도 나머지는 `user_id='정우영2'` 인 채로 남습니다

### 5-3. 아직 안 고친 것

- **`jeong` 은 비밀번호가 없습니다**(`password_hash IS NULL`). 아이디만 알면 로그인됩니다.
  테스트 계정일 땐 무해했지만, 이제 실제 수강이 붙는 유일한 계정입니다. 사장님께 알렸고 지시 대기 중입니다

### 5-4. ⚠️ 이번에 제가 밟은 실수 — 시간 경과 오판

CI 가 도는 동안 **백그라운드 `sleep` 을 여러 개 걸어 놓고 그 합만큼 시간이 흐른 줄 알고** 폴링했습니다.
그 sleep 들은 분리 실행이라 실제 시간은 훨씬 덜 흘렀는데, **「CI 가 30분째 멈췄다」고 잘못 보고**했고
사장님이 그 숫자를 근거로 「로컬 게이트 통과 근거로 병합」을 고르셨습니다(PR #359).

실제로는 약 4분이었고 Actions 는 그냥 큐에 있었을 뿐입니다. 결과적으로 배포 게이트가 CI 에서도
`success` 로 통과해 병합 자체는 안전했지만, **판단 근거가 틀렸던 것은 사실입니다.**

→ **경과 시간을 말할 때는 반드시 `date` 로 실제 시계를 찍어서 확인할 것.** CLAUDE.md 2장에도 넣었습니다.
