**날짜** 2026-08-21 · **PR** #407 · **브랜치** `claude/chinese-class-connection-idhka4`

---

## 1. 왜 했나

수업 «도중» 사장님 제보로 시작했습니다.

> 지금 중국어 수업 하는데 연결이 약해서 교사 화면이 안 보여

수업: `class-851-20260821` (예약 851, 금 19:20, 20분) · 학생 `jeong`(정우영) ·
강사 `teachers.id = 29` 「중국어 강선생님」.

화면에 뜬 「연결이 약해 지금은 음성만 전송 중이에요」는 **고장이 아니라
AAO(저대역 자동 음성전용)의 정상 동작**이었습니다. 강사 쪽 브라우저가 자기
오디오 손실을 보고 스스로 영상을 끈 것이고, 그 사실을 상대에게 `cam-state='aao'`
로 알려 준 것입니다. 즉 **사장님 쪽 문제가 아니라 강사 쪽 회선** 문제였습니다.

이어서 「최대한 문제 없게 할 수 없나」 → 「다음 주 화요일 수업이니 점검하고
고쳐 달라」로 이어졌습니다. 다음 수업은 **예약 848, 8/25(화) 19:20 →
`class-848-20260825`** 입니다.

## 2. 제일 먼저 부딪힌 것 — 답할 데이터가 없었다

「강선생님 회선이 실제로 얼마나 나쁜가」에 답하려 D1 `vc_quality` 를 열었더니:

| 확인된 사실 | 숫자 |
|---|---|
| 최근 한 달 전체 | 675건 |
| `room` 이 빈 값 | **673건 (99.7%)** |
| 실제 강사 회선 데이터 | **사실상 0건** (`role='teacher'` 3건은 전부 본인·테스트 계정) |
| 오늘 수업 조회 | **0건** (방 번호가 안 남아서) |

「강사별 인터넷 품질 파악용」이라 적어 둔 로그가 **그 목적으로 한 건도 쓰이지
못하고** 있었습니다. 원인 두 가지를 찾았습니다.

### ① 방 번호가 안 남던 이유

`vcQualityAcc()` 의 payload 가 `window.vcRoomId` 를 읽는데, 방 번호는
`let vcRoomId = ''` 로 선언돼 있습니다. **`let` 은 `var` 와 달리 전역 객체에
속성을 만들지 않습니다.** 그래서 `window.vcRoomId` 는 **항상 `undefined`** 였고,
대체 경로로 적어 둔 `window.currentRoomId` 는 **어디에도 대입되지 않는 이름**이었습니다.

에러가 나지 않고 조용히 빈 문자열이 되기 때문에 한 달간 드러나지 않았습니다.

### ② 제일 나쁜 구간이 통째로 비던 이유

`vcQualityAcc()` 호출이 **영상 sender 통계 루프 안**, 그것도
`if (dSent + dLost < 25) return;` **뒤에** 있었습니다.

AAO 가 영상을 끄면 전송 패킷이 0 이 되어 그 `return` 에 걸립니다.
= **회선이 무너져 영상이 꺼진 순간부터 로그가 완전히 멈춥니다.**
가장 알아야 할 구간이 정확히 기록되지 않는 구조였습니다.
오늘 강선생님 기록이 0건인 것도 이것으로 설명됩니다.

## 3. 검토했다가 버린 방법 ← 가장 중요

### 3-1. 「AAO 임계값을 낮춰서 영상이 덜 꺼지게 하자」 → 버림

AAO 진입은 `alp > 12 || art > 600` 이 `sev >= 3` 일 때입니다.
코드를 읽다가 **주석과 실제 동작이 어긋나는 것**을 발견했습니다 —
주석은 「sev>=3(≈12초)에서 진입」이라고 «연속»을 전제하는데, 실제로는

```js
if (alp > 12 || art > 600) { A.sev++; A.good = 0; }
else if (alp < 3)          { A.good++; if (A.sev > 0) A.sev--; }
else                       { A.good = 0; }              // ← 3~12% 구간에서 sev 가 «그대로»
```

손실 3~12% 의 «어중간한» 구간에서는 `sev` 가 줄지도 늘지도 않습니다.
즉 **몇 분 간격으로 떨어진 나쁜 표본 3개만으로도** AAO 가 켜질 수 있습니다.

고칠 수 있었지만 **하지 않았습니다.** 이유:
- 임계값을 건드리는 것은 «영상을 살리려다 오디오를 죽이는» 교환이 될 수 있고,
- 지금은 그 판단을 뒷받침할 **실측 데이터가 0건**이기 때문입니다.

→ 먼저 측정을 복구하고(2장), 데이터를 보고 나서 정할 일로 남겨 둡니다.
   **이 어긋남 자체는 다음 사람이 볼 수 있게 여기 적어 둡니다.**

### 3-2. 「AAO 를 없애거나 약화하자」 → 애초에 금지

CLAUDE.md 1-4 「저대역폭 오디오 전용 모드(AAO+DTX) 제거 금지」.
그리고 없애면 회선이 무너질 때 **오디오까지** 끊깁니다. 수업에서 소리가 끊기는
것은 영상이 꺼지는 것보다 나쁩니다.

### 3-3. 「릴레이를 전체 수업에 항상 켜자」 → 버림

가장 균일하지만 전송량 과금이 크게 늘고, 국내 학생끼리도 불필요하게 홉이
늘어납니다. **회선이 나쁜 강사에게만** 켜는 쪽을 골랐습니다.

### 3-4. 「회선이 나쁘면 자동으로 릴레이 전환」 → 이번엔 버림

사람 손이 안 가지만 전환 시점에 잠깐 끊길 수 있고 오판 여지가 있습니다.
무엇보다 **릴레이가 실제로 도움이 되는지 아직 데이터가 없습니다.**
관리자가 명시적으로 켜고 끄면서 전/후를 비교할 수 있게 했습니다.

### 3-5. 「새 API 를 만들어 정책을 내려주자」 → 버림

새 경로는 `src/index.ts`(**공동 금지구역**)의 라우팅·인증 게이트에 등록해야
동작합니다. 대신 **클라이언트가 입장 직전 이미 부르는
`/api/class/sessions/today` 에 한 칸 실어 보냈습니다.**
바로 위에 `student_gate` 가 **똑같은 사정으로 똑같이** 하고 있었습니다
(「정적 화면은 설정을 직접 못 읽는다」). 선례를 그대로 따랐습니다.

확인 결과 `/api/class/` 도 `/api/admin/` 도 **이미 접두사 게이트**라
핸들러만 추가하면 동작합니다(`/api/admin/vc/quality` 가 같은 방식).
→ **`src/index.ts` 를 한 줄도 건드리지 않았습니다.**

### 3-6. 「강사를 이름으로 지정하자」 → 버림

CLAUDE.md 2장: 강사 번호가 세 갈래라 이름·번호로 이으면 조용히 남의 것이 붙습니다.
게다가 `sessions/today` 의 **`sqlNoJoin` 폴백 경로에는 `teacher_name` 이 아예
없습니다**(`sqlJoin` 에만 `t.name AS teacher_name`). 이름을 키로 쓰면 그 경로에서
조용히 실패합니다.

→ **`class_schedules.teacher_id` ↔ `teachers.id` 한 도메인**으로만 지정합니다.
   그 안에서는 어긋날 수 없습니다. (강선생님 = `29`)

### 3-7. 「관리자 화면에 토글 카드를 넣자」 → 이번 PR 에서는 안 함

`admin.html` 은 1.3MB 이고 카드 추가는 CSS 덮어쓰기·RBAC·사이드바 등록 등
자체 함정 목록이 따로 있습니다. **수업까지 4일**이라 사고 반경을 줄이는 쪽을
택했습니다. 서버 API(`/api/admin/vc/relay`)는 완성돼 있으니 화면은 다음에 붙입니다.

### 3-8. 첫 화면 예산 — 결국 기준선을 올렸습니다 (사장님 승인)

처음에는 **주석을 코드에서 덜어내** 여유 48B 안에서 끝냈습니다.
그런데 PR 을 올린 뒤 CI 만 빨간불이었습니다 — **CI 는 PR 머지 커밋(내 브랜치 + 최신 `main`)**
을 검사하는데, 그 사이 `main` 에 `idx-x8.js` **+671B**(사이드바 한/영 전환, PR #403)가
들어와 있었습니다. 로컬 1549KB · CI 1550KB 로 갈린 이유가 이것입니다.

`main` 을 병합하고 다시 재니 **623B 초과**. 제 몫을 한 번 더 줄여
(FLOOR 배열 두 개 → `applyStep` 안 지역변수 하나, 주석은 하니스·이 문서로)
**704B → 435B** 까지 내렸지만 여전히 354B 초과였습니다.

🔴 **결정적인 사실: 제 변경을 통째로 되돌려도 여유가 81B 뿐이었습니다.**
   즉 트리밍으로는 풀 수 없는, 예산 자체가 소진된 상태였습니다.

검토한 대안:
- **화상수업 전용 blocking 스크립트를 defer 로** — `idx-vc-*` 만 60KB 가 넘어서
  필요량의 수십 배가 남고, 학생 29,000명의 첫 화면이 **오히려 빨라집니다.**
  하지만 `public/index.html`(공동 금지구역)의 로드 «순서» 를 바꾸는 일이고,
  `idx-vc-screenmode.js` 머리말에 **라이브 장애 전력**이 적혀 있습니다.
  수업 나흘 전에 곁다리로 할 일이 아니라고 판단해 **별건으로 남겼습니다.**
- **기능 축소(4단계 포기)** — 「교사 화면이 안 보여」에 가장 직접적인 부분이라 버렸습니다.

→ **`index.html` 기준선만 1537 → 1550KB.** `--update` 는 세 페이지를 전부 현재값으로
  고정하는데, `admin.html`·`student-games.html` 은 통과 중이었으므로 원래 값(296·288)으로
  되돌렸습니다 — **남의 페이지 여유까지 같이 리셋하지 않습니다.**

⚠️ 이건 «시간 벌기» 이지 «문제 해결» 이 아닙니다. 그 사실과 진짜 할 일(defer 정리)을
   `first_paint_budget_harness.mjs` 머리말에 **「기준선 변경 이력」** 으로 남겼습니다.

## 4. 고친 것

### ① 측정 복구 (커밋 `6ae333f`)
- `room` 을 어휘 바인딩 `vcRoomId` 로 읽음
- AAO 가 켜져 있는 동안엔 **오디오 손실·RTT 로 이어 기록**

### ② 화질 4단계 신설 (커밋 `8b5eb1f`)
`[1.0, 0.6, 0.35, 0.2]` 다음이 곧바로 «완전 꺼짐» 이라 절벽이 컸습니다.
`0.08` 단계(해상도 1/4, 하한 60kbps/5fps)를 끼웠습니다.
하한을 **단계별**로 바꾼 이유는 앞 단계 동작을 한 톨도 안 바꾸기 위해서입니다.

| 단계 | 0 | 1 | 2 | 3 | **4 (신규)** |
|---|---|---|---|---|---|
| kbps | 1200 | 720 | 420 | 240 | **96** |
| fps | 24 | 14 | 10 | 10 | **5** |
| 해상도 | 1/1 | 1/1.5 | 1/2 | 1/3 | **1/4** |

### ②-2 그 4단계가 «닿지 않던» 빈틈 (PR #409, 2026-08-22)

배포 뒤 사장님이 「이제 전보다 안정적으로 수업 가능해?」라고 물으셨습니다.
답하려고 코드를 다시 읽다가 **4단계가 급격한 붕괴에서는 한 번도 안 쓰인다**는 것을
발견했습니다. 두 판정이 **같은 4초 주기**입니다:

| | 조건 | 발동까지 |
|---|---|---|
| 화질 낮추기 | 영상 손실 6%↑ / RTT 450ms↑ → 한 틱에 한 단계 | 4단계까지 **4틱 ≈ 16초** |
| AAO 영상 끄기 | 오디오 손실 12%↑ / RTT 600ms↑ 가 3틱 | **3틱 ≈ 12초** |

오디오·영상이 동시에 나빠지면 AAO 가 **한 틱 먼저** 옵니다. 즉 «기능은 있는데 닿지 않는»
상태였고, 서서히 나빠지는 경우에만 쓰이고 있었습니다.

고침: ① 오디오가 2틱 나빠지면 **그 자리에서** 최저 단계로 내린다(업로드 240→96kbps,
그 여유로 회복되면 AAO 자체가 안 걸린다) ② AAO 는 **최저 단계를 실제로 써 봤을 때만** 끈다.
⛔ 단 `sev>=5`(≈20초)면 무조건 끈다 — 최저 단계에 못 닿는 상황에서 AAO 가 영영 안 걸려
**오디오까지 죽는 것**을 막는 탈출구. 수업에서 소리가 끊기는 것이 더 나쁩니다.

📌 **교훈**: 「단계를 하나 넣었다」와 「그 단계가 실제로 쓰인다」는 다릅니다.
   같은 주기로 도는 판정이 둘 있으면 **어느 쪽이 먼저 오는지 틱 수로 세어 보세요.**

### ③ 강사별 중계(TURN) 강제 (커밋 `8b5eb1f`)
`vc_relay_force(teacher_id)` → `sessions/today` 의 `net_relay`
→ `window.__vcRelayAlways` → `createPeer`.
⛔ **TURN 미확보 시엔 절대 relay 로 가지 않습니다**(가면 연결 자체가 불가능).
⛔ 관리자 API 는 **강사를 첫 줄에서 차단** — `canEditOrg()` 는 강사를 못 막습니다.
⛔ **Cloudflare TURN 이 설정됐을 때만** 켭니다. 없으면 `/api/ice-servers` 가 대체 목록으로
   **무료 공개 TURN(`openrelay.metered.ca`)** 을 내려주는데, 거기로 «강제» 릴레이하면
   직접 연결보다 나빠질 수 있습니다. **회선을 살리려다 더 망가뜨리는 교환은 하지 않습니다.**
   (이건 코드를 다시 훑다가 뒤늦게 발견해 추가한 안전장치입니다.)

## 5. 확인한 방법

문자열 검사로는 「어떤 값이 실제로 적용되는가」를 볼 수 없어서
**실제 Chromium 에 올려 값을 쟀습니다.**

- 측정: `typeof window.vcRoomId` = **`undefined`** 확인 →
  고친 뒤 전송 payload 의 `room` = **`"class-851-20260821"`**
- 화질: step0~3 = **1200/720/420/240kbps** (고침 전과 동일) · step4 = **96kbps·5fps·1/4**
- 릴레이: 관리자 OFF = **`all`** · ON = **`relay`** · TURN 없음 = **`all`**(안전장치 작동)
- 재현용 페이지: `test-harness/manual/vc-lowstep-relay-browser.html`
  (⚠️ `manual/` 은 자동 게이트가 안 물어 갑니다 — 화질단계·릴레이를 건드리면 사람이 부를 것)

그 밖에:
- 타입체크 통과 · 회귀 하니스 **PASS 195 / FAIL 0** · CI 게이트 4종 통과
- 첫 화면 예산 **1549KB 유지**(여유 48B)
- 새 하니스 2종 — `vc_quality_log_harness`(9종) · `vc_lowstep_relay_harness`(15종).
  **둘 다 사고 상태로 되돌리면 FAIL 하는 것까지 확인**했습니다
  (측정 쪽은 되돌리니 5건 FAIL, 종료코드 1).
- `vc_stability_checklist` 의 「바닥 보장 150kbps/10fps」가 옛 상수를 글자 그대로
  못 박아 둬 깨졌습니다. **끄지 않고 «뜻» 기준으로 고쳤습니다**
  (0~3단계 바닥이 150/10 그대로인지도 함께 검사).

## 6. 다음 사람이 알아야 할 것

- **강선생님(`teacher_id=29`)에게 중계를 켤지는 아직 사람이 정할 일입니다.**
  D1 쓰기라 하지 않았습니다. 켜는 명령:
  `POST /api/admin/vc/relay {"teacher_id":"29","enabled":true,"note":"중국 회선"}`
- 켜면 **전송량 과금이 늘고 홉이 하나 늘어 RTT 가 조금 오릅니다.**
  다만 TURN 은 TCP/443 로도 붙을 수 있어, UDP 가 막히거나 조여지는 회선에서는
  직접 경로보다 안정적일 수 있습니다. **가설이며, 이제 ①번 덕분에 전/후를 숫자로 비교할 수 있습니다.**
