## 1. 왜 했나

사장님이 **PR #479 의 작업보고서 PDF** 를 주시며 「이거 작업 확인하고 승인해줘」.
즉 시작점은 «새 기능을 만들자» 가 아니라 **«남이 한 작업이 보고서대로인지 대조하자»** 였습니다.

검토 도중 #479 가 **물려받은** 구멍이 하나 나왔고, 사장님이 「1번만 고쳐줘」 하셔서 그것만 고쳤습니다.

### 발견한 것 — 학생 계정이 대소문자로 두 벌이 될 수 있다

`students_erp.user_id` 는 `TEXT PRIMARY KEY` 입니다. SQLite 의 기본 대조는 **BINARY** 라
`jeong` 과 `Jeong` 이 **UNIQUE 에도 안 걸립니다.**

그런데 찾는 쪽과 만드는 쪽이 갈려 있었습니다.

| | SQL | |
|---|---|---|
| 로그인 `/api/student/login` | `WHERE user_id = ? COLLATE NOCASE` | 대소문자 **무시** |
| 만들기 3곳 | `WHERE user_id = ?` | 대소문자 **구분** ← 문제 |

→ 중복검사를 통과해 두 벌이 나란히 생기고, 로그인은 `.first()` 라 그중 **«아무 행이나»** 집습니다.
출석·포인트·수업이 계정 단위로 붙으므로 기록이 함께 두 갈래로 쪼개집니다.

**PR #458(`admin_account`)과 같은 뿌리인데 표만 다릅니다.** 그때 강사 계정에서 실제로 터졌던
사고(`mangoi_167` / `Mangoi_167`)가 학생 쪽에 그대로 남아 있었던 셈입니다.

⚠️ 이 구멍은 **#479 가 만든 것이 아닙니다.** #479 는 옆에 있던 `/api/student/register` 의
중복검사 패턴을 그대로 따랐을 뿐이고, 그 패턴 자체가 로그인과 어긋나 있었습니다.

## 2. 무엇을 바꿨나

### 2-1. 고친 곳 — 셋은 «짝» 입니다

한쪽만 막으면 나머지 경로로 그대로 두 벌이 생깁니다.

| 파일 | 경로 | |
|---|---|---|
| `cloudflare-deploy/src/api-admin.ts` | `POST /api/admin/students/create` | 관리자 수동 등록 (#479 가 만든 것) |
| `cloudflare-deploy/src/api-students.ts` | `POST /api/student/register` | 홈 회원가입 |
| `cloudflare-deploy/src/api-students.ts` | `POST /api/parent/link-child` | 학부모–자녀 잇기 |

셋 다 조회를 `WHERE user_id = ? COLLATE NOCASE LIMIT 1` 로 바꿨습니다.

**학부모–자녀 잇기는 증상이 하나 더 있었습니다.** 못 찾으면 그 자리에서
**«빈 학생 행» 을 새로 만들어** 학부모를 그 빈 계정에 이어 놓습니다
(`INSERT INTO students_erp (user_id, student_name, parent_user_id, …) VALUES (…, '신규', …)`).
그래서 화면에는 「연결했습니다」가 뜨는데 **학부모 대시보드는 영영 비어 보입니다.**
찾은 뒤에는 **DB 에 적힌 표기**(`childUid`)로 UPDATE·응답을 통일했습니다 —
여기서 갈리면 대소문자가 그대로 아래로 흐릅니다(PR #458 의 `acctUser` 와 같은 규칙).

부딪혔을 때는 **무엇과 부딪혔는지 그대로 알려 줍니다**:
`이미 «jeong» 가 있습니다(대소문자만 다릅니다).` — 대소문자만 다르면 사람이 눈으로 못 찾습니다.
`staff-create`(`auth-admin.ts`)가 이미 쓰는 방식과 같습니다.

이 하니스의 기존 방식 그대로 **소스에서 SQL 을 오려 내 진짜 SQLite 에 돌립니다.**

## 3. 왜 그렇게 풀었나 — 검토했다가 버린 방법

### ⛔ 버린 것 1: 스키마를 `COLLATE NOCASE` 로 바꾸기

가장 근본적으로 보이지만 **운영 DB 에서 못 합니다.** 대소문자만 다른 행이 이미 있으면
`UNIQUE`/PK 에 걸려 `ALTER` 가 실패하고, SQLite 는 컬럼 대조를 바꾸는 문법이 없어
**표를 다시 만들어야** 합니다. 학생 29,000명 표이고 개발·운영이 같은 DB 입니다(CLAUDE.md 1-1).
→ **찾는 쪽만** 맞췄습니다. PR #458 이 `admin_account` 에서 내린 것과 같은 판단입니다.

### ⛔ 버린 것 2: 관리자 등록(#479) 한 곳만 고치기

사장님 지시가 「1번만」이었으므로 «#479 가 만든 줄만» 고치는 선택지가 있었습니다.
**그러면 구멍이 안 막힙니다** — 홈 회원가입으로 `Jeong` 을 만들면 결과가 똑같습니다.
「1번」은 «그 줄» 이 아니라 «그 결함» 이라고 읽고 **같은 결함이 있는 세 경로를 함께** 고쳤습니다.

### ⛔ 버린 것 3: 이미 생긴 중복을 코드로 정리하기

`students_erp` 는 카페24가 정본이라 지워도 밤에 되살아납니다(CLAUDE.md 2장).
그리고 «어느 쪽이 진짜인지» 는 코드가 못 정합니다 — 정우영 계정 15개 건(260820 기록)이 그랬습니다.
→ **코드는 새로 생기는 것만 막고**, 이미 있는 것은 사람이 봅니다(5장에 확인 쿼리).

### ⛔ 버린 것 4: 로그인 조회를 «정확일치 먼저» 2단계로 바꾸기

PR #458 은 `admin_account` 에서 **① 정확일치 ② 대소문자 후보** 2단계를 썼습니다.
이유는 «두 계정에 서로 다른 비번이 걸려 있어도 한쪽이 잠기지 않게» 였습니다.
학생 로그인은 **이미 NOCASE 단일 조회로 돌고 있고 그대로도 동작합니다.**
인증 경로를 건드리면 반경이 학생 29,000명이라, **지금 문제(=새로 생기는 것)** 만 막고
로그인 조회는 손대지 않았습니다.

### ✅ 안 건드린 것: `ai-command.ts`

AI 운영비서의 수강등록도 학생을 만듭니다. 확인해 보니 만들기 전에
`user_id`·`login_id`·`username` 세 컬럼을 **전부 `COLLATE NOCASE` 로** 먼저 찾고 있어
**원래부터 안전**했습니다. 그래서 손대지 않았습니다.

### 📌 하니스를 «문자열 검사» 로만 쓰지 않은 이유

지켜야 하는 것은 「그 SQL 이 실제로 무엇을 고르는가」입니다.
그래서 ⑤절은 소스에서 SQL 을 오려 내 진짜 SQLite 에 돌리고,
**「스키마만으로는 안 막힌다」는 전제까지 함께 확인합니다**
(`INSERT 'Jeong'` 이 실제로 성공하는지). 이 전제가 언젠가 바뀌면
「찾는 쪽이 유일한 방어」라는 검사의 근거 자체가 사라지기 때문입니다.
