## 1. 왜 했나

사장님이 관리자 › 녹화 관리 화면을 캡처해 보내시며 **「이거 왜 녹화한 것이 없어 이유가 뭐지?」**
목록 **1,692건이 전부 「⚠️ 영상 없음 / 업로드 대기」** 였고, 그런데 상태 칸은 대부분 **초록색 「완료」**
였다. 용량도 「2.1MB」처럼 멀쩡히 적혀 있었다.

캡처의 그 시각 녹화들(2026-08-25 21:33~21:38, `class-895-20260825`·`mangoi-class`)은
길이가 **13초·17초·3초·1초·2초·27초** 였다. 이 숫자가 나중에 결정적인 단서가 된다.

**원인은 하나가 아니라 다섯 개였고, 성격이 두 갈래였다.**

| | 성격 | 문제 |
|---|---|---|
| 1 | 진짜 유실 | 5MiB 가 차기 전(≈17초) 탭이 닫히면 녹화가 통째로 사라짐 |
| 3 | 진짜 유실 | 업로드 성공 여부를 **묻지도 않고** `status='completed'` 로 적음 |
| 2 | 화면이 감춤 | R2 목록을 1,000개까지만 읽어 **있는 파일도** 「영상 없음」 |
| 4 | 화면이 감춤 | 「🔧 진단」이 `recordings/` 만 보고 `rec/` 를 안 봐 늘 「0개」 |
| 5 | 화면이 감춤 | 「📊 저장소 상태」 4칸이 HTML 에 박아 둔 **예시 숫자**, 새로고침은 무동작 |

⚠️ **뒤쪽 세 개가 훨씬 오래 갔다.** 「완료 · 2.1MB」·「0개」·「12.4GB」는 전부
**«고장» 이 아니라 «평범한 숫자»** 로 보였기 때문이다. 이번 건의 진짜 교훈은 여기에 있다.

## 2. 무엇을 바꿨나

### 문제 1 — 짧은 녹화 유실 → 「스냅샷」 안전망 (PR #491)

R2 multipart 는 **비마지막 파트가 5MiB 이상**이어야 한다(R2 규칙). 2.5Mbps 기준 그건 **약 17초**다.
즉 **녹화 첫 17초 동안 서버에는 조각이 하나도 없다.** 그 구간에서 탭이 닫히면
`onBeforeUnload` 가 `abort` 를 보내고 그걸로 끝이었다.

- `cloudflare-deploy/public/js/mango-rec.js`
  `maybeSnapshot()` 신설. **조각이 아직 하나도 안 올라간 동안에만**(`r2PartNumber === 0`)
  버퍼 전체를 통짜 파일로 올린다(첫 9초 → 이후 30초마다, 최대 15장). 버퍼는 비우지 않는다.
  ⚠️ 훅은 `ondataavailable` 에 둔다. `bufferChunk` 안에 넣으면
  `rec_multipart_uniform_harness` 가 **그 함수만 떼어내 실제로 돌리기 때문에** 검사가 깨진다
  (작업 중 실제로 밟아 FAIL 났다).
- `cloudflare-deploy/src/recordings-r2.ts`
  `PUT /api/recordings/upload/snapshot` 신설(파트와 똑같은 관문 `assertUploadable`).
  되살리기는 `promoteSnapshot()` — **abort 순간**(탭 닫힘)과 **크론 스윕**(비콘조차 못 간 경우) 두 곳.
  `complete` 성공·실패 때는 `dropSnapshot()` 으로 정리.

### 문제 2 — R2 목록 1,000개 잘림 (PR #491)

- `cloudflare-deploy/src/index.ts` `handleRecordingList()`
  커서 없이 `list({limit:1000})` 를 한 번만 불렀다. 버킷이 1,000개를 넘으면 **키 사전순 앞
  1,000개만** 온다. 그런데 실제 녹화 키는 `rec/…` 라 `class-…`·`mangoi-…` 보다 **뒤로 밀린다.**
  → 커서로 끝까지(최대 20,000개) 훑고, 그래도 못 읽으면 `truncated` 로 알린다. `.snap` 은 제외.
- `cloudflare-deploy/public/js/adm-core.js`
  `truncated` 면 카운트 줄에 「⚠️ R2 목록이 잘렸습니다 — 「영상 없음」이 사실이 아닐 수 있습니다」.

### 문제 3 — 저장 안 됐는데 「완료」 (PR #506)

- `cloudflare-deploy/src/api-mango.ts` `/api/recordings/stop`
  예전: `status = CASE WHEN status IN ('upload_failed','deleted') THEN status ELSE 'completed' END`
  → **R2 성공 여부를 아예 안 봤다.** 그 「2.1MB」도 브라우저가 잰 **로컬** 크기다.
  지금: 그 행의 `file_url` 로 **R2 `head()` 를 걸어 실물을 직접 확인**하고 적는다.
  `MangoEnv` 에 `RECORDINGS?: R2Bucket` 타입 선언을 더했다(런타임엔 원래 있었고 선언만 없었다).
- `cloudflare-deploy/public/js/mango-rec.js` · `public/video-call/js/recorder.js`
  둘 다 `r2_success` 를 함께 보낸다. **한쪽만 고치면 그 경로는 그대로 거짓말한다.**
  `create` 부터 실패해 키조차 없는 경우는 이 값만이 단서다.

### 문제 4 — 「🔧 진단」이 엉뚱한 칸 (PR #506)

- `cloudflare-deploy/src/index.ts` `/api/recordings/test-r2`
  `recordings/` 한 접두사만 10개 세고 있었다. → `rec/` 와 함께 세고 각각의 개수·`truncated` 를 준다.
- `cloudflare-deploy/public/js/adm-core.js` `testR2()` 가 두 접두사를 함께 적는다.

### 문제 5 — 「📊 저장소 상태」 예시 숫자 (PR #506)

  D1 은 총건수·완료·**실패**·진행중·30일 내 만료를 센다.

  녹화 목록을 불러올 때도 함께 부른다.

## 3. 왜 그렇게 풀었나 — 검토했다가 버린 방법

### ⛔ 스냅샷을 «진짜 키에 그냥 덮어쓰기» (문제 1)

훨씬 단순했다 — D1 `file_url` 이 이미 그 키를 가리키므로 화면이 즉시 「정상」이 된다.
**그런데 안 했다.**

진행 중인 multipart 와 **같은 키**에 `put` 한 뒤 `complete` 가 어떻게 되는지가 R2 문서로
보장되지 않는다. 만약 `complete` 가 실패하면, `upload/complete` 의
**「head() 로 실물이 있으면 성공」 자가복구**(2026-08-04 에 넣은 것)가
**스냅샷(앞부분만)을 완성본으로 오인**해 `completed` 로 확정한다
→ **모든 수업 녹화가 앞부분만 남고 조용히 잘린다.**
라이브 서비스에서 확인할 수단이 없는 가정 위에 올릴 위험이 아니라고 판단했다.
→ `<키>.snap` 옆자리에 쓰고, **multipart 가 확실히 끝난 뒤에만** 옮긴다.

### ⛔ `onBeforeUnload` 의 abort 를 없애기 (문제 1)

처음엔 「abort 가 녹화를 죽인다」로 봤는데, 조각이 0개면 **R2 에 애초에 아무것도 없다.**
abort 는 증상이지 원인이 아니다. 오히려 지금은 abort 가 **«스냅샷을 되살려라» 신호**를 겸한다.

### ⛔ 클라이언트 말만 믿고 상태 적기 (문제 3)

`r2_success` 만 보고 판정하면 옛 클라이언트(캐시된 `?v=46`)는 그 값을 안 보내므로 그대로 거짓말한다.
그래서 **서버가 `head()` 로 직접 확인**하는 것을 정본으로 두고, `r2_success` 는 보조로 쓴다.

### ⛔ 확인 실패를 «실패» 로 적기 (문제 3)

`head()` 조회 자체가 실패할 수 있다(일시적 오류). 그때 강등하면
**통신이 잠깐 흔들린 날에 멀쩡한 녹화 수십 건이 한꺼번에 「저장 실패」로 찍힌다.**
이 경로는 수업이 끝날 때마다 도는 곳이라 **«막는 쪽» 이 아니라 «통과시키는 쪽» 으로 실패**해야 한다.
→ `headChecked` 를 따로 두고, **«없다고 밝혀졌을 때» 만** 강등한다.

### ⛔ KV 호출수·월 청구액을 «그럴듯하게» 채우기 (문제 5)

두 값은 **Worker 안에서 알 수 없다**(Cloudflare 계정 API 영역). 대충 계산해 넣으면
지금까지의 예시 숫자와 똑같은 «그럴듯한 거짓말» 이 된다.
→ **지어내지 않고** 그 두 칸을 빼고, 이 화면에서 실제로 궁금하고 **측정 가능한**
「저장 실패 N건」·「30일 내 만료 N건」으로 바꿨다.
⚠️ 사장님께 바꾼 사실과 이유를 보고했고 되돌릴 수 있다고 말씀드렸다.

### ⛔ 문자열 하니스로 문제 3 을 감시하기

판정이 SQL `CASE` 식이라 「그 조건이 있는가」로는 결과를 알 수 없다.
조건 **순서**만 바뀌어도 뜻이 통째로 달라지는데 코드는 멀쩡해 보인다.
→ 소스에서 `UPDATE` 문을 오려 내 **진짜 SQLite 에 돌려** 상태별 결과를 확인한다.
옛 SQL 로 되돌려 «업로드 안 된 녹화가 `completed`» 가 되는 것까지 확인했다.

## 5. 남은 것 / 주의할 것

### 사람이 확인할 것

1. **관리자 › 녹화 관리 › 저장소 상태 4칸** — 진짜 숫자가 뜨는가(12.4GB·156파일이 사라졌는가)
2. **「🔧 진단」** — `rec/ N` 이 0이 아니면 **파일은 그동안에도 있었다**는 뜻
3. **수업에 20초쯤 들어갔다 창 닫기** — 그 녹화가 목록에 남는가(예전엔 사라졌다)

### 코드에 남은 주의점

- **`.snap` 찌꺼기** — `complete` 성공/실패 때는 지우고, abort·크론에서는 승격하며 지운다.
  다만 `retention.ts` 의 보관기간 파기는 **R2 객체를 아예 지우지 않으므로**(원래 그렇다)
  만료된 녹화의 `.snap` 도 남는다. 새 문제는 아니지만 언젠가 정리 대상.
- **`/api/recordings/stop` 이 `file_url` 을 덮어쓴다** — `video-call/js/recorder.js` 의 폴백이
  `file_url: 'CLIENT_ERR:…'` 를 보내면 진짜 키가 지워진다(예전부터 그랬다).
  이번엔 **UPDATE 전에 읽은 키**로 `head()` 를 걸어 그 영향을 피했지만, 그 덮어쓰기 자체는 그대로다.
- **스냅샷은 최대 15장 × ≤5MiB** — 저대역폭 수업(오디오 위주)에서 5MiB 를 오래 못 채우면
  그만큼 반복된다. 상한을 낮추려면 `SNAP_MAX`·`SNAP_EVERY_MS`(mango-rec.js).

### 이번에 밟은 저장소 함정 (CLAUDE.md 2장에 추가함)

- **`asset-versions.json` 원장 충돌** — main 이 같은 파일의 `?v=` 를 먼저 올려
  **같은 번호에 다른 내용**이 될 뻔했다(adm-core 168). 169 로 새로 매겼다.
- **playwright route 등록 순서** — 나중에 등록한 것이 이긴다. 포괄 스텁을 뒤에 두면
  구체적인 스텁을 전부 삼켜 «화면이 못 채운다» 는 **거짓 실패**가 난다.
