## 왜 했나

「코드 정리 계속 진행하고, 잘 돌아가고 안정될 수 있도록 수리해 달라」는 지시로
남겨 뒀던 목록 중 **데이터 파괴 위험이 가장 큰 것**부터 처리했다.

## 수리 (PR #599)

`importCafe24Students` 가 학생 전원을 지우고 19칸만 다시 넣는데 표는 44칸이라
**25칸이 매일 밤 NULL** 이 됐다. 그중 셋이 우리 코드가 쓰는 값이다 —
`password_hash`·`parent_user_id`·`eval_band`.
**즉 학생 비밀번호를 도입할 수 없는 상태였다**(정해도 그날 밤 사라짐).
이것이 8/28 보안 점검에서 확인한 「아이디를 아는 것 = 로그인」의 해결을 막고 있었다.

- DELETE 를 그 세 칸에 값이 있는 행만 비켜 가게 좁힘
- `INSERT OR REPLACE` → `ON CONFLICT(user_id) DO UPDATE SET <카페24 칸만>`
- `created_at` 은 일부러 갱신하지 않음(«카페24가 정본» 표식 — 체험계정 `lt*` 보호)

## 검토했다가 버린 방법

- **DELETE 를 통째로 없애기** — 카페24를 떠난 학생이 영원히 남는다. purge 를 유지하려면
  «이번 실행에서 본 행» 표식이 필요한데, 야간 배치에 상태를 더하는 것은 사고 반경이 크다.
- **`student_erp_override` 에 비밀번호까지 넣기** — 그 표는 «사람이 지정한 이름·숨김» 용이다.
  비밀번호·학부모연결을 거기 넣으면 성격이 다른 두 가지가 한 표에 섞인다.
- **INSERT 목록에 25칸을 다 더하기** — 카페24가 안 주는 값을 NULL 로 덮는 것이라 같은 사고.

## 🔴 trap-check 가 잡은 것 (이 수리가 낼 뻔한 사고)

보존 조건이 읽는 세 칸은 **«처음 쓰일 때» ALTER 로 생기는 지연 컬럼**이다.
없는 DB 에서는 새 DELETE 가 `no such column` 으로 죽고, 그 예외를
`nightlyCafe24Refresh` 가 삼켜 **학생 29,000명 동기화가 조용히 멈춘다.**
trap-check 가 하니스 가짜 스키마에서 칸을 빼 **재현까지** 해서 알려 줬다.
→ 멱등 ALTER 세 줄을 먼저 두고, 칸이 없는 상태로 하니스를 돌려 살아남는 것을 확인했다.

같은 검사가 지적한 나머지도 반영했다 — 옛 동작을 서술하던 주석 3곳 정정(한 곳만 고치면
다음 사람이 옛 설명을 믿는다), 부정 검사를 주석 벗긴 사본으로, `setBlk` 이 조용히
빈 문자열이 되면 4건이 헛통과하던 것 차단.
