# AI 영작 첨삭 — 「왜 고쳤는지」를 결정론으로 만들기 (2026-08-31)

## 1. 왜 했나

사장님 「문법 문제없는지 다시 확인해줘. 자세히 — 문법 잘 작동하고 있는지 확인해줘」.

운영 D1 을 SELECT 로 읽어 **최근 8건의 첨삭, 교정 21건**을 그대로 꺼내 봤습니다.

**문법 교정 자체는 잘 돌고 있었습니다.**

| 학생이 쓴 것 | AI 가 고친 것 |
|---|---|
| `I LOSED` | `I lost` |
| `I WANT KILL STEALER` | `I want to catch the thief` |
| `we can play ground` | `we can play on the ground` |
| `This place is lab` | `This place is a lab` |

**문제는 «왜» 였습니다 — 교정 21건 전부 이유가 서버 폴백 일반 문구였습니다.**
(「더 자연스러운 표현으로 바꿨어요」·「조금 더 자연스럽게 읽히도록 표현을 보탰어요」)

즉 모델이 `reason` 을 **매번 비워 보내고** 있었고, 화면 코드도 프롬프트도 다 «있는데»
학생은 **무엇을 고쳤는지만 보고 «왜» 는 한 번도 배우지 못했습니다.**
에러가 안 나고 화면도 멀쩡해서 아무도 몰랐습니다.

## 2. 검토했다가 버린 방법

### ⛔ 프롬프트를 더 세게 쓴다
이 저장소의 반복 실측이 「지시만으로는 안 지켜진다」입니다 — 단어 수(웜업 레벨 상한),
문법(「Want play with me」), 구두점(문장 종결부호) 셋 다 프롬프트로는 절반만 지켜졌습니다.
프롬프트는 보조로 남기되(REQUIRED 로 표시), **보장은 코드가** 합니다.

### ⛔ 모르는 것도 그럴듯하게 채운다
CLAUDE.md 「측정할 수 없는 값을 그럴듯하게 채우고 싶을 때」와 같은 자리입니다.
**틀린 설명은 «설명 없음» 보다 나쁩니다** — 아이가 그대로 외웁니다.
그래서 분류가 안 되면 `null` 을 돌려주고 그때만 일반 문구를 씁니다.

### ⛔ 두 번째 LLM 호출로 이유를 만든다
한 번 더 부르면 지연·비용이 늘고, 그 답이 맞는지는 여전히 아무도 모릅니다.
낱말 diff 로 «관사가 하나 늘었다」·「과거형으로 바뀌었다」는 **셀 수 있는 사실**입니다.

## 3. 한 것

정본 **`cloudflare-deploy/src/correction-reason.ts`** 신설 — 원문→교정 한 쌍의
**낱말 단위 diff** 를 분류해 한국어 한 문장을 만듭니다.

| 갈래 | 보기 |
|---|---|
| 관사 | `This place is lab` → 「셀 수 있는 명사 앞에는 관사가 필요해요: 'a'를 넣었어요.」 |
| 전치사 겹침 | `I was at in my house` → 「전치사가 겹쳐서 'in' 하나를 뺐어요.」 |
| 불규칙 과거형 | `I LOSED` → 「이 동사는 -ed 를 붙이지 않는 불규칙 과거형이에요: LOSED → lost (lose → lost).」 |
| 철자 | `sutentents` → 「철자를 다듬었어요: sutentents → students.」 |
| 중복 | `I went I went` → 「같은 말이 두 번 들어가 있어서 하나만 남겼어요.」 |
| 이어 주는 말 | `+and` → 「문장과 문장을 이어 주는 'and'를 넣었어요.」 |
| 어순 | `I soccer play` → 「영어는 «누가 → 무엇을 → 어디서» 순서로 써요.」 |

`src/api-ai.ts` 는 모델 이유가 **한국어 6자 이상**일 때만 그것을 쓰고, 아니면
`explainCorrection()` 을, 그것도 `null` 이면 일반 문구를 씁니다.

### 실측하며 드러난 다섯 가지

1. **`LOSED → lost` 가 «철자 오타» 로 샜습니다** — 편집거리가 2 라 철자 갈래가 먼저 먹었습니다.
   → 불규칙 과거형(`-ed` 를 뗀 원형 후보)을 **철자보다 먼저** 봅니다.
2. **철자 허용거리가 고정 2 라 긴 오타를 놓쳤습니다**(`sutentents → students` 는 거리 4).
   → 길이에 맞춰 2/3/4 로, 그리고 «바뀐 비율 40% 이하 + 첫 글자나 끝 두 글자 일치» 를 함께 봅니다.
   실측 경계: `pootball→football`(비율 0.13, 첫 글자는 다르지만 끝이 같음) = 철자 ·
   `peoples→players`(0.71) = 낱말 바꿈.
3. **조사가 「'an' 를」로 나왔습니다.** 끝 글자로 어림하면 틀립니다(`and` 는 d 로 끝나지만 «앤드» 라 «를»).
   → 실제로 넣거나 빼는 낱말만 **표로 못 박았습니다**.
4. **`i like it` → `I like it.` 이 «설명 없음» 이었습니다** — 원문을 통째로 비교해서
   마침표 하나 때문에 «대소문자만 다름» 갈래를 못 탔습니다. → **낱말 열**로 비교합니다
   (숫자는 따로 대조 — `2 cats → 3 cats` 를 「부호만 다듬었다」고 하면 거짓말입니다).
5. **표시가 소문자였습니다** — 학생이 `LOSED` 라고 썼는데 설명에는 `losed` 가 떠서
   자기 글에서 어디를 보라는지 흐려집니다. → **판정만 소문자, 표시는 원문 그대로.**

### ⚠️ 함께 지켜야 하는 계약

`api-judgment.ts` 의 `guessMisconception()` 이 **이 문구에서 오답유형을 뽑습니다.**
그 정규식은 「시제|과거」를 **맨 먼저** 보므로, 철자 교정 문구에 「과거」를 넣으면
철자 오타가 `TENSE_CONFUSION` 으로 잘못 분류됩니다. 하니스 E절이 그것까지 봅니다.
