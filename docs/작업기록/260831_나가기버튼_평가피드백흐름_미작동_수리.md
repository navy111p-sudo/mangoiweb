# 나가기 버튼 — 평가·피드백 흐름이 통째로 안 뜨던 문제 수리 (2026-08-31)

## 왜 했나

사장님이 화상수업 화면 스크린샷과 함께 제보: "강의실에서 나가기를 누르면
아무 안내 없이 그냥 나가진다" — 8/28에 추가한 "📝 수업 피드백 남기기" 버튼이
전혀 뜨지 않는 상태였음(평가 모달 자체가 안 뜸).

## 원인

학생용 평가 모달(⭐)·피드백 버튼·복습퀴즈 안내는 `index.html`의
`<script id="vc-teacher-rating-on-end">`가 window 캡처 단계에서 나가기 버튼
클릭을 가로채야 뜨는 구조인데, 그 판별 함수 `isExitBtnEl()`의 셀렉터가

```
a#vc-exit-btn-v34, a#vc-exit-btn-v33, #vc-exit-btn-v32, button.ctrl-btn.danger, a.ctrl-btn.danger
```

로, **전부 2026-07-14에 이미 삭제된 옛 상단 X 버튼**들이었다(같은 파일 8401행
주석에 그 삭제 사실이 남아 있음 — "상단 ✕ 나가기(#vc-exit-btn-v34) 삭제 —
하단 독(vc-dock)의 '나가기'와 중복이라 제거"). 즉 이 셀렉터가 가리키는
요소는 지금 DOM에 **하나도 존재하지 않았다.**

실제로 지금 쓰이는 나가기 버튼은 `public/js/vc-dock.js`가 만드는 하단 독의
`<button id="vc-dock-leave" class="leave">`이고, 여기엔 `class="ctrl-btn danger"`가
아니라 그냥 `class="leave"`가 붙어 위 셀렉터 어느 것과도 매치되지 않았다.

그래서 학생이 dock-leave를 클릭하면:
1. `vc-teacher-rating-on-end`의 캡처 리스너가 매치 실패 → 그냥 통과
2. 더 뒤에 등록된 옛 안전망 스크립트 `v29-leave-capture`(14908행 근처)가
   `title` 속성 문자열(`title="수업에서 나가기"`)에 "나가기"가 포함된 것만 보고
   훨씬 느슨하게 매치 → 캡처 성공
3. `v29`는 곧장 `vcLeaveRoom()` + `location.replace('/')`로 **전체 페이지 새로고침**
   → 평가 모달·피드백 버튼·복습퀴즈 안내를 볼 기회 자체가 없이 즉시 종료

같은 문제가 강사/관리자용 "수업만 SPA로 나가기" 흐름(`v35-leave-class-spa`)의
`isExitBtnEl()`에도 똑같이 있었다 — 이쪽은 못 잡으면 v29/v31이 대신 잡아
"전체 새로고침으로 로그인 화면까지 튕겨나감"이 재현된다(같은 파일 주석에
"학생/강사 모두 앱 안에 머문다"고 명시된 설계 의도와 어긋남).

## 무엇을 했나

`index.html`의 두 `isExitBtnEl()` 셀렉터 각각에 `#vc-dock-leave`를 추가.
그 외 로직·순서는 변경 없음(2줄 추가 + 사유 주석).

## 검토했다가 버린 방법

- **`vc-dock.js`의 `bLeave.onclick`을 직접 감싸는 방법** — 버렸다. 지금 구조는
  "캡처 단계에서 먼저 가로채 실제 onclick이 아예 안 뜨게" 만드는 게 핵심
  설계(주석에 명시: "터치·클릭 모두 첫 이벤트에서 확실히 가로챔"). onclick을
  감싸면 v29/v31 같은 뒤쪽 안전망이 여전히 window 캡처에서 먼저 걸려
  `location.replace('/')`를 먼저 실행해버릴 수 있어 근본 수리가 안 됨.
- **v29/v31의 title 매칭 자체를 좁히는 방법** — 버렸다. 그건 지금 살아있는
  진짜 안전망(다른 예외 상황 대비)이고, 이번 문제의 원인은 "그보다 먼저
  가로채야 할 스크립트가 못 가로챈 것"이지 "안전망이 너무 넓은 것"이 아니다.
  범위를 벗어난 별건 정리.
- **`#vc-exit-btn-v32~v34` 옛 항목을 셀렉터에서 빼는 정리** — 하지 않았다.
  이미 죽은 셀렉터라 지워도 동작은 같지만, 이번 수리와 무관한 청소라 범위
  최소화 원칙상 보류.

## 🔴 후속 — trap-check가 실제 CDP 터치 재현으로 잡은 잔여 버그 (같은 날, 이어서 수리)

위 수정은 **PC(마우스 클릭)에서만 완전히 고쳐졌고, 터치 기기(휴대폰·태블릿)에서는
여전히 재현됐다.** trap-check가 코드를 발췌해 동일 로직의 재현 페이지를 만들고
헤드리스 Chromium에 `Input.dispatchTouchEvent`로 실제 터치 이벤트를 흘려서 잡았다:

```
triggerA_match_pointerdown → endOfClassFlow_called →
triggerA_match_touchstart →
v35_match_touchend → v35_yield_student_touchend →
v29_match_touchend → v29_gotoHome_CALLED   ← 여기서 전체 새로고침
```

원인: 트리거 A(학생용 평가/피드백 흐름)의 이벤트 목록이
`['pointerdown','touchstart','mousedown','click']`로 **`touchend`를 안 듣는다.**
그런데 v35(강사/관리자용)는 "학생이면 트리거 A가 이미 먼저 잡았을 것"이라는
전제로 `touchend`에서 학생이면 `stopPropagation` 없이 그냥 `return`한다
(4614행 주석 그대로). 트리거 A가 애초에 그 이벤트를 안 듣고 있으니 이 전제가
깨져, `touchend`가 그대로 흘러가 아직 안 고친 `v29`(title 매칭)가 잡아
`gotoHome()`(전체 새로고침)을 실행한다. `Touch.target`은 `touchstart` 시점에
고정되므로 그 사이 평가 모달이 화면을 덮어도 `e.target`은 여전히 나가기
버튼이라 이 경로가 계속 열려 있었다.

**수정**: 트리거 A의 이벤트 목록에 `'touchend'` 추가
(`['pointerdown','touchstart','touchend','mousedown','click']`). 이미 있는
`STATE.triggered` "이미 처리 중" 가드 덕분에, `touchstart`에서 먼저 흐름을
잡은 뒤 뒤따라오는 `touchend`는 그 가드로 흡수되어(`stopImmediatePropagation`)
v35/v29까지 가지 않는다 — 새로 만든 분기 없이 기존 안전장치가 그대로 작동.

검증: tsc 통과 · `--fast` 하니스 PASS 232/FAIL 0 재확인. 실제 터치 재현
테스트는 trap-check가 수행(위 로그가 그 결과). PC 클릭 경로는 이 수정으로
바뀌지 않음(`pointerdown`에서 이미 `stopImmediatePropagation`되어 있어
`touchend` 리스너 자체가 별 영향 없음).
