# 카페24 미러 «강사 변경 잔재» — 강사 화면에 «실제로 없는 수업» 이 뜬 사고 (Teacher Zee 제보)

- 날짜: 2026-09-01
- 작업자: 정우영 + Claude
- 브랜치 / PR: `claude/missing-class-lms-3rmd9m` → **PR #681** (병합 `b2c6a76`, 배포 확인 완료)
- 데이터 정리: 운영 D1 `class_schedules` **2행**을 «수업 삭제» 와 같은 방식으로 내림(아래 5장)

## 1. 왜 했나

필리핀 매니저를 통해 **Teacher Zee** 제보가 들어왔다.

> Teacher Zee was checking her Mangoi AI account and found a class that was **not reflected in the LMS**.

즉 «망고아이 강사 화면에는 있는데 카페24(LMS)에는 없는 수업» 이 있다는 것이다.
사장님 지시는 「문제가 뭐고 빨리 해결」이었다.

첨부된 강사 화면에는 오늘 수업 6건이 있었고, 그중 셋(16:40·17:20·17:40)에
「No-show · student」 배지가 붙어 있었다.

### 배경 — 왜 하필 오늘인가

**카페24 시간표 미러**(`src/c24-mirror.ts`, 2026-08-31 신설)가 카페24 예약을 망고아이
`class_schedules` 로 옮긴다. 화이트리스트 방식이고, **Zee 는 바로 그날 09:13 에 켜졌다.**
09:15 감시견 sweep 이 그의 카페24 수업 15건을 실제로 만들었다.

## 2. 무엇을 바꿨나

### 2-1. 즉시 조치 — 유령 수업 2건을 내림 (코드 아님, 운영 D1)

| # | 학생 | 강사 | 날짜·시각 | 카페24 class_id | `class_schedules.id` |
|---|---|---|---|---|---|
| ① | 허윤아 | Zee | 9/1 17:40 (30분) | `511745` | 1045 |
| ② | 한채아 | Belle | 9/1 21:00 (20분) | `510478` | 1114 |

둘 다 관리자 화면 「수업 삭제」가 실행하는 것과 **똑같은 문장**을 썼다
(`src/api-admin.ts` 의 DELETE `/api/admin/class-schedules/{id}` 핸들러, 6698행 부근):

```sql
UPDATE class_schedules
   SET status='cancelled', source='c24-mirror:manual', updated_at=?
 WHERE id=? AND source='c24-mirror' AND notes=?
```

⚠️ **`status` 만 바꾸면 15분 뒤 되살아난다.** `planMirror` 이 취소된 행을 «없는 것» 으로
보기 때문이다(`mine` 필터가 `cancelled` 를 제외). **`source='c24-mirror:manual'` 도장이
함께 찍혀야** 미러가 그 행을 영영 안 건드린다.

⛔ 노쇼 기록(`class_no_show` id 56)은 **지우지 않았다.** 학생이 못 본 것은 사실이고,
지우면 「왜 수업이 성립하지 않았나」가 함께 사라진다(CLAUDE.md 2장).
급여 영향은 없다 — `missing_role='student'` 라 수업료 0원 규칙(`teacher_no_show`)에 안 걸린다.

### 2-2. 재발 방지 (PR #681)

| 파일 | 무엇 |
|---|---|
| `cloudflare-deploy/src/c24-mirror.ts` | 판정 **`suspect_dup`** 신설 · **`loadSlotHistory()`**(이력 세기) · `getDupGuard()`(스위치) · `fetchC24ClassPropKeys()`(측정) · `slotKey()` |
| `cloudflare-deploy/public/admin/c24-mirror.html` | 성적표 칩 「⚠ 되풀이 안 되는 자리(안 만듦)」 · `prop_keys`·`dup_guard` 표시 · 이름표 중의성 제거 |
| `test-harness/c24_mirror_harness.mjs` | **O절 34종** 신설 |
| `CLAUDE.md` | 2장 함정 표에 한 줄 추가 |

**판정 규칙 — 두 조건이 «둘 다» 맞을 때만 만들지 않는다:**

1. 그날 그 학생에게 카페24 수업이 **2건 이상**이고
2. 그중 **이 자리가 이력에 1건 이하**

이력은 `attendance` 의 `c24-*` 행을 **(학생 · 카페24 강사번호 · 시각)** 으로 센다.
(Neo4j 를 다시 부르지 않는다 — 야간 동기화가 -60일~+180일을 이미 넣어 두어 미러의
창(3일·14일)보다 훨씬 넓다.)

판정 위치는 **화이트리스트 «뒤»** 다. 안 켠 강사의 `not_whitelisted` 집계를 흐트러뜨리지
않으면서, 그쪽 `detail` 에 「⚠ 켜기 전에 카페24에서 확인하세요」 한 줄만 붙인다.

되돌리는 길: `c24_mirror_config.dup_guard='off'` (기본 켬).

## 3. 왜 그렇게 풀었나 — 검토했다가 버린 방법

### ⛔ 버린 1 — 「같은 학생·같은 날 2건이면 잔재」 (제일 먼저 떠오르는 답)

**이걸 썼으면 멀쩡한 수업이 사라졌다.** 허윤아는 **진짜로 하루 두 번** 수업한다 —
17:00 과 21:30 이고, 9/2·9/3·9/4 가 전부 그 형태다. 실측으로 확인하지 않았으면
그대로 밟았을 함정이다.

### ⛔ 버린 2 — `class_state` 로 거르기

카페24 원본 상태값인데 **잔재와 진짜가 같은 값**이라 못 가른다.
(`attendance` 는 그 값을 `present`/`scheduled` 두 가지로 뭉개기까지 한다.)
→ 대신 «우리가 안 읽고 있는 칸이 답을 들고 있을지» 를 재려고 `prop_keys`(:Class 속성
**이름** 목록)를 성적표에 싣기로 했다. ⛔ **그 값으로 판정하지는 않는다** — 뜻을 카페24에
확인한 뒤가 순서다.

### ⛔ 버린 3 — 카페24 class_id «번호 블록» 으로 판정

유령 `511745` 는 8/31 17:00 한 자리에 네 건(Kes·Sid·Zee·Zee = `511741`~`511744`)이
겹쳐 있던 **잔재 묶음의 바로 다음 번호**였다. 「옛 번호대 = 잔재」로 보고 싶었지만,
같은 묶음의 `511746`(허윤아 9/1 17:00 Teacher Far)은 **진짜 수업**이다. 성립하지 않는다.

### ⛔ 버린 4 — 이미 만들어진 행을 되짚어 취소하기

새 판정이 «지난 일» 을 지우게 하지 않았다. `already`/`update`/`conflict`/`manual` 이
먼저 `continue` 하므로 이 판정은 **«새로 만드는 것» 만** 막는다.
이미 생긴 2건은 사람이 확인한 뒤 손으로 내렸다(2-1).

### ⛔ 버린 5 — 시간 겹침(overlap) 검사

「같은 학생·같은 날·시간대가 겹치면 막는다」는 8/31 의 ×4 사고는 잡지만
**이번 건은 못 잡는다.** 허윤아 9/1 은 17:00(Far) + 17:40(Zee) + 21:30(Zee) 로
**아무것도 겹치지 않는다.** Zee 를 켜기 전 «채점» 이 「겹침 0 · 유령 패턴 0」이라고
통과시킨 이유가 정확히 이것이다.

### ✅ 택한 근거 — «그 자리가 되풀이되는가» (운영 D1 실측)

| 학생·강사·시각 | 이력 건수 | 판정 |
|---|---|---|
| 허윤아 · Zee · **21:30** | 4건 (8/31·9/1·9/2·9/4) | 진짜 |
| 허윤아 · Zee · **17:40** | **1건** (그 유령 자신뿐) | 잔재 |
| 허윤아 · Far · 17:00 | 2건 | 진짜 |
| 한채아 · Belle · 15:10 | 11건 | 진짜 |
| 한채아 · Belle · **21:00** | **1건** | 잔재 (사장님 확인) |

## 4. 확인한 방법

### 4-1. 자동 검사

- **타입체크** `node node_modules/typescript/bin/tsc --noEmit` → exit 0
- **회귀 하니스** `node test-harness/run.mjs --fast` → **PASS 255 / SKIP 20 / FAIL 0**
- **`c24_mirror_harness.mjs`** 단독 → PASS 252 / FAIL 0 (그중 **O절 34종**이 이번 신설)
- **CI** PR #681 run #783 `success` (게이트 57초)
- **배포** `git merge-base --is-ancestor b2c6a76 <배포 성공 run #2903 head_sha>` → 포함 확인

### 4-2. 변이시험 — 「되돌리면 진짜 FAIL 나는가」

| 정본을 이렇게 망가뜨리면 | 하니스 |
|---|---|
| 잔재 판정 자체를 끔 | O-1 · O-6 **FAIL** |
| 입구 조건(그날 2건 이상)을 뺌 | O-3 **FAIL** |
| `slotKey` 에 학생↔강사 인자를 뒤바꿈 | O-8 **5건 FAIL** |
| `COUNT(*)` → `1` | O-8 **3건 FAIL** |
| `swallowErrors` 를 되살림 | O-8b **FAIL** |

### 4-3. 🔴 trap-check 서브에이전트가 잡은 것 — **내 하니스가 헛돌고 있었다**

처음 낸 O-8 절은 머리말에 「이력 SQL 을 «진짜 SQLite» 에 돌린다」고 적어 놓고
**실제로는 SQL 을 손으로 베낀 사본**을 돌리고 있었다. 정본 `loadSlotHistory` 는
**한 번도 실행되지 않았다.** 그래서 위 표의 «인자 뒤바꿈»·«COUNT(*)→1» 두 변이가
그 상태에서는 **246/0 초록**이었다. 두 변이 모두 실서비스에서는 «모든 자리가 1건» 이
되어 하루 2건인 날의 수업을 **무더기로 차단**한다.

→ 진짜 SQLite 를 D1 모양(`prepare` → `bind` → `all`)으로 감싸 **정본 함수에 물리도록**
고쳤다. 본보기는 같은 파일의 N⑥·N⑦(`loadHiddenStudents` 를 가짜 DB 로 실제로 돌린다).

⚠️ 그리고 **처음 짠 O-8b 자신도 헛돌았다** — 성공한 청크가 «빈 결과» 라 올바른 코드와
망가진 코드가 똑같이 빈 Map 을 냈다. 첫 청크가 **진짜 행**을 돌려주도록 고치고
«다 성공하면 실제로 담긴다» 짝 검사를 함께 넣었다.

### 4-4. 운영 D1 백테스트 — 「지금 맞는 것을 깨지 않는가」

새 판정을 **그때 살아 있던 미러 행 48건 전부**에 돌려 봤다.

- **47건 통과**, 걸린 것은 **1건뿐**
- 그 1건이 사람이 따로 의심해 두었던 바로 그 건(한채아·Belle 21:00)
- **오검출 0건.** 하루 두 번 수업하는 학생(허윤아·손현규·이다연·이선우)도 전부 통과

### 4-5. 사후 확인 — 되살아나지 않는가

| 확인 | 결과 |
|---|---|
| 마지막 자동 실행 | **22:45:40 KST** (두 건을 내린 뒤) |
| 그 실행 결과 | `created 0 · updated 0 · cancelled 0` |
| `c24:511745` / `c24:510478` 행 | 각각 **1개뿐**, 둘 다 `cancelled` + `c24-mirror:manual` |
| 19:51 이후 미러가 만든 행 | **0건** |

⚠️ **정확히 말하면** — 마지막 실행 기록은 한 칸에 덮어쓰기라 「매 15분마다 빠짐없이
돌았다」까지는 증명하지 못한다. 확인된 것은 **「두 건을 내린 뒤에도 실행이 돌았고,
그때 아무것도 만들지 않았다」** 까지다.

## 5. 남은 것 / 주의할 것

### 🔴 이 판정은 완전하지 않다

카페24가 **«같은 자리» 에 잔재를 둘 이상** 남기면 이력이 2건이 되어 그냥 통과한다.
실제로 그런 모양이 있다 — 허윤아·Far 17:00 은 8/27·9/1 두 건인데 8/27 에 실제로 있었던
수업은 **17:20** 이었다(그 17:00 도 잔재로 보인다).

**근본 해결은 「카페24가 취소·변경을 어떻게 표시하는가」를 확인해 그것으로 거르는 것**이고,
그 답을 물어볼 근거로 성적표에 `prop_keys`(:Class 속성 이름)를 싣는다.
→ **카페24에 물어봐야 할 숙제**다.

### 🔴 보강(makeup) 수업은 미러가 만들지 않는다

「정규수업이 있는 날에 한 번만 추가되는 수업」은 조건 두 개를 모두 만족해서 보류된다.
야간 동기화가 돌아도 그 수업 «자신» 이 이력 1건이 될 뿐이라 임계값 `< 2` 에 여전히 걸린다.
즉 **«하루 보류» 가 아니라 «그 자리가 두 번째로 잡힐 때까지» 보류**다.

⚠️ 처음에 소스 주석에 「하루 보류됐다가 다음 날 저절로 만들어진다」고 적었다가
trap-check 가 **사실이 아니라고 잡았다.** 지금은 사실대로 적혀 있다.
→ 성적표에 `suspect_dup` 으로 뜨니 **사람이 보고 주간 스케줄에서 손으로 넣으면 된다.**
이것이 이 판정이 치르는 진짜 값이다.

### ⚠️ 성능

`loadSlotHistory` 는 15분마다 돈다. 2026-09-01 실측(학생 약 40명 기준) **142ms · 12,199행 읽기**.
`attendance(user_id)` 인덱스를 탄다. 전환일(`mode='all'`)에 학생 수가 열 배가 되면
비례해 늘어난다 — 그때 다시 재 볼 것.

### ⚠️ `dup_guard` 를 끄려면 운영 D1 을 직접 써야 한다

세터·API·UI 가 없다. 라우팅 허용목록이 **공동 금지구역**(`src/index.ts`)이라 이 PR 에서
손대지 않았다. 급할 때 쓸 스위치라면 세터를 두는 편이 안전해 보인다 — **사람이 정할 일**.

### ⚠️ 화면에 «유령 의심» 이 두 가지 뜻으로 있다

- 기존(강사별 표의 노란 줄): 「같은 **강사**+날짜+시각이 2건 이상」 = **시간 겹침**
- 신설(`suspect_dup`): 「그 **학생**의 그 자리가 이력에서 되풀이되지 않음」

**이번 사고는 겹치지 않아서 앞의 것이 못 잡았다.** 헷갈리지 않게 이름표를 갈라 두었다
(「⚠ 되풀이 안 되는 자리(안 만듦)」).

### ℹ️ 이번 건과 무관한 사실 하나

강사 화면 16:40 조유진·17:20 이은오의 「No-show · student」는 **진짜 수업**에 붙은 것이다.
학생들이 아직 카페24 쪽으로 들어가고 있어서 생긴 표시이지 이 사고가 아니다.
