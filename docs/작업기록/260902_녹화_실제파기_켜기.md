# 녹화 «실제 파기» 켜기 — 그리고 켜기 직전에 잡은 10.46GB

*2026-09-02 · 사장님 지시 「녹화 파기 켜줘」*

## 요약

파기를 켜기 전 dryRun 에서 **보관기간 정책이 옛 데이터에 소급되지 않았다**는 것을 발견했다.
그대로 켰으면 **6~7월 수업 녹화 1,313건 10.46GB 가 첫날 밤에 사라졌다.**
사장님께 보고하고 「3개월 소급 적용 후 켜기」를 선택받아, D1 만료일을 먼저 고친 뒤 켰다.
**그날 파기된 것은 0건이다.**

## 무엇이 문제였나

`retention.ts` 주석은 「녹화본 3개월(2026-08-06 사장님 결정, 그 전 명세는 1개월)」이다.
그런데 `expires_at` 은 **녹화를 만들 때 계산해 박아 두는 값**이라 정책 변경이 소급되지 않았다.

| 보관일수 | 건수 | 수업 기간 |
|---|---|---|
| **30일** (옛 규칙) | **1,483건** | 2026-06-05 ~ 08-07 |
| 90일 (새 규칙) | 615건 | 2026-08-08 ~ 09-01 |

즉 8/6 에 「3개월로 늘리자」고 정하셨지만 **그 전 녹화 1,483건은 여전히 한 달 뒤 만료**였고,
이미 전부 만료되어 `status='deleted'` 로 내려가 있었다(1,329행).

| 켜는 기준 | 그날 삭제량 |
|---|---|
| 지금 `expires_at` 그대로 | **1,313건 · 10.46 GB** |
| 3개월(90일) 소급 적용 | **0건** |

가장 오래된 수업이 6/5 이고 90일 뒤가 9/3 이라, **사장님이 정하신 규칙대로면 그날 지울 것이 없었다.**
⛔ 「켜줘」를 그대로 이행했으면 사장님 결정과 **정반대** 결과가 나왔다.

## 한 일

### 1. D1 만료일 소급 (사장님 승인 후)
```sql
UPDATE recordings SET expires_at = started_at + 7776000000   -- 90일
 WHERE started_at IS NOT NULL AND expires_at < started_at + 7776000000
```
→ **1,483행**. 이후 전 2,098행이 90일로 통일, 그 시점 파기 대상 **0건**(7일 내 만료 87건).

⚠️ **순서가 중요하다** — 코드를 먼저 배포했으면 그날 밤 cron 이 옛 값으로 지웠다. D1 을 먼저 고쳤다.

### 2. 실제 파기 구현 (`src/retention.ts`)
- `PurgeEnv.RECORDINGS?: R2Bucket` (**옵셔널** — 바인딩이 없으면 지우지 않고 미룬다.
  파기가 «안 되는» 것이 «잘못 되는» 것보다 안전하다)
- `PurgeOptions { dryRun, maxRecordingDeletes }` — 배치 상한 기본 200
- **D1 `status='deleted'` 를 먼저, R2 `delete()` 를 나중** ⟵ 반대면 「완료인데 영상 없음」(2026-08-26 사고) 재현
- **삭제에 성공했을 때만 `file_url = NULL`**

### 3. 왜 `file_url` 을 비우는가 (설계의 핵심)
그 칸은 세 가지를 동시에 뜻한다 — ① 파일이 아직 있다 ② 다음 실행에서 재시도할 대상이다
③ 고아 청소기(`recordings-cleanup.ts`)가 **보호할 이유**다.
성공했을 때만 비우면 세 가지가 한꺼번에 정확해진다:
지운 파일은 재시도 대상에서 빠지고, 보호도 저절로 풀린다.

그래서 **`retention.ts` 옛 주석이 요구하던 「고아 청소기의 보호 목록에서 status='deleted' 제외」는 하지 않았다.**
그건 「file_url 을 남긴다」는 전제 위의 해법이고, 우리는 그 전제를 바꿨다.
청소기를 건드리면 «D1 에 있는 파일을 청소기가 지우는» 구조가 되어 책임 소재가 흐려진다.

### 4. 조회에 `status` 를 넣지 않은 이유
D1 표시 뒤 R2 삭제가 실패하면 그 행은 이미 `'deleted'` 다.
`status != 'deleted'` 로 거르면 **그 행은 영영 재시도되지 않는다.**
판정 기준은 «키가 남았는가»(`file_url`) 여야 한다.

## 버린 방법

- **지금 값 그대로 켜기** — 사장님 결정(3개월)과 어긋난다. dryRun 이 없었으면 그대로 했을 것이다.
- **R2 먼저 지우고 D1 나중** — 도중에 죽으면 「목록엔 완료인데 영상이 없는」 상태. 2026-08-26 에 실제로 났던 사고다.
- **한 번에 전부 삭제** — Worker 실행시간이 걸린다. 상한 200 + 남은 건수 보고.
- **고아 청소기에 파기를 맡기기** — 청소기는 «D1 에 없는 파일»을 지우는 도구다. 파기 책임은 `purgeExpired` 하나에 둔다.
- **옛 `status='deleted'` 1,329행을 `completed` 로 되살리기** — 되살리려면 R2 실물 확인이 필요하고(8/26 원칙:
  head() 로 본 것만 승격, 조회 실패 시 강등 금지), 이번 지시 범위 밖이라 **별건으로 남긴다**(아래).

## 함정 대조(trap-check)가 잡아낸 것 — 4건

구현을 마치고 `trap-check` 서브에이전트로 CLAUDE.md 1·2장과 한 줄씩 대조했다.
**내가 만든 결함 4건**이 나왔고 전부 고쳤다. 아래는 그 기록이다.

### ① `file_url` 이 R2 키가 아닌 행을 지우고 «지웠다»고 셌다 (데이터 손실)

그 칸은 키만 담는 칸이 아니었다 — **저장 실패 진단에도 쓰인다**:
`DEBUG:`+업로드 로그(`index.ts` `_saveDebug`) · `FATAL:`+예외 · 외부 녹화의 `https://…`.

**R2 `delete()` 는 없는 키에도 예외를 던지지 않고 성공한다.** 그래서 그런 행이 오면
「지웠다」로 세고 `file_url = NULL` 로 비워 **「왜 저장에 실패했나」의 원자료를 영구히 잃는다.**
2026-08-28 에 「저장 실패 76건이 정상 정리분에 파묻히던 것」을 고쳤는데, 그 화면의 원자료가 이 칸이다.

→ 조회를 `file_url LIKE 'rec/%'` 로 좁혔다. 못 고른 것은 «안 지우는» 쪽으로 실패한다.

**[잰 것 — 2026-09-02 운영 D1]** `rec/` 2,071건 · 빈 값 27건 · **DEBUG/FATAL/외부주소 0건**.
**[거기서 내린 판단]** 지금 반경은 0이지만 그 값을 쓰는 경로가 살아 있으므로 구조적으로 생길 수 있다.

### ② `/api/retention/run` 을 강사·지사·대리점이 실행할 수 있었다

인증 게이트는 «로그인했는가» 까지만 보고, 스코프 차단과 `TEACHER_BLOCKED_PREFIXES` 는
**`/api/admin/` 접두사에만** 걸려 이 경로에 오지 않는다.

⚠️ **이 위험은 이번 변경이 «새로» 만든 것이다** — 전에는 status 플래그만 바뀌어 되돌릴 수 있었다.
→ 핸들러 첫머리에 **두 가드를 따로** 뒀다(`isTeacher` · `isOrgScopedRole`).
⛔ `canEditOrg()` 로 막으면 안 된다 — `'none'`(내부직원·**교사**)에 true 라 강사를 못 막는다.

**`src/index.ts` 는 공동 금지구역이지만 고쳤다.** 내가 만든 보안 구멍이고, 그대로 두면
강사 계정으로 전체 녹화를 파기할 수 있다. 변경은 그 핸들러 한 곳 + import 한 줄이다.

### ③ 주석은 「dryRun 으로 먼저 확인하라」는데 부를 방법이 없었다

호출부 둘(`/api/retention/run`, 야간 cron) 다 `opts` 를 안 넘겼다.
→ `?dry_run=1` 을 그 핸들러에 이었다. **retention.ts 가 요구하는 «dryRun 선행» 을
실제로 부를 수 있는 유일한 통로**다.

### ④ 「남은 건수」가 구조적으로 0 아니면 1이었다 (그리고 하니스가 그걸 못 잡았다)

`LIMIT + 1` 을 바인딩해 `rows.length - LIMIT` 로 셌으니 언제나 최대 1이다.
1,113건이 남아도 「1건 남음」이라 말하고, **dryRun 의 건수도 200 에서 잘려** 「몇 건인지 먼저 세라」는
안전 절차 자체가 성립하지 않았다. → 별도 `COUNT(*)` 로 센다.

🪤 **하니스 ⑦이 통과한 이유가 더 중요하다** — 가짜 D1 의 `all()` 이 **LIMIT 바인딩을 무시하고**
5행을 다 돌려줬다. 그래서 그 시나리오가 한 번도 만들어지지 않았다.
CLAUDE.md 2장 「가짜 D1 이 질의문과 무관하게 늘 같은 값을 돌려주면 되돌려도 통과합니다」 그대로다.
→ 가짜 D1 이 `LIKE 'rec/%'` 와 `LIMIT` 을 **실제로 흉내내도록** 고치고, 250건으로 시나리오를 다시 짰다.

## 후속 — 7월 녹화 다시 보이게 (사장님 지시)

파기를 켜면서 만료일을 90일로 소급했더니, **만료가 아닌데 「삭제됨」으로 내려가 있는 행**이 남았다.
[잰 것 — 2026-09-02] **1,329건** (6월 423 · 7월 902 · 8월 4).

### 어떻게 했나 — 새 API 를 만들지 않았다

기존에 **단건 복원이 이미 있고 판정이 잘 되어 있었다**
(`PATCH /api/recordings/:id/status`, `api-admin.ts`) — R2 `head()` 로 실물을 «봤을 때만» 완료로
올리고, 조회 자체가 실패하면 막지 않는다(fail-open). 8/28 에 그렇게 고쳐 둔 코드다.

그래서 **화면이 그 단건 복원을 여러 번 부르게** 했다(`recRestoreExpiredBulk`, 동시 5개).

⛔ **일괄 API 를 새로 만들지 않은 이유가 둘이다**:
1. 판정이 두 벌이 되어 어긋난다 — 이 저장소가 반복해서 밟은 형태다
2. 새 경로는 관문 등록이 필요한데 그중 하나가 `src/index.ts`(**공동 금지구역**)다.
   이번 작업에서 보안 때문에 이미 한 번 건드렸으므로 더 늘리지 않았다

### 설계에서 지킨 것

- **「파일 없음」(409 `file_gone`)은 실패가 아니라 «사실»** 이다. 그대로 두고 따로 센다.
  화면도 「고장이 아니라 사실입니다」라고 적는다
- 판정은 **«성공이라고 말했는가»**(`ok === true` + 배열)로 — 404 본문에는 `ok` 칸이 없어
  `ok === false` 검사는 그냥 통과한다(2장 함정)
- 함수는 **최상위 선언**(`window.recRestoreExpiredBulk = …`) — 다른 함수 안에 넣으면
  `onclick` 에서 `ReferenceError` 인데 문자열 하니스는 통과한다
- 결과 문구는 목록 재조회 뒤에도 **남긴다**(재조회가 「완료」를 지우던 사고가 있었다)
- 버튼 CSS 는 **조상 id 접두**로 전역 인디고 알약 룰을 이긴다.
  클래스 이름을 `-btn` 으로 끝내지 않았다(`[class$="-btn"]` 규칙에 다시 걸린다)
