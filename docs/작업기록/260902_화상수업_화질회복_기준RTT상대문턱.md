## 1. 왜 했나

사장님 캡처(2026-09-02 19:20 `class-849-20260902`, 강선생님 ↔ jeong) — 「수업시간에 교사의 화면이 흐려지거나
검은색이 되는데 혹시 화면이 커서도 문제가 있어? 연결 상태가 안 좋을 때 화면을 작게 자동으로 해 주는 기능은 어때?」

### 잰 것 (D1 `vc_quality`, 그 수업 19분)

| 항목 | 값 |
|---|---|
| RTT | 양쪽 모두 360ms 기본, 1분 평균 최고 435ms |
| 손실 | 대부분 1% 미만 |
| 영상 표본이 사라진 구간 | 19:30~19:35, **교사·학생 동시에** (`novideo` 13~15/15틱) |
| 음성전용(AAO) 발동 | 0회 |

### 거기서 내린 판단 (추론 — 단계 값은 로그에 없음)

적응 루프(`vcAdaptiveQuality`)의 문턱이 절대값이었다: «손실 6% 초과 **또는 RTT 450 초과**면 한 단계 내림,
손실 1.5% 미만 **그리고 RTT 250 미만**이 32초 이어져야 한 단계 올림».
기준 RTT 가 360ms 인 회선에서는 «250 미만» 이 **한 번도 참이 될 수 없다.** 스파이크로 450 을 넘을 때마다
내려가기만 하고, 최저 단계(해상도 1/4 · 5fps · 약 96kbps)에서 굳는다. RTT 는 양쪽이 같은 값을 재므로
교사와 학생이 **동시에** 바닥으로 떨어진다 — 19:30 부터 양쪽 표본이 함께 사라진 것과 맞는다.
최저 단계에서 얼굴이 가만히 있으면 4초에 25패킷도 안 나가 기록에는 «영상 없음», 화면에는 멈춤·검은 칸.

## 2. 무엇을 바꿨나

`idx-main.js` 판정 블록 — 연결마다 기준 RTT(`pc.__qRttBase` = 본 최소값, 위로는 틱당 2%만 따라감, 상한 500)를 두고

- 내림: `rtt > max(450, 기준 + 200)`
- 올림: `rtt < max(250, 기준 + 100)`

기준이 150 미만인 회선(한국 국내)은 `max()` 때문에 옛 숫자 450/250 그대로다. 손실 문턱은 안 건드렸다.

## 3. 검토했다가 버린 것

- **화면을 자동으로 작게** — 받는 쪽 타일 크기는 P2P 인코더에 전달되지 않아 대역폭이 0바이트 줄어든다.
  흐림을 감출 뿐이고, 교사가 일부러 고른 「얼굴 크게」를 수업 중에 뒤집는다. 사장님께 이유를 드리고 이 수리부터 하기로.
- **회복 조건만 상대화하고 내림 조건은 450 그대로** — 이 회선은 1분에 한 번꼴로 450 을 넘어 `__qBadAt` 이 매번
  갱신되므로 «스파이크 후 30초» 홀드가 영영 안 풀린다. 내림도 기준 대비여야 한다(진짜 «막힘» 은 기준+200).
- **손실 문턱도 상대화** — 손실은 회선이 «나쁜» 신호라 절대값이 맞다. RTT 만 «막힘» 의 증가분이다.
- **기준 상한 없음** — 풀면 기준 RTT 1,000ms 인 회선은 1,100 까지 «막힘» 을 못 본다. 500 으로 못 박음.
- **단계 값을 `vc_quality` 에 남기기** — 서버 ALTER 까지 걸리는 별건. 이번엔 콘솔 `[vc-adapt]` 줄에 기준값만 함께 찍음.
- **`tuneReceiveLatency` 의 `rtt < 150`·AAO 의 `art > 600`** — 전자는 «정말 좋은 회선» 판정이라 360ms 회선에서
  안 켜지는 것이 맞고, 후자는 3틱 연속이라 이번 데이터에서 발동 0회. 손대지 않음.
