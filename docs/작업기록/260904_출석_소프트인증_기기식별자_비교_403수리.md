## 1. 왜 했나

2026-09-03 `cys01`·`jye46712` 화상수업 접속 진단에서 발견된 것.

`cloudflare-deploy/src/api-mango.ts` 의 출석 소프트 인증 `_attnSoftAuthOk(claimedUid, body)`(2026-07-19 도입)는
「토큰이 있으면 토큰 uid 가 claimedUid 와 같아야 통과」인데, 출석 호출부 둘(`/api/attendance/join`·`/api/attendance/checkin`)이
**`b.user_id`** 를 claimedUid 로 넘기고 있었습니다.

그런데 `public/js/mango-attendance.js` 가 보내는 `user_id` 는 계정이 아닙니다 — **기기 식별자(`u_`+난수) 또는 DO 임시번호**이고
(그 파일의 `accountUid` 주석), 계정 아이디는 **`account_uid`** 로 따로 실립니다. 로그인해서 `mango_token` 을 실은 학생은

> 토큰 uid(`jye46712`) ≠ `user_id`(`u_j4cs5c65bp`) → **항상 403 `uid_mismatch`**

통과한 것은 «토큰 없는 요청(비로그인, 그리고 계정은 있는데 토큰이 없는 로그인)» 과 «교사(관리자 세션)» 뿐이었습니다.

**[잰 것 — 2026-09-03 운영 D1]**
- `attendance.account_uid` 가 남은 계정: 전 기간 **4개**(`jeong`·`student`·`delaware`·`Lee`)
- 최근 7일 `vc_quality` 에 잡힌 로그인 학생 11명 중 출석에 `account_uid` 가 남은 사람: 관리자 `jeong` **1명**
- 그날 학생 출석 22행 중 **19행**이 이름·host·account_uid 전부 빈 행 — `/api/gaze-score` 의 «행이 없으면 만든다» 폴백이 만든 것

**[거기서 내린 판단 — 측정 아님]** 관리자 `jeong` 외 셋(`student`·`delaware`·`Lee`)은 `account_uid` 는 실리고(=`getCurrentUser` 가 있었고) 토큰은 없던 로그인(소셜 로그인·홈 통합 로그인 폴백 등)이어야 설명됩니다. 그 셋이 정확히 무엇이었는지는 D1 로 사람이 확인할 일입니다.

**[왜 아무도 몰랐나]** 함수도 조건도 «있고» 틀린 것은 «무엇과 비교하는가» 뿐이라, 「`_attnSoftAuthOk` 를 부르는가」·「`uid_mismatch` 를 돌려주는가」류 문자열 검사는 사고 상태에서도 전부 초록이었습니다. 2026-07-19 의 라이브 검증(`docs/보안_PII_감사.md` 62행 「본인토큰 200」)은 **`user_id` 칸에 계정을 넣어 보낸** 검증이었던 것으로 보입니다 **[추론 — 그 문서에 payload 가 없고, 옛 코드에서 200 이 나오려면 그럴 수밖에 없습니다]**. 7/19 당시 클라이언트(`1a1024641`)도 `user_id: state.userId`(기기·DO 번호)였음은 확인했으므로 「7/19 부터」는 성립합니다.

## 2. 무엇을 바꿨나

| 파일 | 내용 |
|---|---|
| `cloudflare-deploy/src/api-mango.ts` 헬퍼 `_attnSoftAuthOk` | 매개변수 이름을 `claimedAccountUid` 로 바꾸고, **계정 칸이 비어 있으면 통과**하는 줄을 하나 추가(옛 클라이언트·비로그인). 나머지 규칙(관리자 세션 통과 · 토큰 없으면 통과 · 검증 중 예외는 통과)은 그대로 |
| 같은 파일 `/api/attendance/join` · `/api/attendance/checkin` | 넘기는 값을 `b.user_id` / `userId` → **`b.account_uid`** |
| 같은 파일 `/api/consents` · `/api/consents/withdraw` | **그대로 `b.user_id`** — `mango-consent.js` 는 `user_id` 칸에 «계정»(`getCurrentUser` 의 uid)을 싣습니다(그 파일 83·192행). 같은 이름이지만 뜻이 다르다는 주석을 달았음 |
| 같은 파일 녹화 참가자 채우기 주석 | 「user_id 역시 mango_token 과 다르면 거부」→ account_uid 로 정정 |
| `test-harness/attendance_soft_auth_harness.mjs` (신규, 42종) | 헬퍼 본문과 **호출부 넷의 인자식**을 소스에서 중괄호 짝으로 오려 내, 가짜 `checkAdminSession`·`authUidGlobal`·body 를 물려 **실제로 돌립니다**(§4) |
| `docs/보안_PII_감사.md` 62행 | 「본인토큰 200 검증」 정정 블록 추가(코드 수정·미배포로 표시 — PR·배포 스탬프는 병합 뒤 기입) |
| `CLAUDE.md` 2장 | 함정 한 줄 추가(「본인 토큰이면 통과」 게이트가 토큰 실은 사람을 전부 403 으로 막음) |

`src/index.ts`(공동 금지구역)는 **안 건드렸습니다** — 5801행 주석 「토큰이 있는데 다른 uid 면 거부」는 consents 에 대한 서술이라 여전히 맞습니다.

**«계정 칸이 비면 통과» 의 뜻 — 정확히 적어 둡니다.** `account_uid` 칸에는 아무것도 안 적히므로 «계정 칸 위조» 는 성립하지 않습니다. 그러나 `attendance.user_id` 를 계정으로 읽는 곳이 실재합니다(`api-students.ts` 학부모 대시보드 · `api-games.ts` · `api-reports.ts` · `learning-insights.ts` 의 `attendance WHERE user_id = ?`). 토큰 보유자가 `account_uid` 를 비우고 `user_id` 에 남의 계정 문자열을 넣는 것은 막지 않는데, 그건 **익명 요청이 원래부터 할 수 있던 일**이라 7/19 가 의도적으로 남긴 한계와 같은 수준입니다(옛 게이트보다 나빠지지 않습니다 — 옛 게이트는 그 경우 403 이었지만 토큰을 빼면 똑같이 통과했습니다).

## 3. 왜 그렇게 풀었나 — 검토했다가 버린 방법

| 버린 것 | 이유 |
|---|---|
| 클라이언트(`mango-attendance.js`)가 `user_id` 에 계정을 싣게 바꾸기 | `attendance.user_id` 에 출석·발화시간·유령 청소가 이어져 있어 값의 뜻을 바꾸면 그쪽이 흔들립니다(2026-08-12 에 «새 칸만 더한다» 로 정한 이유). 서버가 «계정 칸» 을 보면 됩니다 |
| 완전 강제(토큰 없으면 403) | 7/19 도입 취지 「자격증명 없는 요청은 통과 — 결석률 100% 버그 방어」를 깹니다. 사장님 지시로 명시적으로 금지 |
| 토큰이 있는데 `account_uid` 가 비면 403 | 옛 클라이언트(캐시된 `mango-attendance.js`)가 곧바로 막힙니다. 그리고 그 요청은 토큰을 빼면 어차피 통과하므로 막아도 얻는 것이 없습니다 → 통과 |
| `user_id` 에 남의 계정을 넣는 것까지 막기 | 그러려면 `user_id` 가 «계정인지 기기인지» 를 서버가 가려야 하는데 그 칸의 뜻이 두 가지로 섞여 있습니다(위 §2). 이 사고의 범위(비교 대상)를 넘는 별건 |
| 토큰 uid 를 `account_uid` 로 «덮어써 주기»(서버가 계정을 채움) | 별건. 그리고 교사는 토큰을 안 보내므로 반쪽입니다 |
| 헬퍼를 별도 파일(순수 함수)로 빼기 | 클로저 변수(`request`·`url`·`env`)에 기대는 함수라 빼면 호출부 넷이 다 바뀝니다. 하니스가 소스에서 오려 내 돌리는 것으로 «실행 검사» 는 충분히 됩니다 |
| 문자열 하니스(「account_uid 라는 글자가 있는가」) | 이 사고의 형태가 바로 «글자는 다 있는데 비교 대상만 틀린 것» 입니다. 호출부 인자식을 평가하지 않으면 헛돕니다 |
