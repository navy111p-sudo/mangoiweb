## 1. 먼저 잰 것 — 정말로 아무것도 못 했습니다

`approval_requests.status` 는 **`pending`·`approved`·`rejected` 셋뿐**이었고,
기안자가 부를 수 있는 라우트는 **없었습니다**(`/decide` 는 결재자 전용이고 본인은 403).
즉 「올린 뒤로는 기다리는 것 말고 할 수 있는 게 없다」가 사실이었습니다.

## 2. 무엇을 만들었나

| | 무엇 | 어디까지 |
|---|---|---|
| ① **회수** | 내가 올린 대기 건을 내가 내림 | ⛔ **아무도 결재하기 «전» 에만** |
| ② **다시 올리기** | 회수한 건의 내용을 폼에 채움 | 원래 올린 날을 **이어받음** |
| ③ **취소 결재** | 승인 건을 «지우지 않고» 새 결재를 올려 승인받음 | 승인되면 원본이 `cancelled` |

## 3. 🔴 왜 「수정」을 안 만들었나

결재는 **「그때 그 내용에 도장을 찍는」 기록**입니다.
결재 중에 내용이 바뀌면 **결재자가 본 것과 승인한 것이 달라집니다.**
다단계면 더 나쁩니다 — 1단계가 승인된 뒤 금액을 고치면 그 승인이 뜻을 잃습니다.
그러면 「수정 이력」 표가 하나 더 필요해지고, 안 남기면 나중에
「내가 승인한 건 그게 아니었다」를 **가릴 방법이 없습니다.**

✅ 대신 **회수하면 그 내용을 그대로 채워** 줍니다 — 쓰는 사람에게는 수정과 같습니다.
채우는 규칙은 **`fillFormFrom` 한 곳**이고, 이미 있던 「지난번과 같이」도 그것을 씁니다
(⛔ 두 벌이면 칸을 하나 늘릴 때 한쪽만 고쳐집니다).

## 4. 🔴 왜 승인 건을 그 자리에서 안 지우나

**승인은 바깥으로 나갑니다** — 휴가는 `teacher_unavailability` 에 근무불가를 만들어
**예약을 막고**, 인사·급여는 `approval_period_locks` 로 **그 달을 잠급니다.**
되돌리려면 그사이 잡힌 수업·정산을 어떻게 할지 **사람이 정해야** 합니다.

회계에서 원장을 지우지 않고 **반대 분개를 넣는 것**과 같은 이치입니다.

`applyReversal` 이 하는 일:
- 원본을 `cancelled` 로 — ⛔ **`status='approved'` 일 때만**(두 번 안 되돌림)
- 휴가면 근무불가 해제 — ⛔ **`created_by='결재 자동반영'` 인 «우리가 만든 행» 만**
- 인사·급여면 달 잠금 해제 — ⛔ **그 결재가 건 잠금일 때만**(`request_id` 일치)
- **되돌리지 못한 것을 말합니다**(`left[]`) — 「취소했다」는 말만 남고 강사가 계속 막혀 있는 상태가 최악

## 5. 🔴 「6일째」가 초기화되면 안 됩니다

회수·재작성이 생기면 **「기다리기 지루하니 회수했다가 다시 올리기」가 지연을 지우는 길**이 됩니다.
그래서 `origin_id` 를 두고 화면이 **원래 올린 날부터** 셉니다.

⛔ 아무 건에나 붙일 수 없습니다 — 서버가 **「내 것 + 회수된 것」일 때만** 받습니다
(아니면 조용히 비웁니다. 400 을 주면 결재를 못 올리게 막는 쪽이 더 나쁩니다).
여러 번 재작성해도 **맨 처음**을 가리킵니다.

## 6. 상태를 둘 늘렸습니다 — 세는 곳이 짝입니다

⛔ **`withdrawn`·`cancelled` 를 `rejected` 로 뭉치지 않았습니다.**
「반려당함」·「내가 내림」·「승인됐다가 무효」는 서로 다른 사실이고,
그 값을 **중복 감지**와 **지출 합계**가 함께 봅니다.

함께 고친 곳: 중복 감지 SQL · `summarizeApprovals`(따로 셉니다 — `other` 에 묻으면
사람이 「합계에 왜 없지」를 설명할 수 없습니다) · `buildFindQuery` 상태 필터와 「반려함」 ·
CSV 라벨 · 화면 배지 · 홈 ETag(a6→a7).
맨 위 요약 SQL 은 `status='approved'` 라 **취소되면 저절로 빠집니다**(그게 정확합니다).

정본을 한 곳에 뒀습니다 — `STATUSES` · `countsAsSpend` · `isLive`.

## 7. 검토했다가 버린 것

| 안 한 것 | 왜 |
|---|---|
| **올라간 결재의 내용을 고치기** | 결재자가 본 것과 승인한 것이 달라집니다(3장) |
| **승인 건을 바로 `cancelled` 로** | 바깥 부작용을 사람 판단 없이 되돌리게 됩니다(4장) |
| **회수를 `rejected` 로 저장** | 중복 감지·합계가 그 값을 봅니다 |
| **1단계 승인 뒤에도 회수 허용** | 그건 회수가 아니라 **남의 결재를 지우는 것**입니다 |
| **취소 결재선을 `any` 로 낮추기** | 「올릴 땐 경영진, 없앨 땐 아무나」가 됩니다 |
| **취소 결재 금액을 음수로** | 원본이 합계에서 빠지므로 **이중 차감**됩니다 |
| **본사 직원 전원에게 취소 요청 열기** | 남의 지출을 함부로 무효화합니다(기안자·경영진만) |
| **근무불가를 조건 없이 DELETE** | 사람이 손댄 자리를 지웁니다 |
| **새 API 경로 만들기** | `/api/approval/` 밑이라 관문 셋을 안 건드립니다 |

## 8. 고치면서 밟은 것

| 무엇 | 어떻게 |

| 🪤 검사의 블록 자르기가 **`Promise<{...}>` 의 중괄호**에 걸려 서명만 잘렸습니다 | `applyReversal` 검사 6건이 **그대로 헛돌았습니다** → **줄 끝에 오는 여는 중괄호**(본문 시작)부터 셉니다 |
| 🪤 「채우는 규칙이 두 벌인가」를 **`setVal('f_title')` 개수**로 셌습니다 | 그 글자는 OCR·음성·다시 그리기·초안 복원에도 나옵니다 — **서로 다른 일**입니다 → 「지난번과 같이」가 **정본에 맡기는가**로 물었고, 그러면서 실제 중복도 없앴습니다 |
| 인라인 `onclick` 이 부르는 이름 | 이 화면 스크립트는 **닫힌 스코프**라 `window.` 에 붙여야 합니다(9/4 에 `draftSave` 로 밟은 그 함정) — 하니스가 **전수**로 대조합니다 |

## 8-2. 🔴 함정 대조가 잡은 것 — 넷은 **화면·합계가 거짓말하고 있었습니다**

| 무엇 | 잰 것 | 고침 |
|---|---|---|
| 🔴 **취소 결재가 지출 합계를 한 푼도 안 줄였습니다** | 취소 결재는 원본의 금액·항목을 그대로 복사하므로 **그 자신이 완전한 지출 행**이 됩니다. 정본을 돌려 실측(원본 500,000 승인): 취소 **대기 중** → 승인 500,000 **+ 대기 500,000**, 항목 합계 **1,000,000(2건)** · 취소 **승인 뒤** → **500,000 그대로**(원본이 빠진 자리를 취소 결재가 채움). 제 주석은 「원본이 빠지므로 부호를 안 뒤집는다」였는데 그 전제가 틀렸습니다 | 정본 **`isSpendRow`** 신설 — `reverses_id` 가 있으면 지출이 아닙니다(금액을 들고 있는 것은 **결재자가 얼마짜리를 없애는지 보라고**이지 합계에 넣으려는 것이 아닙니다). 맨 위 요약 SQL·중복 감지·이번 달 합계에도 `AND reverses_id IS NULL` |
| 🔴 **「다시 올리기」가 본문을 300자에서 조용히 잘랐습니다** | 목록은 `rowOf(…, brief)` 로 본문을 300자로 줄여 줍니다. `findLocal` 은 그 목록에서만 찾으므로 **어느 경로로 눌러도 잘린 본문**이 폼에 들어가고, 화면은 「채웠습니다」라고만 합니다 — ②가 「수정」을 대신하는 자리라 **내용이 말없이 바뀌어 다시 올라갑니다** | 서버가 **`body_truncated`** 를 말해 주고, 잘렸으면 **단건 조회로 원문을 받아 온 뒤** 채웁니다. ⛔ 못 받아 오면 **아무것도 안 채웁니다**(잘린 채 「채웠습니다」가 더 나쁩니다). 단건 조회는 목록과 **같은 `canView`** 를 씁니다 |
| 🔴 **진행바가 「대기」라고 말했습니다**(배지는 「회수됨」) | 한 카드 안에서 배지는 「회수됨」인데 그 아래 진행바는 「본사 / **대기**」. `trackHtml` 이 새 상태를 몰랐습니다 — 제 주석의 「세는 곳이 짝」 목록에 **진행바가 빠져 있었습니다** | 끝난 건의 남은 단계는 **«—»**(아무도 안 기다립니다), 「완료」 칸은 **서버가 준 상태 이름** |
| 🔴 **문서함 이름표가 거짓말하고, 회수·취소로 찾을 수가 없었습니다** | 서버 scope `'rejected'` 는 셋을 담는데 화면 라벨은 「반려」 그대로 · 상태 필터에 **선택지가 셋뿐**이라 서버는 다 받는데 **사람은 못 골랐습니다** | 라벨을 **「안 된 것 (반려·회수·취소)」** 으로, 상태 목록은 **서버가 내려주는 `D.statuses`** 로 그립니다 |

### 그 밖에 함께 고친 것

- **되돌리기 실패를 「사람이 손댔다」로 단정**했습니다 — `safe()` 가 예외를 삼키면 `null` 인데 그것도 같은 문구였습니다. 「지울 것이 없었다 / **못 읽었다**」를 갈랐습니다.
- **주간 결재 리포트** — 「승인 a · 반려 b · 대기 c」만 적어 회수·취소가 있으면 **합이 안 맞고**(a+b+c ≠ total), 회수도 `decided_at` 을 쓰므로 **기안자가 5분 만에 내린 회수가 「평균 처리 시간」에 «빠른 결재»로 섞였습니다.** 둘 다 고쳤습니다.
- **토스트가 거짓말**했습니다 — `pick()` 은 같은 분류로 폼이 열려 있으면 **닫고 돌아가는데**, 리팩터로 토스트를 caller 로 옮겨서 **폼이 닫혔는데도 「채웠습니다」**가 떴습니다. `fillFormFrom` 이 성공 여부를 돌려주게 했습니다.

### 🪤 그리고 제 검사 다섯이 헛돌고 있었습니다

- 🔴 **「남의 건에는 아무 버튼도 안 뜬다」가 헛돌았습니다** — 함정 대조가 `isMine` 을 `return true` 로 되돌려 보니 **36건 전부 통과**했습니다. 유일한 남의 건 fixture 가 `inbox`(결재함)에만 있어 `.mineacts` 가 애초에 안 그려졌기 때문입니다 → 남의 건을 **내 카드와 같은 경로**(`urgent`)에도 넣고, 「그 경로로 그려졌는가」를 **전제 검사**로 박았습니다. 이제 그 변이가 실제로 FAIL 납니다.
- 원본+취소 **짝**을 fixture 에 한 번도 안 넣어 위 회계 결함을 못 잡았습니다.
- 문구 검사 둘이 **주석 포함 원본**으로 판정해, 화면에서 지우고 주석에만 남겨도 통과했습니다.
- 「상태 목록을 손으로 안 적는가」가 **서버만** 봤습니다(화면은 손으로 적혀 있었습니다).
- ⓪ 문구는 「여섯 가지」인데 숫자는 7이었습니다.
