## 1. 먼저 잰 것 — 정말로 아무것도 못 했습니다

`approval_requests.status` 는 **`pending`·`approved`·`rejected` 셋뿐**이었고,
기안자가 부를 수 있는 라우트는 **없었습니다**(`/decide` 는 결재자 전용이고 본인은 403).
즉 「올린 뒤로는 기다리는 것 말고 할 수 있는 게 없다」가 사실이었습니다.

## 2. 무엇을 만들었나

| | 무엇 | 어디까지 |
|---|---|---|
| ① **회수** | 내가 올린 대기 건을 내가 내림 | ⛔ **아무도 결재하기 «전» 에만** |
| ② **다시 올리기** | 회수한 건의 내용을 폼에 채움 | 원래 올린 날을 **이어받음** |
| ③ **취소 결재** | 승인 건을 «지우지 않고» 새 결재를 올려 승인받음 | 승인되면 원본이 `cancelled` |

## 3. 🔴 왜 「수정」을 안 만들었나

결재는 **「그때 그 내용에 도장을 찍는」 기록**입니다.
결재 중에 내용이 바뀌면 **결재자가 본 것과 승인한 것이 달라집니다.**
다단계면 더 나쁩니다 — 1단계가 승인된 뒤 금액을 고치면 그 승인이 뜻을 잃습니다.
그러면 「수정 이력」 표가 하나 더 필요해지고, 안 남기면 나중에
「내가 승인한 건 그게 아니었다」를 **가릴 방법이 없습니다.**

✅ 대신 **회수하면 그 내용을 그대로 채워** 줍니다 — 쓰는 사람에게는 수정과 같습니다.
채우는 규칙은 **`fillFormFrom` 한 곳**이고, 이미 있던 「지난번과 같이」도 그것을 씁니다
(⛔ 두 벌이면 칸을 하나 늘릴 때 한쪽만 고쳐집니다).

## 4. 🔴 왜 승인 건을 그 자리에서 안 지우나

**승인은 바깥으로 나갑니다** — 휴가는 `teacher_unavailability` 에 근무불가를 만들어
**예약을 막고**, 인사·급여는 `approval_period_locks` 로 **그 달을 잠급니다.**
되돌리려면 그사이 잡힌 수업·정산을 어떻게 할지 **사람이 정해야** 합니다.

회계에서 원장을 지우지 않고 **반대 분개를 넣는 것**과 같은 이치입니다.

`applyReversal` 이 하는 일:
- 원본을 `cancelled` 로 — ⛔ **`status='approved'` 일 때만**(두 번 안 되돌림)
- 휴가면 근무불가 해제 — ⛔ **`created_by='결재 자동반영'` 인 «우리가 만든 행» 만**
- 인사·급여면 달 잠금 해제 — ⛔ **그 결재가 건 잠금일 때만**(`request_id` 일치)
- **되돌리지 못한 것을 말합니다**(`left[]`) — 「취소했다」는 말만 남고 강사가 계속 막혀 있는 상태가 최악

## 5. 🔴 「6일째」가 초기화되면 안 됩니다

회수·재작성이 생기면 **「기다리기 지루하니 회수했다가 다시 올리기」가 지연을 지우는 길**이 됩니다.
그래서 `origin_id` 를 두고 화면이 **원래 올린 날부터** 셉니다.

⛔ 아무 건에나 붙일 수 없습니다 — 서버가 **「내 것 + 회수된 것」일 때만** 받습니다
(아니면 조용히 비웁니다. 400 을 주면 결재를 못 올리게 막는 쪽이 더 나쁩니다).
여러 번 재작성해도 **맨 처음**을 가리킵니다.

## 6. 상태를 둘 늘렸습니다 — 세는 곳이 짝입니다

⛔ **`withdrawn`·`cancelled` 를 `rejected` 로 뭉치지 않았습니다.**
「반려당함」·「내가 내림」·「승인됐다가 무효」는 서로 다른 사실이고,
그 값을 **중복 감지**와 **지출 합계**가 함께 봅니다.

함께 고친 곳: 중복 감지 SQL · `summarizeApprovals`(따로 셉니다 — `other` 에 묻으면
사람이 「합계에 왜 없지」를 설명할 수 없습니다) · `buildFindQuery` 상태 필터와 「반려함」 ·
CSV 라벨 · 화면 배지 · 홈 ETag(a6→a7).
맨 위 요약 SQL 은 `status='approved'` 라 **취소되면 저절로 빠집니다**(그게 정확합니다).

정본을 한 곳에 뒀습니다 — `STATUSES` · `countsAsSpend` · `isLive`.

## 7. 검토했다가 버린 것

| 안 한 것 | 왜 |
|---|---|
| **올라간 결재의 내용을 고치기** | 결재자가 본 것과 승인한 것이 달라집니다(3장) |
| **승인 건을 바로 `cancelled` 로** | 바깥 부작용을 사람 판단 없이 되돌리게 됩니다(4장) |
| **회수를 `rejected` 로 저장** | 중복 감지·합계가 그 값을 봅니다 |
| **1단계 승인 뒤에도 회수 허용** | 그건 회수가 아니라 **남의 결재를 지우는 것**입니다 |
| **취소 결재선을 `any` 로 낮추기** | 「올릴 땐 경영진, 없앨 땐 아무나」가 됩니다 |
| **취소 결재 금액을 음수로** | 원본이 합계에서 빠지므로 **이중 차감**됩니다 |
| **본사 직원 전원에게 취소 요청 열기** | 남의 지출을 함부로 무효화합니다(기안자·경영진만) |
| **근무불가를 조건 없이 DELETE** | 사람이 손댄 자리를 지웁니다 |
| **새 API 경로 만들기** | `/api/approval/` 밑이라 관문 셋을 안 건드립니다 |
