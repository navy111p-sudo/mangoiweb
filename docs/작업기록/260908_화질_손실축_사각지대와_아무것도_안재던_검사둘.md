### 2-1. 손실 축 사각지대 (PR #862 → #864 에서 값 조정)

**`cloudflare-deploy/public/js/idx-main.js`** (적응 루프 판정 블록, 5086행 근처)

```js
const LOSS_MID_STEP = 2, MID_TICKS = 15;
const held = Date.now() - (pc.__qBadAt || 0) > 30000;
if (lossPct > 6 || rtt > rttDown) {           // 나쁨 → 내려감
    pc.__qGood = 0; pc.__qMid = 0; pc.__qBadAt = Date.now();
    ...
} else if (lossPct < 1.5 && (rtt === 0 || rtt < rttUp)) {   // 완전 양호 → 단계 0 까지
    pc.__qGood = ...+1; pc.__qMid = ...+1;
    if (pc.__qGood >= 8 && held && step > 0) { step--; ... }
} else if (lossPct >= 1.5) {                  // ← 여기가 사각지대였음
    pc.__qGood = 0;                           // 완전 회복은 옛대로 지움
    if (rtt === 0 || rtt < rttUp) {
        pc.__qMid = (pc.__qMid || 0) + 1;
        if (pc.__qMid >= MID_TICKS && held && step > LOSS_MID_STEP) { step--; pc.__qMid = 0; }
    } else { pc.__qMid = 0; }

```

- 내려가는 기준은 `손실 > 6%`, 올라오는 기준은 `손실 < 1.5%`
  ⟹ **그 «사이»(1.5~6%)에 꾸준히 머무는 연결은 어느 쪽에도 안 걸립니다.**
- 옛 코드의 세 번째 분기가 `__qGood` 을 **매 틱 지워서** 8틱을 영영 못 모았습니다.

  좋아도** 수업 끝까지 그대로였습니다.
- 고침은 **카운터를 둘로 나누는 것** — `__qMid`(«나쁘지 않은» 틱)로
  `LOSS_MID_STEP`(=2, ×0.35 · 해상도 1/2)까지만 **부분 회복**.

## 3. 왜 그렇게 풀었나 — 검토했다가 버린 방법

### ⓐ 회복 손실 문턱을 `1.5% → 3%` 로 올리기 — **버림**
칼금이 3% 로 옮겨갈 뿐 사각지대(3~6%)는 그대로입니다. 문턱을 옮기는 것으로는
«두 조건이 안 맞물린다» 는 구조가 안 바뀝니다.

### ⓑ `__qGood` 하나로 겸하기(애매 틱도 그 카운터를 올리기) — **버림, 실제로 FAIL 남**
처음에 그렇게 짰습니다. 그러자 **기존 ④-2 ㉢ 검사가 곧바로 빨간불**이 났습니다 —
「손실 2% 가 28초마다 오면 «조용함» 을 매번 다시 센다(=완전 회복 없음)」.
2026-09-01 진동 방어(class-1015, 「흐렸다 잠깐 좋았다 다시 흐림」)를 정면으로
되돌리는 것이었습니다. ⟹ **카운터를 둘로 나눈 이유가 이것입니다.**

### ⓒ 애매 틱을 «멈추기만»(freeze) — **버림**
#772 가 RTT 축에서 쓴 방식이라 자연스러워 보였지만, **사각지대를 못 고칩니다.**
freeze 는 «좋은 틱과 애매한 틱이 섞일 때» 만 도움이 되는데, 이 사고는 **모든 틱이
애매한** 경우라 카운터가 영영 안 모입니다.

### ⓓ 부분 회복 문턱 **8틱(32초)** — **재 보고 버림(15틱으로)**
값을 바꿔 가며 class-1015 실측 계열로 돌렸습니다:

| 부분 회복 문턱 | class-1015 계열(1분에 한 번 20~27% 스파이크) | 꾸준한 2~4% 손실 |
|---|---|---|
| (옛 코드) | 진동 16회 · 끝 4 **(고착)** | 끝 3 (고착) |
| 8틱 | 진동 **27회(+69%)** · 끝 3 | 끝 2 ✅ |
| **15틱** | 진동 **16회 — 옛 코드와 정확히 같음** | 끝 2 ✅ |

8틱은 「바닥 고착」을 「44초마다 화질 전환」으로 바꾸는 것이었고, 그게 정확히
2026-09-01 제보의 증상입니다. **15틱(60초)이면 되돌림이 0** 입니다.
과적합인지 확인하려고 스파이크 주기를 28·40·60초로 바꿔 봤고 전부 옛 코드와 동일했습니다
(80초 이상 = 진짜로 1분 넘게 조용한 회선에서만 회복이 시작됩니다).

### ⓔ 처음 사장님께 제안했던 `rtt < 250 → 420` — **이미 되어 있어서 버림**
제 첫 보고는 **일주일 묵은 작업 사본**(8/28)을 잰 것이었습니다. 최신 `main` 을 받자
그 수정이 **PR #771·#772·#835 로 이미 들어가 배포까지 끝나** 있었고,
게다가 제 제안(고정값 420)보다 나은 방식(연결별 기준 RTT 대비)이었습니다.
그대로 밀어 넣었으면 **상대 기준 로직을 덮어써서 되돌리는** 변경이 될 뻔했습니다.
→ 5장 「주의할 것」에 남깁니다.

### ⓕ 단계 0 까지 열기 — **버림(⛔)**
손실 4% 짜리 회선을 «정상» 으로 보는 것이라 **그 손실을 우리가 만듭니다.**
`LOSS_MID_STEP = 2` 에서 멈춥니다.

## 5. 남은 것 / 주의할 것

### 🔴 못 잰 것 — 이 수리가 겨냥한 인구의 크기

「손실 1.5~6% 에 꾸준히 머무는 연결이 운영에 실제로 얼마나 되는가」는
**D1 `vc_quality` 로 확인해야 하는데 이 컨테이너에 `CLOUDFLARE_API_TOKEN` 이 없어
조회가 막혔습니다.** 잰 것은 **「판정 블록을 돌린 결과」까지**입니다.

확인하려면 한 줄:
```sql
SELECT COUNT(*) 전체,
       SUM(avg_loss < 1.5)                    AS 양호,
       SUM(avg_loss >= 1.5 AND avg_loss <= 6) AS 갇힘구간,
       SUM(avg_loss > 6)                      AS 나쁨,
       SUM(avg_loss >= 1.5 AND avg_loss <= 6 AND max_loss > 15) AS 갇힘_중_스파이크형
FROM vc_quality WHERE created_at > (strftime('%s','now') - 14*86400) * 1000;
```
