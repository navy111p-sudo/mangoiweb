# B2B 대리점 AI 사용료 청구서 — 신설 (2026-09-10)

> 사장님 요청 — **"B2B 결제 시스템이 필요해. AI를 개인회원이 수강할 수도 있지만,
> 대부분은 B2B 에서 결제가 필요하거든. 다음 달 수업 진행할 인원 x 10,000원 = 총계
> 얼마인지 보여주는 페이지와 실제 그 곳에서 결제도 동작하도록 세팅해줘."**
> + "10,000원 금액은 픽스된 것은 아니야. 본사 관리자 페이지에서는 해당 대리점의
> AI 수업 수강료를 조절할 수 있어야 해."

---

## 1. 왜 새로 만들었나

기존 조사(`docs/B2B결제_현황조사_260807.md`)가 이미 확인해 둔 대로, **「학원(대리점)이
우리에게 내는」 결제 흐름은 이 저장소 코드 어디에도 없었다.** `org-settlement.ts` 는
반대 방향(본사 → 대리점 정산금 지급)이고, `card-payments-b2b`(관리자 화면)는 «통장으로
들어온 입금을 집계» 할 뿐 결제창을 여는 기능이 아니다.

## 2. 세 가지를 사람에게 직접 물었다 (추측하지 않음)

돈이 걸린 기능이라 CLAUDE.md 의 반복된 경고("측정할 수 없는 값을 그럴듯하게 채우지
말 것", "모르면 사람에게 먼저 알리세요")를 따라 세 가지를 `AskUserQuestion` 으로
직접 물었다.

| 질문 | 답 | 반영 |
|---|---|---|
| 「인원」이 «다음 달 예정 수업 회차» 인가, 「재원」 인가? | **"AI 컨텐츠 사용료는 수업의 개념이 아니야"** — 재원 학생 수 | `students_erp` 를 `class_schedules` 가 아니라 `exec-summary.ts` 의 `enrolledCond()` 로 센다 |
| 누가 결제하나? | **"대리점 담당자가 직접 로그인해서"** | `manager.html`(대리점 로그인 화면)에 결제 카드를 만듦 — 사장님이 대신 결제하는 화면은 없음 |
| 청구서를 언제·어떻게 만드나? | **"자동으로 생성하되, 생성 내역을 사람이 볼 수 있게 해주고 추가된 인원이 있으면 눌러서 추가해서도 생성할 수 있게 해줘. 자동 생성 후 학원을 퇴원한 인원이 있다면 뺄 수도 있게 해야해."** | 청구서 = 「학생별 명세」를 가진 스냅샷. 자동 생성은 **덮어쓰지 않고 더하기만**, 개별 학생 포함/제외는 화면 체크박스로 |

## 3. 설계 — 검토했다가 버린 것들

- **새 결제 파이프라인을 따로 만드는 안** → 버렸다. `api-pay.ts` 의 토스 confirm/webhook
  경로는 이미 금액 위변조 방지·멱등·문자 발송을 다 갖추고 있고, 실서비스가 지금 쓰고
  있는 코드다. 새로 만들면 그만큼 새 사고 지점이 생긴다. 대신 **주문번호 접두사
  (`MGB-<invoice_id>-...`)로만 갈래를 나눠**, `activateEnrollment()` 맨 앞에서
  `activateB2bAiInvoicePayment()` 로 위임하고 `return` — 그 아래 개인 결제 로직은
  한 글자도 안 건드렸다. `payment_orders` 의 SELECT 컬럼 목록(3곳)도 그대로.

- **`ai-billing.ts` 가 `api-pay.ts` 의 `ensurePayTable()` 을 import 하는 안** → 순환
  참조가 생긴다(`ai-billing.ts` → `api-pay.ts` → `ai-billing.ts`, 후자는
  `activateB2bAiInvoicePayment` 를 부르려면 반드시 필요). 처음엔 `await
  import('./ai-billing')` 동적 import 로 피하려 했으나, CLAUDE.md 가 명시적으로 금지한
  패턴("하니스에서 해석이 안 되는데 fail-open try/catch 가 그것을 삼켜 늘 빈 집합을
  돌려준다")이라 버렸다. 최종: `ai-billing.ts` 가 `payment_orders` 테이블을 **자기 몫만**
  `CREATE TABLE IF NOT EXISTS` + `ALTER TABLE ADD COLUMN`(멱등, 이미 있으면 조용히
  실패)으로 스스로 보장 — `enroll-ops.ts` 가 같은 표에 독립적으로 컬럼을 보태는 것과
  같은 방식. `api-pay.ts` → `ai-billing.ts` 단방향만 남았다(grep 으로 확인).

- **재원 판정을 이 파일에서 새로 짜는 안** → 버렸다. `status='정상'` 이 운영 DB 에 0건
  이라는 사고(이 저장소가 이미 겪음, `exec-summary.ts` 의 `activeCond()`/`enrolledCond()`
  가 정본)를 또 재현할 뻔했다. 그 두 함수에 `export` 를 붙여 그대로 재사용했다.

## 4. 만든 것

- **`src/ai-billing.ts`**(신설) — `/api/admin/ai-billing/*` 라우터.
  - `GET /rate`, `POST /rate`(본사만) — 대리점별 단가 조회/수정. 안 정하면 기본값(₩10,000).
  - `GET /invoice?shop_name=&month=` — 청구서(없으면 미리보기), `POST /invoice/generate` —
    생성/보강(멱등, 더하기만), `POST /invoice/item` — 학생 개별 포함/제외(draft 일 때만).
  - `GET /history` — 지난 청구서 목록.
  - `POST /invoice/checkout` — 결제 주문 생성. 금액은 **그 순간 DB 에서 다시 계산**
    (포함 인원 수 × 단가) — 클라이언트가 보낸 값은 안 믿는다.
  - `generateMonthlyAiInvoices()` — cron 진입점. 매월 1일 KST, **다음 달** 청구서를
    전 대리점에 대해 자동 생성/보강. `wrangler.toml` 의 cron 슬롯이 5/5 로 꽉 차 있어
    **새 cron 을 못 만든다** — 기존 `0 1 * * *`(KST 03:00, `getUTCDate()===1` 분기) 에
    얹었다.
  - `activateB2bAiInvoicePayment()` — 결제 확정 후 청구서를 `paid` 로 바꾸고 포함된
    학생 전원의 `enrollments` 행을 만든다. 본사 SMS 는 `sendPlainSms` 를 **`kind` 없이**
    불러 기존 음소거 기본 정책(2026-09-08 「일단 모두 꺼줘」)을 그대로 따른다 — 예외
    목록에 스스로를 추가하지 않았다.

- **`public/manager.html`** — 대리점(agency) 스코프 계정에게만 보이는 「AI usage
  invoice」카드. 조회·생성·인원 토글·결제(토스 위젯) 전부 여기서.

- **`public/admin.html`** + **`public/js/adm-ai-billing.js`**(신설) — 본사용
  「🏢 AI 사용료 관리」카드. 대리점 검색 + 단가 편집(입력칸 + 저장 버튼) + 재원 인원
  + 예상 청구액. `card-ai-billing`, CARD_POLICY `mgrOrUp`(경영진+관리자), 사이드바
  두 벌(옛 `#ph85-sidebar`·실제 렌더인 `adm-ia6.js` GROUPS) 모두에 등록.

- **라우팅 3중 등록**(`src/index.ts`) — CLAUDE.md 「새 API 추가」 함정 그대로:
  `isAdminPath` 허용목록, `TEACHER_BLOCKED_PREFIXES`(강사 차단), `isAgencyAllowedApi`
  (대리점·지사 스코프 계정 통과) 세 곳 모두.

## 5. 검증

- `node node_modules/typescript/bin/tsc --noEmit` — 통과(무출력, exit 0).
- `node test-harness/run.mjs --fast` — 처음 PASS 311 / FAIL 3, 전부 고쳐서 **PASS 314 /
  FAIL 0**(SKIP 20 은 E2E 라 그대로). 고친 것:
  1. `admin_site_structure_sync_harness` — `admin/site-structure-admin.html` 의 DATA
     에 새 항목·개수(45→46)를 안 맞췄던 것. 손으로 맞춘 게 아니라 실제 사이드바
     구조에서 다시 뽑아 넣었다.
  2. `asset_version_harness` — `adm-core.js`(CARD_POLICY 등록)·`adm-ia6.js`(GROUPS
     항목 추가)를 고치고 `?v=` 를 안 올렸던 것. 205/60 으로 올림. `adm-ai-billing.js`
     는 신규 파일이라 하니스가 스스로 `?v=1` 을 원장에 기록.
  3. `student_status_literal_harness` — `exec-summary.ts` 에 붙인 설명 주석이
     `* ` 줄머리 규칙을 안 지켜서, 그 규칙("status='정상' 0건" 을 설명하는 문장)이
     하니스의 「주석 줄 건너뛰기」(각 줄이 `//`/`*`/`/*` 로 시작해야 함) 판정을
     못 받고 **자기 자신을 코드로 오인**해 잡혔다. CLAUDE.md 가 이미 경고한
     "부정 검사가 자기 주석을 잡는다" 그대로였다 — 여기서는 `*` 줄머리 누락이 원인.
     설명을 지우지 않고 줄머리만 맞춰 고쳤다.

## 6. 아직 안 한 것 (사람이 볼 자리)

- 토스 라이브 키 전환은 별건 — 이 기능은 기존 `/api/pay/config`·`TOSS_SECRET_KEY` 를
  그대로 재사용하므로, 개인 결제가 이미 실결제라면 이 기능도 그렇다. 새로 설정할 것 없음.
- 관리자 화면에 「청구/결제 상태 전체 열람」(어느 대리점이 아직 결제 안 했는지 한눈에)은
  안 만들었다 — 지금은 `GET history` 를 대리점별로만 볼 수 있다. 필요하면 별건.
