## 2. 잰 것

### 2-1. 그날 실제로 무슨 일이 있었나

⚠️ **도착 시각은 «잰 것» 이지만, «어느 회차인가» 는 «추론» 입니다.**
GitHub API 응답에 「이 run 이 어느 cron 에서 왔나」가 실리지 않습니다.
아래는 그날 도착이 가능했던 크론 셋(00:11Z · 03:35Z · 17:05Z)과 회차 셋을
**순서대로** 맞춘 것입니다.

| run | 도착(UTC) — **잰 것** | KST | 지연 — **추론** | 결과 |
|---|---|---|---|---|
| #3148 | 04:31:17Z | 13:31 목 | 00:11Z 면 +260분 · 03:35Z 면 +56분 | 배포됨 |
| #3152 | 08:20:37Z | **17:20 목** | 03:35Z 면 **+285분** · 00:11Z 면 +489분 | 🔴 **창 «안» 이라 스스로 보류** |
| #3153 | 19:28:35Z | 04:28 금 | **+144분** (앞 크론이면 +953분이라 성립 안 함 — 이 짝은 사실상 확실) | ✅ #919 배포됨 |

⟹ **어느 짝으로 읽어도 «가장 짧게 잡아 +56분»** 이고, 순서대로 맞추면 +260 · +285 · +144 입니다.
🔴 **#3152 가 17:20 KST(창 «안»)에 도착해 스스로 보류된 것은 짝짓기와 무관하게 «잰 것» 입니다.**

`deploy.yml` 이 이미 「마지막 기회 회차가 지연을 받으면 창 «안» 에서 돈다」고
적어 둔 그 일이 **실제로 일어난 기록**입니다.

## 3. 그래서 내린 결론

**「수업 끝나고 바로」는 이 schedule 로는 구조적으로 못 합니다.**
막는 것이 둘인데 성격이 다릅니다.

1. **우리가 정한 안전 규칙** — 23:00 에 수업이 끝나도 **23:20 부터 실제 접속이 다시 시작**됩니다.
   거기에 배포를 떨어뜨리면 이 게이트가 막으려던 바로 그 사고(수업 중 DO 재시작)를
   크론이 스스로 냅니다.
2. **우리가 못 고치는 것** — GitHub schedule 이 «가장 짧게 잡아도» +56분 늦습니다.

⟹ 즉 「23:00 에 자동으로」는 **당길 수 없는 것**이고,
**사람이 누르는 것**만이 진짜 «바로» 입니다.

## 4. 한 것

### 4-1. 몰아 배포 기회를 네 번 → 여섯 번

`.github/workflows/deploy.yml` 의 `schedule` 에 **03:43 · 07:26 KST** 를 더했습니다.

- 둘 다 창(화·목 14:00~23:00) 밖
- 창 밖 수업 넷 모두와 15분 이상 떨어짐
- 크론끼리 90분 이상(가장 좁은 간격 98분)
- 창 열리기 전 마지막 기회 여유 85분

**왜 «당기기» 가 아니라 «늘리기» 인가** — 지연이 들쭉날쭉해서,
한 회차가 크게 밀려도 다음 회차가 잡습니다. 그날처럼 12:35 회차가 통째로 헛돈 경우가
바로 그 자리입니다.

### 4-2. 02:05 는 **일부러 그대로** 뒀습니다

규칙상 01:35 까지 당길 수 있지만, 야간 실접속이 01:20 까지 있어
여유가 **45분 → 15분**으로 줄어듭니다. 그 16분을 지켜 줄 «실접속 판정」(`live-class`)이
지금 **403 으로 잠들어 있어** 다른 방어가 없습니다.
30분을 벌자고 그 자리를 좁히지 않았습니다.

## 6. 진짜 «바로» 가 필요할 때 (사장님용)

**23:00 은 이미 창 밖이라 아무 우회도 필요 없습니다.** 둘 중 하나:

1. GitHub → Actions → **Deploy WebRTC Unified Platform** → **Run workflow**
   (`force_now` 는 **켜지 않아도 됩니다** — 창이 이미 닫혀 있습니다)
2. 로컬에서 `deploy.ps1` (같은 이유로 `-ForceNow` 불필요)

⚠️ 반대로 **수업 시간대에 급히 내보내야 할 때만** `force_now` 또는
커밋 메시지의 `[deploy-now]` 를 씁니다.
