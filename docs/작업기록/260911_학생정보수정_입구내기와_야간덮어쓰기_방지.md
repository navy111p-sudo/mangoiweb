## 1. 왜 했나

사장님 제보(스크린샷: 학생 목록에서 「정우영/jeong」 한 명 조회 화면) —
**「학생 목록에서 학생 정보 수정하게 해 줘. 주소, 아이디 등등 기타 정보들 수정.
학생정보 수정하는 란이 없어.」**

조사해 보니 **두 가지가 서로 다른 문제**였고, 화면보다 저장 쪽이 더 급했습니다.

### ① 「수정하는 란」은 이미 있었다 — 가는 길이 없었을 뿐

`public/admin/student.html` 의 **16개 탭 중 9번 「연락처·정보」** 에
전화 3종·카톡ID 2종·학교·학년·생년월일·가맹점·지점·**주소**·특이사항·비밀번호까지
**13칸**이 이미 있고, `PATCH /api/admin/student/:uid/contact` 로 실제 서버에 저장까지 됩니다.
목록 화면(`admin.html` 학생 목록)에서 **그 자리로 가는 버튼이 없었을 뿐**입니다.

### ② 🔴 그런데 그 저장이 «매일 밤 03:00 에» 지워지고 있었다

`students_erp` 는 카페24가 정본이라 야간 동기화가 행을 **지우고 다시 만듭니다**
(`importCafe24Students` 의 `DELETE` + `INSERT OR REPLACE`). 그 INSERT 의 컬럼 목록은

```
user_id student_id login_id username korean_name grade school status signup_date
end_date shop_name franchise hq_name points parent_phone student_phone phone
created_at updated_at
```

이고, **`address`·`birth_date`·`kakao_id`·`parent_kakao_id`·`notes`·`teacher_phone`·`password_hash`
가 없습니다.** `INSERT OR REPLACE` 는 «행을 지우고 다시 넣는» 것이라 목록에 없는 칸은 NULL 이 됩니다.

즉 **사장님이 콕 집으신 「주소」가 정확히 그 칸이었습니다.** 넣고 다음 날 열면 비어 있습니다.
회색 칸(학교·학년·전화)도 지워지진 않지만 **카페24 값으로 되돌아갑니다.**

⚠️ 이 사고는 화면에 아무 표시도 남기지 않습니다 — 저장은 «성공» 했고, 에러도 없고,
다음 날 빈칸을 본 사람은 「입력을 안 했나 보다」 라고 읽습니다.

📜 **처음 겪는 일이 아닙니다.** 2026-08-18 에 전국 학생 전화번호가 **같은 방식으로 전멸**했고,
그때 전화번호만 컬럼 목록에 넣어 살렸습니다. `cafe24-sync.ts` 주석에 그대로 적혀 있습니다 —
「누가 번호를 채워 넣어도 그날 밤 동기화가 지웠다」. **나머지 칸은 그때 안 고쳐져 계속 사라지고 있었습니다.**

### ③ 아이디는 「수정」이 아니라 「이사」

`user_id` 를 열쇠로 쓰는 표가 **50개**입니다(출결·포인트·수강·평가서·녹화·숙제·단어장·상담 등).
`jeong` 을 다른 글자로 바꾸면 그 학생의 지난 기록이 전부 주인을 잃습니다.
→ 이번 범위에서 제외하고 **잠갔습니다.**

사장님께 네 가지 화면 안을 만들어 보여 드리고(눌러 볼 수 있는 샘플), **④번 + 저장 문제 동시 수리**로 결정받았습니다.

## 2. 무엇을 바꿨나

### 저장이 남게 — `src/student-override.ts` (정본)

- **`OVERRIDE_COLS`** 신설 — 야간 동기화로부터 지켜지는 11칸:
  `student_phone parent_phone teacher_phone kakao_id parent_kakao_id school grade
   birth_date address notes password_hash`
- `ensureStudentOverrideTable()` — 운영에 이미 있는 표에 그 칸들을 ALTER 로 덧붙입니다.
  **«탐침» 을 먼저 던져** 칸이 다 있으면 ALTER 를 한 번도 안 칩니다(cold start 왕복 절약).
  `students_erp` 쪽에도 같은 칸을 함께 보강합니다.
- `applyStudentErpOverrides()` — 이름만 되돌리던 것을 **11칸까지** 확장.
  칸마다 `COALESCE` 라 «주소만 지정한 학생» 의 학교가 덩달아 덮이지 않습니다.
  ⚠️ **폴백을 뒀습니다** — 확장 UPDATE 가 실패하면(칸 하나가 없는 등) 예전 «이름만» 문장으로
  되돌아갑니다. 안 그러면 「정우영」이 하룻밤에 「jeong」으로 돌아가는 회귀가 납니다.
- **`rememberStudentOverrides()`** 신설 — 관리자가 고친 값을 지켜지는 표에 적습니다.

### 저장 API — `src/api-mango.ts` (`PATCH …/contact`)

- 저장한 칸을 `kept` 에 모아 **`rememberStudentOverrides()` 로 한 벌 더** 적습니다.
  students_erp 는 «오늘 화면에 보이게», override 는 «내일도 남게» 하는 일이라 둘 다 필요합니다.
- 정본 `user_id` 를 먼저 조회해 그 값으로 적습니다(별칭으로 적으면 아무것도 안 지켜집니다).
- UPDATE 의 WHERE 에 **`user_id = ?` 를 맨 앞에 추가** — 직접 등록 학생은 `student_id` 가
  비어 있을 수 있어 예전 조건만으로는 «에러도 없이 0행 수정» 이 될 수 있었습니다.
- 응답에 `pinned_fields` 추가.

### 목록에 입구 — `js/adm-core.js` · `admin.html` · `css/admin-inline-a.css`

- 행의 「🎓 상세」 옆에 **「✏️ 수정」** 링크 — `/admin/student?uid=…&tab=contact`.
  **`?tab=` 딥링크는 이미 있던 기능**입니다(`student.html:2729`). 새로 만든 게 아닙니다.
- 열 머리글 「상세보기」 → **「상세 · 수정」**, 열폭 80 → **148px**.
- 설계 안내에 「✏️ 수정을 누르면 바로 그 칸으로 열립니다」 한 줄.
- CSS `td.sm-actions` — **그 칸만 줄바꿈 허용**(§3-D).

### 수정 화면에 규칙 적기 — `admin/student.html`

저장 버튼 위에 안내: 지켜지는 칸 / **가맹점·지점은 예외라 되돌아간다** / 아이디는 못 바꾼다.
가맹점·지점 라벨에 ⚠️ 와 `title` 도 붙였습니다.

### 감시

- `phone_sync_harness.mjs` **E절 신설(11건)** — 진짜 TS 를 컴파일해 SQLite 로 야간 동기화를
  돌린 뒤 주소·생일·메모·카톡·비밀번호·학교·전화가 남는지 확인. 대리점이 **안** 지켜지는지도 함께.
- `admin_student_list_harness.mjs` **+13건** — ✏️ 링크·딥링크·열폭·저장 짝(override 기록).

## 3. 왜 그렇게 풀었나 — 검토했다가 버린 방법

### A. 「야간 동기화 컬럼 목록에 주소를 넣는다」 → 버림

전화번호를 살릴 때 쓴 방법이라 제일 먼저 떠오릅니다. 그런데 **카페24에 그 값이 없습니다** —
주소·생일·카톡ID·메모·비밀번호는 카페24가 아예 주지 않습니다. 목록에 넣어 봐야 `NULL` 을
넣게 되어 **똑같이 지워집니다.** 전화번호 때와 상황이 다릅니다(그건 카페24에 있었습니다).

### B. 「동기화 전에 값을 백업했다가 끝나고 되돌린다」 → 버림

`student_erp_override` 라는 «지켜지는 표» 가 **이미 같은 목적으로 존재**하고
(이름 지정·명부 숨김), 동기화 «직후» 되돌리는 호출 자리도 이미 있습니다.
새 백업 경로를 만들면 **되돌리는 코드가 두 벌**이 되고, 순서가 어긋나면 조용히 죽습니다.
그 표를 넓히는 쪽이 짧고, 이미 검증된 순서를 그대로 씁니다.

### C. 🔴 「가맹점·지점도 함께 지킨다」 → **일부러 뺐습니다**

폼에 있으니 전부 지키는 것이 일관돼 보입니다. 그런데 `shop_name`·`franchise` 는
**정산 트리(`org_nodes`)와 권한 스코프를 만드는 값**입니다. 여기서 고정하면 학생이 실제로
다른 대리점으로 옮겨가도 영영 안 따라가고 **수수료가 옛 대리점으로 갑니다.**
조직 소속의 정본은 카페24입니다(CLAUDE.md 「대리점의 지사 소속을 D1에서 고쳤는데 다음날 원복됨」).
→ 그 두 칸은 지금도 되돌아가고, **화면이 그렇다고 말해 줍니다.**
하니스가 「대리점은 지키지 않는다」를 못 박아 둬서, 나중에 무심코 넣으면 FAIL 납니다.

### D. 「열 너비만 132px 로 키워 링크 두 개를 넣는다」 → 브라우저가 잡아 고침

처음엔 `white-space:nowrap` 그대로 132px 로 넓혔습니다. 그런데 `#sm-students-table td` 에
**`overflow:hidden; text-overflow:ellipsis`** 가 걸려 있어서, 실측(1440px·`zoom:1.3`)에서
**「✏️ 수정」이 9px 잘렸습니다.** 영어("Details·Edit")는 더 깁니다.
폭을 더 키워 막으면 글꼴·언어·zoom 이 바뀔 때마다 또 넘칩니다.
→ **그 칸만 줄바꿈을 허용**(`td.sm-actions`)해 두 줄로 떨어지게 뒀습니다. 잘리는 것보다 낫습니다.

### E. 「아이디도 고칠 수 있게」 → 이번 범위 제외

사장님이 「아이디 등등」 이라고 하셨지만, 그건 필드 수정이 아니라 **50개 표를 함께 옮기는 이사**입니다.
잠그고 화면에 이유를 적었습니다. 「계정 합치기」로 별건(§5).

### F. 「목록에 편집판·팝업을 새로 만든다(②·③안)」 → 나중에

폼이 두 벌이 되면 한쪽만 고쳤을 때 «화면마다 답이 다른» 사고가 시작됩니다(CLAUDE.md 재발 함정).
이미 검증된 폼 하나로 유지하고, 「여러 명을 죽 고치고 싶다」가 실제로 나오면 그때 만듭니다.
