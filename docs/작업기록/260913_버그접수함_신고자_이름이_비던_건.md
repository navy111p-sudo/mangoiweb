## 2. 원인 — 「로그인 세션이 두 갈래」 함정 (CLAUDE.md 2장)

홈 FAB 의 `submit()` 이 신고자를 이렇게 읽습니다:

```js
var u=(window.getCurrentUser?window.getCurrentUser():null)||{};
… reporter_uid:u.uid||'', reporter_name:u.name||'' …
```

`getCurrentUser()`(`js/idx-user-session.js`)는 **`localStorage['mangoi_logged_user']`** 를 읽는데
그것은 **학생 전용 키**입니다. 교사·본사·지사는 `mangoi_admin_session` **쿠키**(+ localStorage
`mangoi_admin_session`)로 로그인하므로 그 키가 없고 → `u = {}` → 빈 문자열 → 서버가 NULL 로 저장.

서버 `POST /api/bug-report`(`api-admin.ts`) 머리말은 이렇게 적혀 있었습니다:

> 공개 — **교사에겐 admin 세션이 없어** 신원은 clientside 전달

**사실이 아닙니다.** 교사는 admin 세션이 «있습니다». 그 거짓 전제 때문에 서버는 본문 값만 믿었고,
본문은 학생 키를 읽어 늘 비어 있었습니다. 요청은 `credentials:'include'` 로 쿠키를 **이미 싣고**
있었으니 서버는 처음부터 «누가 보냈나» 를 알 수 있었습니다.

## 3. 고친 것

### 3-1. 서버 — `src/api-admin.ts` `POST /api/bug-report`
세션 쿠키로 신원을 **먼저** 채웁니다(`getAdminActor`). 규칙:

| 상황 | uid | name | role |
|---|---|---|---|
| 세션 있음 | `actor.username` | `admin_account.name` → 없으면 본문 name → 없으면 username | 강사면 `teacher`, 아니면 `admin` |
| 세션 없음(학생·비로그인) | 본문 값 | 본문 값 | 본문 값 |
| 세션 조회가 던짐 | 본문 값 | 본문 값 | 본문 값 |

- 세션이 있으면 본문에 남의 이름을 적어도 **서버 값이 이깁니다**(위조 방지).
- 조회 실패는 삼킵니다 — **신고가 막히는 쪽이 더 나쁩니다**(fail-open, 보안 게이트가 아님).
- 머리말의 거짓 전제를 정정해 적었습니다.

### 3-2. 화면 — `public/js/adm-bugreports.js` (`?v=3`)
서버 수리 «전» 에 쌓인 4건은 둘 다 NULL 이라 여전히 「-」입니다. 읽을 때 알 수 있는 데까지 보여 줍니다:
① name → ② uid → ③ `page_url` 의 `vc_name`(화상수업 입장 표시이름). ③ 은 **계정이 아니라 주소에
적힌 표기**라 «주소에서» 라고 함께 적습니다. 결과: 3·4번은 「교사 mangoi_167 · 교사 · 주소에서」,
1·2번은 그대로 「-」(주소에 아무것도 없음 — **지어내지 않습니다**).

⛔ D1 을 UPDATE 로 «채우지» 않았습니다(1-1). 그 두 건이 `mangoi_167` 인 것은 주소 표기일 뿐
로그인 계정으로 확인된 것이 아니라, 사람이 보고 판단할 일입니다.
