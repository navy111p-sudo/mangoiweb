# 녹화 목록 「표 안 필터」에 학생 이름·아이디 검색칸

- 날짜: 2026-09-14
- 지시: 사장님 「학생이름도 검색칸을 만들어줘」(표 안 필터 줄 캡처 — 「방 · 교사 글자」 칸 옆)
- 화면: 관리자 › 녹화(`#card-recording-storage`, `admin.html`) › 🔢 표 안 필터

## 1. 왜 했나 — 학생을 «보기는 하는데 찾을 자리가 없었다»

2026-09-04 에 「학생 이름」·「학생 아이디」 두 칸을 표에 넣었고, 그때 「방 · 교사 글자」 칸의 판정
(`_recPassColF`)이 **학생도 함께 보게** 넓혀져 있었습니다. 그런데 안내(placeholder)가 「방 · 교사 글자」라
아무도 그 칸에 학생 이름을 칠 생각을 못 했습니다 — 기능은 있는데 화면이 말을 안 한 상태
(CLAUDE.md 2장 「기능이 «있는데» 아무도 못 씀 — 이름표가 사실과 다름」과 같은 뿌리).

## 2. 무엇을 했나

| 자리 | 변경 |
|---|---|
| `admin.html` | 「방 · 교사 글자」 옆에 **`#recf-student`**(「학생 이름 · 아이디」) 추가. 위 서버 검색칸 `rec-q` 안내를 「방 ID / 교사·학생 이름 또는 ID」로. `adm-core.js` v=213 → **214** |
| `js/adm-core.js` v=214 | `_recColF.student` · `_recPassColF` 에 학생 칸 판정(**`r.students` 의 name/uid 만** — 교사·방 번호는 안 봄) · 바인딩 표(`ids`)·pull·reset 에 student(글자 칸 판정은 `isTxt` 하나로) |
| `src/api-mango.ts` | `/api/recordings` 검색 `q` 가 이미 있던 `EXISTS (class_schedules cs …)` 안에서 **`cs.student_name`·`cs.user_id`** 도 LIKE (바인드 7 → 9) |

학생 «전용» 칸으로 만든 이유 — 기존 칸을 「방·교사·학생」으로 안내만 바꾸면 «교사 이름을 쳤는데 같은
이름의 학생이 걸리는» 식으로 두 축이 섞입니다. 사장님 지시도 «칸을 만들어 달라» 였습니다.
두 글자 칸은 **AND** 로 겹칩니다(교사 Bella + 학생 하나 → 그 조합만).

서버 검색까지 넓힌 이유 — 표 안 필터는 «지금 불러온 쪽(50건)» 안에서만 돕니다. 학생 이름으로 «전체» 에서
찾는 것은 위 「🔍 녹화 검색」(서버) 몫인데, 그 검색은 `participant_names/ids` 만 봐서 **동의 안 한 학생**
(=`participant_ids` 에 없음)은 화면에 이름이 보이는데 검색하면 0건이었습니다. 학생 칸의 첫 근거가 예약표
(`src/recording-students.ts` — `class_schedules.user_id/student_name`)라 그 두 칸을 같은 EXISTS 안에 더했습니다.
⚠️ 이 검색은 «학생만» 이 아니라 «그 방에 적힌 것 전부» 를 봅니다(원래 그렇습니다 — 좁게 걸리는 것보다 낫습니다).

## 3. 검토했다가 버린 것

- **기존 칸 안내만 「방 · 교사 · 학생」으로 바꾸기** — 위 이유(축이 섞임). 그리고 이미 그 상태에서 «찾을 자리가
  없다» 는 제보가 온 것이므로 답이 아닙니다.
- **`cs.` 접두사 없이 학생 칸을 바깥 WHERE 에 두기** — `class_schedules` 는 EXISTS 서브쿼리 안에만 있어
  바깥에서 못 부릅니다. 서브쿼리는 원래부터 `cs.id = CAST(SUBSTR(r.room_id…))` 로 상관이고 `cs.id` 가 PK 라
  한 건 조회입니다(그 자리 주석). 새로 스캔을 만들지 않았습니다 — SQLite `EXPLAIN` 으로 형태를 확인.
- **학생 칸도 `r.started_by`(방을 먼저 켠 사람) 까지 보기** — 그 칸은 «교사» 도 «학생» 도 아닙니다(2026-09-04
  작업기록). 학생 칸은 서버가 예약·명부 완전일치로 풀어 준 `r.students` 만 믿습니다.

## 5. 변이시험에서 배운 것 (🪤)

- **첫 변이가 «헛돌았습니다»** — 학생 칸 판정에 `r.teacher` 를 섞어 넣었는데 브라우저 검사가 43/43 그대로였습니다.
  캐시 탓인 줄 알고 `Network.setCacheDisabled`+`setBypassServiceWorker` 를 넣고 「브라우저가 지금 디스크의
  `_recPassColF` 를 실행한다」 **전제 검사**까지 넣었는데도 초록 → 원인은 캐시가 아니라 **fixture 의 교사 이름이
  `r.teacher` 가 아니라 `r.started_by` 에 실린다**는 것이었습니다(그 변이는 실제 경로를 한 번도 안 지남).
  `started_by` 를 섞는 변이로 바꾸니 **2건 실제 FAIL**. 자동 하니스는 두 변이를 다 잡습니다(그쪽 행은 `teacher` 를 넣음).

## 6. 함정 대조(trap-check)가 남긴 것 — 🔴 0건 · 🟡 3건(전부 «이 변경이 만든 것이 아님», 사람 판단)

- 🟡 `api-mango.ts` 검색어 `%${qSearch}%` 에 **길이 상한이 없습니다**(D1 LIKE 패턴 50자 한도 — 2장). 49자 이상을 치면
  그 조회가 `LIKE or GLOB pattern too complex` 로 죽습니다. 이번은 같은 모양 2개를 더한 것뿐이고 사람 이름·아이디는
  그 길이를 넘을 일이 드뭅니다. ⛔ «잘라서 넣기» 는 검색 뜻을 조용히 바꾸므로 안 했습니다 — 고칠지는 별건.
- 🟡 CSV 내보내기(`/api/admin/export/recordings.csv`)는 주석에 「목록과 같은 검색 파라미터」라 적혀 있지만 실제 `q` 는
  LIKE 3개(방·teacher_name·teacher_id)뿐 — 9/1·9/4 확장 때부터 갈려 있었고 이번으로 «목록에선 학생 이름으로 찾히는데
  CSV 는 0건» 인 틈이 한 칸 더 넓어집니다. 지시 범위 밖이라 손대지 않았습니다(그 주석은 사실과 다릅니다).
- 🟡 화면 「학생 이름」 칸은 `students_erp.korean_name` 에서 오고(`recording-students.ts`), 서버 검색이 보는 것은 예약표
  `cs.student_name` + `participant_*` 라 **둘이 다른 학생**이면 화면에 보이는 이름으로 서버 검색하면 0건일 수 있습니다.
  얼마나 자주 다른지는 **D1 실측 안 함**. 표 안 필터(`recf-student`)는 화면 값 그대로 보므로 해당 없습니다.
