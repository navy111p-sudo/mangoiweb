# 📞 야간 동기화가 학생 전화번호를 덮어쓰던 것 (2026-09-15)

> 사장님 지적(화면 캡처): 「`ON CONFLICT ... DO UPDATE` 가 카페24에 있는 모든 학생의 user_id 에
> 대해 무조건 돌아가서, 파일럿테스트 학생들 번호를 넣어도 그날 밤 빈 값으로 되돌아간다.
> 그리고 안전한 통로(`setOverridePhones`)가 수강신청 등록·수정 두 곳뿐이다.」 → **「이거 처리해줘」**

---

## 1. 지적이 맞았습니다 — 코드로 확인

`cloudflare-deploy/src/cafe24-sync.ts` 의 `importCafe24Students()` 가 이랬습니다.

```sql
ON CONFLICT(user_id) DO UPDATE SET
  ..., parent_phone = excluded.parent_phone,
  student_phone = excluded.student_phone, phone = excluded.phone, ...
```

`excluded.*` 는 **카페24가 방금 보낸 값**입니다. 그런데 카페24 원본의 번호 칸은 비어 있습니다
(2026-09-10 실측: `students_erp` 29,485행의 번호 칸 네 개가 **전부 0건**).
⟹ 매일 밤 03:00 KST 에 우리가 넣은 번호가 **빈 값으로 되돌아갔습니다.**
에러가 한 줄도 안 나고 「그냥 사라진」 것처럼만 보입니다.

### 🔴 그런데 지적보다 한 겹 더 깊었습니다 — DELETE 가 먼저 돕니다

UPSERT 「위」에 DELETE 가 있습니다.

```sql
DELETE FROM students_erp WHERE created_at = CAFE24_STUDENT_SENTINEL
  AND (password_hash ...) AND (parent_user_id ...) AND (eval_band ...)
  AND (level ...) AND (textbook ...)
```

보존 목록에 **번호가 없었습니다.** 그래서 카페24 학생 행은 먼저 지워지고 새로 들어옵니다
— 그러면 UPSERT 는 `ON CONFLICT` 가 아니라 **«새 INSERT»** 가 됩니다.

> ⟹ **SET 절만 고치면 카페24 학생 29,462명 전원에게 효과가 0입니다.**
> 두 곳이 짝입니다. 이 파일이 이미 「순서가 전부다」라고 적어 둔 그 자리입니다.

## 2. 고친 것 — 세 줄기

| # | 무엇 | 왜 |
|---|---|---|
| ① | UPSERT 를 `COALESCE(NULLIF(TRIM(excluded.x), ''), students_erp.x)` 로 | 카페24가 값을 주면 갱신(정본 원칙 유지), **빈 값이면 우리 값을 지킴** |
| ② | DELETE 보존 조건에 `parent_phone`·`student_phone`·`phone` **세 줄** | ①이 발동할 수 있게 하는 짝. 없으면 효과 0 |
| ③ | 그 세 칸에 **멱등 ALTER**(DELETE 보다 «앞») | 칸이 없는 DB 에서 DELETE 가 `no such column` 으로 죽고 `nightlyCafe24Refresh` 가 삼켜 **동기화가 통째로 조용히 멈춤** |

`src/index.ts`·`public/index.html` 등 **공동 금지구역은 한 줄도 안 건드렸습니다.**

### ⛔ 버린 길

- **override 통로만 늘리기** — 지적의 두 번째 절입니다. 그런데 `students_erp` 에 번호를 넣는
  경로가 자가가입(`api-students.ts`)·레벨테스트 체험계정(`leveltest-schedule.ts`)·AI 운영비서
  (`ai-command.ts`)까지 있어, 통로를 늘려도 **그 셋은 계속 샙니다.** 뿌리(동기화)를 막으면
  어느 경로로 들어간 번호든 살아남습니다.
  ℹ️ 지적 시점 기준 「두 곳」은 지금 **네 곳**입니다(수강신청 등록·수정 + 학생 상세 연락처 탭 2곳).
- **번호 칸을 SET 목록에서 통째로 빼기** — 나중에 카페24가 번호를 채우면 그 갱신이 영영 안 옵니다.
- **`COALESCE(students_erp.x, excluded.x)`(방향 반대)** — 한 번 값이 들어가면 카페24 갱신이
  영영 안 와서 **번호가 바뀐 학생이 옛 번호로 굳습니다.**
- **D1 을 직접 UPDATE 해서 번호 되살리기** — 개발·운영이 같은 DB(1-1). 코드로 막는 것이 먼저입니다.

## 3. 맞바꾼 것 — 사람이 알아야 할 두 가지

1. **DELETE 보존을 넓힌 대가** — 카페24를 떠난 학생이라도 번호가 있으면 행이 남고 `status` 가
   옛 값에 굳습니다. `status` 로 세는 명부·정산·리포트가 그 사람을 계속 «재학» 으로 셉니다.
   오늘 반경은 0건이지만 **이 수리의 목적이 «번호를 채우는 것»** 이라 채울수록 늘어납니다.
2. **COALESCE 는 «카페24가 번호를 지운 것» 과 «원래 없는 것» 을 구별하지 못합니다.**
   번호가 바뀌어 카페24에서 빈 값이 오면 **옛 번호가 남아 틀린 번호로 학부모에게 갑니다.**
   「틀린 번호가 빈칸보다 나쁘다」는 이 저장소 원칙과 정면으로 걸리는 자리입니다 —
   카페24가 번호를 채우기 시작하면 다시 볼 것.

둘 다 주석과 `CLAUDE.md` 2장에 적어 두었습니다.

## 5. 🪤 함정 대조가 잡은 것 — 같은 PR 에서 고쳤습니다

### ⓐ 보존 조건 세 줄 중 «한 줄만» 지우면 **아무도 안 잡았습니다**

처음 fixture 의 대상 학생이 세 칸을 **전부** 갖고 있어서, 한 줄만 남아도 행이 보존됐습니다
(실측: 한 줄씩 지워도 **36/0 통과**). 그런데 실제 데이터는 **칸이 하나만 찬 행이 흔합니다** —
`createTrialStudent()` 는 `phone` **하나만** 넣고, 그게 이 수리의 동기인 `lt15`·`lt16`·`lt18`
의 모양 그 자체입니다. 자가가입은 `parent_phone`+`phone`(student_phone 없음).

⟹ 번호가 **한 칸만** 찬 학생 셋(`s7`·`s8`·`s9`)을 fixture 에 넣어 세 줄이 각각 잡히게 했습니다.

> 📌 「변이 3종 전부 FAIL」은 사실이었지만, **그 3종에 «한 줄씩» 이 없었습니다.**

### ⓑ 같은 단정이 «다섯 파일» 에 남아 거짓이 됐습니다

이 저장소가 네 번 사고를 낸 「적어 둔 것 ≠ 사실」 그 형태라 전부 정정했습니다.

| 자리 | 고친 방향 |
|---|---|
| `CLAUDE.md` 2장 | 「매일 밤 덮입니다」 → 「**2026-09-15 «전» 에는** 덮였고, 지금은 ①②로 막았다」 + 위 맞바꿈 두 가지 + 「fixture 에 한 칸짜리 학생이 필요하다」 |
| `student-override.ts` (머리말·`setOverridePhones`) | ⛔ **금지는 유지**하고 «이유» 만 사실로. 그리고 **자가가입·레벨테스트·ai-command 는 이 표에 안 쓴다**(그 번호들에게는 이번 보존이 유일한 보호막)를 덧붙임 |
| `notify-contacts.ts` · `lesson-reminder.ts` | 시제 정정(「덮으므로」 → 「덮었고, 2026-09-15 에 막았지만 카페24가 값을 주면 그쪽이 이긴다」) |
| `enroll_parent_phone_harness.mjs` | 검사는 유지하고 실패 메시지의 이유만 정정 |

### ⓒ 제 주석이 «잰 것» 보다 넓게 말했습니다

「lt15·lt16·lt18 이 번호를 잃었고 **그래서** 7일간 671건을 찾고도 0건 발송」 —
671→0 은 그 세 계정 때문이 아니라 **29,485행 전부에 번호가 없어서**입니다. 문장을 끊었습니다.

### ⓓ 하니스가 «크래시» 하고 있었습니다

`student_ai_onboarding_harness` 가 이 DELETE 문을 오려 내 돌리는데 fixture 테이블에 번호 칸이
없어 **깔끔한 FAIL 이 아니라 스택트레이스**로 죽었습니다(그 아래 검사가 통째로 사라짐).
fixture 를 넓히고 `try/catch` 로 감쌌으며, DELETE 가 못 돌았으면 그 뒤 두 검사를 **`skip`** 으로
돌립니다 — 아무도 안 지워졌기 때문에 ✅ 가 나오는 것은 「확인 안 한 것」이 「문제없음」으로
섞이는 모양입니다. ALTER 위치 검사에도 세 칸을 더했습니다.

### ⓔ 옛 검사 하나가 뜻을 잃을 뻔했습니다

짝 검사를 위해 `s1` 의 번호를 덮어썼더니, 바로 위의 「다시 동기화해도 번호가 남아 있다」가
«카페24가 덮어썼다» 를 재게 되어 새 검사와 완전히 겹쳤습니다 → 짝 검사를 **`s4`** 로 옮겨
옛 검사가 원래 재던 것을 지키게 했습니다.
