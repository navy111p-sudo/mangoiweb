## 1. 무엇이 문제였나 — 한 화면이 두 표를 각각 보고 서로 다른 말을 했다

학생 상세 화면에는 «수업» 을 보여 주는 자리가 **둘** 있습니다.

| 자리 | 무엇을 보나 | 취소된 수업은? |
|---|---|---|
| 위쪽 **주간·월간 캘린더** | **`enrollments`**(신청서) | **그대로 그림** ← 문제 |
| 아래쪽 **스케줄 목록** | `class_schedules`(실제 수업) | 서버가 이미 거름 |

캘린더는 신청서의 «매주 금요일 14:20» 을 보고 카드를 그립니다.
그런데 **실제 수업을 전부 취소해도 신청서는 `confirmed` 로 남습니다** — 두 표 사이에 배선이 없습니다.

`GET /api/admin/class-schedules` 는 `cs.status != 'cancelled'` 로 취소분을 **이미 거르고** 있어서,
같은 화면 아래쪽 목록에서는 사라지고 **캘린더에만 남았습니다.**

### D1 실측 (2026-09-21, SELECT 만)

```
enrollments 103   status=confirmed  type=체험수업  days_of_week=금  time=14:20  end_date=2026-10-11
  └ 그 신청이 만든 실제 수업 (source='adm-enroll:103')
      class_schedules 2332  2026-09-11 15:00  cancelled
      class_schedules 2333  2026-09-18 14:20  cancelled
      class_schedules 2334  2026-09-25 14:20  cancelled   ← 사장님이 X 치신 그 카드
      class_schedules 2335  2026-10-02 14:20  cancelled
```

**네 건 전부 취소인데 신청서만 살아 있었습니다.**

### 반경 — 전수로 셌습니다

신청 **14건 전부 `confirmed`** 이고, 그중 «수업이 만들어졌다가 전부 취소» 인 것은 **1건**
(= 바로 이 건)뿐이었습니다. 나머지 13건은 살아 있는 수업이 있습니다.

⟹ **저장소 전체에서 유일한 사례**라 반경은 작지만, 구조가 남아 있으면 언제든 재발합니다.

## 2. 왜 하니스가 못 잡았나

표도 값도 함수도 전부 «있습니다». 틀린 것은 **«무엇이 그려지는가»** 하나뿐이고
두 코드 다 «자기 표» 를 정직하게 그릴 뿐입니다 — 에러도 경고도 안 납니다.
수리 전에도 `--fast` 가 전부 초록이었습니다.

## 3. 고친 것

### ① 서버는 «사실» 만 준다 — `src/api-admin.ts`

`GET /api/admin/enrollments` 응답의 각 신청에 두 칸을 더했습니다.

- `class_total` — 그 신청이 만든 수업이 몇 건인가
- `class_active` — 그중 살아 있는(취소 아닌) 것이 몇 건인가

```sql
SELECT substr(source, 12) AS enr_id,
       COUNT(*) AS total_n,
       SUM(CASE WHEN status = 'cancelled' THEN 0 ELSE 1 END) AS active_n
  FROM class_schedules
 WHERE source LIKE 'adm-enroll:%'
   AND instr(?, ',' || substr(source, 12) || ',') > 0
 GROUP BY source
```

- `source` 형식이 `adm-enroll:<신청id>` 이고 `'adm-enroll:'` 이 11글자라 **`substr(...,12)`** 부터가 id.
- ⛔ **`IN` 목록을 안 만듭니다**(D1 바인드 100개 한도) — 콤마 문자열 **한 개**를 `instr` 로 봅니다.
- ⚠️ 양쪽에 콤마를 둬서 **앞자리가 겹치는 신청**(103 대 1031)이 새지 않게 했습니다.
- ⚠️ 조회가 실패하면 **칸을 안 싣습니다** → 화면이 예전대로 그립니다(fail-open).

### ② 판정은 화면 한 곳 — `public/admin/student.html`

```js
function enrCalHidden(enr) { ... }
```

- ① 신청서 자체가 끝난 것(`cancelled`·`canceled`·`rejected`·`ended`·`expired`) → 숨김
- ② **«수업이 있었는데 전부 취소»**(`total > 0 && active === 0`) → 숨김
- 그 밖에는 **전부 그대로 그립니다.**

**주간·월간 두 캘린더가 이 함수 하나를 함께 씁니다.**

## 4. 검토했다가 «버린» 방법과 그 이유

| 버린 방법 | 왜 |
|---|---|
| **D1 에서 `enrollments` 103 의 status 를 cancelled 로 UPDATE** | 개발·운영이 같은 DB 라 사람 승인 사항(CLAUDE.md 1-1). 그리고 데이터를 고쳐도 **구조가 그대로**라 다음에 또 납니다. 화면이 사실을 말하게 하는 것이 먼저입니다 |
| **캘린더에서 enrollments 카드를 통째로 없애기** | 아직 수업을 안 만든 신청(방금 확정)이 캘린더에서 사라집니다 — «되던 것» 을 깨는 방향 |
| **«수업이 0건» 도 숨기기** | 위와 같은 이유. 숨기는 것은 «있었는데 전부 취소» 뿐입니다 |
| **서버에서 아예 그 신청을 안 내려주기** | 목록·정산 등 다른 소비처가 그 신청을 못 보게 됩니다. 서버는 사실만 주고 판정은 그리는 쪽이 합니다 |
| **`status` 검사만 넣기** | 이 건은 신청서가 `confirmed` 라 그것만으로는 **안 사라집니다.** 그래서 ②가 필요합니다 |

  **새로 생긴 FAIL 0건**(363 = 362 + 새 하니스 1로 수가 정확히 맞습니다)

### 하니스가 세 번 헛돌았고, 그때마다 고쳤습니다

1. **「선언과 호출의 깊이가 같은가」로 물었더니 멀쩡한 코드가 빨간불** —
   호출은 «함수 안의 for 루프 안» 이라 깊이 2가 정상입니다.
   물어야 할 것은 **«선언 자체가 최상위인가»** 였습니다.
2. **「조회하는가」만 묻고 「응답에 싣는가」를 안 물어**, 조회는 하면서 `items` 에
   **안 싣는** 변이가 그대로 통과했습니다(= 이 사고가 그대로 재현되는데 초록불).
   → 블록을 오려 내 가짜 D1 으로 돌려 «무엇이 실렸는가» 를 답으로 묻고,
   **«다른 값을 주면 그 값이 실린다» 를 짝으로** 뒀습니다(하드코딩 방지).
3. **변이가 «크래시» 가 되어 ❌ 0건으로 위장**했습니다 —
   `instr` 조건을 지우면 `?` 가 0개가 되는데 `prepare().all(인자1개)` 가 던집니다.
   → 바인드 개수는 **돌리기 전** 에 보고, 실행은 `try` 로 감쌌습니다.

## 7. 남은 것 — 사람이 정할 일

- **`enrollments` 103 의 `status`** 는 여전히 `confirmed` 입니다.
  화면은 이제 사실을 말하지만, «신청서도 취소로 정리할지» 는 D1 쓰기라 사장님이 정하실 일입니다.
- **근본은 «수업을 전부 취소하면 신청서도 따라가게» 하는 배선**입니다.
  다만 「수업을 하나 취소한 것」과 「과정을 접은 것」은 다른 뜻이라,
  자동으로 묶으면 반대 사고(멀쩡한 신청서가 취소됨)가 납니다 — **별건**으로 남깁니다.
