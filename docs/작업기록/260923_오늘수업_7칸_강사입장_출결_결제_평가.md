## 1. 왜 했나

매니저 제안(스크린샷 — 관리자 「오늘 수업」 표의 학원 칸과 레벨·교재 칸 사이에 빨간 동그라미):
「강사·매니저의 오늘 수업에 칸을 더해 달라 — ① DATE ② INSTRUCTOR ENTRANCE TIME(강사가 제시간에 들어왔나)
③ PAYMENT TYPE(B2B/B2C) ④ Schedule ⑤ Last class evaluation/feedback ⑥ Today's feedback
⑦ Attendance(student attended/absent/late)」.
그 전에는 출석·평가·결제유형이 전부 다른 화면이라 한 줄에서 판단할 수 없었다.
이어서 사장님 지시 두 개: 「teacher.html 에도 같은 칸」(#1107), 「지사·대리점에는 평가 내용 안 보이게」(#1109).

### 판정 규칙 (정본 한 곳)
- **강사 입장**: `teacherPresenceByRoom`(no-show-truth.ts) 재사용 — 이름 일치만, role 안 믿음. 시작 +1분 초과면 «N분 지각». 기록 없음은 «입장 기록 없음»(⚠ «노쇼» 라고 부르지 않음 — 급여가 걸린 판정이라). 시작 전이면 «아직 전», 이름으로 못 가리면 «확인 불가».
- **학생 출결**: `attendance` 의 `account_uid`(계정) 또는 `user_id` 또는 이름 정확일치. 시작 +5분 초과면 지각. **누군지 못 가린 접속이 방에 있으면 «결석» 대신 «확인 불가»**. 수업 중이면 «아직 입장 안 함», 끝났고 아무도 없으면 «결석(입장 기록 없음)».
- **결제 유형**: `centers.payment_type`(대리점 지정, 학생 `shop_name` = `centers.name`) 정본. 같은 이름에 B2B·B2C 가 섞이면 모름. `students_erp.payment_type` 보조. 줄에 학원이 없으면(강사 포털) 원부 `shop_name`.
- **일정**: `student-schedule-summary.ts` 라벨(명부 「예약」 칸과 같은 값).
- **평가**: `student_evaluations`(1분 수업일지, `student_uid` 있는 행). 같은 방 번호 = 오늘, 방 번호 없는 그날 작성분도 오늘, 그 날짜 전 가장 최근 = 지난. 점수 만점은 값으로 판정(>5 이면 100점 만점).
- **카페24/LMS 줄**: 망고아이 방이 없어 강사 입장·출결은 «카페24 · 기록 없음».

## 3. 왜 그렇게 풀었나 — 검토했다가 버린 방법

- **판정을 각 화면·각 API 에 복제** — 버림. 화면 셋(관리자·매니저·강사)이 같은 수업을 다르게 말하게 된다. 서버 정본 하나, 화면은 «고르기만».
- **강사 입장을 `attendance.role='teacher'` 로 판정** — 버림. CLAUDE.md 가 금지(클라이언트가 보내는 값 + 먼저 온 학생이 강사 역할을 받는 전례). 이름 일치 정본을 재사용.
- **입장 기록 없음 = «노쇼»** — 버림. 노쇼는 급여 0원이 걸린 판정이고 `class_no_show`·`no-show-truth.ts` 가 따로 한다.
- **학생 계정을 못 붙인 접속이 있어도 «결석»** — 버림. 비로그인 입장이 실재해 틀린 결석이 된다.
- **`students_erp.payment_type` 을 주 근거로** — 버림. 실측 거의 전부 NULL(8/18 기준 29,398행 전부).
- **메인 조회(JOIN)에 payment_type 칸 추가** — 버림. 스키마 드리프트로 조인이 깨지면 스코프 걸린 요청은 폴백 없이 빈 목록이 된다. 별도 조회(`selectInChunks`)로 분리.
- **지사·대리점 평가를 화면에서만 가리기** — 버림. 응답에 글이 남는다. 서버가 조회 자체를 안 하고 `eval_hidden` 만 실음. 화면은 «—» 대신 «본사 전용»(없음과 숨김을 구분).
- **teacher.html 에 «지난 평가» 를 항상 표시** — 버림. 기존 「↩ 지난 수업」(prev_lesson)과 겹친다. 그게 있으면 생략.
