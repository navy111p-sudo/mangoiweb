# 260924 — 학원 A.i 공급가 «인원 구간» 청구 반영

## 1. 왜 했나
사장님 공급가 제안서의 5안(추천)을 기준으로 삼았다. 망고아이가 학원에 주는 A.i 학습 공급가(1인·월)는 다음과 같다.

| A.i반 인원 | 1인 단가 |
|---|---|
| 71명 이상 | 4,500원 |
| 51~70명 | 5,500원 |
| 21~50명 | 6,500원 |
| 20명 이하 | 7,500원 |

- 정책: 최소 20명분을 청구한다. 지사 커미션은 학원 공급가의 40%다.
- 기존 청구 코드(`src/ai-billing.ts`, 2026-09-10)는 **재원 전원 × 10,000원**이었다. 문제가 둘 있었다.
  - 가격이 제안서와 달랐다.
  - 화상반 학생까지 세고 있었다. 화상영어는 A.i를 포함하므로 **같은 학생을 두 번 청구**하게 된다.
- 운영에서 그 청구서가 **한 장도 생성되지 않아(표 자체가 없음)** 실제 피해는 없었다.

## 2. 사장님이 고른 것 (2026-09-24)
- **경계 역전은 «아래 구간 상한 보장»으로 막는다.** 5안을 그대로 쓰면 한 명을 더 넣을 때 청구액이 줄어든다.
  - 20명 150,000 → 21명 136,500
  - 50명 325,000 → 51명 280,500
  - 70명 385,000 → 71명 319,500
  - 그래서 «바로 아래 인원의 금액»을 바닥으로 둔다. 21~23명은 150,000원, 71~85명은 385,000원이다.
- **최소 20명분**은 그대로 적용한다.
- **범위는 «구간 단가 + 최소 청구 + 지사 커미션 40% 표시»**로 정했다. 공부방 2곳 연합 합산은 이번에 하지 않았다.
- **이중 청구 방지**는 기본으로 포함했다.

## 3. 무엇을 바꿨나
- **`src/ai-billing-price.ts` (신규)** — 가격 정본이다. D1을 안 쓰는 순수 함수다.
  - `aiPrice(count, customRate?, rule?)` 는 청구 인원, 적용 단가, 총액, 최소청구·보정 여부, 지사 커미션, 본사 몫을 돌려준다.
  - `aiPriceNote()` 는 KO/EN 설명 한 줄을 만든다. 화면은 이 글자를 그대로 그린다.
- **`src/ai-billing.ts`**
  - **A.i반 = 재원 − 화상반** (`LIVE_UIDS_SQL`). 아래 셋 중 하나라도 해당하면 화상반으로 본다.
    - ① 활성 예약 (자리표시 제외, student-track.ts와 같은 규칙)
    - ② 카페24 예약 씨앗(`c24-%`) 최근 30일 이후
    - ③ 망고아이 수업방 계정(`account_uid`) 최근 30일
  - **화상반 조회가 실패하면 아무도 청구하지 않는다.** 미리보기는 503을 돌려주고, 청구서 생성과 월 cron은 0명으로 처리한다.
  - 청구서에 **`price_rule`(JSON) 스냅샷**을 남긴다(지연 ALTER). 그래서 나중에 표를 바꿔도 이미 만든 청구서 금액은 바뀌지 않는다.
    - `rate_krw` 는 이제 «학원 예외 단가(없으면 0)»다.
    - 옛 청구서(NULL)는 `rate_krw × 인원` 그대로 계산한다.
  - 금액 정본은 `invoiceAmount()` 하나다. 미리보기, 청구서, 이력, 결제가 모두 이 함수를 쓴다.
  - `/rate` GET이 학원별로 돌려주는 값: 재원, 화상반, A.i반, 적용 단가 설명, 예상 청구액, 지사 커미션.
  - `/rate` POST에 빈 값이나 0을 보내면 예외 단가를 **해제**한다(행 삭제 → 구간 단가로 돌아감).
  - 월 cron은 화상반 목록을 **한 번만** 읽는다. 대리점마다 읽으면 376곳 × 약 0.3초가 걸린다.
- **관리자 카드** (`admin.html` · `js/adm-ai-billing.js?v=2`)
  - 열: 재원 / 화상반(포함) / A.i반(청구) / 적용 단가 / 예외 단가 / 예상 청구액 / 지사 40%
  - 화면에서 인원 × 단가를 계산하던 `aibRecalc` 는 지웠다. 저장하면 서버 값으로 다시 그린다.
- **학원 화면** (`branch.html` · `manager.html` 의 청구서 카드, 학원 계정 전용)
  - 서버 설명 한 줄, 화상반 제외 인원, 최소 청구 인원을 그린다.
  - **지사 커미션은 학원 화면에 그리지 않는다.** 본사와 지사 사이의 금액이기 때문이다.

## 4. 검토했다가 버린 것
- **보정 바닥을 «아래 모든 구간의 최대 단가 × (경계−1)»로 잡는 방식** — 51명 구간의 바닥이 50 × 7,500 = 375,000으로 부풀어 «50명 325,000 → 51명 375,000»이라는 새 계단이 생긴다. 그래서 «바로 아래 인원의 실제 금액»을 재귀로 쓰는 방식으로 바꿨다.
- **화상반을 활성 예약만으로 판정하는 방식** — 카페24 수업은 `class_schedules` 에 없어서 화상반 대부분을 놓친다. 그대로 두면 이중 청구가 그대로 남는다.
- **화상반 예약을 날짜로 좁히는 방식** — 옛 active 행이 남은 화상반 학생이 A.i반으로 넘어가 청구된다. 넓게 잡아서 «안 받는» 쪽으로 틀리게 했다.
- **화면에서 금액을 계산하는 방식** — 구간, 최소 청구, 보정이 있어서 반드시 틀린다.

## 6-1. 함정 대조(trap-check) 뒤 고친 것
- 화상반 조회를 **청구서 머리 INSERT 앞**으로 옮겼다 — 실패해도 빈 청구서가 안 남는다.
- 화상반 판정은 **대소문자를 무시**한다 — 카페24 씨앗과 명부 표기가 다르면 이중 청구가 된다. 대소문자만 다른 «다른» 계정이 빠지는 쪽은 «덜 받는» 방향이다.
- 학원 화면 캐시 키를 `aibill2` 로 바꿨다 — 조회가 실패했을 때 옛 형식(재원 × 10,000원) 캐시가 되살아나지 않게 하려는 것이다.
- 하니스의 «호출 수» 검사가 함수 선언까지 세던 것을 고쳤다(짝: 선언은 정확히 하나).
- 하니스 한 곳이 **다른 가짜 DB 를 보고 있어** 대소문자 검사가 헛돌았다. 변이시험에서 잡혀 고쳤다.

## 7. 남은 것 (사람이 정할 일)
- **이미 만든 청구서(draft)의 화상반 학생** — 청구서는 «더하기만» 하므로 한 번 들어간 학생은 나중에 화상반이 돼도 남는다. 사람이 체크를 풀 수 있다. 자동으로 뺄지는 사람이 정할 일이다.
- **예외 단가 칸에 0 입력** — 이제 «예외 해제(구간 단가)» 로 해석한다. «무료» 로 하려면 별도 방법이 필요하다.
- **결제 활성화 때 학생별 금액** — `enrollments.monthly_fee_krw` = 총액 ÷ 실제 인원이다. 최소 청구 때문에 5명이면 1인 30,000원으로 적힌다.
- **월 cron 이 화상반 조회 실패로 건너뛰면** `console.warn` 한 줄만 남는다(로그 샘플링 5%). 사람에게 알리는 경로는 없다.
- **공부방 2곳 연합 합산** — 어느 두 곳을 묶는지 정할 방법(표)이 필요하다.
- **지사 정산(`org-settlement.ts`)과의 연결** — 지금 커미션은 «표시»만 하고 정산에 자동으로 들어가지 않는다.
- **학원이 화상반 판정을 확인·수정하는 화면** (보고제안서 추천안 ①)
