# A.i 말하기 연습 — 대기 시간 줄이기 1단계: 첫 문장부터 먼저 읽기 + 대기 시간 재기 (2026-09-25)

## 1. 왜 했나
사장님: 「A.i 말하기에서 대기 시간이 너무 길어. 지금보다 절반으로 줄여 줄 수 있어?」
학생이 말을 마친 뒤 AI 목소리가 나오기까지 기다리는 시간이 길다는 제보.

## 2. 지금 기다리는 시간의 구조 (코드를 읽고 정리 — 실측 아님)
| 단계 | 하는 일 |
|---|---|
| ① 침묵 대기 | 말이 끝났다고 판단하기까지(끝난 문장 1.5초 · 덜 끝난 문장 5초 · 녹음 1.8초) — 오늘 오전 #1195 에서 이미 줄임 |
| ② AI | `/api/warmup/chat` 이 Llama 3.3 70B 로 답장+교정(JSON)을 **다 만든 뒤** 한 번에 보냄. 무너진 답이면 통째로 다시 만듦 |
| ③ 목소리 | 답장 **전체**를 `/api/voice/tts` 로 보내 **전체 소리**를 받은 뒤에야 재생 |

⚠️ 프록시가 `mangoi.ai` 를 막아 이 환경에서는 실제 초를 잴 수 없었다. 그래서 이번에 «재는 장치» 를 같이 넣었다.

## 3. 한 일
### (0) 대기 시간 재기 — `warmup.html`
- 한 턴을 네 토막으로 기록: `wait`(침묵 대기) · `finish`(인식 마무리) · `ai`(보냄→답장 도착) · `voice`(답장 도착→첫 소리).
- 콘솔에 `[warmup-lat]` 로 남기고 `window.__warmLat` 에 최근 30개.
- 주소에 **`?lat=1`** 을 붙이면 화면에 「⏱ 기다림 1.5초 · 마무리 0.3초 · AI 2.0초 · 목소리 0.6초 → 합계 4.4초」 한 줄.
- 녹음(Whisper) 경로는 침묵 시각을 몰라 `wait`·`finish`·`total` 을 «—» 로 적는다(지어내지 않음).
- ⚠️ 서버(`src/index.ts`, 공동 금지구역)는 안 건드렸다 — 그래서 `ai` 는 «서버 계산 + 회선» 합계다.

### (1) 첫 문장부터 먼저 읽기 — `warmup.html`
- 답장을 «첫 문장(20자 미만이면 다음 문장까지)» 과 «나머지» **두 조각**으로 나누고, 두 TTS 요청을 **동시에** 보낸다. 첫 조각이 오는 대로 읽고, 읽는 동안 나머지가 도착한다.
- 한 조각뿐이면 예전 경로 그대로(`_ttsSpeak`).
- 조각마다 기존 규칙 유지: 재시도·기기 목소리 폴백·«남의 목소리는 캐시 안 함»·중국어 남자 굵게 굽기·배속.
- `_stopSpeak()`(끼어들기·새 턴)이 번호를 올리면 남은 조각은 스스로 물러난다.
- 끄기(비교 측정용): **`?chunk=0`** 또는 localStorage `mangoi_warm_chunk='0'`.

### (2) 함정 대조 검사 뒤 고친 것 (같은 날)
- `play0` 의 끝맺음(`fin`)이 onerror·play().catch 로 **두 번** 불리면 둘째 조각이 두 번 재생되고 done 이 두 번 되던 것 → «한 번만».
- 조각 모드에서 자동재생이 막히면 다음 조각으로 넘어가 사람이 탭한 순간 **뒷문장만** 재생되던 것 → 거기서 끝내고 unlockAudio 가 답장 전체를 다시 읽게.
- 오디오 생성 자체가 실패하면 기기 목소리가 «답장 전체» 를 읽으며 다음 조각과 겹치던 것 → «그 조각» 만 읽게(`say`).
- **중국어 남자(Azure)는 나누지 않음** — Azure 는 IP 하루 호출 «횟수» 상한이라 두 배로 닳고, 걸리면 한 답장 안에서 목소리 질감이 갈린다.
- 재기: 다시 듣기(btn)·소리 꺼짐 차례는 재지 않고, 15초 넘게 늦은 재생(탭해서 다시 읽음)은 버린다. 타이핑 오판을 줄이려 침묵→전송 창을 4초 → 2.5초.
- ⚠️ 남은 것: 끼어들면 둘째 조각 요청은 취소되지 않고 서버까지 간다(비용·경미). 영어도 서버가 한 조각만 대체 화자로 주면 그 답장 안에서 목소리가 한 번 바뀔 수 있다(드묾 · 캐시는 안 함). TTS 호출 수는 턴당 최대 2배.

## 4. 검토했다가 이번에 안 한 것
- **문장마다 잘게 나누기** — 요청이 늘고 조각 사이 틈이 늘어 뚝뚝 끊겨 들린다. 두 조각으로 제한.
- **교정 카드를 답장 뒤로 미루기(제안 2번)** — 교정은 답장과 «같은 한 번의 AI 호출»(JSON)에서 나온다. 떼려면 AI 를 두 번 불러야 해 비용이 늘고, 교정이 있을 때만 출력 토큰이 늘어 이득이 작다. 측정값을 본 뒤 결정.
- **스트리밍(제안 3번)** — `src/index.ts`(공동 금지구역)의 응답 구조와 재시도·검증 안전장치를 다시 짜야 한다. 측정값을 본 뒤 별건.
- **침묵 대기 더 줄이기** — 2026-07-23 «아이가 쉬는 사이 끊겨 보내짐» 사고 때문에 안 줄임.

## 5. 확인한 방법
- 새 하니스 `test-harness/warmup_first_sentence_tts_harness.mjs` — 64종. 함수를 오려 내 가짜 부품으로 실제로 돌림(나누기·동시 요청·순서·끊김·실패 폴백·대체 목소리 캐시·배선·재기). 변이 16종 전부 실제 FAIL(«기다리는 도중 끊김» 순서·play0 실패 경로·캐시 적중 시 재요청·조건 씌우기·미리 받기 가드 제거 포함 — 함정 대조가 «헛돈다» 고 지적한 곳을 채움).
- 기존 하니스 두 곳(`azure_tts_zh`·`warmup_zh_lang`)이 `play0(u, false)` 라는 «식 모양» 을 글자로 못 박고 있어, 셋째 인자(onEnd)를 더하자 거짓 FAIL → «false 까지» 로 묻도록 고침(뜻은 같음). warmup.html 을 읽는 하니스 25개 전후 결과 동일.
- 로컬 서버 + 크로미움: TTS 응답 시간이 글자 수에 비례한다고 가정한 스텁으로 쟀더니 두 요청이 같은 순간(14ms)에 나갔고, 두 조각이 모두 재생됐으며, `voice` 가 1,915ms(`?chunk=0`) → 576ms 로 줄었다. ⚠️ 실제 Aura 서버의 응답 시간이 글자 수에 얼마나 비례하는지는 **못 쟀다** — 배포 뒤 `?lat=1` 로 사람이 확인해야 한다.

## 6. 다음
배포 뒤 폰에서 `mangoi.ai/warmup.html?lat=1` 로 몇 턴 말해 보고, `?lat=1&chunk=0` 과 합계를 비교. `ai` 토막이 가장 크면 2단계(스트리밍)로 간다.
