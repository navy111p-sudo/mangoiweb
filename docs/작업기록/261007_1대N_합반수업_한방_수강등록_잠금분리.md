# 1:N 합반 수업 — 한 수업 한 방 · 수강등록 합류 · 강사 시간 잠금 분리 (2026-10-07)

## 1. 왜 했나
사장님 지시: 「1대N 수업 테스트 여러 번 해서 문제없게 — ① 학생 동시 입장 ② 수강등록 ③ 교사 1명 + 학생 여러 명 수업 ④ 기타」.
재 보니 1:N 은 «화면에서 고를 수만» 있고 실제로는 성립하지 않았습니다.

| 잰 것 | 결과 |
|---|---|
| 방 번호 | `class-{예약id}-{날짜}` 라 같은 강사·같은 시각이라도 **학생마다 다른 방** → 서로 못 만남 |
| 수강등록 | 운영 D1 에 `uq_sched_teacher_slot(teacher_id, scheduled_date, start_time)` UNIQUE 인덱스가 있어 둘째 학생부터 `INSERT OR IGNORE` 로 **조용히 버려짐** |
| 화상방 정원 | DO `MAX_USERS = 10` → 강사 1 + 학생 9 가 상한 |

## 2. 무엇을 바꿨나
- **한 수업 한 방** — 정본 `src/group-room.ts`. 같은 강사·같은 날·같은 시작·같은 길이 = 한 반, 방 번호는 그 반의 **가장 작은 예약 id**. 1:1 은 방 번호가 그대로(자기 id 가 곧 최소). 조회 실패는 옛 방으로(fail-open).
  - 쓰는 곳: 학생 `sessions/today` · 강사 포털 · `verify-room` · SFU 허용 · 녹화 참가자 · 결석 감지(학생마다 따로 판정) · 급여(강사 노쇼는 반 전체 행에) · 오늘 수업 · 지금 수업.
- **잠금 분리** — `ensureTeacherSlotIndexes()`(enroll-ops.ts): 칸 `group_seat` 추가 → 새 인덱스 둘(1:1 잠금 `…_1to1` = `group_seat` 아닌 행만 · 합반 자리 `uq_sched_group_seat` = 강사·날짜·시각·학생) 을 **먼저 만들고, 둘 다 성공했을 때만** 옛 인덱스를 DROP. 행은 하나도 안 지웁니다. 실패하면 옛 잠금 그대로(= 예전과 같음).
- **수강등록 합류** — 1:N 신청(class_size 2 이상)은 `group_seat=1` 로 넣고, 같은 시각에 열려 있는 같은 반을 찾아 합류(정원 = 그 반의 가장 작은 N, 절대 상한 9). 1:1 행이 있는 강사는 후보에서 빠짐.

### 사장님 지시와 다르게 한 점
지시는 「잠금 교체」였는데, 옛 인덱스를 «통째로» 없애면 **1:1 수업 이중배정을 막던 유일한 DB 잠금**(수업 나누기·주간 연기가 이것에 기댐)이 사라집니다. 그래서 1:1 잠금은 그대로 두고 **합반 자리(group_seat=1)만 예외**로 뺐습니다.

## 3. 검토했다가 버린 것
- 방 번호를 «첫 등록 학생 id» 로 고정 저장 — 첫 학생이 취소하면 방이 바뀜. 매번 «활성 행 중 최소 id» 로 계산.
- 인덱스를 그냥 DROP — 위 이유.
- 결제 경로(자동결제 활성화)까지 합반 — 금액·회차 축이 달라 별건(지금은 1:1 그대로).

## 5. 사람이 정할 일 / 남은 것
- 급여: 합반은 **학생 행마다** 수업료가 잡힘(지금 규칙 그대로). 반당 1회로 볼지 결정 필요.
- 강사 화면: 합반이 학생 수만큼 줄로 보임(같은 방으로 들어감).
- 결제(자동결제) 경로는 1:1 로만 만듦.
- 다른 흐름(수업 이동 등)이 1:1 수업을 합반 시각으로 옮기는 것은 DB 가 막지 않음(화면·서버 충돌 검사가 판단).
- 알림·수업 정보의 학생 이름은 반의 대표(최소 id) 학생.
- 배포 시 운영 D1 의 옛 인덱스가 코드로 DROP 됩니다(새 인덱스 생성 성공 시에만).
