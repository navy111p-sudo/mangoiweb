# 이탈 위험 스캔 — «아무 500명» 대신 «기록 있는 학생», 출석은 계정 기준 (2026-10-13)

## 1. 왜 했나
사장님 「이탈 화면이 여러 개로 분산」 → 이탈 케어 보드 제안서(5단계) 중 **1단계 «숫자 바로잡기»**.
`GET /api/admin/retention/risk`(AI 이탈 위험 자동 분석) 에 결함이 둘 있었습니다(코드 읽기로 확인).

1. 명부에서 **정렬 없는 `LIMIT 500`** — 활성 학생이 500명을 넘으면 «아무 500명» 만 봤고, 화면은 그 사실을 말하지 않았습니다.
2. 출석 신호 4종·연속결석을 **`attendance.user_id IN (계정)`** 으로 셌습니다. user_id 는 «기기 임시번호» 라 실제 화상수업 접속(account_uid 에만 계정)이 안 잡혔고, 카페24 씨앗(user_id=계정)만 잡혔습니다 (CLAUDE.md 2장 「학생 상세 출결이 통째로 0」과 같은 뿌리).

## 2. 고친 것
- 정본 `src/attendance-uid.ts` 에 목록판 추가: `ATTENDANCE_BY_UID_LIST`(json_each 바인드 2개 — D1 100개 한도 무관) · `ATTENDANCE_ACCOUNT_KEY` · `attUidListBinds`.
- 후보 = «최근 90일 학생 출석 기록이 있는 계정» ∪ `student_retention`(만료 목록), 그중 활성·스코프 안. 오래 안 온 순 → 아이디 순 결정론 정렬, 상한 1000(`RISK_SCAN_MAX`), 넘으면 `truncated`.
- 출석 4신호·연속결석을 계정 기준으로. 미래 예약 씨앗(joined_at 미래)은 안 셈.
- 기록 없을 때 「999일 전」 대신 「출석 기록 없음」.
- 응답 `scan`(활성 수·후보 수·본 수·잘림) → 화면이 «누구를 봤는지» 한 줄로 말함(한/영). 캐시 키 `retrisk3`.

## 3. 검토했다가 버린 것
- **명부 전체를 다 점수 매기기** — 29,000명 × 질의 여러 개. 90일 기록이 없으면 출석 신호가 어차피 「안 옴」 하나라 이 화면의 목적(조기 경보)과 다릅니다.
- **lastJoin·연속결석에 90일 하한 걸기** — S1·S2 점수(+25 「최근 30일 출석 0회」는 `daysSinceLastJoin<999` 조건)가 만료 목록 학생에서 바뀝니다. 대신 성능을 쟀습니다: 로컬 SQLite `EXPLAIN QUERY PLAN` = **MULTI-INDEX OR**(account·user 인덱스 각각), 풀스캔 아님. ⚠️ 운영 D1 은 미측정(이번 세션 D1 조회 401).

## 4. 사람이 정할 일
- **좁아진 범위**: 예전엔 출석 0건인 신규 활성 학생이 「출석 기록 없음 +45」로 떴는데, 이제 만료 목록에 없으면 안 뜹니다. 화면은 그 사실을 말합니다.
- **장기 결석생 화면과의 차이**: long-absent 는 여전히 `a.user_id` 로 묶고 기간 하한이 있어 같은 학생의 연속결석 숫자가 다를 수 있습니다.
- 「심각+주의+관찰 486」 등 숫자가 어떻게 바뀌는지는 배포 뒤 화면으로 확인(운영 D1 미측정).
