# 몰아 배포 «새벽 2시 회차» — 100건 전수 실측과 「어느 회차가 깨웠나」 기록

- 작업자: 클로드 (사장님 지시)
- 브랜치: `claude/deployment-class-issue-otvyha`

## 1. 왜 했나

사장님 「**새벽 2시 회차가 안 뜨는 것도 고쳐줘**」.

배경 — 2026-09-01 부터 화·목 수업 시간대(현재 12:00~15:00 KST)에는 배포를 보류하고,
보류된 커밋은 `deploy.yml` 의 `schedule` 다섯 회차가 창 밖에 몰아서 내보냅니다.
그 첫 회차가 `5 17 * * *`(17:05 UTC = **02:05 KST**)인데, 실행 목록에 그 시각 실행이
보이지 않았습니다.

## 2. 무엇을 쟀나 (잰 것 — 추론과 줄을 나눕니다)

**[잰 것]** `deploy.yml` 의 `event=schedule` 실행 **100건 전수**(2026-09-27 ~ 10-16, KST 20일).
`mcp__github__actions_list` 응답을 파일로 받아 파싱.

**[추론 — 도착 «순서» 로 회차를 짝지은 것]** REST 응답에 크론이 **한 글자도 없어서**

### 결론 두 가지

1. **회차는 하나도 안 빠집니다.** 「안 뜬다」가 아니라 **GitHub 가 2~6.5시간 늦게 깨웁니다.**
   크론 시각은 «GitHub 에게 부탁하는 시각» 이고 «도착 시각» 이 아닙니다.
   ⟹ 「새벽 2시에 나간다」는 한 번도 참이 아니었습니다.

2. **「창이 열리기 전 마지막 기회」(09:11 회차)는 이름만 그렇습니다.**
   도착이 12:04~15:41 로 **20일 중 20일 전부** 11:20 이후였고, 화·목에는 창 «안» 으로
   들어와 **스스로 보류돼 버려졌습니다** — 09-29 14:36 · 10-01 14:41 · 10-08 14:53 ·
   10-13 12:04 · 10-15 13:26 (run `38681494683` 은 Deploy step 이 `skipped` 인 것을 확인).
   ⚠️ 그래도 보류된 커밋이 하루 묶이지는 않습니다 — 화·목에도 도착 04:35~11:20 의
   네 번이 창 밖이라 다음 날 아침에는 반드시 나갑니다.

## 3. 무엇을 바꿨나

### (1) 「어느 회차가 깨웠나」를 실행에 남깁니다 — `.github/workflows/deploy.yml`

- `수업 시간대 배포 보류 판정` step: `SCHEDULE_CRON: ${{ github.event.schedule }}` 를
  **env 로** 넘기고 `echo` 로 로그에 남김.
- `Deploy summary` step: 같은 값을 요약에 한 줄(`⏱ 몰아 배포 회차: …`) — **로그를 열지 않고** 보이게.
  그리고 그 실행이 «몰아 배포 회차 자신» 인데 보류됐으면
  「⚠️ 이 실행이 몰아 배포 회차 자신입니다 … 아무것도 내보내지 못했습니다」를 함께 적습니다.

⛔ `run:` 안에서 `${{ }}` 로 펼치지 않습니다(커밋 메시지와 같은 셸 주입 이유) — env 로만.
⛔ 시각을 숫자로 적지 않습니다. GitHub 가 주는 크론 식을 **그대로** 옮깁니다(정본은 `schedule` 목록 하나).

### (2) 거짓이 된 주석 두 곳을 실측으로 고쳤습니다 — 같은 파일

- `5 17 * * *` 주석에 「이 시각은 부탁하는 시각이고 도착 시각이 아니다」 + 위 숫자.
- `11 0 * * *` 주석의 「창이 «열리기» 전 마지막 기회(창까지 169분)」 — **도착 기준으로는
  한 번도 참이 아니었다**는 사실과 버려진 다섯 날짜를 적었습니다.

### (3) 되돌리기 방지 — `test-harness/deploy_class_window_harness.mjs` ⑪절 (6건)

- 판정 step 에 `github.event.schedule` 이 **env 로** 넘어가는가
- 판정 step 이 그 값을 **쓰는가**(로그)
- 배포 요약도 그 값을 쓰는가
- **짝** — `schedule` 이 아니면 그 줄을 안 넣는가(`-n "$SCHEDULE_CRON"` 가드 «안» 인지 줄 단위로)
- 크론 값을 `run:` 안에서 펼치지 않는가

### (4) CLAUDE.md 2장 — 그 행에 100건 실측을 덧붙였습니다

기존 숫자(「+56~286분, 표본 6개」)는 지우지 않고 **그 아래에 전수 실측**을 더했습니다.
그 행이 스스로 「표본이 6개뿐이라 …」라고 적어 둔 자리입니다.

## 4. 왜 그렇게 풀었나 — 검토했다가 버린 방법

| 버린 방법 | 왜 |
|---|---|
| **크론을 앞으로 당겨 02시에 «도착» 하게** | 최소 지연이 **123분**이라 22시대로 당기면 도착이 **00:23** 까지 내려와 야간 실접속(23:20~01:20) 한복판입니다. 고치려던 사고(수업 중 끊김)를 직접 일으킵니다. |
| **창이 닫힌 직후(16:20 류)에 회차 추가** | CLAUDE.md·`deploy.yml` 주석이 **이미 해 보고 되돌린** 기록입니다 — 지연이 착지시키는 곳이 17~21시이고 그 시간대가 화·목 실접속 피크(17시 28 · 19시 62 · 21시 142)입니다. 「지연되면 스스로 보류」(손해=늦음)가 「지연되면 피크에 그대로 나감」(손해=수업 끊김)으로 **위험의 종류가 나쁜 쪽으로 맞바뀝니다.** |
| **보류된 실행이 창이 닫힐 때까지 `sleep`** | 같은 이유. 그리고 Actions 분을 그만큼 태웁니다. |
| **`run-name:` 으로 크론을 실행 제목에 넣기**(REST 응답에 보이게) | `run-name` 은 조건부로 «추가» 할 수 없는 단일 식이라, 넣으면 **push 실행의 제목(커밋 메시지)까지 갈아치웁니다.** 실행 목록 가독성을 잃는 대가가 측정 편의보다 큽니다. 그래서 로그 + 요약으로 두었습니다. |
| **`live-class` 실접속 판정 깨우기**(지금 `http-403`) | 그것은 **일부러** 잠들어 있습니다 — 깨우면 수·금·월에도 보류가 시작되어 사장님이 정한 «화·목만» 정책을 벗어납니다(CLAUDE.md 2장). |
| **바깥 트리거**(Cloudflare Worker cron → `workflow_dispatch` + PAT) | 지연 자체를 피하는 유일한 길이지만 **새 GitHub PAT 시크릿**이 필요하고 `wrangler.toml` 이 **공동 금지구역**이며 Cloudflare cron 칸이 **5/5** 입니다 → **사람이 정할 일**로 남겼습니다. |
