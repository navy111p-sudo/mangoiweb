## 1. 왜 이 범위인가

전체 정리 요청을 버그 패치만으로 끝내지 않고, 책임이 섞인 순수 생성기를 행동 보존 방식으로 정리했다. 큰 API/화상수업/AI 말하기 진행 영역을 동시에 추출하면 다른 작업 및 운영 정책과 충돌하므로 이번에는 제외했다.

`xlsx.ts`에는 ZIP 바이너리 오프셋/CRC, 워크시트 셀/서식/이름, 워크북 패키지 조립, HTTP 응답이 함께 있었다. 현재 호출부는 `accounting-reports.ts`의 내보내기 helper다. **회계 계산·쿼리·권한·라우트는 변경하지 않고** 순수 출력 계층만 분리했다.

이는 알고리즘 복잡도를 줄이거나 줄 수를 무조건 줄인 변경은 아니다. 전체 운영 코드 합계는 import/export 경계 때문에 4줄 늘었지만, workbook 진입부가 바이너리 기록 세부 상태와 셀 렌더링 분기를 소유하지 않게 됐다. 이름만 바꾼 복제본을 만들지 않았다. 각 구현은 한 곳에만 있다.

정확한 baseline xlsx.ts는 293줄이다. 작업 중 짧은 진행 메시지에서 언급한 295줄 대신 git blob 기반 `structure-comparison.json` 수치를 정본으로 삼는다.

## 3. 행동 보존을 어떻게 입증했나

분리 전 고정 시계로 165개 입력의 생성 바이트 SHA-256 및 응답 헤더를 기록했다. 빈 시트, null 기본값, 중복/긴/금지문자 시트명, 한·중·일·이모지·XML 특수문자, 정수·소수·0·NaN/Infinity, 빈 셀, Z 이후 열, 열 너비 상한과 고정 seed 생성 입력 160종을 포함한다.

`xlsx_serialization_harness.mjs`는 현재 실제 모듈 그래프를 esbuild로 번들해 실행한다. 참조 해시는 1차 SHA의 원본 소스에서 만든 fixture이며, 새 구현이 자기 결과를 정상값으로 자동 덮어쓰는 기능은 없다. 원본과 수정본 각각 **344 PASS / 0 FAIL**이다. 입력 불변 비교는 structuredClone/deepEqual로 NaN·undefined도 보존한다.

추가로 작성기 helper를 사용하지 않는 central-directory 읽기로 ZIP entry/offset/셀 타입/XML escape/서식/응답을 확인한다. 함수를 옮기며 스타일·타임스탬프 정책을 바꾸지 않았다. 이 검사는 Excel 앱의 실사용 검사를 대체하지 않으며, 기존 생성기의 모든 한계까지 고쳤다는 뜻이 아니다.

## 4. 독립 리뷰에서 확인한 기존 검증 공백과 보완

### 테스트용 네트워크 보호기

1차 `offline-tests.cjs`는 direct Socket.connect는 보았지만 `net.createConnection`이 전달하는 `[options, callback]` 정규화 배열을 놓칠 수 있었다. 실제 외부 API 호출이 발생했다는 증거는 아니지만 **전면 차단 주장의 근거가 부족했다**.

재사용 가능한 `test-harness/support/offline-network.cjs`와 무연결 `offline-network.test.cjs`를 추가했다. 2차 보호기는 배열을 해석하고, 지원하지 않는 형태·외부 host·사용자 지정 DNS lookup을 거부한다. 검증에서는 **원래 connect와 fetch부터 stub으로 바꾼 다음** 보호기를 로드한다. 실제 외부 연결이나 DNS를 시도하지 않고 direct overload/정규화 배열/net.createConnection/net.connect/IPv4·IPv6/기본 host/로컬 pipe/fetch 문자열·URL·Request 28개를 확인했다.

적용 범위는 Node의 통상적인 global fetch 및 net.Socket TCP 경로다. native 자식 프로그램·UDP·hook 재정의·preload가 없는 worker/process까지 막는 OS 샌드박스가 아니다. localhost도 테스트 환경의 정상 로컬 해석을 전제로 한다. Chromium은 별도 route 및 폐쇄 proxy를 사용했고 2차에는 QUIC도 비활성화했다. `npm_config_offline=true`로 게이트 중 npx의 원격 설치도 막았다.

정적 literal/identifier 감사 결과 root 하니스에서 native shell 네트워크 명령 후보 0, dgram import 0, npx/esbuild 후보 9개였고 라이브 opt-in MANGO_BASE/BASE_URL은 설정하지 않았다. 이는 완전한 동적 호출 그래프/커널 egress 증명이 아니다. 세부 후보는 network-path-audit.json에 있다.

### 회귀 러너

1차에서 남겼던 기존 공백을 별도 커밋으로 보완했다.

- `PASS 5 / FAIL 1`을 exit 0만 보고 PASS로 읽던 경로.
- 실제 실패 줄 뒤에 상세 26줄이 붙으면 마지막 25줄 밖이라 놓치던 경로.
- 주석·문자열 속 import 예문을 실제 브라우저 의존성으로 오인하던 경로.
- `PASS 5 FAIL 0`의 passing count 5를 `5 FAIL`로 읽는 기존 오인.

출력 판정은 `runner-result.mjs`의 순수 함수, 의존성 구문 판정은 `runner-source.mjs`로 분리했다. 이미 CI 타입 검사에 필요한 TypeScript parser를 사용하며 없으면 정규식 fallback으로 조용히 분류하지 않고 오류가 난다. 러너는 소스 한 번 읽기/한 번 판정 결과를 실행·재시도에서 재사용한다.

전체 출력 스캔의 중간 실행은 기존 정상 항목 «✅ 실패 1회 안내», «✅ 실패 1건이 집계된다»를 실패 요약으로 오인해 2 FAIL이 났다. 이를 숨기거나 해당 하니스를 빼지 않고 숫자 뒤 결과 토큰 경계를 좁혔다. 실제 출력 사례를 회귀에 추가했다. 판정 검사 **43 PASS**, 소스 구문 검사 **23 PASS**다.

자유 문장의 뜻을 완벽히 이해하는 파서는 아니다. 인식하는 결과형 요약과 프로세스 종료코드가 계약이다. 브라우저 전체 실패를 SKIP으로 분류하는 기존 정책·실행 실패 재시도 정책은 유지했다. 기계 판독 결과/명시적 skip 사유로 전환하는 후속 작업은 남아 있다.

### JPEG EOI 음성 대조

운영 EOI guard는 정상이나, 1차 fixture는 guard 하나만 제거해도 통과할 수 있었다. `FF D8 FF D9 00 02` 뒤 가짜 SOF가 오는 입력을 추가했고 EOI guard만 제거한 변이가 실제로 실패하는지 확인했다. 현재 이미지 검사 **19 PASS**, 기존 해상도 검사 24 PASS. 운영 이미지 함수는 1차 이후 바꾸지 않았다.

다음 저위험 후보는 읽기 전용 진단의 binary parser와 보고서 조립 경계 분리, 하니스의 명시적 machine result/skip 계약이다. 먼저 현재 후속 diff의 독립 리뷰를 받고 분리 하니스의 import/의존성 로딩 계약을 확인해야 한다. 큰 API를 단순 줄 수 기준으로 조각내거나 동작이 다른 CSV·채점 코드를 억지로 통합하지 않는다.

1차 수량 오류의 정확한 원인은 src의 .cypher 1파일, public/js의 JSON 2파일을 TS/JS로 잘못 표기한 것이다. baseline/1차 final은 TS 280 / JS 295이며, 이번에 TS leaf 2개가 추가돼 최종 TS 282 / JS 295다. 새 baseline.json·asset 원장을 낮추거나 갱신하지 않았다.

1차는 부모 스레드의 독립 리뷰에서 신규 운영 차단 결함 없음·원본 보존 확인 결과를 전달받았다. **이번 후속 변경의 별도 독립 리뷰는 아직 대기**다. 전체 저장소 정리·모든 버그 제거 완료로 주장하지 않는다.
