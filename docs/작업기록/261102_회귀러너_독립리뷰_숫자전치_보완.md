## 1. 독립 리뷰에서 발견한 회귀

후속 러너가 exit 0의 `5 PASS 1 FAIL`, `5 통과 1 실패`, `Summary: 5 PASS 1 FAIL`을 PASS로 읽었다. 이 형식은 1차에서는 실패로 잡혔으므로 후속 변경의 실제 게이트 약화다.

`PASS 5 FAIL 0`의 거짓 실패를 막으려고 label-first 범위를 먼저 전부 보호한 것이 원인이었다. `5 PASS 1 FAIL`에서 겹치는 `PASS 1` 범위가 진짜 `1 FAIL`의 1을 삼켰다.

이제 label-first/count-first 후보를 **왼쪽부터 겹치지 않게 소비**한다. 첫 `5 PASS`를 소비하면 겹치는 `PASS 1`은 버리고 다음 `1 FAIL`을 읽는다. 반대로 `PASS 5 FAIL 0`은 먼저 `PASS 5`를 소비해 잘못된 `5 FAIL`을 버린다. 출력 전체 스캔·구문 기반 브라우저 판정·기존 E2E 정책은 유지했다.

## 3. TCP loopback과 논리 HTTP 목적지 구분

독립 리뷰에서 외부 HTTP URL이 환경 proxy를 거치면 TCP host가 loopback으로 바뀌어 TCP guard를 통과할 수 있음을 stub으로 재현했다. normalized-array 처리 실패와는 별개의 **로컬 relay 한계**다.

제작 환경 변수는 값 대신 존재 여부만 기록했다: HTTP_PROXY/HTTPS_PROXY 및 소문자 변형·NO_PROXY가 존재했고 NODE_USE_ENV_PROXY는 없었다. 이것만으로 기존 프로세스의 모든 client가 proxy를 쓰지 않았다고 증명할 수 없다.

`offline-network.cjs`에 검증용 `http.request/get`, `https.request/get` 논리 목적지 검사도 추가했다. URL·options host/hostname·URL 뒤 options override·absolute proxy request target·CONNECT를 underlying 함수 전에 검사한다. 기존 global fetch와 Socket.connect의 최종 TCP 목적지 검사도 유지한다.

검사에서는 원래 connect/fetch 및 HTTP(S) request/get을 **전부 stub으로 대체한 뒤** 보호기를 로드한다. 실제 외부 요청·DNS 없이 68개가 통과했다. 가짜 loopback proxy 환경과 NODE_USE_ENV_PROXY=1을 준 별도 실행도 68개 통과했다. 별도 loopback 연결 확인은 127.0.0.1:9가 ECONNREFUSED였으며 HTTP payload를 보내지 않았다.

최종 게이트 프로세스에서는 NODE_USE_ENV_PROXY, HTTP_PROXY, HTTPS_PROXY, ALL_PROXY, NO_PROXY 및 소문자 변형을 `env -u`로 제거하고 NODE_OPTIONS에는 보호기만 지정했다. npm은 offline 모드·update notifier 비활성으로 실행했다. 사용자나 시스템 proxy 설정 자체는 바꾸지 않았다.

이 보호기는 통상적인 Node fetch/TCP/HTTP(S) 경로에 대한 검증 도구다. native 프로그램·UDP·hook 재정의·preload가 없는 worker/process·임의의 로컬 서버가 수행하는 forwarding을 전부 막는 OS 네트워크 샌드박스는 아니다. 과거 전체 외부 통신의 부재를 소급해 보장하지 않는다.
