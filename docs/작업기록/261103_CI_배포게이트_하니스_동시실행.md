## 2. 무엇을 바꿨나

- `test-harness/run.mjs`
  - fast 모드는 하니스를 **CPU 수만큼 동시에** 돌린다(full=브라우저 E2E 는 예전처럼 1개).
  - 검사 목록·판정(`classify`, 예전 `runHarness` 의 분류 그대로)·FAIL 1회 재시도·기준선 검사는 **그대로**.
  - 결과 줄은 **이름 순서대로** 찍는다 → 로그가 매번 같은 모양.
  - **`EXCLUSIVE` 9개는 혼자 먼저** 돈다 — 저장소 안 공용 자리에 파일을 쓰는 하니스(아래 4절 실측).
  - 동시 실행 중 FAIL 은 **끝에 혼자 한 번 더** — 옆 하니스 간섭이면 통과하고, 그 이름을 요약 «🔀» 목록에 찍는다.
  - `--serial`(=하나씩) · `--jobs=N` · `HARNESS_JOBS=N` · 끝에 «⏱ 걸린 시간» 한 줄.
- `test-harness/inline_js_syntax_harness.mjs` — 조각을 먼저 순서대로 모은 뒤 `node --check` 를 동시에(`SYNTAX_JOBS`).
  임시 파일 이름 앞에 순번을 붙여 «`/`→`_` 로 바꾼 이름이 같은 두 조각» 이 서로 덮어쓰지 않게 했다.
- `test-harness/ai_dubbing_resume_harness.mjs` — `until()` 을 «30틱» → «최소 30틱 + 최대 5초».
- `CLAUDE.md` 2장 함정 한 줄 + 4-4 의 하니스 시간 문구.

워크플로(`ci.yml`·`deploy.yml`)와 게이트 목록(`ci-gates.sh`)은 **한 글자도 안 바꿨다.**

## 3. 왜 그렇게 풀었나 — 검토했다가 버린 방법

- **배포 워크플로에서 게이트를 빼기**(PR 에서 이미 돌았으니) — ⛔ 4-1-1 「게이트 우회 금지」. PR 검사는 «그때의 main» 과
  합친 것이고, 병합 시점의 main 은 그 사이 움직일 수 있다. 배포 직전 게이트는 그 틈을 막는 자리다.
- **paths 필터로 문서만 바뀐 PR 은 검사 생략** — ⛔ `ci.yml`·`deploy.yml` 이 2026-08-07 에 필터를 뺀 이유(큰 push 에서 조용히 안 도는 사고).
- **하니스를 여러 job(matrix)으로 쪼개기** — job 마다 저장소 받기 50초 + `npm ci` 를 다시 해서 이득이 작고,
  기준선 검사(전체 PASS/SKIP 수)를 한 곳에서 할 수 없다.
- **저장소 받기 줄이기(sparse checkout)** — 배포가 `cloudflare-deploy/public`(1.8GB)을 통째로 올리므로 필요하다. 50초는 그대로 둔다.
- **인라인 JS 를 `vm.Script`/`new Function` 으로 프로세스 안에서 검사** — `node --check`(CJS 래퍼라 최상위 `return` 허용 등)와
  판정이 미세하게 달라질 수 있다. 검사 도구는 그대로 두고 «동시에» 만 바꿨다.
- **`ai_dubbing_resume` 를 재시도에 맡기기** — 재시도로 대개 통과하지만 뿌리는 «틱 수로 기다리기» 라 고쳤다.
- **EXCLUSIVE 를 코드 읽기로 고르기** — 쓰기 호출이 119개 파일 331곳이라 눈으로는 못 가른다. 하니스마다 실행 전후
  저장소 파일·폴더의 mtime 을 비교해(폴더 mtime 변화 = 그 안에 만들었다 지움) **실측**으로 골랐다.

## 4. 확인한 방법

- **저장소 쓰기 실측**(하니스 661개를 하나씩, 실행 전후 mtime 비교) — 바뀐 자리가 있는 하니스 11개:
  - 공용 자리 → `EXCLUSIVE`: `correction_reason`(`src/__cr_mutant.ts`) · `pii_mask`/`recordings_cleanup`(`test-harness/.build` 생성/삭제) ·
    `azure_pronunciation`·`teacher_legacy_login`·`voice_acoustic`·`voice_score_calibration`·`voice_score`(`test-harness/.*.mjs` 생성/삭제 —
    `harness_portability` 가 `test-harness/*.mjs` 를 전부 읽는다) + `asset_version`(새 `?v=` 면 `asset-versions.json` 을 고침 —
    `recording_diagnosis`·`today_plan` 이 읽는다. 이번 실측에선 새 버전이 없어 안 잡혔지만 코드로 확인).
  - 자기만 쓰고 아무도 안 읽는 `*_report.txt`(`core_features`·`lesson_insight`·`review_quiz`) → 동시 실행 그대로.
  - `/tmp` 고정 이름은 두 개(`eleader-books-turn-matrix.json`·`mangoi-lt-ticket-harness.mjs`) — 각각 쓰는 하니스가 하나뿐이라 그대로.
- **하니스 661개 판정 대조** — 순차(`--serial`, 433초) · 동시 4개(145초) · 동시 8개(131초) 의 `▶` 줄을 정렬해 `diff` → **0줄 차이**.
  셋 다 PASS 661 / SKIP 20 / FAIL 0, 기준선 유지, 재시도·«혼자 다시» 0건(`ai_dubbing_resume` 수정 뒤).
- **러너 판정 대조(가짜 하니스 8종)** — 통과·실패·죽음·가끔 실패·puppeteer·옆 하니스 간섭·출력 없이 exit 3 을 옛 `run.mjs` 와 새 `run.mjs`
  (동시 4·`--serial`)에 넣어 → 최종 PASS 4 / SKIP 1 / FAIL 3, 실패 이름·종료코드(1) 모두 같음. 간섭 피해 하니스는 «혼자 다시» 로 통과하고 «🔀» 목록에 찍힘.
- **인라인 JS** — 가짜 트리(일부러 깨진 조각 3개 + 이름 충돌 짝)에서 옛·새 출력 `diff` 0(동시·`SYNTAX_JOBS=1` 둘 다).
  실제 저장소 1,569조각: 47초 → 13초, 오류 0건 동일.
- **`ai_dubbing_resume`** — 8개를 동시에 돌리면 고치기 전 3/8 FAIL(`Timed out waiting for the player to settle`), 고친 뒤 16/16 통과.
- 로컬은 Node 22.23(CI 는 24). CI 실측 시간은 PR 에서 확인.

## 5. 남은 것 / 주의할 것

- 새 하니스가 **저장소 안에** 임시 파일을 만들면 `run.mjs` 의 `EXCLUSIVE` 에 넣어야 한다. 빠뜨려도 초록으로 새지는 않고
  요약 «🔀 동시 실행에서만 실패» 목록에 이름이 뜬다(그때 넣으면 된다). 가장 좋은 것은 `mkdtempSync(join(tmpdir(), …))`.
- 저장소 받기 50초, 배포 단계의 게이트 재실행, 연달아 병합할 때의 배포 대기(`concurrency`), 수업 시간대 배포 보류는 **의도된 것**이라 그대로다.
- 「Warmup browser verification」·「AI speaking entry sandbox」(5~7분)는 그 파일을 고친 PR 에만 돈다 — 이번 범위 밖.
  `playwright install --with-deps` 캐시로 1~2분 줄일 여지가 있다(사람이 정할 일).
- `CLAUDE.md` 2장 「CI 가 몇 십 분째 멈췄다」 줄의 「이 저장소 CI 는 평소 약 90초」 는 이미 오래전부터 사실이 아니었다(2026-11-03 실측 8분) —
  남의 줄이라 이번엔 안 고쳤다.
