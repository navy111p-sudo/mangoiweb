## 1. 왜 했나

웜업·A.i 말하기 화면을 고친 PR 은 「Warmup browser verification」(5분 30초~7분)과
「AI speaking entry sandbox」(4~5분)가 CI 와 함께 돌아, 초록불이 다 뜨기까지 그만큼 기다렸다.

| 단계 | 시간 |
|---|---|
| 체크아웃 | 46~55초 (거의 전부 `git fetch --depth=1` — 내려받기) |
| playwright 설치 | 18~23초 |
| 웜업: 아바타 입모양 18건 | 28초 |

## 2. 무엇을 바꿨나

- `test-harness/helpers/browser-pool.mjs`(새 파일) — 서로 독립인 사례를 최대 N개 동시에 돌리는 도우미.
  - 기본 N = CPU 수(최대 4). `BROWSER_JOBS=1` 이면 예전처럼 하나씩.
  - 하나가 던지면 새 사례는 그만 꺼내고, 돌던 사례가 끝나기를 기다린 뒤 **가장 앞 번호의 오류**를 던진다
    (브라우저를 닫는 `finally` 가 남의 사례 도중에 돌지 않게).
- `test-harness/manual/speech-preferences-browser.mjs` · `ai-speaking-browser.mjs` 가 그것을 쓴다.
  - 사례마다 브라우저 컨텍스트(저장소·쿠키)가 따로라 서로를 못 본다. 말빠르기는 계정 이름을
    «사례 번호»(`'Sandbox_'+index`)로 — 예전 순차 실행과 **같은 이름**이고 동시에 돌아도 안 겹친다.
  - A.i 말하기는 실패 보고를 **사례 순서로 정렬**해 낸다(끝나는 순서가 섞여도 같은 보고).
  - 말빠르기는 «50건 다 돌았나» 를 새로 센다(A.i 말하기는 원래 320건을 셌다).
- `.github/workflows/warmup-browser.yml` — matrix 두 갈래로 **다른 러너에서 동시에**.
  - `wiring`: 아바타 입모양 + 웜업 화면 배선·변이 (예전과 같은 순서로 하나씩)
  - `speech`: 계정 말빠르기 50건 (동시 실행)
  - 시각에 민감한 아바타 검사는 **동시 실행 없이 혼자** 돈다.
- 두 워크플로 path 필터에 `test-harness/helpers/browser-pool.mjs` 추가(도우미를 고치면 두 검사가 다시 돈다).
- `test-harness/browser_ci_split_harness.mjs`(새 하니스, fast 게이트에서 돈다) — 아래가 깨지면 FAIL:
  - 단계마다 `if: matrix.part == '…'` 의 갈래가 matrix 목록에 있는가(이름이 어긋나면 «에러 없이» 영영 안 돈다)
  - 갈래마다 도는 검사가 하나 이상 있는가 · 예전 6개 검사를 정확히 한 번씩 돌리는가
  - 아바타 검사가 도우미를 쓰지 않는가 · 아바타와 말빠르기가 다른 갈래인가
  - 두 검사가 «전부 돌았나» 를 세는가 · 도우미가 두 워크플로 path 필터에 있는가

## 3. 검토했다가 버린 방법

| 방법 | 버린 이유 |
|---|---|
| playwright 설치 캐시 | 설치는 18~23초뿐 — 고쳐도 남는 것이 거의 없다 |
| 줄마다 브라우저를 따로 띄우기 | 4줄 모두 약 7초로 한 브라우저와 같았다(로컬 16건 실측). 띄우는 비용만 늘어 버렸다 |
| 탭을 8개로 | 4개와 같았다(로컬 141초 대 141초) — 막는 것은 CPU |
| 아바타 검사도 동시에 / 같은 러너에서 다른 검사와 함께 | 짧은 입모양 구간을 놓친다(CLAUDE.md 「브라우저 검사가 짧은 구간 관측에서 시간초과」). 그래서 갈래를 나눠 «혼자» 돌게 했다 |
| 시간초과를 늘리기 · 자동 재시도 | 금지(CLAUDE.md 4-1-1). 동시 실행에서 흔들리면 `BROWSER_JOBS` 를 낮춘다 |
| 일부만 받는 체크아웃(sparse) — 약 50초 중 30초 남짓 줄 것으로 짐작 | 페이지가 못 받는 파일이 생기면 검사가 실제 화면과 달라진다(404 가 조용히 넘어가거나 거짓 FAIL). **사람이 정할 일**로 남겼다 |
| A.i 말하기 320건을 두 러너로 쪼개기 | «320건 전부 돌았나» 검사를 쪼개야 하고, 동시 실행만으로 충분히 줄었다 |

## 4. 확인한 방법

[잰 것 — 로컬 4코어 VM. ⚠️ 이 VM 은 CI 러너보다 느리고 디스크 대기가 커서 숫자 자체는 CI 와 다르다]

| 검사 | 하나씩 | 4개 동시 | 결과 |
|---|---|---|---|
| 말빠르기 50건 | 200초 | 141초 | 50건 · assertion 300 · 실패 0 (둘 다) |
| A.i 말하기 320건 | 308초 | 233초 | 320건 · assertion 3,280 · 실패 0 (둘 다) |

- 제품을 일부러 깨뜨림(A.i 말하기 허브의 `id="friend-mode"` 바꾸기, 390×844 32건): **하나씩·4개씩 보고가 글자 하나까지 같다**
  (32건 · assertion 244 · 같은 16건 실패 · 같은 순서). 복구 확인.
- 말빠르기 저장을 끊음(`pref.set` 의 `save()` 제거): 7초 만에 `server did not persist Sandbox_0 warmup 1` 로 exit 1. 복구 확인.
- 가드 변이 5종(갈래 이름 바꾸기 · speech 의 if 지우기 · 아바타를 speech 갈래로 · 아바타가 도우미 import · guided 빠뜨리기) 전부 실제 FAIL.
- `node test-harness/run.mjs --fast`: PASS 664 / FAIL 0 / SKIP 20.

[잰 것 — CI 러너, PR #2015]

| | 예전 (최근 성공 실행) | 이번 (run 41660510371 · 41660510265) |
|---|---|---|
| 웜업 워크플로 전체 | 5분 16초 ~ 7분 22초 (13회, 중앙 6분 37초) | **4분 17초** (두 갈래 동시: wiring 4분 2초 · speech 4분 13초) |
| 웜업: 말빠르기 50건 단계 | 136 ~ 214초 (중앙 약 197초) | 158초 |
| A.i 말하기 워크플로(작업) | 3분 58초 ~ 5분 57초 (9회, 중앙 4분 37초) | **3분 40초** (이번 체크아웃이 72초로 평소보다 느림) |
| A.i 말하기: 320건 단계 | 163 ~ 220초 (중앙 204초) | **123초** · 320건 · assertion 3,280 · 실패 0 · «4 at a time» |

- 갈래가 맞게 건너뛰었다: wiring 갈래는 말빠르기를, speech 갈래는 아바타·배선을 «skipped».
- 웜업 두 갈래 모두 예전과 같은 판정으로 통과(아바타 18건 · two-way 65 · guided 181 · bts 115 · 변이 검출 · 말빠르기 50건/300).

⚠️ **정직하게 — 말빠르기 단계는 동시 실행으로 거의 안 빨라졌다.** CI 러너에서 10건마다 26~34초로 예전과 같은 속도였다
(로컬은 1.4배). 그 검사는 사례마다 무거운 화면(`warmup.html` 368KB · 요청 77개)을 7번씩 다시 여는데, 화면 하나를 여는 일이
이미 CPU 여러 개를 쓰는 것으로 보인다(추론 — 러너에서 CPU 를 재지는 못했다). **웜업 워크플로가 줄어든 것은 «두 러너로 나눈» 덕**이다.
동시 실행 코드는 판정이 같고 로컬에서 1.4배라 그대로 두었다 — 걷어낼지는 다음에 정해도 된다.

이제 PR 에서 가장 늦게 끝나는 것은 브라우저 검사가 아니라 「CI (PR 검사)」(약 4분 30초)다.
