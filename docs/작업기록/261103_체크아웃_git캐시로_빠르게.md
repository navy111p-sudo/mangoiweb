# 체크아웃 빠르게 — .git 을 캐시에서 되살려 «바뀐 것만» 받기

- 날짜: 2026-11-03
- 작업자: Claude (사장님 요청 「체크아웃도 빠르게 해줘」 — 바로 앞 PR #2002(CI 게이트)·#2015(브라우저 검사)에 이어서)
- 브랜치 / PR: `claude/git-cache-checkout` · navy111p-sudo/mangoiweb#2023

## 1. 왜 했나

모든 워크플로의 첫 단계 `actions/checkout` 이 매번 저장소 전체를 새로 받았다.

[잰 것 — 2026-11-03 Actions API 단계별 시각, 워크플로마다 최근 성공 실행 6회]

| 워크플로 | checkout |
|---|---|
| CI (PR 검사) | 77~167초 |
| 배포(deploy.yml) | 53~280초 |
| 웜업 브라우저 검사 | 46~99초 (이 PR 의 첫 실행에서는 한 갈래가 **307초**) |
| A.i 말하기 브라우저 검사 | 46~102초 |
| 관리자 수리 오프라인 검사 | 50~280초 |
| 수업 일정 회귀 | 47~208초 |

- 한 실행 로그(ci 15:29): `git fetch --depth=1` 이 **162초**, 파일 쓰기는 몇 초. 시간은 거의 전부 «내려받기».
- 받는 양: HEAD 의 파일 합계 **약 1.9GB** — `public/media` 727MB · `public/library` 370MB · `public/img` 281MB · `docs` 약 124MB · `public/videos` 91MB.
- 같은 날에도 46초~307초로 흔들린다 — GitHub git 서버 쪽 사정으로 보인다(추론, 잰 것 아님).

## 2. 무엇을 바꿨나

- PR·브라우저 검사 워크플로 6개(`ci` · `warmup-browser` · `ai-speaking-browser` · `admin-repairs-offline-browser` · `weekly-postpone` · `vc-recovery-browser`):
  checkout **앞** 에 `actions/cache/restore@v4`(path `.git`, restore-keys `repo-git-v1-`) — **읽기만**.
- `deploy.yml` › `deploy` 잡도 같은 restore(읽기만) · checkout 에 `persist-credentials: false`.
- `deploy.yml` › **새 `git-cache` 잡** — 유일한 저장자. 단계가 정확히 «열쇠 → 그 주 캐시가 있나(lookup-only) → 없으면 **새로** checkout → 저장» 뿐이다.
  열쇠 `repo-git-v1-YYYY-Www`(주 단위 — 그 주 첫 실행만 받고 저장, 나머지는 몇 초). 배포 잡과 다른 러너에서 동시에 돌아 배포를 늦추지 않는다.
- 감시 하니스 `test-harness/git_cache_checkout_harness.mjs`(69종).

되살린 `.git` 이 있으면 checkout 이 «기존 저장소» 경로를 탄다(`prepareExistingDirectory` —
ref 정리 → `git clean -ffdx` → `git reset --hard HEAD`) → `fetch --depth=1` 은 **그 사이 바뀐 객체만** 받고 →
정확한 sha 를 `checkout --force`. 그래서 **받은 뒤의 파일은 전과 똑같다.** 캐시가 없으면(첫 실행·만료) 예전과 똑같이 전부 받는다.

### 3-2. 병합 뒤 실측 — main 이 저장한 주간 캐시로

[잰 것 — 2026-11-03 Actions API 단계 시각 + 잡 로그, 병합 직후 실행 «전부»]

- **저장**: 병합 커밋(`e70ffc9`)의 배포 실행(run 41676959590) `git-cache` 잡이
  「Cache not found for input keys: repo-git-v1-2026-W45」 → 새로 받기 **99초** → 「Cache saved with key: repo-git-v1-2026-W45」(1,564,620,526바이트, 약 180MB/s).
  같은 실행의 `deploy` 잡 checkout 은 아직 캐시가 없어 **331초**(예전처럼 전부 받음).
- **그 뒤 저장 잡**(배포 run 41679719057·41682147402): 「Cache found and can be restored from key: repo-git-v1-2026-W45」 → 새로 받기·저장 **건너뜀**, 잡 4~5초.
- **되살리기**: 병합 뒤 실행 5개 잡 모두 「Cache hit for restore-key: repo-git-v1-2026-W45」 → 「Cache restored from key: repo-git-v1-2026-W45」.
  되살린 `.git` 의 HEAD 는 `refs/heads/main` @ `e70ffc9` — 이 PR 의 임시 캐시가 아니라 **main 저장 잡이 새로 받은 것**이다.
  그 뒤 checkout 은 «detach → `clean -ffdx` → `reset --hard`(약 4.5~5초)» 를 지나 그 커밋 하나만 `fetch --depth=1`(**0.5~1.2초**) 받았다.

|---|---|---|---|
| CI 배포 게이트 | 94~290초 (4회) | 10+7 = **17초** (PR #2027) · 11+7 = **18초** (PR #2028) | 259~501초 → 225~228초 |

| 운영 배포(deploy 잡) | 81~253초 (4회) | 14+6 = **20초** · 14+9 = **23초** | 371~500초 → 215~252초 |

- 내려받기 속도는 실행마다 **130~240MB/s** 로 갈렸다(오프라인 검사가 가장 느려 16초).
- 병합 전 숫자는 같은 날 16:03~16:35 UTC 의 CI 4회(run 41674053292·41671188451·41670279445·41672194541) · 오프라인 1회(41670279413) · 배포 4회(41675819512·41672654087·41671321245·41669837996).
- [아직 못 봄] 웜업·A.i 말하기·수업 일정 회귀·화상수업 복구 브라우저 검사는 병합 뒤 한 번도 안 돌았다(그 파일을 건드린 PR 이 없음 — path 필터). 같은 단계를 쓰지만 main 캐시로 잰 숫자는 없다.
- 곁가지: 되살린 `.git` 에는 작업 파일이 없어서 checkout 의 «ref 정리» 단계가 `git checkout --detach` 로 **13,218줄**의 `D 파일명` 을 로그에 찍는다(0.5초 · 결과 무관 · 잡 로그만 길어짐). 고치지 않았다.

## 4. 검토했다가 버린 방법 · 지킨 것

### 4-1. 부분 체크아웃(sparse) — 버림

무거운 폴더(`public/media`·`library`·`videos`, 1.2GB)를 안 받는 안. 전체 트리와 부분 트리에서 `--fast` 하니스를 전부 돌려 대조했다.

- [잰 것] 종료코드가 0 → 1 로 바뀐 하니스 **5개** — `ai_dubbing_harness`·`ai_dubbing_lantern_harness`(media/dubbing 25MiB 상한) ·
  `manager_pay_guide_harness`(library/agency PDF) · `scene_curriculum_harness`(videos/scene-clips) · `today_plan_harness`(영상 크기).
  ⟹ **배포 게이트(ci·deploy)에는 원리상 못 쓴다.**
- 출력만 다른 39개는 다시 돌려 보니 잡음이었다 — `weekly_postpone_routes_harness` 는 전체·부분 트리 **둘 다** 실행마다 통과 줄이 4,134 ↔ 10,205 로 갈린다(트리와 무관).
- 브라우저 검사에만 쓰는 안도 있었지만, 폴더를 «훑는» 검사가 그 폴더가 없어서 «덜 세는» 것은 감시 장치로도 못 잡는다(읽기 감시 도우미를 만들어 봤다가 버렸다).
  캐시는 파일이 **하나도 안 빠지므로** 그 위험 자체가 없다.

### 4-2. PR 워크플로도 저장하기 — 버림

PR 이 저장하면 PR 마다(그 PR 의 ref 범위에) 1.5GB 가 생긴다. 하루 수십 PR 이면 저장소 캐시 한도(10GB)를 계속 밀어내고 npm 캐시까지 지워진다.
→ 저장은 `deploy.yml › git-cache` 잡(main) 하나, PR 은 main 의 것을 읽는다(PR 실행은 기본 브랜치 캐시를 읽을 수 있다).

### 4-3. 실측은 어떻게 했나

캐시는 main 배포가 저장하기 전에는 없으니 PR 안에서는 «되살리기» 를 잴 수 없다. 그래서
1. 첫 커밋: ci.yml 만 **임시로** `actions/cache@v4`(열쇠 `repo-git-v1-probe`, `TEMP-PROBE` 표시)로 저장 — 이 PR 범위에만 생긴다.
2. 둘째 커밋: restore 로 되돌리고 하니스를 넣음(하니스가 `TEMP-PROBE` 가 남으면 FAIL).
⚠️ 하니스를 첫 커밋에 넣지 않은 이유 — `actions/cache` 의 저장은 `post-if: success()` 라 **실행이 빨간불이면 저장을 안 한다.**
그 PR 범위의 probe 캐시는 7일 동안 안 쓰이면 GitHub 이 지운다.

### 4-4. 저장을 «배포 잡» 에서 하지 않은 이유 — 함정 대조가 잡음

첫 판은 `deploy` 잡이 `actions/cache@v4` 로 저장했다. 함정 대조(trap-check)가 두 가지를 짚었다.
- **오염이 이어진다** — deploy 잡은 저장(post 단계) **전에** `npm ci` 설치 스크립트·wrangler 같은 남의 코드를 돌린다.
  actions/checkout 은 되살린 `.git` 의 `hooks/`·`config` 의 `core.fsmonitor`·`filter.*`·`info/attributes` 를 **건드리지 않으므로**(소스 확인),
  그런 코드가 한 번 `.git` 을 건드리면 그것이 캐시를 타고 모든 PR·다음 배포의 checkout 에서 실행된다. 게다가 매주 «되살리기 → 저장» 으로 이어져
  문제의 패키지를 고쳐도 남는다. 이 변경 전에는 잡마다 `.git` 을 새로 받았으니 «지속성» 자체가 새 위험이었다.
- **캐시가 계속 커진다** — 지난주 것을 되살려 이어 저장하면 옛 객체가 안 지워진다([잰 것] 하루에 바뀐 blob 약 31.7MB → [추론] 한 달 약 1GB).

→ 저장을 **checkout 말고 아무것도 안 돌리는 잡**으로 떼고, 그 잡은 지난 캐시를 되살리지 않고 **매주 GitHub 에서 새로** 받는다.
둘 다 한 번에 사라진다(그 잡이 돌리는 것은 actions/checkout·actions/cache 뿐 — 어차피 모든 잡이 믿는 것). PR 잡이 되살린 `.git` 을 건드려도 저장하지 않으니 남지 않는다.

### 4-5. 토큰이 캐시에 실리지 않게

checkout v4 는 토큰을 `.git/config` 의 `http.https://github.com/.extraheader` 에 두고 «post» 단계에서 지운다.
post 단계는 등록 역순으로 돌아 checkout 의 정리가 캐시 저장보다 먼저다(이 PR 로그에서 확인: 16:02:43.79 extraheader 삭제 → 16:02:44.03 tar 시작).
그래도 순서에만 기대지 않으려고 저장하는 `git-cache` 잡의 checkout 에 `persist-credentials: false` 를 줬다 — checkout 단계가 끝나는 즉시 토큰이 지워진다
(저장을 `actions/cache/save` 로 나눴기 때문에 이 잡에서는 저장이 checkout 정리보다 «먼저» 돈다 — 그래서 이 줄이 필수다. 하니스가 못 박음).
`deploy` 잡도 같은 값을 줬다 — checkout 뒤에 git 인증을 쓰는 단계가 없다(`git push` 없음 · 함정 대조도 확인). 저장 잡에는 비밀(`env`)도 없다.

### 4-6. 손대지 않은 것

- `android.yml` — checkout 뒤에 main 으로 `git push` 하는 드문 작업이라 뺐다(하니스가 «예외» 로 못 박음).
- 첫 판은 열쇠 단계가 `deploy` 잡에 있어 `defaults.run.working-directory: cloudflare-deploy` 를 `.` 로 덮어야 했다. 지금은 `defaults` 가 없는 `git-cache` 잡에 있다(하니스는 «defaults 가 생기면 덮었는가» 를 그대로 본다).

## 5. 감시 — `git_cache_checkout_harness.mjs`

워크플로를 «잡 → 단계 순서·값» 으로 읽어 확인한다:
읽는 잡마다 `.git` 캐시 단계가 checkout **앞**에 정확히 하나 · `actions/cache/restore` · path `.git` · restore-keys `repo-git-v1-` · 조건(`if:`) 없음 ·
저장은 `deploy.yml › git-cache` 의 `actions/cache/save` 하나 · 저장 잡의 단계가 정확히 4개(열쇠 → lookup-only → 새 checkout → save) ·
열쇠 명령이 «글자 그대로» 주 단위 · 저장 잡에 비밀·서비스 없음 · `persist-credentials: false` · `save-always` 없음 ·
checkout 이 `clean` 을 끄지 않음(`${{ false }}` 같은 식도) · ci·deploy 는 sparse 금지 · `TEMP-PROBE` 없음.
`.git` 판정은 path 값 «안» 을 본다 — 여러 줄(`path: |`)·`./.git`·`${{ github.workspace }}/.git`·남의 캐시 액션까지.

[잰 것] 변이 **22종 전부 실제 FAIL** — PR 이 저장(`path: |` 블록 · `./.git` · 작업폴더 경로 · restore→cache) · 되살리기 삭제 · 되살리기를 checkout 뒤로 ·
열쇠에 run_id 덧붙이기 · 열쇠를 실행마다 · 출력 이름 바꾸기 · `clean: false` · `clean: ${{ false }}` · `save-always` · restore 에 `if: false` ·
저장 잡이 이어 붙이기(restore-keys) · 저장 잡이 통째로 되살리기 · 저장 잡에 npm · 저장 잡 토큰 남김 · 저장 잡에 비밀 · deploy 잡이 저장 · 접두사 어긋남 · ci 에 sparse · TEMP-PROBE 잔존.
🪤 **첫 판(62종)은 함정 대조가 구멍 7개를 실제로 뚫었다** — path 를 «.git» 정확일치로만 세서 위 세 가지 저장이 «캐시 단계 아님» 으로 빠졌고,
열쇠는 «%G-W%V 라는 글자가 있는가» 라 run_id 를 덧붙여도 통과했으며, `clean` 은 글자 `'false'` 만, `save-always`·`if:`·출력 이름은 아예 안 봤다.
그때 작업기록·CLAUDE.md 에 「열쇠를 실행마다 → FAIL」이라고 적었는데 그건 `%G-W%V` 를 «지운» 모양에만 맞는 말이었다.
🪤 그리고 변이 하나(`persist-credentials`)는 치환이 **설명 주석** 의 같은 글자를 먼저 바꿔 처음엔 «통과» 로 나왔다 — 실제 YAML 줄을 겨냥하니 FAIL.
⚠️ 이 하니스는 `run.mjs --fast` → 배포 게이트 ②에 들어간다. 새 워크플로가 되살리기를 빠뜨리면 «느려질 뿐» 인데도 그 PR 의 CI 가 빨간불이 된다 —
병합 «전» 에 보이는 빨간불이라 일부러 그렇게 뒀다(조용히 느려지는 것보다 낫다고 판단).

## 6. 남은 것 · 사람이 볼 일

- ✅ 병합 뒤 **첫 배포 실행의 `git-cache` 잡**이 캐시를 저장했고(새로 받기 99초 + 저장), 그다음 PR·배포부터 실제로 빨라졌다(3-2).
  매주 월요일(UTC, ISO 주) 첫 배포 실행이 그 주 캐시를 새로 받아 저장한다 — 그 실행의 `deploy` 잡까지는 지난주 캐시(최대 한 주 묵은 것)를 읽는다.
- 되살리는 캐시는 **최대 한 주 묵은** 것이다 — 그 주에 바뀐 만큼은 fetch 로 받는다.
- CI 실측은 PR 범위 임시 캐시(PR 잡의 detached HEAD `.git`)로 잰 것이다. 실제 main 캐시는 checkout 이 `-B main` 으로 브랜치에 붙인 `.git` 이라
  «되살린 뒤 detach → 브랜치 삭제» 경로를 탄다 — 함정 대조가 로컬에서 그 경로를 재현해 결과 트리가 정확함을 확인했다.
  ✅ 병합 뒤 CI 에서도 그 경로를 지났다(PR #2027·#2028·배포 2회 — 로그에 `refs/heads/main` → `git checkout --detach`, 최종 HEAD 가 각 실행이 받아야 할 sha(PR 머지 · PR head · main 푸시), 게이트·배포 성공).
- 되살리기가 «반쯤» 실패하면(경고만 남는다 — actions/cache 동작, 여기서 실행해 보진 못함) checkout 이 fetch·checkout 에서 시끄럽게 실패할 수 있다. 다시 돌리면 풀린다.
- 나중에 `.gitattributes` 에 eol·filter 규칙이 생기면 안 바뀐 파일은 다시 안 써져 새로 받은 트리와 줄바꿈이 다를 수 있다(지금은 `mobile-app/.gitattributes` 의 `binary` 뿐 — 해당 없음).
- 캐시가 망가진 것 같으면 접두사를 `repo-git-v2-` 로 한 번에 바꾸면 된다(모든 워크플로·하니스 `PREFIX` 를 함께).
- 한 주 동안 바뀐 양만큼 차이 fetch 가 커진다(실측 이틀 30MB — 한 주 100MB 안팎으로 보임, 추론). 매주 새로 받으므로 캐시 자체는 커지지 않는다.
