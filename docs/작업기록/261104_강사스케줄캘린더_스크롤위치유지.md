- 사장님 요청: 「스크롤 위치 유지 실패도 고쳐줘」.
- 출발점은 브라우저 검사 `test-harness/manual/teacher-calendar-accordion-browser.mjs` 의 「스크롤 위치가 유지된다(300)」 한 줄이 계속 실패하던 것이다. 그 검사는 «달력 칸을 300px 내린 뒤 접힌 요일을 펼치면 300 이 그대로인가» 를 본다. 앞선 판(`adm-q6.js` v=17)에서도 실패하고 있었다.
- 그대로 두면 「접힌 요일을 펼쳤더니 보던 시간대가 맨 위(06시)로 튄다」가 사람 화면에서도 나는지 알 수 없었다.

## 2. 무엇을 바꿨나

**원인이 둘이었다 — 하나는 검사, 하나는 코드.**

### 2-1. 검사가 실패하던 원인 (검사 쪽)

- Playwright `page.click()` 은 누르기 «전에» 그 요소를 화면에 보이게 스크롤한다.
- 요일 머리글은 달력 칸(`#ph54-cal-body`) «안» 의 sticky 머리글이라, 그 스크롤이 **달력 칸을 0 으로 되돌렸다**(이벤트 기록으로 확인 — pointerdown «전» 에 이미 0).
- 사람은 이미 보이는 sticky 머리글을 누르므로 이 스크롤이 일어나지 않는다. ⟹ 이 실패는 화면 버그가 아니라 검사 도구의 거짓 실패였다.
- 고친 것: `test-harness/manual/teacher-calendar-accordion-browser.mjs`
  - 누르기를 «포커스(`preventScroll`) → `el.click()`» 로 `page.evaluate` 에서 보낸다(스크롤 없이 실제 마우스와 같은 상태).
  - 키보드 Enter 로 펼칠 때도 위치가 유지되는지(250) 본다.
  - 요일을 바꿔 가며 6번 펼치고, **매번 «정말 펼쳐졌나»(접힌 머리글이 사라졌나)를 짝으로** 본다.

### 2-2. 고치다 찾은 진짜 결함 (코드 쪽)

- 검사를 고친 뒤 Enter 경로를 더해 보니 **실행마다 들쭉날쭉 0** 이 났다. 잰 것:
  - `ph54Render` 안에서 `calBody.scrollTop = keepTop` 직후 다시 읽으면 **0**.
  - 그 자리에서 `scrollHeight` 를 한 번 읽고 다시 넣으면 **들어간다**.
  - `#legacy-cards details{content-visibility:auto}`(`css/admin-inline-c.css` — 화면 밖 카드 렌더 생략)를 끄면 **옛 코드도 3/3 통과**.
  - 실패한 실행은 카드 상자가 화면 밖이었다(예: top −890 · bottom −672).
- ⟹ **카드가 렌더 생략 상태인데 포커스(tabindex=0 머리글)만으로 살아 있다가, 그 포커스 요소를 `innerHTML` 로 지우면 바로 뒤의 `scrollTop` 대입을 크로미움이 조용히 무시한다.** 에러는 나지 않는다.
- 고친 것: `cloudflare-deploy/public/js/adm-q6.js`
  - 새 도우미 `ph54SetScrollTop(el, v)` — ① 숫자가 아니면 아무것도 안 함(`null >= 0` 이 참이라 숫자인지 먼저 본다) ② `void el.scrollHeight` 로 배치를 먼저 확정 ③ 넣고 ④ 그래도 안 들어갔고 스크롤 끝 안쪽이면 다음 화면 갱신(rAF) 때 한 번 더(그 사이 칸이 문서에서 떨어졌으면 안 넣음).
  - `ph54Render` 의 두 대입(«이전 위치 그대로» · 처음 열 때 «첫 수업 한 시간 위»)이 전부 이 도우미를 쓴다. 렌더 안에 `calBody.scrollTop =` 직접 대입은 남지 않았다.
  - `admin.html` 의 `adm-q6.js?v=` 22 → (#2029 에서) 23, `test-harness/asset-versions.json` 원장 기록.

### 2-3. 검사 보강 (자동으로 매번 도는 쪽)

- 브라우저 검사(`manual/`)는 CI 가 자동으로 부르지 않는다. 그래서 `test-harness/teacher_calendar_lanes_harness.mjs` 에 두 절을 넣었다.
  - **[E]** 도우미를 가짜 요소(«배치를 읽기 전 대입은 무시» 를 흉내)로 실제 실행 — 10종.
  - **[E-2]** `ph54Render` 의 «이전 칸 읽기 ~ `if (calBody){…}` 끝» 을 중괄호 짝으로 오려 가짜 document·도우미로 실행 — 이전 300 → 새 칸 300 · 이전 0 → 0 · 처음이면 첫 수업 한 시간 위 · 수업이 없으면 안 넣음.
- 옛 «`if (keepTop >= 0) calBody.scrollTop = keepTop;` 이 있는가» 글자 검사는 «이전 값을 읽어 도우미로 넣는가 + 렌더 안에 직접 대입이 없는가» 로 바꿨다.

## 3. 왜 그렇게 풀었나 — 검토했다가 버린 방법

- ⛔ **`content-visibility:auto` 를 끄거나 이 카드만 빼기** — 2026-06-12 «관리자 카드 100+ 동시 렌더로 수십 초 프리즈» 방지책이다. 고치면 이 화면 하나 때문에 관리자 화면 전체가 느려진다.
- ⛔ **검사만 고치고 끝내기** — 검사 실패의 직접 원인은 검사 도구였지만, 고친 검사로 «진짜 결함» 이 드러났다. 그걸 덮으면 사람 화면에서 드물게 튀는 상태가 남는다.
- ⛔ **검사에서 포커스를 빼고 누르기** — 그렇게 하면 이 결함(포커스로 살아 있던 요소를 지울 때)이 검사에서 아예 안 보인다. 그래서 검사는 «포커스 → `el.click()`» 으로 사람과 같은 상태를 만든다.
- **«조금 뒤에» 넣는 방식을 기본으로 삼지 않은 이유** — 실측으로 «배치를 먼저 읽고 바로 넣기» 만으로 동기로 들어갔다. 그래서 그것을 기본으로 두고, 다음 프레임(rAF) 재시도는 안전망으로만 뒀다. (기다렸다 넣는 방식은 따로 만들어 재 보지 않았다.)
- ⛔ **도우미만 검사하기** — 처음엔 [E] 만 두었는데, 함정 대조가 `if (false && calBody)` · `keepTop = -1` 덧붙이기를 넣어 보니 **둘 다 통과**했다(«렌더가 그 값을 넘기는가» 를 글자로만 봤기 때문). 그래서 [E-2] 로 렌더 배선 자체를 실행한다.

## 5. 남은 것 / 주의할 것

- ⚠️ **사람 화면에서 이 결함이 얼마나 자주 났는지는 못 쟀다.** 사람이 카드를 보며 누르면 그 카드는 화면 안이라 렌더 생략 상태가 아니므로 드물었을 것으로 본다(추론). 실제 화면 확인은 사람이 해야 한다 — 관리자 › 강사 스케줄 캘린더에서 아래로 내린 뒤 다른 요일을 눌러 보던 시간대가 그대로인지(새 파일이 안 받아졌으면 Ctrl+Shift+R).
- ⚠️ **rAF 재시도 갈래는 실제 브라우저에서 한 번도 돌지 않았다** — 실패하던 상태에서도 «배치 먼저 읽기» 만으로 동기로 들어갔다. 그 갈래는 가짜 요소([E])로만 확인했다.
- ⚠️ 남은 가장자리: 같은 프레임에 렌더가 한 번 더 오면 실패한 값(0)을 «이전 위치» 로 읽는다 · 두 번째 시도마저 실패해도 기록이 남지 않는다.
- ⛔ `content-visibility:auto` 를 끄는 방향으로 «정리» 하지 말 것.
- ⛔ 검사를 Playwright `page.click()` 으로 되돌리지 말 것 — 거짓 실패가 다시 난다.
- 같은 함정은 다른 관리자 카드에도 있을 수 있다 — «다시 그린 뒤 `scrollTop` 을 넣는» 코드를 새로 쓰면 `ph54SetScrollTop` 방식을 따르세요.

## English summary

**Problem.** In Admin › Teacher Schedule Calendar, opening a folded day could make the view jump back to the top (6 AM). The browser test "scroll position is kept (300)" kept failing.

**Causes (two).**
1. *Test tool.* Playwright's `page.click()` scrolls the element into view before clicking. The day header is a sticky header inside the calendar's scroll area, so that scroll reset the calendar to 0. A person clicks a header that is already visible, so this never happens to real users — it was a false failure.
2. *Real bug found while fixing it.* The admin page skips drawing off-screen cards (`content-visibility:auto`). When the card was in that skipped state, kept alive only by the focused header (tabindex=0), and that focused header was removed by `innerHTML`, Chromium silently ignored the next `scrollTop` assignment. Confirmed: turning draw-skipping off made the old code pass 3/3; reading `scrollHeight` before setting made it stick.

**Fix.**
- `adm-q6.js`: new `ph54SetScrollTop()` — ignore non-numbers (`null >= 0` is true), read layout first (`scrollHeight`), set, and retry once on the next frame if it did not stick. Both scroll assignments in `ph54Render` use it. Cache version bumped (`?v=22`, then `23`).
- Browser test clicks via focus + `el.click()` (no scroll), also checks Enter, and opens six days checking each one really opened.
- CI harness sections [E] (helper) and [E-2] (render wiring), both executed, not string-matched.
- CLAUDE.md pitfall row; the code comment's "rarely happens" claim is marked as an assumption.

**Verification.** Lanes harness 140/140 · browser test 26/26 (3 runs) · cancelled-card browser test 64/64 · regression PASS 669 / FAIL 0 · 12 automated mutations all fail as expected. Deployed Nov 4 at 01:59, 02:14 and 05:15 KST.

**Not measured.** How often this hit real users (likely rare — an assumption). The next-frame retry path never ran in a real browser; it was only verified with a fake element. Do not turn off `content-visibility:auto` to "fix" this.
