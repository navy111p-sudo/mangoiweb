## 1. 왜 했나

- 매니저 제보: «can we not delete the schedule if being cancelled? … add another column … No more cancel class option, I think it's okay as we all need postpone». 함께 온 화면에는 연기·변경 창의 «Cancelling a class is done by an HQ account.» 문구가 보였다.
  - 상태 칸(취소·연기)은 11/3(06b676ae)과 11/4 #2057 로 이미 반영됐다. 남은 것은 «권한 분리» 였다.
  - «No more cancel class option» 은 «강사·지사 화면에는 취소가 없어도 된다(연기만 쓴다)» 는 확인이다. 화면(연기·변경 창)은 이미 본사(canCancel)에게만 취소 버튼을 준다.
- 그런데 **서버는 강사 세션의 직접 호출을 막지 않았다.** `DELETE /api/admin/class-schedules/:id` 에는 역할 확인이 없었다. 그 경로는 강사 차단 접두사에도 없다. 강사가 같은 경로의 PATCH 로 수업을 옮기므로 접두사로는 막을 수 없다. 지사·대리점은 index.ts 스코프 관문이 이미 403 이다.

## 3. 왜 그렇게 풀었나 — 검토했다가 버린 방법

- **취소 기능 자체를 없애기** — 퇴원·환불·휴원·오입력을 정리할 길이 사라진다. 연기만 있으면 끝에 «보강» 회차가 계속 생겨 정산·급여·알림이 틀어진다. 제보도 «없어도 된다» 는 확인이었다. → 본사 전용으로 두고 서버에서 강사 직접 호출만 막았다.
- **강사 차단 접두사(index.ts)에 경로 추가** — 같은 경로를 강사가 PATCH(옮기기)로 쓴다. 접두사는 메서드를 가리지 않아 강사의 연기·변경까지 막힌다. 그리고 index.ts 는 공동 금지구역이다. → 핸들러 안에서 DELETE 만 막았다.
- **스코프(hq/none)로 판정** — 강사 계정 스코프가 잘못 'hq'·'none' 인 사례가 있다(index.ts «항상 role 기준»). → 역할(`isTeacher`)로 판정했다. K1 이 그 두 경우를 따로 잰다.
- **역할을 못 읽으면 통과** — 되돌릴 수 없는 쪽은 «모르면 막기» 가 맞다. 그래서 `!_delActor || !_delActor.ok` 도 403 이다(K2 · 변이 «역할 모름 통과» 로 확인).
- **원래 날짜 줄(옮겨 간 회차)도 이 PR 에서 구현** — 처음엔 이 세션도 만들었다(서버 판정·오늘 수업·강사 달력·화면 4종·하니스 M/J/P절, 약 127KB). 그런데 같은 기능이 다른 세션의 #2057 로 먼저 들어갔다. 두 판이 같은 함수 이름(`judgeMovedAway` 등)을 쓰고 있어 합치면 충돌한다. → 커밋하지 않고 버렸다. 그 판에만 있던 빈틈 두 가지의 논리는 그 세션에 메시지로 넘겼다(아래 §5 — #2069 로 반영됨).
