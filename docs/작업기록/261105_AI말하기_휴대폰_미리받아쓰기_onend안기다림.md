- 작업자: Claude (사장님 요청)

## 1. 왜 했나

사장님:
- 「휴대폰에서 A.i 말하기 아직도 아바타 대답 응대 속도가 느려. 더 빠르게 해줘. 내가 말하면 바로 응답하게 최대한 만들어줘.」
- 「**듣기 시간과 녹음시간** 등도 최소화해서 아바타가 말하는 것을 가능한 빨리 할 수 있게 해줘. 특히 휴대폰에서 더욱더 빨리해줘」

앞의 두 PR 로 «말 끝 판단»(침묵 시계·짧은 대답)과 «소음 때문에 20초 녹음» 은 고쳤다. 이번에는 **학생이 말을 마친 뒤 글자가 손에 들어올 때까지** 차례로 더해지던 대기를 봤다.

## 2. 원인 (코드를 읽고 내린 판단 — 실제 폰에서 몇 초인지는 못 쟀다)

| # | 경로 | 차례로 더해지던 것 |
|---|---|---|
| 1 | **녹음(Whisper)** — 안드로이드 «자동으로» · 앱(WebView) · 카카오 인앱 | 말 끝 → **침묵 1.6초를 다 기다림** → 그제야 업로드 → 서버 받아쓰기(약 1~2초 추정). 받아쓰기가 침묵 대기 «뒤» 에 시작해서 둘이 더해졌다 |
| 2 | **브라우저 인식(STT)** — 아이폰 · PC · 안드로이드 버튼 모드 | 침묵 1.2초 → `stop()` → 브라우저가 «최종 결과» 를 다시 받아 **`onend` 를 줄 때까지** 또 기다림 → 그 뒤에 전송. 그동안 화면은 «듣는 중» 그대로 |
| 3 | 자동 말하기 | AI 말이 끝나고 **0.6초** 뒤에야 마이크를 염(잔향 대기) — 그 뒤에 마이크 준비 시간이 또 붙는다 |

## 3. 바꾼 것

### ① 녹음 경로 «미리 받아쓰기» — 새 파일 `js/mangoi-voice-early.js` (defer, 웜업만 싣는다)

- 말이 멎고 **0.5초** 지나면 «지금까지 녹음분» 을 먼저 서버에 보내 받아 적어 둔다.
  - 그 사이 **다시 말하면 그 결과는 버린다**(다음 멈춤에서 새로 받는다 — «지난 말» 을 보내지 않는다).
  - **침묵 대기가 다 차서 끝나면** 미리 받은 글자를 그대로 쓴다 — 같은 말을 다시 올리지 않는다.
  - **자동 모드**: 받은 글자가 «끝난 말»(브라우저 인식 경로와 **같은 판정** `micUnfinished`)이고 **1초 넘게 조용했으면** 1.6초를 다 안 채우고 그 자리에서 끝낸다.
  - **수동(⏹) 모드**: 스스로 끝내지 않는다(⏹ 로만 끝남). 미리 받기만 해서 ⏹ 뒤 «받아적는 중» 을 줄인다.
- ⛔ **webm·ogg 만** — iOS 의 mp4 는 녹음 «도중» 을 잘라 보내면 서버가 못 읽을 수 있어 예전대로(끝까지 녹음 → 한 번 업로드).
- ⛔ **한 녹음에 미리 받기 5번까지** — 매번 «처음부터 지금까지» 를 올리므로 길게 쉬며 말하면 비용이 쌓인다.
- 미리 받기가 실패하면(서버 오류·네트워크) 끝에서 **예전처럼 전체를 올린다** — 글자를 잃지 않는다.
- 웜업 배선: `warmup.html` `_micEarly(manual, opts)` 가 `MangoiVoice.record(...)` 의 opts 를 감싼다. 모듈이 없거나 던지면 예전 opts 그대로.

### ② 공용 녹음 모듈 `js/mangoi-voice-input.js` (v8 → v9) — «고리» 만

- `opts.early(x)` — 말이 멎으면 `x = { snap, stop, mime }`(`snap()` = `requestData()` 로 받은 «지금까지 분량» FormData), 다시 말하면 `0`. **넘긴 화면만** 쓴다 — 다른 12개 화면은 `early` 를 안 넘겨 동작이 같다(하니스 A-3: `requestData` 0번).
  - ⚠️ 새 «상태값» 을 `onState` 로 퍼뜨리지 않은 이유: `student-game-avatar.html` 은 `stEl.textContent = m[state] || ''` 라 모르는 상태가 오면 안내 글자가 지워진다.
  - `early` 가 던져도 녹음은 계속된다(try/catch — 하니스 E-1).
- 기본 업로드를 `post(fd)` 로 빼서 `MangoiVoice.post` 로 내보냄(미리 받아쓰기가 같은 주소·같은 응답 해석을 쓰게 — 베끼지 않음). 파일 만들기는 `form(blob)` 하나로(끝 업로드와 미리 받기가 같은 이름·언어 힌트).
- **크기**: `index.html`·`student-games.html` 이 이 파일을 **첫 화면(blocking)** 으로 싣는데 `student-games.html` 여유가 **92바이트**였다(KB 반올림 기준으로 정확히 잼). 다른 줄과 겹치는 설명 주석을 줄여 파일은 원본보다 **+15바이트**(9,737 → 9,752). 판단 로직은 전부 ①의 defer 파일에 둔 이유가 이것이다.
- `?v=8 → ?v=9` 13개 화면 — **`index.html`(공동 금지구역)은 버전 숫자 한 줄**. 병합 버튼을 누르시는 것이 그 승인입니다(직전 PR #2098 과 같은 방식).

### ③ 브라우저 인식 경로 — `onend` 안 기다리기 (`warmup.html` `_micFast`)

- 침묵 타이머가 끝났을 때 **자동 모드 + 들은 말이 있으면** 그 인식기의 `onresult`·`onerror`·`onend` 를 떼고 `abort()` 한 뒤 **곧바로** `_finishMic()`(전송).
  - 떼는 이유: 늦게 온 최종 결과·`onend` 가 같은 말을 **또 보내지 않게**.
- **⏹ 를 누른 것도 같다**(`_micFast(true)` — `toggleMic` 이 세션 밖에서 `_micFastStop()` 으로 부른다). 버튼 모드가 **기본**이고, 폰 크롬·아이폰의 버튼 모드가 바로 이 경로라 휴대폰 학생 대부분이 여기에 해당한다.
- ⛔ 수동인데 침묵으로 끝난 것(입력칸에 남김)·빈손은 예전처럼 `onend` 뒤에 끝낸다 — 빈손이면 서버 Whisper 로 한 번 더 듣거나(🎤 C) «다음부터 녹음 방식» 으로 바꾸는데, 일부 안드로이드는 입력 세션이 하나뿐이라 **인식기가 다 닫힌 뒤** 마이크를 잡아야 한다.

### ④ 자동 말하기 마이크 여는 대기 — `js/warmup-auto-talk.js` `ARM_DELAY_MS` 600 → **300ms** (`?v=9`)

- 마이크 준비(권한·getUserMedia·인식기 시작) 0.1~0.5초가 이 뒤에 또 붙으므로 실제로 듣기 시작하는 것은 더 늦다. 녹음 경로는 에코 제거가 켜져 있고 말/조용 판정이 소음 바닥에 맞춘다.
- ⛔ 200ms 아래로는 내리지 않는다(스피커 잔향을 학생 말로 받음) — 하니스 0-3 이 «0.2~0.4초» 를 짝으로 본다.

## 4. 기대 효과 (시뮬레이션 — 서버 받아쓰기 0.8초로 가정)

| 경우 | 예전 «말 끝 → 글자» | 지금 |
|---|---|---|
| 녹음 경로 · 끝난 말(I like pizza.) | 1.6초 + 0.8초 = **2.4초** | 0.5초 + 0.8초 = **1.3초** (≈ −1.1초) |
| 녹음 경로 · 덜 끝난 말(I like) | 2.4초 | **1.6초**(미리 받아 둠) |
| 녹음 경로 · 수동 ⏹ | ⏹ + 0.8초 | 미리받기가 끝났으면 ⏹ **즉시** |
| 브라우저 인식(아이폰·PC) · 자동 | 1.2초 + `onend` 대기 | 1.2초 + **0** |
| 브라우저 인식 · ⏹ 누름(폰 크롬·아이폰 버튼 모드) | ⏹ + `onend` 대기 | ⏹ **즉시** |
| 자동 말하기 · 마이크 열림 | AI 말 끝 + 0.6초 | + **0.3초** |

⚠️ **실제 폰에서 잰 숫자가 아닙니다.** 서버 받아쓰기·`onend` 대기의 실제 길이는 이 환경에서 잴 수 없었습니다(운영 화면을 못 엶). `?lat=1` 로 보시면 «기다림·끝냄» 이 화면에 찍힙니다.

## 5. 맞바꿈 (사람이 알고 계셔야 할 것)

- **받아쓰기 호출이 늘어납니다** — 학생이 0.5초 넘게 쉬었다가 다시 말하면 그 미리 받기는 버려지고 새로 받습니다. 한 녹음에 최대 5번 + 끝 1번. 쉬지 않고 말하면 예전과 같은 1번입니다.
- **녹음 경로 «끝난 말» 은 1초 조용하면 보냅니다**(예전 1.6초). 「I like pizza. (1초 쉬고) And chicken.」 처럼 끝난 문장 뒤에 1초 넘게 쉬고 덧붙이면 뒤 문장이 잘릴 수 있습니다 — 브라우저 인식 경로(1.2초)와 같은 종류의 맞바꿈입니다. 늘리려면 `MIN_MS` 한 줄.
- 브라우저 인식 경로는 «최종 확정 결과» 를 안 기다리므로 마지막 순간에 인식기가 고쳐 적었을 글자(대소문자·마침표 수준)를 못 받습니다. 침묵 대기 동안 새 낱말이 없었던 상태라 대개 같습니다.

## 6. 검토했다가 안 한 것

- **TTS R2 캐시 저장을 기다리지 않기(`waitUntil`)** — `/api/voice/tts` 가 새 문장마다 `await r2.put` 을 끝낸 뒤에야 소리를 돌려준다(첫 문장마다 약 0.05~0.3초 추정). 그런데 `handleGamesApi(request, url, env)` 에 `ctx` 가 안 넘어와, 고치려면 **공동 금지구역 `src/index.ts`** 를 바꿔야 한다 → 사람이 정할 일. (await 없이 던져 두기는 응답 뒤 취소될 수 있어 안 함)
- **브라우저 인식 침묵 1.2초 더 줄이기** — 그 경로의 하한(«숨 한 번»)으로 앞 PR 들이 정한 값. 그대로.
- **녹음 비트레이트 낮추기(업로드 크기)** — 모든 화면(발음 채점 포함)의 소리 품질이 바뀌는 별건.
- **모델 바꾸기** — 가장 큰 덩어리(답 만들기 평균 3.9초)지만 교정 품질이 걸린 결정(앞 PR 과 같음).

## 7. 확인한 것

- 새 하니스 `voice_early_harness` **27/0** — 공용 모듈과 미리 받아쓰기를 **원문 그대로** 가짜 브라우저(대본대로 소리를 내는 마이크 · `requestData` 를 아는 가짜 녹음기 · 지연을 주는 가짜 서버 · 가짜 시계)에서 돌려 «언제 글자가 손에 들어왔나» 를 잼. 짝: 빨라짐(B) ↔ 다시 말하면 안 끊음·지난 말 안 보냄(C) ↔ iOS·실패·수동·상한(D) ↔ 고리가 던져도·공용 모듈이 옛 판이어도 녹음 계속(E) ↔ 다른 화면은 예전 그대로(A).
