**작성 2026-08-08** · 근거는 전부 이 저장소의 코드와 실측치입니다. 추정한 부분은 「추정」이라고 표시했습니다.

## 0. 한 장 요약

먼저 통념 하나를 깨고 시작해야 합니다.

**필리핀의 문제는 «느린 인터넷»이 아닙니다.** 2025년 7월~2026년 6월 기준 필리핀 모바일 평균은 다운로드 47.4 Mbps · 핑 49ms, 고정회선은 109 Mbps · 핑 29ms입니다. 숫자만 보면 우리 서비스를 돌리기에 부족하지 않습니다.

진짜 문제는 **평균이 아니라 «끊김»** 입니다. 정전(브라운아웃), 태풍, 지역 편차, 그리고 한 집에 여러 명이 물린 공유회선. 우리 제품이 이미 그걸 알고 있습니다 — `/teacher` 화면에 **「정전 · 인터넷 장애가 났나요?」 카드**가 이미 있고, 강사가 그걸 누릅니다.

그래서 이 제안서의 뼈대는 이렇습니다.

> **바이트를 줄이는 것보다 «끊겨도 죽지 않는 것»이 몇 배 중요하다.**

그리고 측정해 보니, 우리는 이미 절반은 해 놓았고 절반은 정반대로 해 놓았습니다.

| | 지금 | 제안 후(추정) |
|---|---|---|
| 강사 `/teacher` | **0.83초** · 요청 3개 | 그대로 + 기능 완결 |
| 매니저 `/admin/mypage` | 2.42초 · 요청 17개 | — |
| 매니저가 실제로 쓰는 화면 `admin.html` | **19~21초** · 요청 145개 | **1.5초 이내** · 요청 10개 이하 |
| 끊겼을 때 | 화면이 비거나 멈춤 | 마지막 화면이 그대로 뜨고, 쓴 내용은 큐에 담겼다 나중에 전송 |

*(회선 조건: 지연 350ms · 400KB/s 흉내 서버로 측정. 흉내 서버는 HTTP/1.1이라 요청 수 벌점이 실서비스(HTTP/3)보다 과장돼 있습니다. 절대값보다 «비교»로 보시면 됩니다.)*

## 1. 먼저 확인된 사실 — 이게 제안의 근거입니다

### 1-1. 강사는 이미 가벼운 화면을 씁니다

`admin/login.html:304`가 teacher 역할을 `/teacher`로 보냅니다. 그래서 강사는 `admin.html`을 아예 받지 않습니다.

```
/teacher            0.83초   요청 3개    DOM 노드 141개
/admin/mypage       2.42초   요청 17개   DOM 노드 383개
admin.html         19~21초   요청 145개  DOM 노드 8,762개
```

**25배 차이입니다.** 강사 쪽은 이미 잘 되어 있습니다.

### 1-2. 그런데 매니저(지사·대리점)는 934KB짜리 화면을 받고, 그중 90%는 못 씁니다

`src/index.ts`의 `isAgencyAllowedApi`가 지사·대리점에게 허용하는 API를 명시적으로 정해 두었습니다. 그 목록과 `admin.html`이 실제로 부르는 API를 대조했습니다.

> **admin.html 계열이 부르는 관리자 API: 231개**
> **매니저에게 서버가 허용하는 것: 25개 (10%)**
> **→ 매니저는 화면의 약 90%를 「열어도 403」으로 만납니다.**

`js/adm-scope-guard.js`라는 파일이 이미 있는데, 하는 일이 **"어차피 403 날 요청을 아예 안 보내서 콘솔 에러를 조용히 만드는 것"** 입니다. 파일 머리 주석에 그렇게 적혀 있습니다.

즉 우리는 **"매니저에게는 안 맞는 옷"이라는 걸 이미 알고 있었고, 옷을 바꾸는 대신 소음만 껐습니다.**

### 1-3. 서비스워커는 관리자 화면에서 «일부러» 꺼져 있습니다

`public/sw.js:63`에 이렇게 적혀 있습니다.

> 🛡️ (2026-07-22) 관리자 화면은 SW 캐시를 아예 안 태움 — 네트워크로 직접 통과.
> networkFirst의 timeout(4~5초) 폴백이 느린 회선에서 "옛날 CSS/이미지/API 응답"을 보여줘 관리자 페이지에 옛 화면 잔상이 생기던 원인.

**이 판단은 그때는 옳았습니다.** 다만 전제가 바뀌었습니다. 뒤에서 다시 다룹니다(3장).

## 4. 제안 C — 오프라인 캐시(서비스워커)

### 4-1. 지금 상태를 정확히 알고 시작해야 합니다

- 서비스워커 `public/sw.js`는 **살아 있고 배포돼 있습니다**(10KB).
- 전략은 **전 경로 네트워크 우선(network-first)** 입니다.
- 그런데 **관리자 계열은 통째로 제외**돼 있습니다 — `/admin.html`, `/admin/*`, `/js/adm-*`, `/api/admin/*`, 그리고 관리자 페이지가 불러오는 모든 서브리소스(referrer로 판정).
- 그리고 **배포할 때마다 캐시 이름이 바뀝니다**(`mangoi-20260808074508-fresh`). 즉 **배포 한 번에 전 사용자 캐시가 통째로 버려집니다.**
- `controllerchange → reload`는 관리자에서 제거됐고 **재추가 금지**로 못이 박혀 있습니다. 학생 홈에서는 「로드 30초 이내엔 reload 안 함 · 수업 중엔 절대 안 함」 조건부로 남아 있습니다.

### 4-2. 왜 껐는지, 무엇이 달라졌는지

당시 이유는 명확했습니다. **network-first의 4~5초 타임아웃 폴백**이 느린 회선에서 자주 발동해서, 옛날 CSS·이미지·API 응답이 나와 «옛 화면 잔상»을 만들었습니다. 관리자에게는 오프라인보다 최신성이 훨씬 중요하니 끄는 게 맞았습니다.

**달라진 것 — 그 판단은 «전부 아니면 전무»의 선택이었습니다.** 지금은 나눌 수 있습니다.

| 자원 종류 | 옛 방식 | 제안 |
|---|---|---|
| `?v=` 붙은 JS·CSS (내용이 바뀌면 URL이 바뀜) | 캐시 안 함 | **cache-first(영구)** — 옛 것이 나올 수가 없습니다. URL이 곧 버전이므로 |
| 이미지·아이콘·폰트 | 캐시 안 함 | **cache-first** |
| HTML | 네트워크 우선 + 4초 폴백 | **네트워크 우선, 폴백은 «완전 실패»일 때만**(타임아웃 폴백 없음) |
| 읽기 API(`GET /api/admin/*`) | 캐시 안 함 | **캐시 안 함** — 그대로 둡니다 |
| 쓰기 API(POST 등) | — | **오프라인이면 큐에 담고 복구 시 전송**(Background Sync) |

핵심은 **「옛 화면 잔상」을 만든 범인이 정확히 「타임아웃 폴백」이었다**는 점입니다. 그것만 빼면 나머지는 안전합니다. **`?v=` 자산은 URL이 곧 내용이라 오래된 것을 줄 수가 없습니다.**

또 하나 — 지금은 **배포마다 캐시를 통째로 버립니다.** `?v=` 자산을 파일 단위로 캐시하면 **배포해도 안 바뀐 파일은 그대로 재사용**됩니다. 지금은 JS·CSS가 `max-age=31536000, immutable`이라 브라우저 HTTP 캐시가 이미 그 일을 하고 있는데, **서비스워커가 그걸 매 배포마다 무효화하는 쪽으로 작동**하고 있습니다.

### 4-3. 무엇을 넣을 것인가

1. **`?v=` 자산 cache-first** — 두 번째 방문부터 JS·CSS 요청 0건
2. **타임아웃 폴백 제거** — 「옛 화면 잔상」의 원인 제거
3. **오프라인 안내 화면** — 끊기면 흰 화면 대신 「지금 인터넷이 끊겼습니다. 마지막으로 본 내용입니다」
4. **쓰기 큐(Background Sync)** — 강사가 **피드백을 쓰다가 정전**되면 지금은 날아갑니다. 큐에 담았다가 복구 시 자동 전송
5. **서버 멱등성 키** — 큐 재전송이 중복 저장을 만들지 않도록 `operation_id`

### 4-4. 무엇을 안 할 것인가 (금지 유지)

- ❌ **`controllerchange → 자동 reload` 재추가 금지** — 과거 사고 원인. CLAUDE.md에도 금지로 명시
- ❌ **읽기 API 캐시 금지** — 관리자에게 옛 데이터를 보이면 안 됩니다
- ❌ **오디오/비디오·Range 요청 가로채기 금지** — 이미 무음 버그로 제외돼 있음
- ❌ **화상수업(`/ws/*`) 근처는 손대지 않음**

### 4-5. 예상 효과

| 상황 | 지금 | 제안 후(추정) |
|---|---|---|
| 두 번째 방문(캐시 있음) | JS·CSS 재검증 왕복 | **요청 0건, 즉시 표시** |
| 배포 직후 첫 방문 | 캐시 전체 폐기 → 처음부터 | 바뀐 파일만 새로 |
| 수업 중 인터넷 10초 끊김 | 화면 요소가 비거나 멈춤 | 마지막 화면 유지 |
| 피드백 쓰다 정전 | **작성 내용 유실** | 큐 보관 → 복구 시 자동 전송 |

**⚠️ 이건 사장님 결정 사항입니다.** 과거에 의도적으로 끈 것을 되살리는 일이라, 제 판단만으로 하지 않았습니다. 다만 위처럼 **「무엇을 캐시하고 무엇을 안 하는지」를 자원 종류별로 갈라 두면** 그때의 사고는 재발하지 않는다고 봅니다.

## 5. 경쟁사·글로벌 기업에서 배울 것

### 5-1. 우리 업계는 «요구사항»으로 해결합니다 — 여기가 기회입니다

51Talk의 재택 강사 기술요건은 **인터넷 25 Mbps 이상**, i5 10세대, RAM 8GB입니다. 즉 업계 표준 해법은 **"좋은 회선을 가진 강사만 뽑는다"** 입니다.

이건 엔지니어링이 아니라 **채용 필터**입니다. 그리고 그만큼 **강사 풀이 좁아집니다.**

> **배울 점이 아니라 «반대로 갈 기회»입니다.**
> 우리가 「25 Mbps 없어도 되는 플랫폼」이 되면, 지방·소도시 강사를 쓸 수 있습니다. 이건 원가와 채용 속도에 직접 영향을 줍니다.

### 5-2. Meta — Facebook Lite: «클라이언트를 얇게, 서버를 두껍게»

Facebook Lite는 APK **1MB 미만**이고, 2009년형 저사양 기기(RAM 290MB)에서 도는 것을 목표로 만들었습니다. 핵심 설계는 **화면 레이아웃 계산 같은 무거운 일을 서버가 하고, 클라이언트는 그리기만 하는 것**입니다. 애니메이션과 무거운 UI 상호작용은 아예 피했습니다.

**우리에게 적용:**
- `admin.html`은 정반대입니다 — JS 600KB(gz)를 내려서 클라이언트가 전부 계산합니다.
- 매니저 페이지는 **서버가 만든 요약을 받아 그리기만** 하는 구조로 가야 합니다.
- 우리가 이미 뺀 것들(hover 확대, 애니메이션)이 같은 방향이었습니다. 일관되게 밀면 됩니다.

### 5-3. Google — YouTube Go: «비용을 사용자에게 보여준다»

YouTube Go는 기존 앱에 기능을 더하고 빼는 걸로는 안 된다고 보고 **처음부터 다시 만들었습니다.** 그리고 홈 화면에 **각 영상이 데이터를 얼마나 쓰는지 표시**했습니다.

**우리에게 적용:**
- 「처음부터 다시」가 바로 제안 A·B의 논리입니다. `admin.html`을 깎는 것보다 **역할별로 새로 만드는 것**이 옳습니다. 이미 `/teacher`로 증명됐습니다(25배).
- **데이터 비용 표시**는 우리도 쓸 수 있습니다. 예: 녹화 다시보기 버튼에 「약 40MB」 표시. 강사가 데이터 요금을 스스로 관리하게 됩니다.
- Google의 「Building for Billions」는 연결성·기기성능·**데이터 요금·배터리**·콘텐츠 5개 축으로 봅니다. 우리는 지금까지 연결성만 봤습니다. **배터리**는 이번에 처음 손댔습니다(UI 보정 루프를 숨은 탭에서 늦춤).

### 5-4. Learning Equality — Kolibri: «인터넷을 선택사항으로»

Kolibri는 카빈 없는 지역을 위해 **인터넷 없이 도는 교육 플랫폼**입니다. 라즈베리파이 같은 저가 기기에 담아 **로컬 네트워크로 기기끼리 콘텐츠를 나눠 갖습니다.** 30개국·196개 지역에서 씁니다.

**우리에게 적용:**
- 화상수업은 본질적으로 온라인이라 Kolibri처럼 갈 수는 없습니다.
- 다만 **「예복습·단어장·퀴즈」는 오프라인으로 갈 수 있습니다.** 정전 중에도 학생이 학습을 이어갈 수 있다면 그건 경쟁사에 없는 기능입니다.
- **우선순위는 낮게 봅니다.** 지금은 강사·매니저 화면이 먼저입니다.

### 5-5. 업계 공통 — 오프라인 우선 설계의 정석

현재 표준은 이렇게 정리됩니다.

- **네트워크를 «있으면 좋은 것»으로 다룬다** — 없을 때를 기본으로 설계
- **자원 종류별로 캐시 전략을 다르게** — app shell은 미리 캐시, 신선도가 필요한 읽기는 network-first, 나머지는 stale-while-revalidate
- **쓰기는 큐에 담는다** — 탭을 닫아도 서비스워커가 나중에 재전송
- **서버는 중복 전송을 견뎌야 한다** — 재전송이 전제이므로 **멱등성 키 필수**

마지막 항목이 우리에게 가장 중요합니다. **큐를 넣으려면 서버가 먼저 준비돼야 합니다.** 이건 프런트만의 일이 아닙니다.

### 5-6. 우리가 이미 잘하고 있는 것 (버리지 말 것)

- 화상수업 **저대역폭 오디오 전용 모드(AAO+DTX)** — 회선이 나쁠 때 영상을 버리고 소리를 지키는 것. 정확한 판단입니다
- **`dropped` 상태로 수업을 자동 종료하지 않는 것** — 「끊김 ≠ 종료」. 오프라인 우선 사고방식 그 자체입니다
- **정전·장애 신고 카드** — 사용자가 상황을 알리는 통로. 경쟁사에는 잘 없습니다

## 부록 — 측정 방법

로컬은 응답이 1ms라 「동시에 겹치는 요청」도 「느린 회선」도 재현되지 않습니다. 그래서 지연·대역폭·동시요청 경합을 흉내내는 서버를 만들어 측정했습니다(지연 350ms · 400KB/s · 동시 요청이 실제로 대역폭을 나눠 씀).

이 흉내 서버로만 잡힌 문제가 4개였습니다.

1. 학생 2,000명 명부가 4ms 안에 5건씩, 세 차례 = 15건 나가고 있었음
2. 회선 판정을 `load` 이벤트 뒤에 하면 **느린 회선일수록 늦게 알아차리는** 정반대 구조가 됨
3. `navigator.connection`은 회선의 «이름표»만 말함 — 「표시는 4G인데 실속도는 형편없는」 경우를 통째로 놓침
4. 36px로 그리는 마스코트 이미지가 1136px·283KB였고, 그게 mypage에서 가장 무거운 파일이었음

**⚠️ 흉내 서버의 한계:** HTTP/1.1(연결 6개)이라 요청 수 벌점이 실서비스(HTTP/3 다중화)보다 과장돼 있습니다. 이 문서의 절대 시간값보다 **«비교»** 로 읽으시는 것이 정확합니다.
