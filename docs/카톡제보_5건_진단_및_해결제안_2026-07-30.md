## 1. 비로그인 결제 허용 🔴 P0

### 확인된 사실

결제 흐름의 **어느 단계에도 로그인 여부를 막는 코드가 없습니다.**

| 지점 | 파일:라인 | 실제 동작 |
|---|---|---|
| 결제창 진입 | `idx-payment-modal.js:91-129` (`openPaymentModal`) | 로그인 여부와 무관하게 모달이 열림. 로그인 상태면 안내 배너만 하나 더 보일 뿐 |
| 카드 결제 | `idx-payment-modal.js:427-486` (`executeCardPayment`) | `getCurrentUser()`가 null이면 `uid: null`로 그대로 서버 전송 |
| 가상계좌 결제 | `idx-payment-modal.js:496-552` (`executeVirtualAccountPayment`) | 위와 동일 |
| 결제 완료 확인(수기접수) | `idx-payment-modal.js:1161-1186` (submit 핸들러) | 결제자·학생·연락처 **텍스트 입력값**만 검사, 로그인 여부는 검사하지 않음 |
| 서버 주문 생성 | `api-pay.ts:94, 141` | `const uid = String(body.uid||'').trim() || null;` — uid가 없어도 주문이 정상 생성(INSERT 성공) |

유일하게 로그인을 강제하는 곳은 어제 제가 만든 **1:1 수강권 → `enroll.html` 리다이렉트**(`idx-payment-modal.js:320`)뿐입니다. 그런데 이건 "1:1 상품 + 로그인 상태"일 때만 걸리는 조건이라, **비로그인 상태**이거나 **그룹/비즈니스/키즈/시험 등 1:1이 아닌 상품**이면 그대로 뚫립니다.

**즉 지금은 회원가입도, 로그인도 하지 않은 방문자가 그룹 수업이나 키즈 영어를 카드로 결제까지 끝낼 수 있는 상태**이고, 그 결제 기록은 `payment_orders.uid = NULL`로 저장돼 나중에 수강 배정도, 결제 내역 조회도, 환불 처리도 안 됩니다.

### 해결 방안

**클라이언트 + 서버 이중 방어** (한쪽만 하면 우회 가능하므로 반드시 둘 다):

1. **클라이언트**: 상품 카드를 클릭하는 시점(`document.querySelectorAll('.product-card')` 클릭 핸들러, `idx-payment-modal.js:292` 부근)에서, 선택한 상품이 유료(가격 > 0)이고 `getCurrentUser()`가 없으면 **로그인 모달을 강제로 띄우고 결제 단계 진입을 막습니다.** 로그인 완료 후 원래 선택했던 상품으로 자동 복귀시킵니다.
2. **신규 회원(비회원)의 경우**: 로그인 모달에 "회원가입" 링크가 이미 있으므로, 그 경로를 그대로 타면 됩니다. 결제 이전에 반드시 회원가입 → 로그인이 선행되도록 흐름만 강제하면 되고, 별도 신규 개발은 필요 없습니다.
3. **서버**: `api-pay.ts`의 `/api/pay/create-order`, `/api/pay/manual-request` 둘 다 `uid`가 없으면 **400 거부**로 바꿉니다(현재는 null 허용). 클라이언트를 우회해서 API를 직접 호출해도 막히도록 하는 최종 방어선입니다.
4. **무료체험(trial)·상담(other) 제외 여부**: 무료체험은 이미 결제 자체를 안 거치고(`/api/student/inquiry`로 분리됨, 어제 조치), 'other'(맞춤 상담)는 서버 가격표에 없어 카드/가상계좌로는 원천적으로 완결 안 됩니다. 다만 수기접수(`manual-request`)의 'other' 경로는 지금 로그인 없이도 접수는 가능하므로, 일관성을 위해 이 경로도 로그인을 요구하도록 함께 처리하겠습니다.

**공수**: 클라이언트 가드 0.5일 + 서버 검증 0.5일 = **총 1일**. 기존 로그인 모달·회원가입 흐름을 그대로 재사용하므로 새 화면은 필요 없습니다.

## 2. 강사 선택 화면 — 사진·MBTI·요일·시간대 🟠 P1

이 항목은 4개 요청이 섞여 있는데, **성격이 완전히 다릅니다.** 하나씩 보겠습니다.

### 2-1. 강사 사진·MBTI 미노출 — 구조적 문제 (관리자 화면 손보는 걸로는 해결 안 됨)

**확인된 사실**: 강사 관련 데이터가 서로 **연결되지 않은 3개의 테이블**에 흩어져 있습니다.

| 테이블 | 용도 | 건수 | 사진 | MBTI |
|---|---|---|---|---|
| `teachers` | 급여·스케줄용 (enroll.html이 강사 목록을 여기서 가져옴) | 29건 | ❌ 컬럼 자체가 없음 | ❌ 컬럼 자체가 없음 |
| `teacher_profiles` | 인사 프로필(관리자 화면) | 30건 | ✅ `image_url` 26건 | ✅ `mbti` 컬럼 보유 |
| `teacher_mbti` | `mbti.html` 매칭 전용 | 19건 | ✅ `photo_url` | ✅ `mbti` |

`enroll.html`의 강사 선택 화면(`enroll-ops.ts:473`)은 `teachers` 테이블만 조회합니다. 이 테이블엔 애초에 사진·MBTI 컬럼이 없어서(SELECT 자체가 실패하고 폴백 쿼리로 넘어감, `enroll-ops.ts:477`), 아무리 관리자 화면에서 사진을 올려도 **올릴 곳이 없습니다.**

더 심각한 건, `teachers.name`과 `teacher_profiles.korean_name/english_name`, `teacher_mbti.teacher_uid`를 서로 대조해봤더니 **29명 중 정확히 매칭되는 사람이 1명뿐**이었습니다(이름 표기가 다르거나, 애초에 다른 사람 목록이거나). 즉 "사진 테이블에 사진이 있으니 그냥 조인하면 된다"가 아니라, **어느 `teachers.id`가 어느 `teacher_profiles` 행인지 지금은 시스템이 알 방법이 없습니다.**

**해결 방안** — 2단계로 나눠야 합니다:

- **1단계 (개발)**: `teacher_profiles` 테이블에 `linked_teacher_id INTEGER` 컬럼을 추가하고, `enroll.html`의 강사 목록 쿼리가 `teachers`에 이 컬럼으로 LEFT JOIN해서 `image_url`·`mbti`·`intro_video_url`을 함께 받아오도록 수정합니다. 급여·스케줄 로직은 지금처럼 `teachers.id`를 그대로 쓰므로 **기존 기능에 영향 없음**.
- **2단계 (데이터 작업, 사람이 해야 함)**: 29명의 `teachers.id` ↔ `teacher_profiles.id` 매칭표를 만들어야 합니다. 이름이 안 맞아서 코드가 자동으로 매칭할 수 없고, **잘못 매칭하면 다른 강사의 사진이 나가는 사고**가 됩니다. 관리자 화면에 "이 급여용 강사 계정은 이 프로필입니다"를 고르는 드롭다운을 하나 만들어 사람이 확인하며 연결하는 것을 권장합니다.
- MBTI는 `teacher_profiles.mbti`를 그대로 쓰면 되고(이미 있음), `mbti.html`과의 연동은 이번 작업 범위에 포함하지 않고 "강사 선택 화면에 MBTI 노출"까지만 우선 처리하는 것을 제안합니다(연동은 `teacher_mbti` 테이블까지 얽혀 있어 별도 검토 필요).

**공수**: 1단계 개발 0.5일. 2단계 매칭 작업은 **사람이 해야 하는 일**이라 개발 공수에 포함 안 됨 — 아래 §4 결정 필요 항목 참고.

### 2-2. 요일 선택에 토·일요일이 노출됨 — 간단한 수정

`enroll.html:165`의 요일 배열이 일~토 7일을 전부 그대로 보여주고 있습니다. 정책상 평일만 되는데 막고 있는 코드가 없었을 뿐입니다.

**해결**: 요일 칩 렌더링에서 일(0)·토(6)를 제외한 월~금만 클릭 가능하게 하고, 그 자리에 "주말 수업은 별도 문의" 버튼(카카오 상담 연결)을 넣습니다. **공수 0.5일.**

### 2-3. 요일별로 다른 시간 지정 불가 — 데이터 구조 자체를 바꿔야 함

지금 구조는 "요일 여러 개 + 시각 1개"입니다(`st.time`은 문자열 하나, `st.days`는 배열 — 모든 요일에 같은 시각이 적용됨). 서버 파싱(`enrollParse`, `enroll-ops.ts:187-207`)도 같은 구조입니다.

"월요일 19시, 수요일 20시"처럼 요일마다 다른 시각을 넣으려면:
- 화면: 요일 칩을 고르면 그 요일 옆에 개별 시각 선택이 나오는 UI로 교체
- 서버: 슬롯 충돌 확인(`enrollConflicts`)과 스케줄 생성(`enrollCreateSchedules`)이 지금은 "요일 배열 + 시각 1개"를 전제로 짜여 있어서, "요일-시각 쌍의 배열"을 받도록 로직을 다시 짜야 합니다.

이건 UI 몇 줄 고치는 게 아니라 **수강신청 스케줄링 로직의 재설계**에 가깝습니다. 다른 3개 항목과 묶지 말고 별도 작업으로 잡는 것을 권장합니다. **공수 2~3일** (충돌검사·저장 로직 회귀 위험 있어 테스트 비중이 큽니다).

## 3. 학부모 페이지 인증 잔존 🟠 P1

### 확인된 사실

`parent.html:893-905`에서 최초 인증 성공 시 `localStorage`에 `mangoi_parent_uid` + `mangoi_parent_token`을 저장하고, 다음 방문부터는 이 토큰만 있으면 비밀번호 재입력 없이 바로 대시보드(`pdLoad()`)가 열립니다.

토큰 자체는 서버가 서명(`auth-token.ts:29`)하므로 위조는 불가능합니다. 문제는 **유효기간이 30일**이라는 점입니다(`signUidToken(uid, env, ttlMs=30*86400*1000)`). 같은 브라우저를 쓰는 자녀(학생)가 30일 이내에는 비밀번호 없이 학부모 페이지를 열 수 있습니다. 비밀번호를 아예 설정하지 않은 계정은 uid만으로도 토큰이 발급됩니다(`api-students.ts:429`).

### 해결 방안

제보 원문에 이미 정확한 방향이 적혀 있습니다: **"기본값은 매번 재인증, 필요한 사람만 선택적으로 자동로그인 유지."** 이대로 구현하는 것을 제안합니다.

1. 학부모 페이지 진입 시 **기본은 항상 비밀번호(또는 동등한 인증) 재입력**을 요구합니다. 지금처럼 토큰만 보고 자동으로 열리는 경로를 제거합니다.
2. 인증 화면에 **"이 기기에서 30일간 로그인 유지"** 체크박스를 추가합니다. 기본값은 **체크 해제**. 학부모가 직접 체크해야만 토큰이 저장됩니다.
3. 체크하지 않았다면, 페이지를 벗어나는 순간(또는 세션 종료 시) 토큰을 즉시 지웁니다.
4. 로그아웃 버튼을 누르면 로컬 토큰과 서버측 유효성 모두 확실히 만료되는지 함께 점검합니다.

**공수**: 0.5~1일. UI(체크박스 하나)와 저장 조건 분기만 바꾸면 되고, 서버의 토큰 서명·검증 로직은 그대로 재사용합니다.

## 4. 연장결제 "결제수단 선택" 미노출 🔴 P0

### 확인된 사실 — 여기가 이번 제보에서 가장 심각합니다

연장결제(같은 코스/업그레이드/추가회차) 흐름에서 "결제수단 선택"까지는 정상적으로 화면에 진입합니다(`selectedProgram`/`selectedPrice` 동기화 코드 자체는 정상 동작, `idx-payment-modal.js:236-247`). 하지만 **어떤 결제수단을 선택해도 결제가 완결되지 않습니다.**

원인은 연장 패키지에 붙는 ID 값입니다.

```js
// idx-payment-modal.js:860, 880, 916
id: s.current_program + '-extend',        // 예: '1on1-8-extend'
id: series[idx+1] + '-extend',            // 업그레이드
id: 'addon-' + n,                         // 추가회차
```

이 ID들을 그대로 서버에 보내는데, 서버의 가격표(`api-pay.ts:26-42` `PRICES`)에는 `1on1-8`, `group-12` 같은 **신규 구매용 상품 ID만** 있습니다. `1on1-8-extend`, `addon-8` 같은 연장 전용 ID는 **단 하나도 없습니다.** 그래서:
- 카드/가상계좌(`create-order`) → `unknown_program` 오류로 거부(`api-pay.ts:103`)
- 카카오·토스·계좌이체(`manual-request`) → `not_payable` 오류로 거부(`api-pay.ts:167`)

즉 결제수단 카드 자체는 보이지만, **어느 것을 눌러도 서버가 상품을 못 알아봐서 결제가 끝까지 갈 수 없는** 상태입니다. (제보 원문의 "빈 화면"이라는 표현과 정확히 같은 증상인지는 알림창이 뜨는지 여부에 따라 다를 수 있어, 수정 후 실제 클릭으로 재확인이 필요합니다.)

**더 중요한 사실 하나**: `enroll.html`에는 이미 **정상 동작하는 별개의 연장결제 기능**이 있습니다(`/api/pay/enroll/renew-order`, `enroll-ops.ts:557`). 이쪽은 금액을 고정 가격표에서 찾지 않고 **서버가 그때그때 다시 계산**해서 정확한 금액으로 주문을 만듭니다. 즉, **이번에 고친 홈 결제창의 연장 기능과, 이미 잘 되고 있는 enroll.html의 연장 기능이 서로 다른 두 벌로 존재**하고 있었고, 새로 만든 쪽(홈 결제창, 업그레이드·추가옵션까지 지원하는 더 복잡한 버전)이 처음부터 서버와 안 맞은 채로 배포됐던 것으로 보입니다.

### 해결 방안 — 두 가지 선택지

| 안 | 내용 | 장단점 |
|---|---|---|
| **A. 서버가 연장 금액을 동적으로 인식하게 함** | `create-order`/`manual-request`가 연장 주문일 때는 고정 가격표 대신, 클라이언트가 계산한 금액을 서버가 다시 계산해서 대조하는 방식으로 바꿈(`enroll.html`의 renew-order가 이미 하는 방식과 동일) | 지금의 업그레이드·추가옵션(강사고정·영작첨삭 등) 기능을 그대로 살릴 수 있음. 다만 이 복잡한 로직이 실제로 한 번도 결제 성공까지 간 적이 없어서(서버가 항상 거부해왔으므로), 검증이 많이 필요함 |
| **B. enroll.html의 이미 검증된 연장 기능으로 통일** | 홈 결제창의 "연장 결제" 버튼을 눌렀을 때, 어제 1:1 신규결제를 enroll.html로 보낸 것과 같은 방식으로 연장도 enroll.html로 보냄 | 이미 정상 동작 확인된 코드를 재사용해 안전함. 다만 업그레이드·추가옵션(부가서비스) 같은 세부 기능은 enroll.html에 없어서, 그 기능을 원하시면 이 안으로는 부족함 |

**권장**: **B안.** 이유는 어제와 같습니다 — 검증된 코드를 재사용하는 편이 사고 반경이 작고, 지금 A안대로 복잡한 로직을 살리려면 "한 번도 성공한 적 없는 기능"을 처음부터 제대로 검증해야 해서 오히려 공수가 더 듭니다. 업그레이드·추가옵션 기능이 꼭 필요하시면 A안으로 가되, 그 경우는 별도 일정으로 잡는 것을 제안합니다. **어느 안으로 갈지는 의사결정이 필요합니다 (§4 참고).**

**공수**: B안 1일 / A안 2~3일(검증 포함).

- 그 자리가 비면서 카드 레이아웃이 어색해지지 않는지 확인 후 여백을 재정렬합니다.

## 7. 결정이 필요한 사항

1. **#4 연장결제 — A안(기능 유지, 검증 필요) vs B안(검증된 기능 재사용, 일부 기능 축소)** 중 선택 필요. 업그레이드·부가옵션(강사고정·영작첨삭 등) 기능이 실제 운영에 꼭 필요한 기능인지 확인 부탁드립니다.
2. **#2-1 강사 사진·MBTI 연결 — 29명분 매칭 작업**은 개발이 자동으로 할 수 없습니다(이름이 안 맞아 자동 매칭 시 강사를 잘못 연결할 위험). 관리자 화면에 매칭용 드롭다운을 만들어 사람이 확인하며 연결하는 방식을 제안드리는데, 이 작업을 누가·언제 할지 정해주셔야 합니다.
3. **#2-3 요일별 다른 시간 지정**은 스케줄링 로직 재설계급 작업이라 다른 항목과 일정을 분리하는 걸 권장드립니다 — 언제까지 필요하신지 알려주시면 그에 맞춰 일정을 잡겠습니다.
