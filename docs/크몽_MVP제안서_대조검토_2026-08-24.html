외주 제안서 대조 검토

망고아이에 없는 것과
있어도 보완할 것

「망고아이 화상영어 플랫폼 신규 구축(MVP) 제안」(크몽 엔터프라이즈 × 똑똑한개발자, 2026.08)을
현재 운영 중인 망고아이 코드베이스와 항목별로 대조한 결과입니다.

한 줄 결론

제안서가 6,600만원에 「신규 구축」하겠다는 MVP 범위는 망고아이가 이미 갖고 있는 것의 부분집합입니다. 다만 그 안에 정말로 우리에게 없는 것이 3가지 있고, 그중 하나(환불 실행·기록)는 실제 돈이 오가는데 시스템에 흔적이 남지 않는 상태라 우선 처리가 필요합니다.

검토 대상  제안서 10쪽 (MVP 6,600만원 / AI 추가 시 7,700만원)
대조 기준  저장소 navy111p-sudo/mangoiweb — 백엔드 96개 파일, 화면 HTML 100여 개, 회귀 하니스 222종
검토 방법  소스 코드 직접 확인 (실서비스 DB·화면은 이 환경에서 접근할 수 없어 코드 기준으로 판정)
작성일  2026-08-24

SECTION 2 · A

현재 망고아이에 없는 것

제안서 범위 안에서, 코드로 확인한 실제 결손 4건입니다.

최우선A-1. 환불을 «실행»하고 «기록»하는 길이 없습니다

있는 것 환불 금액 계산기 하나. 기간 할인을 취소하고 정가로 사용분을 정산해 잔액을 산출합니다.
없는 것 ① 결제 취소(PG) 호출 ② 환불 신청 접수 → 승인 → 실행 흐름 ③ 환불 내역 테이블 ④ 관리자 화면의 환불 처리 버튼
결과 환불은 담당자가 토스 대시보드에서 직접 처리하게 되고, 우리 시스템에는 그 사실이 남지 않습니다. 나중에 신한 계좌 거래 적요를 「학생환불」로 분류해 사후에 금액만 회계에 잡습니다 — 누가·왜·어느 주문을 환불했는지는 복원할 수 없습니다.
왜 중요한가 환불은 분쟁이 가장 잦은 지점입니다. 「얼마를 언제 왜 돌려줬는지」를 시스템이 못 말하면 학부모 응대와 회계 대사가 모두 사람 기억에 의존하게 됩니다. 제안서도 이 항목만은 MVP에 넣었습니다.
확인 방법 토스 API를 부르는 지점은 코드 전체에 4곳뿐이며(payments/confirm, billing/authorizations/issue, billing/{key}, payments/orders/{id}) 결제취소(payments/{key}/cancel)는 0건입니다. enroll-ops.ts:1104 주석에도 「계산만. 실제 환불 실행은 사람이」라고 적혀 있습니다. admin.html에서 「환불」이 나오는 12곳은 전부 계산기·안내문·회계 조회입니다.

확장A-2. 코스(상품) 카탈로그가 없습니다

현재 수강신청은 상품을 고르는 방식이 아니라 「주 N회 × M개월 × 수업길이」 계산식으로 값을 냅니다(enroll_prices). 커리큘럼 화면은 소개용 정적 페이지입니다.
한계 그룹 수업·특강·단기 패키지·이벤트가 같은 계산식에 안 맞으면 팔 방법이 없습니다. 새 상품마다 코드 수정이 필요합니다.
참고 지금 사업 형태(1:1 정기 수업)에는 계산식이 오히려 잘 맞습니다. 상품을 늘릴 계획이 없다면 급하지 않습니다.
확인 방법 courses·products 성격의 테이블 정의가 코드에 없습니다. 가격 결정은 enroll-ops.ts의 enrollQuoteCalc() 한 곳입니다.

확장A-3. 레벨테스트 결과 → 코스·반 자동 추천이 없습니다

있는 것 레벨테스트 신청·자동 일정 배정·입장 티켓·시험 응시 엔진·AI 자동 진단까지 전부.
없는 것 「결과 점수 → 추천 코스/교재/강사」로 이어지는 매핑 규칙. 지금은 강사·관리자가 사람 판단으로 다음 단계를 정합니다.
영향 레벨테스트를 마케팅 유입(무료 체험)으로 쓰려면 결과 화면에서 바로 신청으로 이어져야 하는데, 그 연결이 끊겨 있습니다.
확인 방법 leveltest-schedule.ts·judgment-level.ts에 추천·매핑 로직이 없습니다. 판단력 훈련의 밴드 조정(auto)은 훈련 난이도용이지 코스 배정용이 아닙니다.

위험A-4. 화상수업이 멈췄을 때의 «대체 경로»가 없습니다

현재 자체 WebRTC 한 갈래뿐입니다. 외부 솔루션(Zoom·Meet) 링크로 임시 전환하는 스위치가 코드에 0건입니다.
왜 문제인가 자체 구현은 기능·비용에서 유리하지만, 장애가 나면 그날 수업 전체가 멈춥니다. 실제로 워커가 두 벌 배포되면서 방(Durable Object)이 갈려 7월 31일~8월 19일 여덟 번의 수업에서 강사와 학생이 한 번도 만나지 못한 사고가 있었습니다.
제안 관리자가 수업 단위로 「외부 링크로 대체」를 켤 수 있는 최소 스위치 — 링크 입력 → 학생·강사 화면에 그 링크 노출 → 문자 발송. 기능이 아니라 보험입니다.
확인 방법 src/ 전체에서 zoom 문자열이 나오는 파일은 법인카드 동기화(가맹점명) 1건뿐입니다.
SECTION 2 · B

있어도 보완해야 할 것

기능은 있으나 신뢰할 수 없거나, 사람 손이 계속 들어가는 지점입니다. 우선순위 순.

돈에 직접 걸리는 것

최우선B-1. 강사 급여가 «어디에도 안 잡히는» 달이 생길 수 있습니다

증상 진짜 급여명세(payslips)가 없는 달에는 손익계산서의 「강사 급여」 줄이 메트로은행 송금분만 잡습니다. 그런데 국내 계좌에서 「급여이체」로 분류된 출금은 「강사급여와 중복이니 제외」라는 전제로 판관비에서도 빠집니다.
즉 겹쳐 보이는 게 문제가 아니라, 양쪽 어디에도 안 잡히는 누락일 수 있습니다. 손익이 실제보다 좋게 나옵니다.
필요한 일 최근 몇 달의 「급여이체」 출금 목록과 payslips를 나란히 놓고 대사 — 사람이 한 번 확인해야 판정됩니다.
근거 CLAUDE.md 2장에 「아직 고치지 않은 위험」으로 명시. accounting-reports.ts·bankacct-sync.ts의 BANK_CAT_RULES.

최우선B-2. 「카페24 회계 실데이터」 화면이 빈 채로 운영 중입니다

증상 그 화면이 읽는 Neo4j AccBook 노드가 0건입니다. 같은 DB의 Book 62건은 조회되므로 연결 문제가 아니라 카페24 쪽이 회계 노드를 아직 적재하지 않은 것입니다(우리 저장소엔 적재 코드가 없고 읽기만 합니다).
영향 회계 메뉴 중 한 탭이 계속 비어 있고, 「데이터가 없다」와 「기능이 고장났다」를 화면만 봐서는 구분할 수 없습니다.
필요한 일 코드 수정이 아니라 카페24에 적재 요청. 요청서는 이미 작성돼 있습니다(docs/카페24_회계데이터_적재요청_2026-08-18.md).

위험B-3. 지사 이름이 겹쳐 매출이 통째로 배정되지 않는 곳이 있습니다

증상 centers.name이 유일하지 않아, 같은 이름이 두 지사 이상으로 갈리면 가맹점 정산이 「어느 쪽인지 모름」으로 판정해 아무 데도 배정하지 않습니다(아무 쪽에 몰아주는 것도 오류라서).
규모 2026-08-16 기준 5개 이름 · 학생 2,603명이 이 상태였습니다. 그 지사의 정산서 매출이 0으로 찍힙니다.
필요한 일 코드로는 못 풉니다. 카페24에서 지사·대리점 이름을 구분되게 정리해야 합니다.
확인 쿼리 SELECT name FROM centers GROUP BY name HAVING COUNT(DISTINCT franchise_id)>1

개선B-4. 중복 결제는 «찾아만» 주고 되돌리지 않습니다

중복 결제 탐지 화면(admin/duplicate-payments.html·api-refund-audit.ts)은 있으나, 찾은 뒤 환불로 이어지는 길이 A-1 때문에 끊깁니다. A-1을 만들면 여기에 「이 건 환불」 버튼 하나로 붙습니다.

데이터가 조용히 틀리는 것

위험B-5. 강사 식별번호가 «세 벌»이고 겹치는 자리에서 다른 사람입니다

구조 카페24 강사번호(9~196) · 원부 teachers.id(1~29) · 프로필 teacher_profiles.id(4~37) — 셋이 서로 다른 체계입니다.
실제 카페24 24번 = Teacher Mariane인데 원부 24번 = HANNAH, 카페24 26번 = Teacher Rica인데 원부 26번 = MELCA. 숫자로 이으면 에러 없이 조용히 남의 이름·남의 수업·남의 급여가 붙습니다.
현재 이름 완전일치로만 잇고 모르면 비우도록 고쳤고 회귀 감시도 붙었습니다. 다만 attendance_seed 경로는 아직 옛 방식이 남아 지금은 0건이라 피해가 없을 뿐, 쓰는 순간 재현됩니다. 2026-08-18 동기화가 이미 602행에 남의 이름을 넣었고, 그중 창 밖 28행은 야간 동기화로도 안 고쳐집니다.
필요한 일 남은 씨앗 경로 정리 + 이미 잘못 들어간 행 정정(사람 확인 필요 — 실 데이터라 CI가 막아 주지 못함).

위험B-6. 대소문자만 다른 중복 계정이 실재합니다

원인 계정 아이디에 대소문자 구분이 걸려 있어 mangoi_167과 Mangoi_167이 다른 계정이 됩니다. 로그인 조회가 못 찾으면 옛 인증 경로가 그 자리에서 새 계정을 만들어, 휴대폰 키보드 자동 대문자 한 번에 계정이 두 벌이 됩니다.
영향 출근·급여가 계정 단위라 기록이 갈라지고, 정작 쓰는 쪽에 강사 연결이 없어 「수업 없음」이 뜹니다(실제 발생).
현재 2026-08-24에 대소문자를 무시하도록 고쳤습니다. 다만 이미 생긴 중복 계정은 코드가 못 지웁니다 — 사람이 정리해야 합니다.
확인 쿼리 SELECT LOWER(username) k, COUNT(*) n, GROUP_CONCAT(username) FROM admin_account GROUP BY k HAVING n>1

위험B-7. 학생 명부의 주인이 우리가 아닙니다

구조 카페24에서 온 학생 행은 매일 밤 03:00에 전부 지우고 다시 넣습니다(UPSERT가 아니라 삭제 후 재삽입). 그래서 이름 수정도, 행 삭제도, 새로 적어 둔 값도 하룻밤이면 사라집니다.
현재 별도 override 테이블로 이름 고정·명부 숨김을 우회하고 있습니다. 동작은 하지만 구조적으로 취약합니다 — 읽는 쪽 네 곳이 짝을 맞춰야 하고, 한 곳만 빠지면 「명부엔 없는데 로그인은 되는」 상태가 됩니다.
실제 사례 한 학생의 계정이 카페24에 15개 있었고, 정작 쓰는 계정은 카페24에 이름이 없어 아이디로만 찍혀 이름 검색에 안 걸렸습니다.
판단 필요 「학생 마스터를 망고아이로 가져올 것인가」는 사업 결정입니다. 지금 구조에서는 카페24를 고쳐야만 근본 수정이 됩니다.

개선B-8. 주간 스케줄 표의 대부분이 실제 수업이 아닙니다

활성 스케줄 667행 중 658행이 자리표시였습니다 — 옛 LMS 점유 518행 + 시연 시드 140행. 이 때문에 특정 요일·시간에 수업을 넣을 수 없었습니다(「이미 예약된」).
현재 판정에서 제외하도록 고쳤고, 8-24에 일괄 정리 버튼(취소 처리·되돌릴 수 있음)까지 붙었습니다. 남은 일은 실행과 확인 — 건수 확인 후 사람이 실행합니다.

점검B-9. 레벨테스트는 만들어졌지만 실전 데이터가 0건입니다

2026-08-20 확인 시 신청 17건이 전부 데모였고 실제 신청은 0건이었습니다. 기능이 도는지는 실제 신청이 한 번 통과해 봐야 알 수 있습니다. 마케팅에 쓰기 전 실전 1건 검증을 권합니다.

위험B-11. 옛 도메인을 아직 못 지웁니다 (앱 때문에)

리다이렉트로 넘기는 것도 안 됩니다 — 그 도메인으로 등록된 패스키 6건이 무효화되고 앱 사용자 로그인이 날아갑니다.
필요한 일 새 APK 보급률을 확인한 뒤 마지막에 정리. 지금은 「그대로 둔다」가 정답이며, 이 사실을 팀이 아는 것이 중요합니다.

개선B-12. 화면이 틀린 버그를 자동 검사가 못 잡습니다

회귀 하니스 222종은 문자열 검사라 「함수가 있는가」는 보지만 「화면 어디에 그려졌는가」는 못 봅니다. 실제로 타입체크·하니스·CI가 전부 초록불인 상태에서 화면 버그가 여러 건 나왔습니다.
진짜 브라우저로 좌표를 재는 검사 23종이 있지만 manual/에 있어 자동으로 돌지 않습니다 — 사람이 불러야 합니다.
제안 최소한 「경로 줄·사이드바·수업 입장」 3종만이라도 CI에 편입할지 검토. 브라우저는 이미 컨테이너에 있습니다.

선행 이력 크몽을 통한 2026-07-09 제안은 「처음부터 다시, 약 3천만원」이었습니다. 당시 검증(docs/크몽_진단_검증.md)에서 그 업체가 짚은 진짜 문제 두 가지(관리자 API 무인증 노출·통짜 HTML 구조)는 사실로 확인돼 보안 문제는 그날 근본 수정했고, 「전면 재개발이 유일한 해법」이라는 결론은 성립하지 않는 것으로 판정했습니다. 이번 제안은 금액이 6,600만원으로 늘었고 범위 판정 결과는 그때와 같습니다 — 다만 이번 제안서는 기존 시스템 비승계를 스스로 명시하고 있어, 논점이 「고칠 것인가 다시 만들 것인가」로 더 분명해졌습니다.
