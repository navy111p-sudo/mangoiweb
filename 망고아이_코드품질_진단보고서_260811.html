3. 남은 위험 (빨간불) — 구조, 이 세션에서 손대지 않음

위험 A 개발과 운영이 같은 DB를 씁니다

wrangler.toml의 기본 환경과 [env.production]이 같은 mango-db를 가리킵니다. 테스트용 DB가 따로 없어, 개발 중 실수 한 번이 운영 데이터에 바로 닿습니다.

어떻게 — 출시 전 지금이 mango-db-dev를 하나 더 만들어 분리할 적기입니다. 학생 표는 Cafe24에서 다시 받으면 되고 나머지는 테스트 데이터입니다. 분리 전까지는 변경 쿼리(DELETE/UPDATE/DROP) 금지·SELECT만. 난이도: 중 · 위험: 낮음(출시 전) · 효과: 큼

위험 B 주소 찾기가 if 609번 — "새 API가 404" 사고의 뿌리

src/index.ts는 요청 주소를 if로 순서대로 609번 비교합니다(8/9엔 472번, 계속 늘고 있음). 여기에 등록을 빠뜨리면 만든 기능이 라이브에서 404가 됩니다.

어떻게 — { 'POST /api/x': 함수 } 형태의 목록(라우팅 테이블) 하나로 바꾸면 등록 누락이 구조적으로 불가능해지고 속도도 빨라집니다. 하니스 157개를 합격 기준으로 삼아 단계적으로. 난이도: 상 · 효과: 큼 · 기간: 며칠~1주

7. 오늘 무엇으로 확인했나 · 이 세션의 한계

  • ✅ 컴파일: node node_modules/typescript/bin/tsc --noEmit → 오류 0건(오늘 3회, 수정 후 포함).
  • ✅ 문법: 고친 JS는 node --check 통과.
  • ✅ 전수 재스캔: 비-벤더 소스에 raw NUL·제어문자·BOM 0건, 머지충돌마커 없음(=======는 장식).
  • ⚠️ 회귀 하니스 전체(run.mjs --fast)는 이 클라우드 샌드박스에서 온전히 못 돌렸습니다. 폴더의 node_modules가 Windows용(@esbuild/win32-x64)이라 Linux에서 네이티브 바이너리가 동작하지 않습니다. 이건 코드 문제가 아니라 환경 문제이며, 운영자 PC나 CI(Linux)에서는 정상입니다.

그래서 마지막 확인 한 가지 부탁드립니다 — 운영자 PC에서 리포 루트에서 node test-harness/run.mjs --fast를 한 번 돌려 PASS 유지·FAIL 0을 확인하고 커밋/배포해 주세요. (기준선: PASS 115 / SKIP 20 / FAIL 0)
